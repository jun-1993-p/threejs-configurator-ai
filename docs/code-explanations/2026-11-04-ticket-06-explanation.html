티켓 06: 축 반응 검증

슬라이더가 움직일 때 각 부품이 명세에 선언한 대로 움직이는지(형태가 바뀌는지, 자리만 옮겨지는지, 가만히 있는지)를 단독 스윕의 Fusion 형상에서 재고, 어긋나면 부품 이름과 고칠 명세 위치를 담은 피드백으로 돌려보내는 변경이다.

배경

이 영역이 처음이면 펼쳐서 읽는 깊은 배경

구성기의 명세(JSON)는 AI가 쓰는 산출물이다. 슬라이더마다 어느 축(W 폭, D 깊이, H 높이)을 움직이는지와, 그 슬라이더가 어느 부품에 어떻게 영향을 주는지를 선언한다. 부품은 Fusion 컴포넌트 하나에 해당하는 상품의 구성 단위이고(서랍, 문, 선반 등), 컴포넌트가 없는 모델에서는 바디 하나다(ADR-0006).

티켓 04의 수치 검증은 변형 엔진의 결과가 Fusion 형상과 합격선 안에서 맞는지만 본다. 엔진이 Fusion을 그대로 따라 해도, 명세가 "이 슬라이더는 서랍 폭을 바꾼다"고 틀리게 적었다면 수치 검증은 통과한다. 선언과 실제의 일치는 다른 검증이 맡아야 하고, 그것이 이 티켓이다.

명세의 슬라이더에는 두 목록이 있다. affects.shape는 형태 변경 부품, 곧 슬라이더를 움직이면 해당 축 치수가 바뀌어야 하는 부품이다. affects.move는 위치 이동 부품, 곧 치수는 그대로이고 자리만 옮겨지는 부품이다(예: 서랍 폭이 늘 때 밀려나는 칸막이). 어느 목록에도 없는 부품은 변하지 않아야 한다. 이렇게 단독 스윕에서 슬라이더 하나가 부품들을 어느 축으로 어떻게 움직이는지를 축 반응이라 부르고, 선언과 실제 축 반응의 비교가 이 변경의 일이다.

이 문서의 코드 이름을 먼저 정리한다.

  • verifyAxisResponse: 축 반응 검증의 진입 함수.
  • AXIS_RULES: 판정 규칙을 담은 표. 부품의 선언된 역할마다 앞에서부터 보고, 처음 걸린 규칙 하나만 알린다.
  • CHANGE_THRESHOLD: "바뀌었다"고 보는 문턱. 0.2 mm.
  • specReferenceChecker: 명세가 업로드 묶음의 이름을 맞게 가리키는지 보는 검사.
  • measure.ts: 수치 검증기와 축 반응 검증기가 함께 쓰는 측정 도우미 모음.
핵심 개념: 치수와 가운데 위치 부품의 축 반응은 두 양으로 잰다. 치수는 그 축 방향 바운딩 박스 길이이고, 가운데 위치는 바운딩 박스 중심 좌표다. 형태가 바뀌면 치수가 바뀌고, 자리만 옮겨지면 가운데 위치만 바뀐다.

핵심 아이디어

샘플마다 기본 형상 대비 각 부품의 W·D·H 치수와 가운데 위치가 얼마나 변했는지를 잰 뒤, 선언된 역할이 기대하는 모습과 비교한다. 비교 규칙은 표 하나로 정리된다.

부품의 선언슬라이더 축에서 기대어기면 kind
affects.shape치수가 바뀐다missing_axis_change
affects.move치수는 그대로, 자리가 옮겨진다치수가 바뀌면 unexpected_shape_change, 자리가 그대로면 missing_axis_change
선언 없음그대로치수가 바뀌면 unexpected_shape_change, 자리가 옮겨지면 unexpected_move
모든 부품다른 축의 치수와 위치가 그대로off_axis_change

표는 docs/spec-schema.md의 "축 반응" 표와 같고, 코드 주석에 따르면 AXIS_RULES도 이 표와 같다.

작은 예시: 깊이 슬라이더 두 개가 한 축을 나눠 쓸 때

슬라이더 (D축)맡은 부품기대하는 반응
body_d (전체 깊이)몸통, 서랍두 부품 모두 D 치수가 바뀐다
drawer_d (서랍 깊이)서랍서랍만 D 치수가 바뀌고, 몸통은 그대로

이 구성은 티켓의 시험이 쓰는 합성 서랍장과 같다(티켓 파일). 한 축에 슬라이더가 여러 개여도 슬라이더마다 따로 보기 때문에, drawer_d를 움직였을 때 몸통이 같이 변했다면 그 슬라이더의 선언이 틀린 것으로 잡힌다.

코드 따라가기

흐름: 명세가 이름 검사를 통과 → 실행기가 수치 검증 뒤에 축 반응 검증을 호출 → 검증기가 샘플별 변화량을 모음 → 규칙 표로 판정 → 피드백이 명세 다시 쓰기로.

1. 명세의 이름과 목록 모순을 먼저 거른다

specReferenceChecker는 JSON Schema 검사를 통과한 명세에 쓰는 두 번째 검사다. 슬라이더 id가 스윕한 파라미터인지, affects의 부품이 업로드 묶음의 부품인지, 한 부품이 형태 변경과 위치 이동에 함께 들어 있지 않은지 본다. 실행기의 checkProductSpec에서 불리므로, 위반하면 형식 오류와 같은 방식으로 이유를 붙여 AI에게 다시 묻는다(configurator/pipeline/runner.ts:166).

configurator/pipeline/schemas.ts:62-73

export function specReferenceChecker(bundle: { parts: { name: string }[]; sweeps: { parameter: string }[] }) {
  const parts = new Set(bundle.parts.map((p) => p.name));
  const swept = new Set(bundle.sweeps.map((s) => s.parameter));
  return (spec: { sliders: { id: string; affects: { shape: string[]; move: string[] } }[] }): string[] =>
    spec.sliders.flatMap(({ id, affects }, i) => [
      ...(swept.has(id) ? [] : [`/sliders/${i}/id: ${id}는 스윕한 파라미터가 아닙니다`]),
      // elided: affects.shape와 affects.move의 부품 이름이 업로드 묶음에 있는지 보는 검사
      ...affects.shape.filter((part) => affects.move.includes(part)).map((part) => `/sliders/${i}/affects: ${part}가 shape와 move에 함께 있습니다`),
    ]);
}

3. 검증기: 샘플마다 기본 형상 대비 변화량을 모은다

verifyAxisResponse(configurator/pipeline/verify-axis.ts:83)는 부품이 어느 바디들로 이루어졌는지 먼저 정한다. 부품은 그 부품에 속한 바디 전체의 면으로 재므로(ADR-0006) 샘플의 면 구성이 기본 형상과 달라도 잴 수 있다(configurator/pipeline/verify-axis.ts:85). 그다음 슬라이더마다 보는 샘플을 고른다. 재계산에 성공했고, 슬라이더 범위 안이며, 기본값이 아닌 샘플과 검증점이 모두 대상이다(configurator/pipeline/verify-axis.ts:98).

샘플 하나에서 부품 하나의 변화는 W·D·H별 치수 변화와 가운데 위치 변화로 이루어진 Change가 된다. 같은 슬라이더와 부품의 Change를 모은 PartResponse가 onAxisFeedback과 offAxisFeedback으로 넘어간다.

4. 규칙 표로 판정한다

onAxisFeedback는 부품의 선언(shape, move, 없음)을 정하고, AXIS_RULES에서 그 선언의 규칙을 위에서부터 훑는다. 규칙마다 치수 또는 위치(amount) 중 어느 쪽을 보고, 바뀌었을 때 실패인지(changed) 바뀌지 않았을 때 실패인지(unchanged)를 갖는다. 알리는 샘플은 그 양이 가장 크게 바뀐 하나다.

configurator/pipeline/verify-axis.ts:124-130

const role: Role = slider.affects.shape.includes(part) ? "shape" : slider.affects.move.includes(part) ? "move" : "none";
for (const rule of AXIS_RULES.filter((r) => r.role === role)) {
  const sample = largest(changes, (c) => c[rule.amount][axis]);
  if (!sample) continue;
  const amount = sample[rule.amount][axis];
  const changed = Math.abs(amount) > CHANGE_THRESHOLD;
  if (changed !== (rule.failsWhen === "changed")) continue;

마지막 줄이 핵심이다. 샘플이 실제로 바뀌었는지가 규칙의 실패 조건(failsWhen)과 다르면 다음 규칙으로 넘어간다. 같으면 그 규칙의 kind, path, 힌트로 피드백을 만든다. path는 규칙의 field(affects.shape 또는 affects.move)에 슬라이더 번호를 붙인 sliders[i].affects.shape 같은 값이다. 힌트는 부품을 어느 목록에 넣거나 빼라고 하고 자식 수식을 확인하라고 한다.

이어서 offAxisFeedback(configurator/pipeline/verify-axis.ts:149)가 슬라이더 축이 아닌 두 축의 치수와 위치를 본다. 문턱을 넘은 것 중 가장 큰 변화 하나를 off_axis_change로 알리고, 고칠 곳은 sliders[i].axis다.

5. 새 실패 종류와 공용 측정 도우미

기존 12개 종류에는 "선언한 반응이 없다"와 "선언 없는 부품이 옮겨졌다"가 없어서 missing_axis_change와 unexpected_move를 FEEDBACK_KINDS에 더했다. 또 수치 검증기에 들어 있던 W·D·H 목록, 축 이름의 좌표 번호 대응, 반올림, 바운딩 박스 계산을 pipeline/measure.ts로 옮겨 두 검증기가 같이 쓴다(configurator/pipeline/measure.ts:17). verify-numeric.ts는 그만큼 줄었다.

리뷰에서 반영하지 않은 것 Feedback.measured를 종류별 타입으로 나누지 않았다. 수치 검증도 자유 형식으로 쓰고 형식은 docs/spec-schema.md가 정하며, 종류별 타입은 모든 검증기를 같이 바꿔야 해서 이 티켓 범위 밖이라고 티켓 파일이 적었다.

퀴즈

위치 이동 부품(affects.move)으로 선언한 칸막이의 폭(W) 치수가 슬라이더(W축)를 움직이자 0.5 mm 바뀌었다. 피드백의 kind와 path는?

위치 이동 부품은 치수가 그대로여야 한다. 치수가 바뀌었으므로 규칙 표의 이 행에 걸려 unexpected_shape_change가 나고, path는 그 부품이 선언된 affects.move다. 힌트는 affects.shape로 옮기라고 한다.

위치 이동 부품으로 선언한 서랍이 범위 안에서 가장 크게 움직인 샘플에서도 0.15 mm만 옮겨졌다면 어떤 일이 생기는가?

문턱은 0.2 mm이고 0.15는 그 이하라 "안 움직였다"로 본다. 위치 이동 부품은 움직여야 하므로 선언한 반응이 없다는 missing_axis_change가 된다.

한 부품을 affects.shape와 affects.move 양쪽에 적은 명세는 어느 단계에서 걸러지는가?

specReferenceChecker가 shape와 move에 함께 있는 부품을 이유와 함께 알려, 축 반응 검증이 돌기 전에 AI에게 다시 묻는다. 코드의 role 판정은 shape를 먼저 보기 때문에, 이 검사가 없으면 move 쪽 선언이 조용히 무시될 것이다.

판정 규칙을 if 연쇄가 아니라 AXIS_RULES 표 데이터로 둔 것은 무엇에 도움이 되는가?

코드 주석은 표가 docs/spec-schema.md의 "축 반응" 표와 같다고 적는다. 표 한 줄이 문서 표 한 줄에 대응하므로 둘을 맞춰 두기 쉽다는 것이 이 문서의 추론이고, 코드는 속도나 AI의 변경 권한을 말하지 않는다.

슬라이더 축이 D인데 서랍의 높이(H) 치수가 0.4 mm 바뀌었다. 어느 path의 어떤 힌트가 나오는가?

슬라이더 축이 아닌 축의 변화는 부품이 어느 목록에 있든 off_axis_change이고, 고칠 곳은 axis다. 서랍이 D의 형태 변경 부품이어도 H 변화는 별도로 알려진다.

티켓 26 Fusion 실물 확인: 처음 실제 Fusion에서 돌려 보고 고친 것

합성 녹화본으로만 시험하던 Fusion 애드인을 실제 Fusion에서 처음 돌리자 나온 결함을, 세 절(면·모서리 이름, 첫 업로드와 녹화, 업로드 뒤 연결)의 흐름에 따라 어떻게 찾고 고쳤는지 설명한다.

jun-1993-p/threejs-configurator-ai 티켓 26 커밋 7개(5ac2742, 6615b52, cb1b0c8, 7249d60, c1e0958, 7eb42db, 6253a54), 기준 커밋 6253a54, explained 2026-11-04. References link to this commit.

Background

처음 보는 사람을 위한 배경: 애드인, 업로드 묶음, 합성 녹화본

이 프로젝트는 Fusion으로 만든 가구 모델을 쇼핑몰에서 슬라이더로 바꿔 볼 수 있는 three.js 구성기로 만든다. 브라우저에서 Fusion을 돌릴 수는 없으므로 모델의 치수 파라미터를 바꿔 가며 형상을 미리 뽑아 두고 브라우저는 그 사이를 보간한다.

형상을 뽑는 쪽이 Fusion 애드인(addin/ConfiguratorUploader)이다. 애드인은 사용자 파라미터를 하나씩 기본값의 ±50% 범위에서 움직여 재계산시키고(스윕), 샘플마다 면과 모서리 위의 점을 읽어 업로드 묶음으로 서버에 올린다. 서버는 샘플 사이에서 같은 면의 같은 점끼리 짝지어 이동량을 계산한다. 짝짓기가 맞으려면 샘플이 달라져도 같은 면에는 같은 이름이 붙어야 한다.

티켓 26이 만들어질 때 Fusion에는 접근할 수 없는 상태였다(티켓 코멘트). 그동안 SolidCraft라는 다른 CAD로 만든 합성 녹화본이 시험 데이터를 대신했다. 합성 녹화본은 서버와 파이프라인을 시험하기에는 충분하지만, Fusion API가 실제로 어떻게 동작하는지는 알려 주지 못한다.

티켓 26이 생긴 까닭

Fusion에서만 할 수 있는 사람 확인이 애드인 업로드(티켓 01), 명세 쓰기(티켓 15), 경계 맞춤 격자(티켓 25)에 흩어져 있었다. 커밋 .scratch/configurator-pipeline/issues/26-fusion-real-check.md:1의 티켓이 이를 한곳에 모은다(첫 커밋 5ac2742). 코드가 끝난 세 티켓을 ready-for-agent로 되돌려, 사람 확인에 막혀 있던 다른 티켓 다섯 개(16·18·19·22·05)를 풀었다.

이 문서는 티켓 26의 1절(면·모서리 이름과 점 추출), 2절(첫 업로드와 녹화), 3절(업로드 뒤 연결)을 다룬다. 4절 이후(이후 티켓용 실물 녹화본, 실제 모델 확인, 예비 모델 전환)는 이 커밋들에서 바뀌지 않아 다루지 않는다.

이 문서에서 쓰는 말

면 표시: 애드인이 기본 형상의 면마다 붙이는 이름표(Fusion attribute, 묶음 이름 ConfiguratorUploader). 다른 샘플에서 같은 면을 알아보는 데 쓴다.
경계 맞춤 격자: 한 면의 점 집합. 경계 모서리 위의 점과 경계에 대한 상대 위치로 정한 안쪽 점으로 이루어진다(ADR-0016).
추가 샘플 요청: 업로드 뒤 검증 중에 서버가 연결된 애드인에 보내는 형상 요청.
Fusion 연결 필요: 추가 샘플 요청 중에 애드인 연결이 끊긴 상태. 검증 실패로 세지 않고 다시 연결될 때까지 멈춘다.
기본 형상: 파라미터를 기본값으로 둔 형상. 면 이름과 점 배치의 기준이다.
위상 변화: 샘플에서 면 구성이 기본 형상과 달라지는 일. 서버가 이름으로 알아본다.
오커런스: 컴포넌트를 어셈블리에 놓은 인스턴스 하나.
위저드: 사람이 Fusion에서 할 일만 안내하고 나머지는 스스로 재는 단계별 셸 스크립트(scripts/*-wizard.sh).
녹화본: 실제 상품 데이터로 저장한 업로드 묶음. 공개 저장소에 올리지 않고 fixtures/private에 둔다.

공개 저장소 규칙 녹화 결과를 티켓에 옮길 때는 통과·실패와 수치 오차 같은 판정만 적는다. 실제 상품의 부품 이름, 파라미터의 뜻, 치수, 모델 구조를 드러내는 개수는 적지 않는다. 이 문서도 같은 규칙을 따라, 티켓과 커밋 메시지에 이미 공개된 이름과 판정만 쓴다.

Intuition

Fusion은 재계산할 때마다 같은 면의 순서와 임시 번호를 바꾼다. 그래서 면 이름을 샘플마다 새로 지으면 같은 면이 다른 이름을 받는다. 이 애드인은 이름을 기본 형상에서 한 번만 짓고, 그 이름을 면에 붙여 둔다(장면 1). 나머지 수정은 Fusion API가 문서와 다르게 동작한 곳과, 사람이 눈으로 하던 확인을 애드인이 대신 재게 한 곳이다(장면 2, 3).

장면 1: Fusion은 재계산마다 면의 순서를 바꾼다

1절의 탐색은 시험용 모델의 사용자 파라미터를 하나씩 0.8배와 1.2배로 바꿔 재계산시키며 무엇이 그대로이고 무엇이 변하는지 쟀다. 결과는 아래와 같다.

그래서 이름은 매 샘플마다 새로 짓지 않는다. 기본 형상에서 피처:역할로 한 번 짓고, 그 이름을 면 표시로 붙여 둔다. 다른 샘플에서는 표시를 읽어 같은 이름을 돌려준다. 아래는 이 생각을 보이려고 내가 만든 예시 데이터이며, 실제 탐색 값이 아니다.

순번은 Fusion이 주는 순서에 기대므로 바뀐다. 면 표시는 면에 붙어 있어 순서와 무관하다.

표시가 항상 하나씩 남지는 않는다. 샘플에서 표시가 겹치는 면(한 면이 둘로 갈라진 경우)과 표시가 없는 면(새로 생긴 면)은 기본 형상에 없는 이름을 받는다. 서버는 이 이름을 보고 위상 변화로 알아본다. 이름을 못 찾는 면은 그대로 위상 변화의 신호가 된다.

장면 2: 사람이 비교하기를 멈추고 애드인이 재기 시작했다

첫 실제 업로드는 두 번 실패했다. 실패한 사이에 바꾼 파라미터가 모델에 남아 있었고, 사람이 하던 확인("파라미터가 원래대로인가: 예")은 이를 잡지 못했다. 커밋 7249d60의 메시지와 티켓 기록에 따르면 운영자는 이렇게 지적했다. "내가 일일이 비교하는 것은 사실상 불가능하다." 이후 확인 방식이 그 방향으로 옮겨 간다.

장면 3: 실행한 코드가 새 코드인지부터 의심한다

두 번째 녹화에서는 점검 파일이 하나도 없었다. 원인은 코드가 아니라 사용 방식이었다. Fusion 로그에 마지막 애드인 실행이 점검 기능을 넣은 커밋보다 앞서 있어, 예전 코드로 업로드한 것이다. 애드인이 실행할 때 흔적을 남기고, 위저드가 그 흔적보다 새로 고친 코드가 있으면 업로드로 넘어가지 않게 했다.

Code walkthrough

흐름 한 줄: 티켓 분리 → 탐색으로 Fusion의 동작 재기 → 면 이름 짓기와 면 표시 → 경계 맞춤 격자로 점 뽑기 → 첫 업로드·녹화 위저드 → 첫 업로드 결함과 자동 점검 → 예전 코드 업로드 막기 → 세 번째 녹화 → 연결 확인 위저드.

1. 사람 확인을 한 티켓으로 모은다 (5ac2742)

티켓 01·15·25에서 Fusion 확인 항목을 티켓 26으로 옮기고, 코드가 끝난 세 티켓의 상태를 ready-for-agent로 돌린다. 애드인 README의 안내도 "티켓 26 사람 확인을 기다린다"로 바뀐다. 코드는 건드리지 않는 커밋이다.

2. 탐색으로 Fusion의 동작을 먼저 잰다 (6615b52)

이름 문법을 정하려면 Fusion이 재계산 뒤에 무엇을 그대로 두는지부터 알아야 한다.addin/FaceNameProbe는 모델을 읽고 파라미터를 바꿔 가며 면 역할·순서·tempId·면 표시를 기록하는 별도 애드인이고, scripts/fusion-probe-wizard.sh가 실행 절차를 안내한다. 결과는 위 Intuition의 표다. 결론은 ADR-0016의 "바뀐 것" 절에 기록됐다(2026-11-04).

3. 이름을 한 번 짓고 면 표시로 잇는다 (6615b52)

이름 문법은 새 모듈 face_names.py에 모았다. 모듈 머리말에 따르면 이름을 짓는 Fusion 어댑터와 모서리 이름을 두 면 이름으로 나누는 쪽을 한곳에 둔 것이다. SolidCraft 어댑터도 같은 파일을 쓴다. 핵심은 face_names다.

addin/ConfiguratorUploader/uploader/face_names.py:57-70

    if baseline:
        return _numbered([f.fresh_name() for f in faces], [f.order for f in faces], lambda n, k: f"{n}:{k}", False)
    names = [""] * len(faces)
    tagged = [i for i, f in enumerate(faces) if f.tag is not None]
    fresh = [i for i, f in enumerate(faces) if f.tag is None]
    split = _numbered(
        [faces[i].tag or "" for i in tagged], [faces[i].order for i in tagged], lambda n, k: f"{n}:split{k}", False
    )
    new = _numbered(
        [faces[i].fresh_name() for i in fresh], [faces[i].order for i in fresh], lambda n, k: f"{n}:new{k}", True
    )
    for i, name in [*zip(tagged, split), *zip(fresh, new)]:
        names[i] = name
    return names

baseline이면 표시를 보지 않고 새로 짓는다. 같은 이름이 여럿일 때만 :순번이 붙는다. 기본 형상이 아니면 면을 둘로 나눈다. 표시가 있는 면은 표시를 이름으로 쓰되 같은 표시가 여럿이면 :split순번, 표시가 없는 면은 새로 지은 이름에 :new순번을 붙인다. 순번은 면의 order로 정한다. order는 표면 방향(평면은 바깥 법선, 원기둥은 축)과 면 중심을 소수 셋째 자리로 반올림한 열쇠여서, Fusion이 주는 순서에 기대지 않는다.

Fusion 어댑터는 기본 형상에서 이 이름을 면에 붙인다. _tag_baseline이 앞 업로드의 표시를 지운 뒤 새로 붙이고, 다른 샘플은 _face_roles가 표시를 읽어 FaceRole.tag에 채운다.

addin/ConfiguratorUploader/uploader/fusion_model.py:204-212

    def _tag_baseline(self) -> None:
        """앞 업로드의 표시를 지우고, 기본 형상의 면에 이름을 붙인다."""
        self.clear_tags()
        roles = self._roles()
        for _, body, _ in self._visible_bodies():
            names = face_names(self._face_roles(body, roles), baseline=True)
            for face, name in zip(body.faces, names):
                native = face.nativeObject or face
                native.attributes.add(TAG_GROUP, TAG_NAME, name)

새 업로드를 시작하면 앞 업로드의 추가 샘플 응답을 멈춘다. 새 어댑터가 표시를 다시 붙이면 앞 어댑터가 쓰던 이름과 배치가 어긋나기 때문이다(addin/ConfiguratorUploader/ConfiguratorUploader.py:60-62의 forget).

4. 경계 맞춤 격자로 점을 뽑는다 (6615b52)

Fusion 어댑터의 sample_faces와 sample_edges를 경계 맞춤 격자로 구현했다. 이전에는 sample_edges가 NotImplementedError를 냈고, 면 점은 매개변수 범위의 n×n 격자였다. 면 표본을 만드는 공통 코드는 face_sampling.py에 있고, 경계 맞춤 격자 자체인 fitted.py는 합성 쪽에서 애드인 패키지로 옮겼다. 모서리 방향은 면의 고리를 따른다.

Fusion에만 있는 모양이 하나 있다. 이음선이 없는 원기둥(원으로 돌출한 구멍이나 다리)은 펼칠 자리가 없다. 어댑터는 직선 모서리가 없고 원 두 개로 둘러싸인 원기둥 면을 찾아 반쪽 원기둥 둘(:half1, :half2)로 나눈다.

addin/ConfiguratorUploader/uploader/fusion_model.py:349-358

def _seamless_cylinder(face: adsk.fusion.BRepFace, body: str, name: str) -> bool:
    """이음선 없는 원기둥: 직선 모서리가 없는 원기둥 면. 원 두 개로 둘러싸인 것만 반쪽 둘로 나눠 다룬다."""
    if face.geometry.surfaceType != adsk.core.SurfaceTypes.CylinderSurfaceType:
        return False
    if any(e.geometry.curveType == adsk.core.Curve3DTypes.Line3DCurveType for e in face.edges):
        return False
    loops = list(face.loops)
    if len(loops) == 2 and all(loop.edges.count == 1 and _is_circle(loop.edges.item(0)) for loop in loops):
        return True
    raise UnsupportedFaceError(f"{body} 면 {name}: 원 두 개로 둘러싸이지 않은 이음선 없는 원기둥은 아직 다루지 않습니다")

원 두 개로 둘러싸이지 않은 이음선 없는 원기둥은 아직 다루지 않고 UnsupportedFaceError를 낸다. 나누는 자리는 부호를 정한 원기둥 축의 좌표계로 정해, 같은 축의 원은 같은 각도에서 나뉘고 재계산 뒤에도 같다(ADR-0016 "바뀐 것").

wait_for() {
  local id="$1" limit="$2" start=$SECONDS
  shift 2
  note "기다리는 중(최대 ${limit}초)…"
  while :; do
    LAST=$(state "$id")
    WORD=${LAST%% *}
    WAITED=$((SECONDS - start))
    [[ " $* lost " == *" $WORD "* ]] && return 0
    (( WAITED >= limit )) && return 0
    sleep 3
  done
}

wait_for는 3초마다 상태를 읽다가 기대한 낱말이 나오거나 요청을 잃거나 시간이 다 되면 돌려준다. 서버가 다시 떠서 메모리의 요청을 잊으면 404이므로 lost로 본다.

아직 확인되지 않은 것 티켓은 위저드를 돌리기 전의 예상을 적어 두었다. 애드인은 답하던 업로드 ID를 메모리(_Serving)에만 두므로, Fusion을 다시 켜면 그 업로드에는 답하지 않을 것으로 본다. 위저드가 실제로 확인하며, 이어지지 않으면 이 항목은 열어 두고 다시 실행된 애드인이 같은 업로드에 이어 답하게 하는 일을 새 티켓으로 만든다. 이 커밋 시점에는 그 결과가 아직 없다.

이 커밋은 따로 정리도 했다. 커밋 메시지에 따라 세 번째 녹화 기록에서 모델 구조를 드러내는 개수(파라미터, 면, 모서리 수)를 지웠다. 공개 저장소 규칙(Background의 마지막 상자)에 해당하는 정리다.

복원이 스윕이 끝날 때만 있었으므로 중간 예외에서는 바꾼 값이 그대로 남았다. 실제로 사용자 파라미터 하나가 0.75배 값으로 남아, 이어서 성공한 업로드의 기본 형상이 되었다. 면 표시는 다음 업로드가 시작할 때 지우는 별도 경로가 있고, 업로드 묶음은 스윕이 끝나야 서버로 가므로 반쯤 올라가지 않는다.

애드인이 시작할 때 자기 하위 모듈을 sys.modules에서 지우지 않고 Fusion도 지우지 않는다면, loaded.txt를 믿는 위저드에 어떤 문제가 생길 수 있는가?

위저드는 애드인 실행 시각과 .py 수정 시각만 견준다. 이미 불러온 하위 모듈이 남아 있으면 진입 파일만 새 코드로 돌고 기록은 새로 써지므로, 위저드는 모든 코드가 새것이라 믿는다. 그래서 시작 코드가 하위 모듈을 지우는 것이 기록의 뜻을 지킨다.

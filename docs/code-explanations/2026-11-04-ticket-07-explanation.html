티켓 07: 여러 슬라이더 덧셈

슬라이더를 여러 개 함께 움직였을 때 변형 엔진이 단독 스윕 이동량을 더하는 동작을 시험으로 묶고, 그 시험이 쓰는 교차 검증 샘플을 뽑는 애드인 함수와 합성 녹화본 도구를 더한 변경이다.

jun-1993-p/threejs-configurator-ai 티켓 07 (f82b855) at f82b855, explained 2026-11-04. References link to this commit.

배경

이 영역이 처음이면 펼쳐서 읽는 깊은 배경

구성기는 Fusion에서 미리 뽑아 둔 형상 묶음(스윕)을 섞어 고객이 고른 값의 형상을 만든다. 파라미터 하나만 움직여 뽑은 것이 단독 스윕이다. 슬라이더가 둘 이상이면 가능한 모든 값 조합을 Fusion에서 뽑을 수는 없다. 조합의 수가 슬라이더 수의 곱으로 늘어 애드인 시간이 감당되지 않기 때문이다(ADR-0004의 검토한 선택지).

그래서 ADR-0004는 단독 스윕의 꼭짓점 이동량을 더해서 섞기로 하고, 덧셈이 맞는지는 교차 검증 샘플로 확인하기로 했다. 교차 검증 샘플은 부모 파라미터 두 개를 동시에 움직여 뽑은 형상이고, 덧셈이 맞는지 보는 데만 쓴다.

티켓 04의 검증점은 단독 스윕의 이웃 샘플 사이 값으로, 한 슬라이더의 보간 오차를 잰다. 이 티켓의 교차 검증 샘플은 그와 달리 두 파라미터를 함께 움직인다.

꼭짓점 이동량은 "기본 형상의 꼭짓점에서 해당 샘플의 같은 꼭짓점까지의 벡터"다. 변형 엔진(createMorph)은 슬라이더마다 샘플별 이동량을 미리 만들어 두고(Track의 deltas), 슬라이더 값이 들어오면 값을 감싸는 두 샘플의 이동량을 선형으로 섞어 기본 형상 위에 더한다. 티켓 파일에 따르면 이 덧셈은 티켓 02부터 있었다. 티켓 파일은 "코드는 그대로 두고 시험을 더했다"고 적는다.

핵심 개념: 덧셈이 맞는 쌍과 틀리는 쌍 티켓 파일은 서로 영향이 없는 쌍에서 덧셈이 맞는 것으로 시험한다. 영향 부위가 다르니 이동량이 겹치지 않는다는 풀이는 이 문서의 해석이다. 이 변경의 예는 전체 폭(몸통과 서랍의 X)과 전체 높이(몸통의 Z)다. 서로 영향을 주는 쌍(ADR-0004의 예는 전체 폭과 서랍 폭)은 덧셈이 틀릴 수 있어서 교차 검증 샘플로 찾아낸다. 그 확인은 다음 티켓의 일이다.

핵심 아이디어

엔진이 슬라이더별 이동량을 따로 계산해 더하므로, 시험이 확인할 것은 두 가지다. 슬라이더 하나만 움직이면 그 슬라이더만 둔 명세와 결과가 같아야 하고, 둘을 함께 움직이면 Fusion이 두 값을 한 번에 적용해 만든 형상과 합격선 안에서 맞아야 한다.

작은 예시: 전체 폭 525, 전체 높이 612.5를 함께 움직이기

기본 형상
폭 525의 이동량
+ 폭 단독 스윕 보간
높이 612.5의 이동량
+ 높이 단독 스윕 보간
비교
Fusion이 두 값을 함께 적용한 형상

525와 612.5는 티켓 파일의 두 교차 검증 샘플 중 첫째 값 쌍이다. 둘째는 (725, 812.5)이고, 두 샘플 모두 슬라이더 범위 안이며 단독 스윕 샘플 사이 값이다. 티켓 파일에 따르면 실제 오차는 1e-13 mm 정도이고, 한 슬라이더 이동량만 적용하면 37.5~112.5 mm로 실패한다. 그래서 시험은 덧셈이 맞는지 틀린지를 가려낸다.

경계 사례: 이 시험이 증명하지 못하는 것 시험이 쓰는 쌍은 서로 영향이 없는 전체 폭과 전체 높이뿐이다. 이 시험이 통과해도 영향을 주는 쌍의 덧셈이 맞다는 뜻은 아니다. 티켓 파일의 완료 기준도 "서로 영향이 없는 두 슬라이더"로 한정한다.

코드 따라가기

흐름: 합성 녹화본 도구가 교차 검증 샘플을 뽑음(애드인 핵심 함수 사용) → 시험이 샘플을 읽음 → 엔진이 이동량을 더함 → 시험이 형상 오차 합격선과 비교.

1. 엔진: 바뀐 곳이 없는 덧셈

이 커밋은 엔진 코드를 바꾸지 않는다. 시험이 확인하는 동작은 이미 있는 positions와 addDelta에 있다. positions는 기본 형상에서 시작해 슬라이더마다 addDelta를 부른다. 값을 주지 않은 슬라이더는 명세의 기본값을 쓴다.

configurator/src/engine.ts:123-127

positions(values) {
  const out = Float64Array.from(basePositions);
  for (const track of tracks) addDelta(out, track, values[track.id] ?? track.defaultValue);
  return out;
},

addDelta(configurator/src/engine.ts:132)는 값을 감싸는 두 샘플의 이동량을 선형으로 섞어 out에 더한다(out[i] += ...). 슬라이더가 여러 개면 이 호출이 슬라이더 수만큼 out 위에 쌓이므로 결과가 이동량의 합이 된다.

2. 시험: 두 가지를 확인한다

시험은 전체 폭과 전체 높이를 둔 명세 widthHeightSpec을 만들어 쓴다(configurator/test/engine.test.ts:67). 첫 시험은 슬라이더 하나만 움직이면 그 슬라이더만 둔 명세(single)와 값이 정확히 같은지 deepEqual로 본다. 오차 허용이 없다. 티켓 파일도 "완전히 같다"고 적는다. 움직이지 않은 슬라이더가 기본값이라 이동량을 보태지 않기 때문일 것이라는 점은 이 문서의 추론이다.

configurator/test/engine.test.ts:83-91

test("슬라이더 하나만 움직이면 단독 스윕 보간과 결과가 같다", () => {
  for (const slider of widthHeightSpec.sliders) {
    const single = createMorph({ ...widthHeightSpec, sliders: [slider] }, recording);
    const multi = createMorph(widthHeightSpec, recording);
    for (const value of [slider.min, (slider.min + slider.default) / 2 + 1, slider.max - 23]) {
      assert.deepEqual(multi.positions({ [slider.id]: value }), single.positions({ [slider.id]: value }), `${slider.id}=${value}`);
    }
  }
});

둘째 시험은 교차 검증 샘플마다 값이 슬라이더 범위 안인지 확인하고, 엔진의 morph.positions(sample.values)와 녹화된 Fusion 형상의 꼭짓점 거리 최댓값이 형상 오차 합격선(shapeTolerance) 이하인지 본다. 합격선은 그 Fusion 형상 전체의 바운딩 박스 대각선으로 정한다. 이 계산에 필요한 diagonal이 verify-numeric.ts에서 pipeline/measure.ts로 옮겨져 시험과 수치 검증기가 같이 쓴다(configurator/pipeline/measure.ts:30).

3. 애드인: 여러 파라미터를 함께 바꾼 형상을 뽑는다

cross_check_sample(model, values)는 이름과 값의 사전을 받아 파라미터를 모두 바꾸고 형상을 단독 스윕 샘플과 같은 형식으로 돌려준다. 다만 value 대신 values를 담는다. 모델에 없는 이름이 있으면 아무것도 바꾸기 전에 거절한다. 단독 스윕 샘플과 겹치는 부분은 _shape_or_failure로 빼서 함께 쓴다.

addin/ConfiguratorUploader/uploader/core.py:140-154

def cross_check_sample(model: FusionModel, values: dict[str, float]) -> dict[str, Any]:
    # elided: 함수 설명 docstring
    parameters = {p.name: p for p in model.parameters()}
    unknown = [name for name in values if name not in parameters]
    if unknown:
        raise ValueError(f"모델에 없는 파라미터: {', '.join(unknown)}")
    # 모두 바꾼 뒤에 재계산 결과를 본다. 앞에서 실패해도 나머지를 마저 바꿔야 되돌릴 목록이 맞는다.
    recomputed = all([model.set_parameter(name, value) for name, value in values.items()])
    sample = {"values": dict(values), **_shape_or_failure(model, recomputed)}
    for name in values:
        model.restore_parameter(parameters[name])
    return sample

수식을 상수로 덮지 않으려고 값이 아니라 원래 수식을 되돌리는 점은 단독 스윕과 같다(ADR-0003). 이 커밋에서는 예외 때문에 되돌리기가 빠지는 경우를 막지 않는다. 그 처리는 다음 티켓에서 들어온다.

4. 합성 녹화본 도구

synthetic/make_cross_checks.py는 SolidCraft 모델로 이 샘플을 뽑아 fixtures/synthetic/drawer.cross-checks.json으로 남긴다. 도구는 먼저 fix_baseline_layouts(synthetic/solidcraft_model.py:148)로 기본 형상의 꼭짓점 배치(경계 맞춤 격자의 점 위치)를 한 번 정해 둔다. 파라미터를 바꾸기 전에 불러야 합성 녹화본과 면과 점의 순서가 같아진다.

퀴즈

모든 슬라이더 값 조합을 Fusion에서 뽑지 않고 이동량을 더하는 방식을 고른 까닭으로 맞는 것은?

ADR-0004의 검토한 선택지가 적은 이유다. 격자 스윕은 정확하지만 샘플 수가 슬라이더 수의 곱으로 늘어 시간이 감당되지 않는다.

슬라이더가 전체 폭과 전체 높이 둘일 때 morph.positions({ body_w: 525 })의 전체 높이 몫은 어떻게 되는가?

values[track.id] ?? track.defaultValue로 명세의 default가 쓰인다. 기본값의 샘플은 기본 형상과 같아 이동량이 0이다. 폭만 움직인 결과가 폭 단독 스윕의 보간과 같은 이유다.

cross_check_sample이 set_parameter 결과를 리스트로 먼저 모은 뒤 all로 묶는 까닭은?

코드 주석이 이유를 밝힌다. 앞에서 실패해도 나머지를 마저 바꿔야 되돌릴 목록이 맞는다. 제너레이터를 all에 바로 넘기면 첫 실패에서 멈춘다.

티켓 04의 검증점(checks)과 이 티켓의 교차 검증 샘플은 각각 무엇을 확인하는가?

검증점은 단독 스윕의 이웃 샘플 사이 값이라 보간이 Fusion과 얼마나 다른지 재고, 교차 검증 샘플은 파라미터 두 개를 함께 바꿔 이동량 덧셈이 맞는지 본다.

두 슬라이더의 덧셈이 틀릴 수 있는 쌍을 이 티켓의 시험이 대표하지 못하는 것은 어느 점 때문인가?

영향이 없는 쌍은 이동량이 겹치지 않아 덧셈이 맞는 쪽이다. 영향을 주는 쌍은 다음 티켓의 교차 검증이 다룬다. 두 샘플은 범위 안이고 합격선은 ADR-0012의 값이다.

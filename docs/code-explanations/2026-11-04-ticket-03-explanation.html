티켓 03: 파이프라인 실행기 관통

상품 하나를 업로드 묶음, 정보 입력, 사람 결정 각본으로 넣으면, 10단계가 코드에 고정된 순서로 진행되어 구성기 결과물이 제출된다. AI는 각본대로 답하는 가짜이고, 바깥 의존은 세 포트로만 닿는다.

jun-1993-p/threejs-configurator-ai 티켓 03 (커밋 3a3d851, 5a444f8) at 5a444f8, explained 2026-11-04. References link to this commit.

배경

이 프로젝트의 큰 그림이 낯설다면 펼쳐서 읽는다.

이 프로젝트는 Fusion CAD 모델을 쇼핑몰용 three.js 구성기로 바꾼다. 사람이 Fusion에서 모델을 업로드하면, AI가 슬라이더 구성 후보를 제안하고, 사람이 고르고, AI가 슬라이더 범위와 부모 자식 관계를 적은 JSON(명세)을 쓰고, 코드가 그 명세로 결과물을 조립해 검증한 뒤 사람이 최종 승인한다. 이 흐름 전체를 하나의 파이프라인이 순서대로 진행한다.

티켓 01과 02에서 두 끝이 만들어졌다. 한쪽은 Fusion 애드인과 서버가 만드는 업로드 묶음이고, 다른 쪽은 명세와 스윕 데이터로 구성기를 띄우는 변형 엔진과 고정 코어다. 이 티켓은 그 사이를 잇는 실행기를 처음 만든다.

이 티켓이 따르는 결정은 ADR-0014 "순서는 코드가 정하고 AI는 단계 안에서만 일한다"다. 단계 순서와 실패 때 돌아가는 경로는 코드에 고정하고, AI는 정해진 단계에서 정해진 입력을 받아 정해진 형식(JSON Schema)으로만 답한다. ADR은 에이전트가 스스로 다음 단계를 고르게 하면 실행마다 경로가 달라져 재현과 검증이 어렵다고 적었다.

  • 포트: 바깥 의존을 숨기는 인터페이스. 여기서는 Fusion 연결, AI 모델, 저장소 세 가지다(티켓의 "테스트 경계 1").
  • 단계(Stage): 업로드, 정보 입력, 후보 제시, 후보 선택, UI 스타일, 명세 작성, 조립, 검증, 최종 승인, 제출 열 가지.
  • 정보 입력(Intake): 상품명, 종류, 원하는 슬라이더 메모, 두께 선택 노출 여부를 담은 사람의 입력.
  • 후보(Candidate): AI가 제안하는 슬라이더 구성 하나. 정면 방향, 노출할 부모 파라미터, 두께 선택 노출 여부, 요약과 다른 후보와의 차이 한 줄을 갖는다.
핵심 개념 AI의 모든 응답은 검사 전에는 믿지 않는 값이다. 포트는 응답을 unknown으로 돌려주고, 실행기가 JSON Schema로 검사한다. 통과하지 못하면 오류 문장을 붙여 다시 묻고, 정해진 횟수 뒤에도 틀리면 그 단계에서 멈춘다.

핵심 아이디어

runPipeline은 위에서 아래로 읽히는 하나의 긴 함수다. 단계를 건너뛰는 분기도, AI가 고르는 경로도 없다. 열 단계는 코드의 문장 순서로만 정해진다. 단계 하나가 끝날 때마다 저장소 포트에 처리 기록이 남는다.

고정된 단계 순서(예시: 서랍장 "1단 서랍장")

상품명, 종류, 메모

후보 2~4개

후보 id c1

승인

AI 응답을 다루는 규칙이 이 티켓의 핵심 로직이다. 후보, 스타일, 명세의 세 응답에 같은 방식이 적용된다. 응답을 검사해서 통과하면 쓰고, 틀리면 오류 목록을 schemaErrors로 다음 질문에 붙여 다시 묻는다. 처음 질문 한 번에 다시 묻기 3번까지, 합쳐 4번 물어도 통과하지 못하면 그 단계에서 stopped로 끝난다.

장난감 예시는 시험에서 가져왔다. AI가 처음 낸 명세에서 슬라이더의 unit이 "cm"이면 스키마의 unit: mm 상수에 어긋난다. 실행기는 /sliders/0/unit이 틀렸다는 문장을 붙여 다시 묻고, AI가 고친 명세를 내면 그 명세로 조립한다. 틀린 명세로는 조립 단계에 가지 못한다.

아직 빈 자리 검증 단계는 비어 있다. 수치 검증(티켓 04), 축 반응 검증(티켓 06), AI 판정(티켓 19)이 여기에 들어오고, 피드백 루프와 3회 제한도 티켓 04에서 붙는다. Fusion 연결 포트는 인터페이스만 있고 호출되지 않는다. 최종 승인은 승인만 지원하고, 사례 기록은 메모리에 담기만 한다(티켓 21). 고른 스타일은 결과물에 아직 반영되지 않는다(티켓 18).

코드 따라가기

흐름: 포트와 단계 타입 → 검사기(schemas.ts) → 실행기 본체(runner.ts의 askUntilValid와 열 단계) → 조립(assemble.ts) → 각본 AI와 메모리 저장소 → 시험. 이어서 리뷰 반영으로 바뀐 점.

1. 포트와 단계: 바깥 세계와의 경계

단계 이름은 문자열 합집합 타입이고, 순서는 타입이 아니라 runPipeline의 코드가 정한다. AI 포트의 세 메서드는 응답을 unknown으로 돌려주며, 저장소 포트는 스타일 목록, 처리 기록, 결과물 제출, 사례 기록을 맡는다.

세 포트와 별도로, 사람의 결정(후보 고르기, 최종 승인)은 HumanPort로 들어온다. 시험에서는 각본이, 운영에서는 화면이 답한다고 주석이 적었다. 실행기에 넘기는 PipelineInput은 bundle, intake, human과 세 포트다(configurator/pipeline/runner.ts:116-121).

2. 검사기: 어떤 응답이 통과하는가

세 가지 검사기가 있다. 업로드 묶음과 명세는 서버와 같이 쓰는 schema/ 폴더의 JSON Schema 파일을 읽는다. 후보는 코드 안에 적은 스키마로 검사하며 2개에서 4개여야 한다. 스타일은 저장소가 가진 스타일 id 목록 밖의 값이 통과하지 못하게 한다. AI는 목록 안에서 하나만 고른다는 ADR-0001의 약속이 이 검사로 지켜진다.

configurator/pipeline/schemas.ts:27-55

      front: { enum: FRONTS },
      parents: { type: "array", minItems: 1, items: { type: "string", minLength: 1 } },
      showThickness: { type: "boolean" },
      summary: { type: "string" },
      diff: { type: "string" },
    },
  },
});

/** UI 스타일 응답. 저장소의 스타일 목록 밖의 값은 통과하지 못한다(ADR-0001). */
export function styleChoiceChecker(styleIds: string[]): Check {
  return checker({
    type: "object",
    required: ["style"],
    additionalProperties: false,
    properties: { style: { enum: styleIds } },
  });
}

명세 스키마(schema/spec.schema.json)는 이 티켓에서 새로 만들었다. 단위는 mm 상수로 못 박고, 정면은 +X에서 -Z까지 여섯 값, 슬라이더는 id부터 affects까지 열한 개 필드를 필수로 둔다. 검사기는 Ajv(ajv 8.17.1)로 만들고, 오류를 경로: 메시지 문장 목록으로 바꾼다(configurator/pipeline/schemas.ts:18-22).

3. 실행기 본체: 다시 묻기와 멈춤

askUntilValid가 세 응답에 공통인 다시 묻기 반복이다. 첫 질문은 오류 목록이 빈 채로 나가고, 통과하지 못할 때마다 처리 기록에 오류를 남기고 그 오류를 붙여 다시 묻는다. 반복은 attempt 0부터 SCHEMA_RETRIES(3)까지라 질문은 최대 4번이다. 끝내 통과하지 못하면 PipelineStop 예외를 던진다.

configurator/pipeline/runner.ts:125-151

/** 형식이 틀린 AI 응답을 다시 묻는 횟수 */
const SCHEMA_RETRIES = 3;

class PipelineStop extends Error {
  readonly stage: Stage;
  constructor(stage: Stage, reason: string) {
    super(reason);
    this.stage = stage;
  }
}

export async function runPipeline({ bundle, intake, human, ports }: PipelineInput): Promise<PipelineResult> {
  const { ai, store } = ports;
  const log = (stage: Stage, detail?: unknown) =>
    store.appendLog({ product: intake.name, stage, at: new Date().toISOString(), ...(detail === undefined ? {} : { detail }) });

  /** AI 응답이 스키마를 통과할 때까지 다시 묻는다. 끝내 통과하지 못하면 그 단계에서 멈춘다. */
  async function askUntilValid<T>(stage: Stage, check: Check, call: (schemaErrors: string[]) => Promise<unknown>): Promise<T> {
    let errors: string[] = [];
    for (let attempt = 0; attempt <= SCHEMA_RETRIES; attempt++) {
      const answer = await call(errors);
      errors = check(answer);
      if (errors.length === 0) return answer as T;
      await log(stage, { schemaErrors: errors });
    }
    throw new PipelineStop(stage, `AI 응답이 ${SCHEMA_RETRIES}번 다시 물어도 형식 검사를 통과하지 못했습니다: ${errors.join("; ")}`);
  }

티켓의 판단 기록에 따르면 형식 오류 다시 묻기는 사용자 스토리 81(모든 AI 응답의 JSON Schema 검사)을 단계마다 같은 방식으로 적용한 것이고, 횟수와 stopped 종료는 티켓 04와 15에서 바뀔 수 있다.

열 단계는 이 함수 안에서 위에서 아래로 이어진다. 후보를 고르는 사람의 응답이 제시되지 않은 후보 id이면 choice 단계에서 멈춘다. 명세는 스키마 검사에 더해 product가 정보 입력의 상품명과 같은지도 본다. 상품명은 실행할 때 들어오는 값이라 정적인 스키마 파일로는 적을 수 없다. 코드는 이 이유를 적어 두지 않았고, 이것은 내 추정이다.

configurator/pipeline/runner.ts:178-205

    // 명세의 상품명은 정보 입력에서 가져온다(docs/spec-schema.md).
    const checkProductSpec: Check = (value) => {
      const errors = checkSpec(value);
      if (errors.length === 0 && (value as Spec).product !== intake.name) {
        errors.push(`/product: 정보 입력의 상품명 "${intake.name}"이어야 합니다`);
      }
      return errors;
    };
    const spec = await askUntilValid<Spec>("spec", checkProductSpec, (schemaErrors) =>
      ai.writeSpec({ bundle, intake, candidate, feedback: [], schemaErrors }),
    );
    await log("spec");

    // 업로드 단계에서 스키마를 통과했으므로 엔진이 읽는 스윕 데이터 형식이다.
    const files = await assembleProduct(spec, bundle as SweepData);
    await log("assembly");

    // 수치 검증(티켓 04), 축 반응 검증(티켓 06), AI 판정(티켓 19)이 여기에 들어온다.
    const feedback: Feedback[] = [];
    await log("verification", { feedback });

    const { decision } = await human.finalApproval({ spec, files });
    await log("approval", decision);

    await store.submit(intake.name, files);
    await store.recordCase({ kind: intake.kind, intake, candidates, chosen: candidate.id, spec });
    await log("submission");
    return { status: "submitted" };

맨 바깥의 catch는 PipelineStop만 잡아 멈춘 단계를 처리 기록에 남기고 status: "stopped" 결과로 돌려준다. 다른 예외(AI 포트가 던진 오류 등)는 그대로 밖으로 나간다(configurator/pipeline/runner.ts:206-210).

4. 조립: 메모리에서 결과물 만들기 (리뷰 반영으로 위치가 바뀜)

첫 커밋에서 조립 함수 assembleProduct는 명령행 스크립트 scripts/build.ts 안에 있었고, 실행기가 그 스크립트를 불러다 썼다. 리뷰 반영 커밋(5a444f8)이 이 함수를 pipeline/assemble.ts로 옮겼다. 티켓 기록은 이유를 "실행기가 명령행 스크립트에 기대지 않게" 하려는 것이라고 적었다. 이제 build.ts는 조립 결과를 디스크에 쓰는 일만 한다.

configurator/pipeline/assemble.ts:62-73

/** 결과물 파일 이름과 내용. 쇼핑몰에는 이 파일들을 그대로 올린다. */
export type ProductFiles = Record<"configurator.js" | "spec.json" | "sweeps.json" | "index.html", string>;

/** 고정 코어 번들과 명세·스윕 데이터·붙여 넣을 div를 메모리에서 만든다. */
export async function assembleProduct(spec: Spec, bundle: SweepData): Promise<ProductFiles> {
  return {
    "configurator.js": await buildCore(),
    "spec.json": JSON.stringify(spec, null, 2),
    "sweeps.json": JSON.stringify(sweepDataFor(spec, bundle)),
    "index.html": SNIPPET,
  };
}

티켓 02의 buildCore는 파일에 썼지만, 여기서는 esbuild의 write: false로 결과를 문자열로 받는다(configurator/pipeline/assemble.ts:11-24). 실행기가 파일 시스템 없이도 결과물을 제출할 수 있다. build.ts의 writeProduct는 이 파일 목록을 폴더에 쓰기만 한다.

configurator/scripts/build.ts:9-14

export async function writeProduct(spec: Spec, bundle: SweepData, outDir: string): Promise<void> {
  mkdirSync(outDir, { recursive: true });
  for (const [name, content] of Object.entries(await assembleProduct(spec, bundle))) {
    writeFileSync(join(outDir, name), content);
  }
}

5. 시험용 포트: 각본 AI와 메모리 저장소

각본 AI는 단계마다 정해 둔 답 목록을 차례로 꺼내 준다. 같은 단계가 다시 불리면 다음 답을 내므로 "처음엔 틀리고 두 번째엔 맞는" 장면을 시험할 수 있다. 받은 입력은 calls에 남는다. 답이 바닥나면 일반 Error로 거절한다. 리뷰 반영은 단계 목록을 STAGES 한 곳에서 만들어 세 군데에 흩어졌던 키 목록을 줄였다.

configurator/pipeline/scripted-ai.ts:15-31

export function scriptedAi(script: Script): ScriptedAi {
  const byStage = <T>(make: (stage: ScriptStage) => T) =>
    Object.fromEntries(STAGES.map((stage) => [stage, make(stage)])) as Record<ScriptStage, T>;
  const remaining = byStage((stage) => [...script[stage]]);
  const calls = byStage((): unknown[] => []);
  const answer = (stage: ScriptStage, input: unknown) => {
    calls[stage].push(input);
    if (remaining[stage].length === 0) return Promise.reject(new Error(`각본에 남은 ${stage} 답이 없습니다`));
    return Promise.resolve(structuredClone(remaining[stage].shift()));
  };
  return {
    calls,
    proposeCandidates: (input) => answer("candidates", input),
    chooseStyle: (input) => answer("style", input),
    writeSpec: (input) => answer("spec", input),
  };
}

메모리 저장소는 처리 기록, 제출물, 사례를 배열에 담아 시험이 들여다볼 수 있게 한다(configurator/pipeline/memory-store.ts:11-22).

6. 리뷰 반영의 나머지

두 번째 커밋에는 작은 정리가 더 있다. 후보의 정면(front)이 문자열 대신 Front 타입으로 좁혀졌다. 여섯 값 목록 FRONTS를 schemas.ts에 한 번 두고, 후보 검사기와 Front 타입이 같은 목록을 쓴다(configurator/pipeline/schemas.ts:12-13). 스키마 읽기 함수는 shared에서 loadSharedSchema로 이름이 바뀌었다. 티켓은 상품 종류와 검증 피드백 kind의 문자열 타입은 목록이 정해지는 티켓 16과 04에서 좁히기로 하고 이번에 반영하지 않았다고 기록했다.

7. 시험

configurator/test/pipeline.test.ts는 일곱 개 시험으로 경계 1을 본다. 서랍장 합성 녹화본을 쓰고 AI는 각본, 저장소는 메모리, Fusion 연결은 부르면 실패하는 가짜다. 보는 것은 다음과 같다.

  • 열 단계가 정해진 순서로만 처리 기록에 남는다.
  • 승인하면 제출된 결과물의 명세와 스윕 데이터, 붙여 넣을 div, 그리고 제출된 코어 번들이 실제로 서랍장 형상을 만든다.
  • 승인된 결정이 사례로 기록된다.
  • 틀린 명세(unit: "cm")는 이유를 붙여 다시 묻고, 고친 명세로 조립한다.
  • 끝내 틀리면(네 번 모두 front: "앞") 조립하지 않고 spec 단계에서 멈춘다.
  • 명세의 상품명이 다르면 다시 묻는다.
  • 처리 기록 항목마다 상품명이 남는다.

퀴즈

단계 순서를 AI가 고르지 않고 runPipeline의 코드 순서로 고정한 이유로 ADR-0014가 드는 것은?

ADR은 에이전트가 다음 단계를 스스로 고르면 실행마다 경로가 달라져 재현과 검증이 어렵고, 1인 프로젝트에서 실패 원인을 추적하기 힘들다고 적었다. 유연성을 포기하고 예측 가능성을 택한 결정이다.

각본 AI가 형식이 틀린 명세를 네 번 연속으로 낸다. 실행기가 stopped로 끝내기까지 writeSpec은 몇 번 불릴까?

반복은 attempt 0부터 SCHEMA_RETRIES(3)까지라서 처음 질문 한 번에 다시 묻기 세 번, 합쳐 네 번이다. 시험의 각본에 틀린 명세가 네 개 들어 있는 것도 같은 이유다.

명세의 product가 정보 입력의 상품명과 같은지는 스키마 파일이 아니라 실행기 코드가 확인한다. 이렇게 나눈 이유로 가장 알맞은 것은?

상품명은 실행할 때마다 달라지는 값이고 스키마는 정적 파일이다. 코드가 이유를 적지 않았으므로 이것은 추정이다. 서버와 스키마를 공유하는 것은 사실이지만, 그래서 확인을 못 넣는 것은 아니다.

assembleProduct를 scripts/build.ts에서 pipeline/assemble.ts로 옮긴 리뷰 반영의 효과는?

첫 커밋에서는 실행기가 명령행 스크립트 파일을 불러와 조립 함수를 썼다. 조립을 파이프라인 쪽으로 옮기면 의존 방향이 실행기에서 스크립트가 아니라 스크립트에서 조립으로 바뀐다. 스타일 반영은 티켓 18의 몫이다.

각본의 spec 답이 틀린 명세 하나뿐인데 실행기가 다시 물으면 어떻게 될까?

각본 AI는 답이 바닥나면 일반 Error로 거절한다. 실행기의 catch는 PipelineStop만 처리하므로 이 오류는 그대로 밖으로 나간다. 형식 검사를 끝내 통과하지 못한 경우와 달리 stopped 결과가 되지 않는다.

티켓 02: 녹화 묶음으로 구성기 띄우기

명세 하나와 업로드 묶음을 넣으면, 변형 엔진이 단독 스윕 샘플 사이의 꼭짓점 이동량을 섞어 형상을 만들고, 고정 코어가 그 형상을 슬라이더가 달린 three.js 구성기로 div 하나 안에 띄운다.

jun-1993-p/threejs-configurator-ai 티켓 02 (커밋 dcf3e6c) at dcf3e6c, explained 2026-11-04. References link to this commit.

배경

이 프로젝트와 3D 메쉬 개념이 낯설다면 펼쳐서 읽는다.

이 프로젝트는 Fusion으로 만든 CAD 모델을 쇼핑몰 페이지의 div 하나 안에서 도는 three.js 구성기로 바꾼다. 고객은 슬라이더로 값을 바꾸고, 구성기는 모델의 형태를 그에 맞게 바꿔 보여준다. 브라우저에서 Fusion을 다시 계산할 수는 없으므로, 미리 뽑아 둔 형상 표본(스윕)을 섞는 방식을 쓴다(ADR-0002).

three.js에서 3D 모양은 꼭짓점 위치 목록과, 세 꼭짓점 번호씩 묶은 삼각형 목록(연결)으로 그려진다. 모양이 변해도 연결이 그대로이면 꼭짓점 위치만 바꾸면 된다. 앞선 티켓 25가 이 전제를 만들었다. 샘플마다 꼭짓점 개수와 순서가 같고, 연결은 기본 형상에서 한 번만 정해 둔다.

이 티켓이 쓰는 입력은 둘이다.

  • 명세(JSON): 상품의 슬라이더, 범위, 축 등을 적은 파일. 원래는 AI가 쓰는 산출물인데, 이 티켓에서는 손으로 쓴 슬라이더 1개짜리(fixtures/synthetic/drawer.spec.json)를 쓴다. 슬라이더는 body_w("전체 폭", 400~800 mm, 기본값 600)다.
  • 스윕 데이터: 업로드 묶음(schema/upload-bundle.schema.json) 중 엔진이 읽는 부분. 입력으로는 티켓 24와 25의 서랍장 합성 녹화본을 쓴다.
핵심 개념 고정 코어(ADR-0001): 상품과 무관하게 같은 바이트로 유지되는 구성기 코드. 상품마다 달라지는 것은 명세와 스윕 데이터뿐이다. 이 티켓은 코어와 변형 엔진을 처음 만든다.

핵심 아이디어

스윕은 파라미터마다 샘플 5개로 이루어진다. 서랍장 body_w의 기본값이 600이므로 샘플 값은 300, 450, 600, 750, 900이다. 샘플 사이의 값은 이웃 두 샘플의 형상을 직접 섞지 않고, 기본 형상에서 각 꼭짓점이 얼마나 움직였는지(이동량)를 선형으로 섞는다. 그 결과를 기본 형상 위치에 더한다.

예를 들어 슬라이더가 525이면 450과 600 샘플 사이이고 비율은 (525 − 450) / (600 − 450) = 0.5다. 몸통의 한쪽 가장자리 꼭짓점이 450 샘플에서 x = −225, 600 샘플에서 x = −300이면 525에서는 −262.5다. 그래서 폭이 525인 몸통의 x 범위는 −262.5에서 262.5가 된다(엔진 시험의 기댓값과 같다).

스윕이 샘플 값 자체에서는 정확하다는 점도 중요하다. 샘플 값에서 엔진이 내는 위치는 녹화된 형상과 일치하고, 둘 사이만 선형으로 근사한다. 이 근사가 얼마나 맞는지를 검증하는 일은 뒤 티켓의 몫이다.

띄우기까지의 흐름(예시 데이터)

drawer.spec.json + drawer.json
슬라이더 body_w의 단독 스윕만
build.ts: 결과물 만들기
configurator.js, spec.json, sweeps.json
쇼핑몰 페이지의 div
fetch로 JSON 두 개
core.ts: mount
body_w = 525
engine.ts: 꼭짓점 위치 → 화면
이 티켓이 하지 않는 것 면 구성이 기본 형상과 다른 샘플이 있으면 엔진은 오류를 낸다. 위상 묶음(ADR-0005)은 티켓 10과 11이 맡는다. 슬라이더가 여럿이면 이동량을 더하지만 그 시험은 티켓 07 몫이다. 부품 색은 임시이고(스타일 선택은 티켓 18), 슬라이더 UI는 자동 시험이 없다.

코드 따라가기

흐름: 결과물 만들기(build.ts) → 페이지에서 JSON 불러오기와 구성기 붙이기(core.ts의 mountAll) → 변형 엔진의 이동량 준비(createMorph) → 슬라이더 값에서 위치 만들기(addDelta) → 화면 갱신 → 시험.

1. 결과물 만들기

스크립트는 네 파일을 낸다: 고정 코어 번들(configurator.js), 명세(spec.json), 스윕 데이터(sweeps.json), 쇼핑몰에 붙일 index.html. 코어는 esbuild로 한 파일(IIFE)로 묶고 전역 Configurator로 내보낸다.

configurator/scripts/build.ts:14-26

export async function buildCore(outfile: string): Promise<void> {
  await esbuild.build({
    entryPoints: [CORE],
    outfile,
    bundle: true,
    format: "iife",
    globalName: "Configurator",
    target: "es2020",
    minify: true,
    legalComments: "none",
    logLevel: "warning",
  });
}

스윕 데이터는 업로드 묶음에서 명세의 슬라이더가 쓰는 부분만 남긴다. 슬라이더 id와 같은 이름의 단독 스윕만 고르고, 면은 이름과 점만(기본 형상은 연결까지) 둔다. 형식은 업로드 묶음 그대로여서 엔진이 바로 읽는다.

configurator/scripts/build.ts:29-47

export function sweepDataFor(spec: Spec, bundle: SweepData): SweepData {
  const ids = new Set(spec.sliders.map((s) => s.id));
  return {
    parts: bundle.parts.map(({ name, faces }) => ({ name, faces })),
    baseline: {
      faces: bundle.baseline.faces.map(({ body, name, points, triangles }) => ({ body, name, points, triangles })),
    },
    sweeps: bundle.sweeps
      .filter((s) => ids.has(s.parameter))
      .map(({ parameter, samples }) => ({
        parameter,
        samples: samples.map(({ value, status, faces }) => ({
          value,
          status,
          faces: faces.map(({ body, name, points }) => ({ body, name, points })),
        })),
      })),
  };
}

코어가 데이터를 번들에 넣지 않고 JSON으로 따로 불러오는 이유를 티켓은 이렇게 적었다. 고정 코어를 상품마다 같은 바이트로 두기 위해서다(ADR-0001). 대가로 file://에서는 동작하지 않고 http로 서비스해야 한다. 쇼핑몰 페이지에는 div 한 줄과 script 한 줄만 붙인다(configurator/scripts/build.ts:57-59).

2. 고정 코어: 페이지에서 붙이기

번들이 불려 오면 페이지의 data-configurator div마다 data-spec과 data-sweeps의 주소에서 JSON을 불러와 mount를 부른다. DOM이 없는 곳(Node)에서 번들을 읽으면 이 자동 붙이기는 건너뛴다. 덕분에 같은 번들 안의 엔진을 Node 시험이 그대로 쓸 수 있다.

configurator/src/core.ts:163-184

export async function mountAll(root: ParentNode = document): Promise<Configurator[]> {
  const divs = [...root.querySelectorAll<HTMLElement>("[data-configurator]")];
  return Promise.all(
    divs.map(async (div) => {
      const load = async (attr: string) => {
        const url = div.getAttribute(attr);
        if (!url) throw new Error(`구성기 div에 ${attr} 속성이 없습니다`);
        const response = await fetch(new URL(url, document.baseURI));
        if (!response.ok) throw new Error(`${url}을 불러오지 못했습니다(${response.status})`);
        return response.json();
      };
      const [spec, sweeps] = await Promise.all([load("data-spec"), load("data-sweeps")]);
      return mount(div, spec, sweeps);
    }),
  );
}

// 번들을 Node 등 DOM 없는 곳에서 불러오면 엔진만 쓴다
if (typeof document !== "undefined") {
  if (document.readyState === "loading") document.addEventListener("DOMContentLoaded", () => void mountAll());
  else void mountAll();
}

3. 변형 엔진: 이동량 준비

createMorph가 엔진의 중심이다. 먼저 기본 형상의 모든 면을 한 줄로 이어 붙여 꼭짓점 위치 하나의 배열(basePositions)과 연결(triangles)을 만든다. 면마다 시작 번호(start)와 점 수(count)를 기억하고, 면은 바디/이름으로 찾는다.

configurator/src/engine.ts:77-92

export function createMorph(spec: Spec, data: SweepData): Morph {
  const baseline = data.baseline.faces;
  const partOf = new Map<number, string>();
  for (const part of data.parts) for (const i of part.faces) partOf.set(i, part.name);

  const faces: MorphFace[] = [];
  const base: number[] = [];
  const triangles: number[] = [];
  baseline.forEach((face, i) => {
    const start = base.length / 3;
    faces.push({ body: face.body, name: face.name, part: partOf.get(i) ?? face.body, start, count: face.points.length });
    for (const p of face.points) base.push(...p);
    for (const t of face.triangles) triangles.push(start + t[0], start + t[1], start + t[2]);
  });
  const basePositions = Float64Array.from(base);
  const faceIndex = new Map(baseline.map((f, i) => [key(f), i]));

슬라이더마다 트랙을 만든다. 트랙은 재계산에 성공한 샘플을 값 순으로 정렬한 것과, 샘플별 이동량(샘플 점 − 기본 형상 점)이다. 샘플이 2개보다 적거나, 면 개수나 면 이름, 점 수가 기본 형상과 어긋나면 오류를 낸다.

configurator/src/engine.ts:94-117

  const tracks: Track[] = spec.sliders.map((slider) => {
    const sweep = data.sweeps.find((s) => s.parameter === slider.id);
    if (!sweep) throw new Error(`슬라이더 ${slider.id}: 스윕 데이터에 이 파라미터의 단독 스윕이 없습니다`);
    const samples = sweep.samples.filter((s) => s.status === "ok").sort((a, b) => a.value - b.value);
    if (samples.length < 2) throw new Error(`슬라이더 ${slider.id}: 재계산에 성공한 샘플이 2개보다 적습니다`);
    return {
      id: slider.id,
      defaultValue: slider.default,
      values: samples.map((s) => s.value),
      deltas: samples.map((s) => {
        const delta = new Float64Array(basePositions.length);
        if (s.faces.length !== baseline.length) throw topologyChanged(slider.id, s.value);
        for (const face of s.faces) {
          const i = faceIndex.get(key(face));
          if (i === undefined || face.points.length !== faces[i].count) throw topologyChanged(slider.id, s.value);
          const offset = faces[i].start * 3;
          face.points.forEach((p, j) => {
            for (let c = 0; c < 3; c++) delta[offset + j * 3 + c] = p[c] - basePositions[offset + j * 3 + c];
          });
        }
        return delta;
      }),
    };
  });

4. 변형 엔진: 슬라이더 값에서 위치 만들기

positions는 기본 위치를 복사한 뒤 슬라이더마다 addDelta로 이동량을 더한다. 값이 없으면 명세의 default를 쓴다. 슬라이더가 둘 이상이면 이동량이 더해지는데, 이 덧셈이 맞는지는 ADR-0004가 교차 검증으로 확인하도록 한 부분이고 이 티켓에서는 시험하지 않는다.

addDelta는 값을 감싸는 두 샘플을 찾는다. 샘플 범위 밖의 값은 끝 샘플에 붙인다(비율 t를 0과 1 사이로 자른다).

configurator/src/engine.ts:130-141

/** 값을 감싸는 두 샘플의 이동량을 선형으로 섞어 더한다. 샘플 범위 밖의 값은 끝 샘플에 붙인다. */
function addDelta(out: Float64Array, track: Track, value: number) {
  const { values, deltas } = track;
  let hi = values.findIndex((v) => v >= value);
  if (hi === -1) hi = values.length - 1;
  if (hi === 0) hi = 1;
  const lo = hi - 1;
  const t = Math.min(1, Math.max(0, (value - values[lo]) / (values[hi] - values[lo])));
  const a = deltas[lo];
  const b = deltas[hi];
  for (let i = 0; i < out.length; i++) out[i] += a[i] + (b[i] - a[i]) * t;
}

면 구성이 다른 샘플에 대한 오류 메시지는 위상 묶음이 아직 지원되지 않음을 알려 준다(configurator/src/engine.ts:143-146). 이 엔진 파일은 DOM이나 three.js에 기대지 않는다고 첫 주석이 밝히며, 구성기와 검증기가 같은 파일을 쓴다는 것이 이유다(configurator/src/engine.ts:1-2).

5. 고정 코어: 화면 만들기와 갱신

mount는 엔진으로 처음 위치를 얻고, 부품마다 메쉬 하나를 만든다. 모든 메쉬가 하나의 위치 버퍼를 공유하고, 부품별 인덱스만 다르다. 그래서 슬라이더를 움직일 때 버퍼 하나만 갱신하면 모든 부품이 따라 움직인다.

configurator/src/core.ts:51-73

  // 부품마다 메쉬 하나. 꼭짓점 위치는 모든 부품이 한 버퍼를 같이 쓴다.
  const position = new THREE.BufferAttribute(new Float32Array(morph.positions(values)), 3);
  position.setUsage(THREE.DynamicDrawUsage);
  const geometries: THREE.BufferGeometry[] = [];
  const parts = [...new Set(morph.faces.map((f) => f.part))];
  const partOfVertex = new Uint32Array(position.count);
  for (const face of morph.faces) partOfVertex.fill(parts.indexOf(face.part), face.start, face.start + face.count);
  parts.forEach((_, n) => {
    const index: number[] = [];
    const t = morph.triangles;
    for (let i = 0; i < t.length; i += 3) if (partOfVertex[t[i]] === n) index.push(t[i], t[i + 1], t[i + 2]);
    const geometry = new THREE.BufferGeometry();
    geometry.setAttribute("position", position);
    geometry.setIndex(index);
    geometry.computeVertexNormals();
    geometries.push(geometry);
    const material = new THREE.MeshStandardMaterial({
      color: PART_COLORS[n % PART_COLORS.length],
      roughness: 0.8,
      side: THREE.DoubleSide,
    });
    scene.add(new THREE.Mesh(geometry, material));
  });

슬라이더 UI는 명세에서 자동으로 만든다. 슬라이더마다 min, max, step, default를 명세에서 읽는다. 값이 바뀌면 set이 범위로 자르고 update가 새 위치를 버퍼에 쓴 뒤 법선을 다시 계산해 그린다.

configurator/src/core.ts:115-120

  const update = () => {
    (position.array as Float32Array).set(morph.positions(values));
    position.needsUpdate = true;
    for (const g of geometries) g.computeVertexNormals();
    render();
  };

6. 시험

엔진 시험(configurator/test/engine.test.ts) 세 개는 서랍장 합성 녹화본을 입력으로 쓴다. 샘플 값에서 녹화된 형상과 1e-9 안에서 일치하는지, 525에서 몸통이 ±262.5이고 서랍이 ±242.5로 폭만 바뀌는지, 값을 주지 않으면 기본 600(몸통 ±300)을 쓰는지를 본다. 서랍이 ±242.5인 것은 이 모델에서 서랍 폭이 몸통 폭에서 40을 뺀 값이기 때문이다(시험 주석).

번들 시험(configurator/test/bundle.test.ts) 세 개는 결과물이 네 파일로 이루어지는지, 번들 안의 엔진이 Node 엔진과 같은 꼭짓점을 내는지(400, 433.3, 600, 777, 800에서 비교), 스윕 데이터에 명세의 슬라이더 스윕만 남는지를 본다. 번들은 브라우저 대신 Node의 vm에서 실행해 비교한다. 티켓은 실제 브라우저(Chrome)에서 손으로 같은 값을 확인했다고 기록했다.

퀴즈

코어는 명세와 스윕 데이터를 번들에 넣지 않고 페이지에서 JSON으로 따로 불러온다. 이 구조의 이유로 가장 알맞은 것은?

상품마다 달라지는 것은 명세와 스윕 데이터뿐이어야 한다(ADR-0001). 데이터를 번들에 넣으면 코어가 상품마다 달라진다. 오히려 fetch를 쓰므로 file://에서는 동작하지 않고 http로 서비스해야 한다.

슬라이더 body_w의 샘플이 300, 450, 600, 750, 900이다. 엔진에 body_w = 1000을 넘기면 몸통 폭은 얼마가 될까?

addDelta는 샘플 범위 밖의 값을 끝 샘플에 붙인다. 비율 t를 0과 1 사이로 자르기 때문에 이동량이 900 샘플의 것에서 더 늘지 않는다. 화면의 슬라이더는 어차피 min과 max로 한 번 더 자른다.

슬라이더에 연결된 스윕의 샘플 하나에서 면 이름 하나가 기본 형상에 없다. 이 티켓의 createMorph는 어떻게 할까?

건너뛰는 것은 recompute_failed인 샘플뿐이다. 면 구성이 다른 샘플은 위상 묶음(티켓 10, 11)이 있어야 다룰 수 있어서, 그 전까지는 조용히 틀린 형상을 내는 대신 오류로 알린다.

슬라이더는 body_w 하나뿐인데 525에서 서랍 폭도 함께 줄어든다(±242.5). 엔진의 어떤 성질 때문일까?

티켓 22: Docker 운영과 모델 예비 전환

서버 전체를 LAN의 로컬 Docker 구성 하나로 띄우고, LiteLLM 설정만으로 Cerebras, Groq, 로컬 모델 사이를 전환하게 한다. 모델이 바뀌어도 파이프라인이 받는 입출력 형식은 그대로 유지한다.

jun-1993-p/threejs-configurator-ai 티켓 22, 최신 커밋 bbe3c6b, 포함한 커밋: 444e9ec (티켓 22: 임베딩 모델 선택 기록), bbe3c6b (티켓 22: Docker 운영과 모델 예비 전환), explained 2026-11-04. References link to this commit.

배경

이 영역이 처음이면 펼쳐서 읽는 기본 배경

LiteLLM은 여러 AI 제공자를 OpenAI 호환 API 하나로 중계하는 프록시다. 호출하는 쪽은 model_name(예: llm)만 보내고, 그 이름이 어느 제공자의 어느 모델인지는 프록시 설정이 정한다. Ollama는 모델을 내려받아 로컬에서 돌리는 도구이고 OpenAI 호환 주소를 연다. Docker Compose는 여러 컨테이너(서비스)를 설정 파일 하나로 띄운다.

추론 모델은 답을 내기 전에 생각을 길게 쓰는 모델이다. 제공자마다 그 생각을 다른 곳에 담는다: 답 본문 앞에 <think> 블록으로 붙이거나, 응답의 별도 필드(reasoning, reasoning_content)에 싣는다.

이 프로젝트의 파이프라인은 AI 모델 포트(AI를 부르는 코드의 경계)의 LiteLLM 구현(파이프라인이 모델을 부르는 코드 liteLlmAi)으로 단계마다 정해진 model_name을 부른다. 이 커밋 시점의 ADR-0015는 AI 모델을 외부 API로 쓰되 공개된 가중치의 모델(오픈 웨이트)만 쓰고 LiteLLM으로 중계해, 외부 API를 쓸 수 없으면 로컬 머신(운영체제·기종 무관)의 같은 계열 모델로 바꿀 수 있게 하라고 정했다. 상품의 파라미터·명세·렌더링 이미지가 LAN 밖으로 나가는 것은 받아들인 결정이다.

이 문서의 용어: 예비 모델은 외부 API(Cerebras)가 응답하지 않거나 오류를 낼 때 LiteLLM이 대신 부르는 모델이다. Groq, 그다음 로컬 모델 순서다. 파이프라인은 어느 모델이 답했는지 모른다(용어집). 경계 1 시험은 같은 합성 서랍장 녹화본(SolidCraft로 만든 시험용 업로드 묶음)으로 업로드부터 제출까지 가는 시험이며, 모델이 바뀌어도 통과해야 한다.

티켓 22는 두 커밋이다. 앞 커밋(444e9ec)은 코드 없이 티켓 파일에 임베딩 모델 선택 기록만 더했고, 뒤 커밋(bbe3c6b)이 Docker 구성과 코드를 넣었다.

핵심 개념

파이프라인이 아는 것은 llm·vlm·embedding 세 이름과 단계별 입출력 형식뿐이다. 모델 전환과 예비 순서는 docker/litellm/config.yaml만 고쳐 바꾼다.

핵심 아이디어

모델 이름은 세 가지다. llm은 글 모델, vlm은 그림을 읽는 모델, embedding은 임베딩 모델이다. llm은 Cerebras이고 llm-groq·llm-local이 그 예비 이름이며, vlm도 같은 규칙이다. 호출 한 번이 외부 모델에서 로컬 모델까지 어떻게 떨어지는지를 따라가 보자. 모든 시간은 설정 값이다.

외부 API 둘이 모두 120초씩 답하지 않으면 240초가 지나고, 로컬 모델이 최대 900초 일해도 합쳐서 1,140초(19분)다. 파이프라인의 기본 제한 20분(1,200초)은 그보다 길게 잡았다(docs/docker.md와 코드 주석이 같은 취지로 적는다). 변경 전에는 Node fetch의 기본 제한(헤더 300초)에 걸려, 외부 둘(240초) 뒤 로컬 모델이 답하는 중에 파이프라인이 끊길 수 있었다(티켓의 "리뷰 뒤 반영과 남긴 것" 항목).

임베딩이 늘 로컬인 이유는 Cerebras·Groq에 임베딩 API가 없기 때문이다. 앞 커밋의 선택 기록에 따르면 모델은 로컬 Ollama의 embeddinggemma(308M, 768차원)다. 서랍장 사례 4개를 "3단 원목 서랍장 / 폭과 높이만 조절, 칸 수 고정"으로 검색해 보니 같은 3단 원목 사례가 0.900, 5단 칸 수 선택이 0.770, 철제 서류 서랍장이 0.715, 1단 협탁형이 0.665로 순위가 상식에 맞았다. 다른 후보로 bge-m3(568M, 1024차원)가 있고, 티켓 기록에 따르면 모델을 바꾸면 사례 저장소(비슷한 과거 사례를 찾는 저장소, 티켓 21)가 벡터 길이 변화를 보고 색인을 다시 만든다.

모델이 바뀌면 같은 단계에 다른 모양의 답이 온다. 이 변경이 실제로 본 세 모양과 빈 답 하나를 시험으로 고정한다. 추론 모델은 답 전에 생각을 쓰는 모델이고, 제공자마다 그 생각을 담는 곳이 다르다. 파이프라인이 벗겨 내는 일은 4절의 readJson이 한다.

실제 키로 Cerebras와 Groq 순서가 도는지, Cerebras의 VLM 이름 qwen3.8-27b가 실제 모델 이름인지는 확인하지 못했다. 티켓 26(Fusion 실물 확인)으로 옮겼다. 로컬 gpt-oss:20b·qwen3-vl:8b는 내려받지 않아(약 13GB, 6GB) 로컬 채팅 예비는 qwen2.5:3b로만 확인했다. 수동 확인 기록은 티켓 파일에 있다(.scratch/configurator-pipeline/issues/22-docker-and-fallback.md:32-37).

1. Docker 구성: 서비스 넷

docker-compose.yml 하나에 server(업로드 서버, 8000), litellm(모델 중계, 4000), ollama(로컬 모델, 포트를 열지 않음), pipeline(실행 도구)이 있다. pipeline은 tools 프로필이라 늘 떠 있지 않고 docker compose run --rm pipeline …으로만 돈다. 이미지 안 배치는 저장소와 같게 /app 아래에 두어 schema/·data/를 같은 상대 경로로 찾게 했다. data/와 fixtures/(server는 fixtures/private만)는 컨테이너 밖 폴더를 연결한다(실제 상품 데이터는 이미지에 넣지 않는다). 운영 안내는 docs/docker.md다.

LAN에 열리는 프록시가 키 없이 뜨지 않도록, LITELLM_MASTER_KEY가 비어 있으면 compose가 시작하지 않는다(${VAR:?메시지} 형식). 외부 API 키는 비어도 뜬다. .env.example은 그러면 그 API가 실패하고 다음 예비로 넘어간다고 적는다.

2. 비밀값은 저장소 밖 환경 파일로

.env.example이 필요한 변수를 보인다: LITELLM_MASTER_KEY, CEREBRAS_API_KEY, GROQ_API_KEY, 로컬 모델 주소 LOCAL_MODEL_URL, 임베딩 주소 EMBEDDING_MODEL_URL. 실제 .env는 .gitignore 대상이다. 프록시 키는 예시 파일에서 비워 두었다. 예시 값을 그대로 쓰면 알려진 키로 LAN에 열리기 때문이다.

3. 모델 설정: 이름은 고정, 모델만 갈아 끼운다

4. 파이프라인의 호출 제한과 답 읽기

liteLlmAi는 이제 한 번 묻고 기다리는 시간을 timeoutMs(기본 20분)로 정한다. Node의 HTTP 클라이언트 undici가 두는 기본 제한(헤더·본문 300초)을 Agent 설정으로 끄고 AbortSignal.timeout으로만 기다린다. 넘기면 "LiteLLM이 N초 안에 답하지 않았습니다(모델)"로 실패한다.

configurator/pipeline/litellm-ai.ts:162-191

export function liteLlmAi({ baseUrl, apiKey, models, timeoutMs = DEFAULT_TIMEOUT_MS }: LiteLlmOptions): AiPort {
  const chat = apiUrl(baseUrl, "v1/chat/completions");
  // 기다리는 시간은 signal 하나로 정하고, undici 자체 제한(헤더·본문 300초)은 끈다
  const dispatcher = new Agent({ headersTimeout: 0, bodyTimeout: 0 });
    const timedOut = (error: unknown): never => {
      throw (error as Error).name === "TimeoutError" ? new Error(`LiteLLM이 ${timeoutMs / 1000}초 안에 답하지 않았습니다(${models[stage]})`) : error;
    };
    const response = await fetch(chat, {
      method: "POST",
      dispatcher,
      signal: AbortSignal.timeout(timeoutMs),
      headers: { "content-type": "application/json", ...authorization(apiKey) },
      body: JSON.stringify({
        model: models[stage],
        messages: [
          { role: "system", content: instructions },
          { role: "user", content },
        ],
      }),
    }).catch(timedOut);
    if (!response.ok) throw new Error(`LiteLLM 호출 실패(${models[stage]}): ${response.status} ${await response.text()}`);
    const body = (await response.json().catch(timedOut)) as { choices: { message: { content: string | null } }[] };
    return readJson(body.choices[0].message.content);

위 발췌에서 ask 함수의 선언과 요청 내용(content)을 만드는 줄(166~172행)은 이 변경과 관계없어 뺐다. 답을 읽는 쪽은 로컬 추론 모델이 content 앞에 붙이는 <think> 블록을 벗기고, 추론만 하다 끝나 content가 null인 답은 빈 문장으로 읽는다. 빈 문장은 JSON이 아니므로 실행기(파이프라인을 진행하는 코드)의 형식 검사가 같은 단계를 다시 묻는다. 변경 전에는 <think>가 붙으면 형식 오류를 되풀이했다.

configurator/pipeline/litellm-ai.ts:125-140

/** 로컬 추론 모델(Ollama 등)이 답 앞에 붙이는 추론 블록. Cerebras·Groq은 추론을 content 밖의 필드에 싣는다. */
const THINK_BLOCK = /^\s*<think>[\s\S]*?<\/think>/;

/**
 * 모델이 낸 문장을 JSON으로 읽는다. 지시해도 코드 블록으로 감싸는 모델이 있어 감싼 것은 벗긴다.
 * 읽을 수 없으면 문장 그대로 돌려줘, 실행기의 형식 검사에 걸려 다시 묻게 한다.
 * 추론만 하다 끝난 답은 content가 null이라 빈 문장으로 본다.
 */
function readJson(raw: string | null): unknown {
  const content = (raw ?? "").replace(THINK_BLOCK, "");
  try {
    return JSON.parse(content.match(CODE_BLOCK)?.[1] ?? content);
  } catch {
    return content;
  }
}

퀴즈

외부 API 둘이 120초씩 답하지 않을 때 로컬 모델까지 가는 데 걸리는 최대 시간과, 파이프라인의 기본 대기 시간(20분)의 관계는?

120 + 120 + 900 = 1,140초(19분)다. 기본 20분(1,200초)이 그보다 길어야 예비 모델이 답하는 중에 파이프라인이 끊기지 않는다. 1,200초는 기본값이고, 2,040초는 로컬 제한을 두 번 센 값이다.

num_retries를 0으로 둔 까닭에 가장 알맞은 것은?

같은 모델에 다시 묻는 동안 응답하지 않는 외부 API를 제한 시간(120초)만큼 한 번 더 기다리게 된다. 바로 예비로 넘어가는 편이 낫다. 다른 두 선택지는 사실이 아니다.

사례 저장소의 임베딩에 예비 모델을 두지 않은 이유는?

Cerebras와 Groq에는 임베딩 API가 없어서 임베딩은 늘 로컬에서 돈다. 작은 모델이라 CPU로 충분하다.

gpt-oss의 reasoning 필드와 로컬 모델의 <think> 블록은 파이프라인에서 각각 어떻게 다뤄지는가?

포트는 응답의 content만 읽으므로 별도 필드는 처음부터 보지 않는다. content 앞에 붙은 <think> 블록은 readJson이 벗긴다. 그래서 모양이 다른 세 답이 같은 JSON으로 읽혀 제출까지 간다.

운영 중 llm이 가리키는 Cerebras 모델을 같은 계열의 다른 모델로 바꾸려 한다. 무엇을 고치는가?

파이프라인은 model_name(llm)만 부르고 실제 모델은 LiteLLM 설정이 정한다. 설정의 model 값을 바꾸고 docker compose restart litellm으로 반영하면 된다(docs/docker.md). 파이프라인 코드와 compose는 그대로다. 같은 계열이어야 하는 까닭은 단계별 입출력 형식이 유지되어야 해서다.

티켓 19: AI 판정

수치 검증과 축 반응, 교차 검증을 모두 통과한 명세만, 슬라이더 끝값과 쌍별 모서리 조합을 그려 VLM(그림을 읽는 AI 모델)이 뚫림·겹침·비례 깨짐을 보게 한다. 실패는 검증 피드백이 되어 명세 작성으로 돌아가고, 판정만 3번 실패하면 이유를 붙여 최종 승인으로 넘어간다.

배경

이 영역이 처음이면 펼쳐서 읽는 기본 배경

이 프로젝트는 Fusion CAD 모델을 쇼핑몰용 three.js 구성기로 바꾼다. 구성기의 형상은 업로드 때 뽑아 둔 스윕(파라미터를 바꿔 가며 얻은 형상 묶음)에서 변형 엔진이 섞어 만든다. 어떤 파라미터 값에서 형상이 어떻게 보일지는 AI가 쓴 명세(JSON)가 정하고, 명세가 맞는지는 검증이 확인한다.

VLM은 그림을 읽을 수 있는 AI 모델이다. 이 프로젝트는 부품 탐색에서 이미 VLM을 써서 기본 형상을 여섯 방향에서 그린 그림을 보게 한다. 같은 포트(AI 모델 포트)와 같은 모델 설정을 이번에도 쓴다.

파이프라인의 검증은 여러 층이다. 두께 고정 실측은 판재 두께가 고정인지, 수치 검증은 치수가 규칙 안에 드는지, 축 반응은 슬라이더를 움직일 때 맞는 축이 반응하는지, 교차 검증은 슬라이더 두 개를 동시에 움직였을 때 이동량 덧셈이 맞는지를 본다. 모두 수치 검사다. 판재 사이가 벌어져 뚫려 보이는 것, 부품이 파고드는 것, 상품 종류로 보아 모양이 이상한 것은 숫자만으로 잡기 어렵다. 이 변경은 그 틈을 VLM이 그림으로 보게 한다.

검증에서 실패하면 검증 피드백(Feedback)이 만들어지고, 같은 후보로 명세를 다시 쓴다. 피드백에는 어디를 고칠지 가리키는 path, 종류 kind(이번에 더해진 값이 ai_judgment), 잰 값 measured, 기대 expected, 힌트 hint 같은 필드가 있다. 같은 후보로 피드백을 받아 명세를 다시 쓰는 횟수는 3번까지이고, 넘으면 후보 제시로 돌아간다(SPEC_RETRIES).

핵심 개념

판정은 비싼 VLM 호출이므로 수치로 잡을 수 있는 실패를 먼저 모두 통과한 명세에만 부른다. 그리고 판정만 반복해서 실패하면 VLM의 오판일 수 있으므로, 사람이 보게 한다.

핵심 아이디어

슬라이더가 둘(body_w, body_h)인 명세를 예로 든다(이름은 티켓 기록의 그림 이름 예에 맞춘 설명용 값이다). 판정이 보는 그림은 아래와 같다.

그림 이름움직인 슬라이더나머지
body_w=400body_w 최솟값기본값
body_w=800body_w 최댓값기본값
body_h=(최솟값), body_h=(최댓값)body_h 끝값 2장기본값
body_w=400·body_h=1000 등두 슬라이더의 모서리 4조합기본값

슬라이더가 n개이면 그림은 2n + 4·C(n,2)장이다. n이 2이면 8장, 4이면 32장이다. 티켓 기록은 32장이 VLM의 그림 수 제한에 걸릴 수 있다고 적고, 실제 모델로 돌려 보는 최종 확인(티켓 23)에서 걸리면 나눠 묻기로 미뤘다.

그림은 모두 같은 축척으로, 정면에서 오른쪽 위로 비켜 본 직교 투영으로 그린다. 후보 카드 미리보기와 같은 시점이다. 부품마다 색이 달라, VLM은 어느 부품이 어디로 갔는지 색으로 짚을 수 있다.

수치 검증 → 축 반응 → 교차 검증 통과
sweeps.json + 명세
엔진이 그림을 그림 (2n + 4·C(n,2)장)
renders[], colors[]
VLM이 문제 있는 그림을 짚음
{ problems: [{ image, reason }] }
ai_judgment 피드백 + 그림 저장
피드백으로 명세 다시 쓰기
3번 쌓이면 최종 승인으로

실패가 3번 쌓이면 후보 제시로 돌아가는 대신, 마지막 명세와 결과물에 판정 이유를 붙여 사람에게 넘긴다. 사람(운영자)이 최종 승인 화면에서 이유와 그림을 보고 결정한다.

연속이 아니라 누적

판정 실패는 연속으로 세지 않고, 같은 후보의 최대 4시도 안에서 쌓인 횟수로 센다. 판정 실패, 수치 실패, 수치 실패, 판정 실패 순이면 판정 실패는 2번이라 후보 제시로 돌아간다. 사이에 수치 검증 실패가 끼어도 판정 실패 3번이 쌓였다는 사실은 그대로이기 때문이다. 티켓 기록은 이것이 VLM의 오판으로 막히지 않게 하려는 뜻에 맞다고 적는다. 그 결과 최종 승인 화면에는 마지막 판정 이유만 보인다. 앞선 두 판정은 다른 명세에 대한 것이고 처리 기록의 검증 항목에 남는다.

코드 따라가기

흐름: 검증 통과(configurator/pipeline/runner.ts:486-487) → 그림 만들기(configurator/pipeline/verify-judgment.ts:41-59) → VLM 판정(configurator/pipeline/runner.ts:409-425, configurator/pipeline/litellm-ai.ts:163-170) → 판정 응답 검사(configurator/pipeline/schemas.ts:170-192) → 피드백 만들기(configurator/pipeline/verify-judgment.ts:65-76) → 3번 쌓이면 최종 승인(configurator/pipeline/runner.ts:490, configurator/pipeline/operator-screens.ts:139-165).

1. 판정을 부를 자리

writeVerifiedSpec의 시도 루프(처음 시도와 다시 쓰기 3번을 합쳐 최대 4시도) 끝에서, 앞선 검증(두께 고정 실측·수치 검증·축 반응·교차 검증과 격자 보강)에서 피드백이 하나도 없을 때만 실행기 안의 함수 judge(아래 4절, AI 모델 포트의 ai.judge를 부른다)를 부른다(487행). judged는 이번 시도가 판정까지 갔다는 표시이고, 판정에서 피드백이 나왔을 때만 judgmentFailures를 올린다. 그 수가 JUDGMENT_FAILURES(3)에 닿으면 이 명세를 실패로 돌리지 않고 judgment 목록에 피드백을 담아 돌려준다(490행). 통과하면 judgment는 빈 목록이다(489행).

2. 그림 만들기

judgmentShots는 슬라이더마다 최솟값·최댓값, 그다음 슬라이더 쌍마다 두 슬라이더의 끝값 4조합을 목록으로 만든다(43~49행). 나머지 슬라이더는 기본값이다. 그림은 결과물에 담긴 스윕 데이터로 변형 엔진을 만들어 그리므로, 고객이 구성기에서 보게 될 형상과 같다. 시점은 후보 카드와 같은 obliqueView(configurator/pipeline/candidate-cards.ts:19-24)이고, 위쪽은 명세의 H(높이)에 대응하는 Fusion 축 axes.H에서 얻는다.

configurator/pipeline/verify-judgment.ts:41-59

export function judgmentShots(spec: Spec, sweeps: SweepData): { shots: JudgmentShot[]; colors: PartColor[] } {
  const defaults = Object.fromEntries(spec.sliders.map((s) => [s.id, s.default]));
  const places: { slider: string; place: Record<string, number> }[] = [];
  for (const s of spec.sliders) for (const v of [s.min, s.max]) places.push({ slider: s.id, place: { [s.id]: v } });
  spec.sliders.forEach((a, i) => {
    for (const b of spec.sliders.slice(i + 1)) {
      for (const va of [a.min, a.max]) for (const vb of [b.min, b.max]) places.push({ slider: a.id, place: { [a.id]: va, [b.id]: vb } });
    }
  });

  const morph = createMorph(spec, sweeps);
  // 명세의 front와 axes는 명세 검사를 통과한 값이다
  const view = obliqueView(spec.front as Front, `+${spec.axes.H}` as Front);
  const colorOf = partPalette(sweeps.parts.map((p) => p.name));
  const values = places.map(({ place }) => ({ ...defaults, ...place }));
  const images = renderPngs(values.map((v) => morph.shape(v)), view, RENDER_SIZE, colorOf);
  const shots = places.map(({ slider, place }, k) => ({ slider, render: { name: placeOf(place), values: values[k], image: images[k].toString("base64") } }));
  return { shots, colors: partColorsOf(morph.faces.map((f) => f.part), colorOf) };
}

이 목록의 앞 슬라이더가 바깥 고리다. 피드백이 가리킬 슬라이더(slider)는 슬라이더 끝값이면 그 슬라이더, 모서리 조합이면 앞 슬라이더다. 리뷰 뒤에 이 대응을 객체 키 순서에 기대지 않고 필드로 두었다.

응답은 { "problems": [{ "image", "reason" }] } 형식이다. 스키마는 image가 보낸 그림 이름 중 하나여야 하고(열거), reason이 한 줄(줄바꿈 없음)이어야 한다고 본다. 보내지 않은 이름이나 두 줄짜리 이유는 형식 오류이므로 같은 방식으로 다시 묻는다.

configurator/pipeline/schemas.ts:170-192

/** AI 판정 응답. 문제는 보낸 렌더링 이름(images)을 가리키고 이유는 한 줄이다. 문제가 없으면 통과다. */
export function judgmentSchema(images: string[]) {
  return {
    type: "object",
    required: ["problems"],
    additionalProperties: false,
    properties: {
      problems: {
        type: "array",
        items: {
          type: "object",
          required: ["image", "reason"],
          additionalProperties: false,
          properties: { image: { enum: images }, reason: { type: "string", pattern: "^[^\\n]+$" } },
        },
      },
    },
  };
}

export function judgmentChecker(images: string[]): Check {
  return checker(judgmentSchema(images));
}

4. 판정에서 피드백으로

judge는 같은 그림을 여러 번 짚은 이유를 ; 로 이어 붙여 그림 하나에 피드백 하나로 만든다. 문제가 있는 그림은 저장소 포트의 saveRender로 저장해 경로를 얻는다(없던 포트 메서드이고, 피드백이 이미지 경로를 담으려면 그림을 둘 곳이 필요했다). 그 경로가 measured.image가 된다.

configurator/pipeline/runner.ts:409-425

  async function judge(spec: Spec, files: ProductFiles): Promise<Feedback[]> {
    const { shots, colors } = judgmentShots(spec, JSON.parse(files["sweeps.json"]));
    const renders = shots.map((s) => s.render);
    const { problems } = await askUntilValid<{ problems: JudgmentProblem[] }>("verification", judgmentChecker(renders.map((r) => r.name)), (schemaErrors, rejected) =>
      ai.judge({ intake, spec: structuredClone(spec), renders: structuredClone(renders), colors, rejected, schemaErrors }),
    );
    // 같은 렌더링을 여러 번 짚으면 이유를 이어 붙여 그림 하나에 피드백 하나로 둔다
    const reasons = new Map<string, string[]>();
    for (const { image, reason } of problems) reasons.set(image, [...(reasons.get(image) ?? []), reason]);
    const feedback: Feedback[] = [];
    for (const [image, said] of reasons) {
      const shot = shots.find((s) => s.render.name === image)!;
      const path = await store.saveRender(intake.name, `${image}.png`, Buffer.from(shot.render.image, "base64"));
      feedback.push(judgmentFeedback(spec, shot, said.join("; "), path));
    }
    return feedback;
  }

피드백의 kind는 ai_judgment이고, 부품은 판정이 짚지 않으므로 part는 빈 문자열이다. 힌트는 "그 끝값을 범위에서 빼거나 affects의 형태 변경·위치 이동 부품 확인"이라고 명세 작성에게 길을 일러 준다.

configurator/pipeline/verify-judgment.ts:65-76

export function judgmentFeedback(spec: Spec, { slider, render }: JudgmentShot, reason: string, image: string): Feedback {
  const measured: JudgmentMeasured = { image, values: render.values, reason };
  return {
    path: `sliders[${spec.sliders.findIndex((s) => s.id === slider)}]`,
    slider,
    part: "",
    kind: "ai_judgment",
    measured,
    expected: "뚫림·겹침·비례 깨짐 없음",
    hint: `${render.name}에서 렌더링 판정 실패: 그 끝값을 범위에서 빼거나 affects의 형태 변경·위치 이동 부품 확인`,
  };
}

5. 최종 승인 화면

3번 쌓여 넘어오면 finalApprovalHtml이 마지막 판정의 이유와 그림을 보인다. 이 화면은 이유를 보이기 위한 최소한이고, 이름 고치기·범위 좁히기·반려는 다음 티켓(20)에서 붙인다.

configurator/pipeline/operator-screens.ts:139-165

export function finalApprovalHtml({ spec, judgment }: { spec: Spec; judgment: Feedback[] }): string {
  const sliders = spec.sliders.map((s) => `<li>${escape(s.name)} ${s.min}~${s.max} ${escape(s.unit)} (기본 ${s.default})</li>`).join("\n");
  const reasons = judgment.map((f) => {
    const { image, values, reason } = f.measured as JudgmentMeasured;
    const place = escape(placeOf(values));
    return `<figure><img src="${escape(image)}" alt="${place}"><figcaption>${place}: ${escape(reason)}</figcaption></figure>`;
  });
  const judged =
    reasons.length === 0
      ? ""
      : `<section class="judgment">
<h2>AI 판정을 ${JUDGMENT_FAILURES}번 통과하지 못해 넘어왔습니다</h2>
<p>수치 검증과 축 반응은 통과했습니다. 아래 렌더링을 눈여겨보고 결정하세요.</p>
${reasons.join("\n")}
</section>
`;
  return page(
    `${spec.product} 최종 승인`,
    `<h1>${escape(spec.product)} 최종 승인</h1>
${judged}<ul>
${sliders}
</ul>
<form method="post">
<p><button type="submit" name="decision" value="approve">승인</button></p>
</form>`,
  );
}

사람 결정 포트의 finalApproval은 이제 judgment를 입력으로 받는다(configurator/pipeline/runner.ts:224). 실행기는 명세 작성 결과의 judgment를 그대로 넘긴다(configurator/pipeline/runner.ts:568-570).

퀴즈

AI 판정을 수치 검증·축 반응·교차 검증 뒤에만 부르는 가장 알맞은 이유는?

VLM 호출은 비싸고, 앞선 검증이 잡을 실패는 숫자로도 잡힌다. 그림은 결과물의 스윕 데이터로 언제든 그릴 수 있어 순서의 이유가 아니고, 어느 쪽이 더 정확한지도 이 순서의 이유가 아니다.

슬라이더 3개인 명세에서 판정에 보내는 그림은 몇 장인가?

끝값 2n = 6장, 슬라이더 쌍 C(3,2) = 3쌍에 쌍마다 모서리 4조합이라 12장, 합해 18장이다. 12장은 모서리 조합만 센 것이고, 24장은 쌍마다 8조합으로 센 것이다.

같은 후보로 시도가 이렇게 흘렀다: 판정 실패, 판정 실패, 수치 검증 실패, 판정 실패. 어떻게 되는가?

판정 실패는 연속이 아니라 누적으로 센다. 판정까지 간 시도에서만 올리고 수치 실패는 영향을 주지 않으며, 3에 닿으면 마지막 명세와 판정 이유를 사람에게 넘긴다. 이 설계는 VLM의 오판 하나로 상품 생성이 막히지 않게 하려는 것이다.

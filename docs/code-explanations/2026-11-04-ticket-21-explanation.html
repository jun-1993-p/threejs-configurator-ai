티켓 21: 사례 저장소

최종 승인된 상품의 결정 기록을 사례로 쌓고, 다음 상품의 후보 제시·명세 작성·AI 판정에 같은 상품 종류에서 임베딩 유사도가 높은 사례 3개를 예시로 넣는다. 학습은 하지 않는다.

jun-1993-p/threejs-configurator-ai 티켓 21, 최신 커밋 159d87a, 포함한 커밋: 159d87a (티켓 21: 사례 저장소), explained 2026-11-04. References link to this commit.

배경

이 영역이 처음이면 펼쳐서 읽는 기본 배경

임베딩은 문장을 숫자 벡터로 바꾸는 것이다. 뜻이 비슷한 문장은 벡터가 가깝고, 가까운 정도를 코사인 유사도로 잰다. 임베딩 모델 호출도 LiteLLM 프록시가 중개하며, 임베딩은 작아서 계속 로컬에서 돈다(ADR-0015). 색인은 LanceDB에 저장한 사례의 벡터 표를 뜻한다. LanceDB는 벡터를 파일로 저장하고 가까운 벡터를 찾아 주는 로컬 데이터베이스다. JSONL은 한 줄에 JSON 하나를 적는 텍스트 형식이라 편집기로 줄을 직접 지울 수 있다.

AI에게 사례를 예시로 주는 방식은 모델을 다시 훈련하지 않는다. 입력에 예시를 붙여 주면 모델이 그 방식을 따라 답한다. 사례를 빼는 일은 입력에서 예시가 사라지는 것이므로 바로 되돌릴 수 있다.

티켓 20까지의 실행기는 승인된 상품마다 store.recordCase로 사례를 한 번 남겼지만, 그 기록은 메모리 저장소의 배열에 쌓일 뿐이었다. 고른 후보도 id(chosen: string)만 남았고, AI는 기록을 읽지 못했다. 이 티켓이 그 기록을 실제 저장소로 만들고, AI 입력으로 되돌려 보낸다.

이 문서의 용어는 다음과 같다. 사례 기록(CaseRecord)은 최종 승인된 상품의 결정 한 묶음이다. 사례 저장소(CaseStore)는 사례 기록을 모아 두고 비슷한 사례를 꺼내는 곳이다. 예시(examples)는 AI 입력에 붙는 사례 3개다. 상품 종류(kind)는 서랍장·책장 같은 정해진 목록의 분류다.

핵심 개념

ADR-0011은 사례를 학습이 아니라 예시로만 쓰기로 정했다. 사례가 수십 개 수준이면 학습 비용에 견줄 효과가 없고, 예시 방식은 잘못된 사례를 빼기만 하면 되돌릴 수 있기 때문이다. 사례에는 최종 명세와 함께 선택되거나 버려진 후보, 사람이 고친 내용, 거절 이유가 남는다. ADR은 사람이 고친 내용이 다음 명세를 개선하는 가장 큰 신호라고 적는다.

핵심 아이디어

파이프라인은 정보 입력(상품 종류·상품명·메모), 후보 제시, 후보 선택, 스타일 선택, 명세 작성, 검증(AI 판정 포함), 최종 승인, 제출 순으로 진행한다. 이 변경의 흐름은 쓰기와 읽기 두 방향이다.

설계의 핵심은 원본과 색인의 분리다. 원본은 JSONL 한 파일이라 사람이 줄을 지우면 사례가 빠진다. LanceDB 색인은 그 파일에서 만드는 파생물이고, 검색할 때마다 기록에 맞춘다. 그래서 줄을 지우든 임베딩 모델을 바꾸든 색인만 다시 맞추면 된다.

유사도를 재는 문장은 정보 입력의 상품 종류·상품명·메모를 줄바꿈으로 이은 것이다(caseQuery). 사례도 지금 상품도 같은 문장으로 임베딩해야 유사도가 뜻을 가진다. 예를 들어 "서랍장 / 1단 서랍장 / 폭은 600~900"과 "서랍장 / 2단 서랍장 / 폭 700 안쪽"은 "책장 / 5단 책장 / 폭 1200"보다 서로 가까울 것이다(설명을 위한 가상의 문장이고 실제 값으로 확인한 것이 아니다).

사례를 빼려면 node scripts/cases.ts remove <id>를 쓰거나 cases.jsonl에서 줄을 직접 지운다. 예시는 상품마다 처리 시작 때 한 번 꺼내므로, 사례를 빼면 다음 상품부터 예시에서 사라진다.

사례 기록이 담는 것

상품 종류, 정보 입력, 후보 제시 회차마다의 후보 전부(candidates: Candidate[][]), 고른 후보, 고친 내용을 넣은 최종 명세, 고친 내용(edits), 거절 이유(rejections), 거절 이유 없이 "다른 후보"로 반려한 후보(backToChoice). 사례 기록 파일은 기본 폴더 data/cases/에 있고, .gitignore의 data/라 공개 저장소에 올라가지 않는다(시험이 git check-ignore로 확인한다).

남긴 한계

유사도가 같을 때 순서는 메모리 구현에서만 먼저 기록된 사례가 앞서고, LanceDB는 보장하지 않는다. 티켓은 같은 점수가 정보 입력 문장이 같다는 뜻이라 어느 쪽이 먼저 와도 예시의 쓸모는 같다고 적었다(이 문서가 보증하는 판단은 아니다). 또한 예시가 AI 입력을 키운다. 사례마다 명세와 모든 회차의 후보가 들어가며, 지금은 줄이지 않고 최종 확인(티켓 23)에서 토큰 한도에 걸리면 단계별로 필요한 필드만 남기기로 미뤘다.

1. 사례 기록의 모양

변경 전 CaseRecord는 상품 종류를 문자열로, 후보 목록을 한 회차 분량으로, 고른 후보를 id 문자열 하나로 남겼다. 이제 회차마다 후보를 2차원 배열로, 고른 후보는 축 대응과 부모가 붙은 ChosenCandidate로 남긴다. 거절 기록(Rejection)의 후보 타입도 실제로 넣던 ChosenCandidate로 바로잡았다(티켓 기록).

3. 저장소 포트

CaseStore는 기록(record), 같은 상품 종류에서 유사도 상위를 꺼내기(similar), 목록(list), 빼기(remove) 네 가지다. 임베딩은 Embed 함수 하나로 주입받는다. 운영은 LiteLLM 임베딩, 시험은 외부 모델 없이 글자 두 개 묶음의 해시를 쓴다(ngramEmbedding, configurator/pipeline/case-store.ts:166-180).

configurator/pipeline/case-store.ts:15-32

/** 문장마다 임베딩 벡터 하나. 운영에서는 LiteLLM 임베딩 모델(liteLlmEmbed)이다. */
export type Embed = (texts: string[]) => Promise<number[][]>;

export interface CaseStore {
  /** 사례를 기록하고 그 id를 돌려준다 */
  record(record: CaseRecord): Promise<string>;
  /** 그 상품 종류의 사례 중 query와 임베딩 유사도가 높은 순서로 limit개 */
  similar(kind: ProductKind, query: string, limit: number): Promise<CaseRecord[]>;
  /** 기록된 순서대로 모든 사례 */
  list(): Promise<StoredCase[]>;
  /** 뺀 사례는 다음 similar부터 나오지 않는다 */
  remove(id: string): Promise<void>;
}

/** 임베딩할 정보 입력의 문장. 사례도 지금 상품도 이 문장으로 임베딩해야 유사도가 뜻을 가진다. */
export function caseQuery(intake: Intake): string {
  return [intake.kind, intake.name, intake.memo].join("\n");
}

4. JSONL이 원본, LanceDB 색인은 검색 때마다 맞춘다

lanceCaseStore는 cases.jsonl에 줄을 덧붙여 기록한다(record). 검색(similar)은 JSONL을 읽고 질의 문장을 임베딩한 뒤, 그 벡터의 길이를 받아 synced로 색인을 기록에 맞춘다. 순서는 다음과 같다.

  1. 색인 표의 벡터 길이가 지금 임베딩 모델의 길이와 다르면 표를 지우고 새로 만든다(임베딩 모델을 바꾼 경우). 121~124행.
  2. 기록에서 빠졌거나 정보 입력 문장이 달라진 색인 줄을 지운다(remove나 손으로 지운 줄, 손으로 고친 정보 입력). 125~128행.
  3. 색인에 없는 사례만 임베딩해 넣는다. 129~137행.

configurator/pipeline/case-store.ts:117-138

  /** 색인을 사례 기록과 지금 임베딩 모델의 벡터 길이(length)에 맞춘 표. 사례가 하나도 없으면 null이다. */
  async function synced(cases: StoredCase[], length: number): Promise<lancedb.Table | null> {
    const db = await lancedb.connect(join(dir, "cases.lance"));
    let table = (await db.tableNames()).includes("cases") ? await db.openTable("cases") : null;
    if (table && (await vectorLength(table)) !== length) {
      await db.dropTable("cases");
      table = null;
    }
    const texts = new Map(cases.map((c) => [c.id, caseQuery(c.intake)]));
    const rows = table ? await table.query().select(["id", "text"]).toArray() : [];
    const stale = rows.filter((row) => texts.get(row.id) !== row.text).map((row) => row.id as string);
    if (table && stale.length > 0) await table.delete(`id IN (${stale.map(quoted).join(", ")})`);
    const indexed = new Set(rows.map((row) => row.id as string).filter((id) => !stale.includes(id)));
    const missing = cases.filter((c) => !indexed.has(c.id));
    if (missing.length === 0) return table;
    const vectors = await embed(missing.map((c) => texts.get(c.id)!));
    const added: IndexRow[] = missing.map((c, i) => ({ id: c.id, kind: c.kind, text: texts.get(c.id)!, vector: vectors[i] }));
    // LanceDB 표는 첫 줄로 열 형식을 정하므로 처음 넣을 때 만든다
    if (!table) return db.createTable("cases", added as unknown as Record<string, unknown>[]);
    await table.add(added as unknown as Record<string, unknown>[]);
    return table;
  }

그 뒤 kind가 같은 줄만 코사인 거리(작을수록 유사)로 상위 limit개를 찾고, 찾은 id로 JSONL에서 읽은 기록을 돌려준다(configurator/pipeline/case-store.ts:147-157). AI 입력에는 id를 싣지 않는다(recordOf, configurator/pipeline/case-store.ts:34-37). 운영자가 파일을 직접 고칠 수 있으므로, 읽을 수 없는 줄은 줄 번호를 붙여 실패시킨다(configurator/pipeline/case-store.ts:102-115).

5. 임베딩 호출

liteLlmEmbed는 LiteLLM의 OpenAI 호환 임베딩 API(v1/embeddings)에 문장 목록을 한 번에 보내고, 응답을 index 순서로 정렬해 벡터 목록으로 돌려준다. 모델 이름은 LiteLLM 설정의 model_name이고, 수동 실행 도구는 환경 변수 LITELLM_EMBED_MODEL(기본 embedding)로 정한다. 채팅 호출에 인라인이던 주소·인증 처리를 apiUrl과 authorization으로 빼서 임베딩 호출과 같이 쓴다.

configurator/pipeline/litellm-ai.ts:133-145

export function liteLlmEmbed({ baseUrl, apiKey, model }: { baseUrl: string; apiKey?: string; model: string }): Embed {
  const url = apiUrl(baseUrl, "v1/embeddings");
  return async (texts) => {
    const response = await fetch(url, {
      method: "POST",
      headers: { "content-type": "application/json", ...authorization(apiKey) },
      body: JSON.stringify({ model, input: texts }),
    });
    if (!response.ok) throw new Error(`LiteLLM 임베딩 실패(${model}): ${response.status} ${await response.text()}`);
    const { data } = (await response.json()) as { data: { index: number; embedding: number[] }[] };
    return [...data].sort((a, b) => a.index - b.index).map((d) => d.embedding);
  };
}

6. 예시 꺼내기와 AI 입력

예시는 정보 입력이 형식 검사를 통과한 직후, 상품마다 한 번 꺼낸다. 이 값이 후보 제시·명세 작성·AI 판정 세 호출의 examples로 들어간다. 세 호출 모두 복사본(structuredClone)을 넘기고, 같은 상품 처리 중에는 값이 바뀌지 않는다.

configurator/pipeline/runner.ts:639-640

    // 형식 검사를 통과한 정보 입력의 상품 종류로 거른다
    examples = await store.cases.similar(intake.kind, caseQuery(intake), CASE_EXAMPLES);

AI 지시문은 단계마다 예시를 다르게 쓰라고 일러 준다. 후보 제시는 운영자가 고른 구성과 고친 이름을 따르고 거절 이유가 가리킨 구성은 피한다(configurator/pipeline/litellm-ai.ts:84). 명세 작성은 이름 짓는 방식과 범위·step 고르는 방식을 따르고 edits가 고친 쪽으로 처음부터 쓴다(configurator/pipeline/litellm-ai.ts:103). AI 판정은 승인된 상품의 범위 안 비례를 비교 기준으로 삼는다. 후보 제시 지시문은 파라미터 이름을, 명세 작성 지시문은 파라미터 이름과 범위의 근거를 이 상품의 업로드 묶음·치수 규칙·정보 입력에서 찾으라고 한다.

7. 사례 관리 도구

JSONL이 원본이고 색인은 검색마다 기록에 맞춘다. 기록에 없는 id의 색인 줄은 낡은 줄로 보고 지운다. 전체를 다시 임베딩하는 경우는 벡터 길이가 바뀔 때뿐이고, 새로 필요한 것만 임베딩한다.

임베딩 모델을 바꿨더니 벡터 길이가 달라졌다. 이때 색인은?

한 표에 길이가 다른 벡터가 섞이면 유사도를 재지 못한다. 그래서 길이가 다르면 표를 지우고 JSONL 전체를 새 모델로 임베딩한다. 원본이 JSONL이라 색인은 언제든 다시 만들 수 있다.

# 코드 설명 문서의 한국어 가독성 검토 보고서

- 검토 대상: `docs/code-explanations/`의 HTML 33개 (티켓 01~31, 티켓 26은 둘로 나뉨, 커밋 `f00a11d` 설명 1개)
- 검토 방법: HTML에서 코드 블록을 빼고 본문 약 20만 자(문장 4,444개)를 뽑아, 수치로 먼저 재고 표본을 직접 읽었다. 코드 블록 안은 보지 않았다.
- 한 줄 결론: **"영어식 문장"이라는 의심은 절반만 맞다.** 문법 수준의 번역투는 적다(문장 구조는 대체로 자연스러운 한국어다). 읽기를 어렵게 하는 것은 **문장의 틀이 아니라 용어와 정보 밀도, 그리고 문서마다 다른 말투**다.

## 1. 수치로 본 문장 상태

| 항목 | 결과 | 판단 |
|---|---|---|
| 문장 길이 | 평균 45자, 중앙값 37자, 상위 10%가 85자 이상 | 평균은 읽기 좋은 범위. 단, 80자 넘는 문장이 12%, 120자 넘는 문장이 2.5% |
| "~를 통해", "~에 의해/의한" | 거의 0회 | 영어 번역투의 대표 표지인데 쓰지 않았다. **좋은 점** |
| 피동("~된다/되어") | 천 자당 0.8회 | 낮다. 영어식 수동태 남발은 없다 |
| "~에 대해/대한", "~를 위해" | 천 자당 0.1회 안팎 | 낮다 |
| 분열문("~하는 것은 ~이다") | 천 자당 0.3회 | 낮다 |

즉 "The X is computed by Y" 같은 영어 문장을 그대로 옮긴 흔적은 드물다. 이 부분은 걱정하지 않아도 된다.

## 2. 실제로 읽기를 어렵게 하는 것들 (중요도 순)

### 2.1 한 낱말이 너무 많은 뜻을 진다 — 가장 큰 문제

"**묶음**"이 서로 다른 개념 여섯 개 이상에 쓰인다.

| 표현 | 횟수 | 뜻 |
|---|---|---|
| 업로드 묶음 | 59 | 애드인이 서버로 보내는 JSON 전체 |
| 위상 묶음 | 58 | 면 구성이 같은 샘플의 모임 |
| 값 묶음 | 28 | 파라미터 이름-값 짝의 목록 |
| 기본 묶음 | 18 | 위상 묶음 중 기본 형상이 속한 것 |
| 칸 묶음 ("2칸 묶음", "4칸 묶음") | 13 | 칸막이 수로 나눈 위상 묶음 |
| 묶인 파라미터 | 다수 | 한 두께 선택에 함께 묶은 파라미터 |

영어 원문이라면 bundle / group / tuple / set으로 갈렸을 것을 한국어 한 낱말로 뭉갠 것이다. 한국인 독자는 "이 묶음"이라는 말을 만날 때마다 "어느 묶음?"을 되짚어야 한다. 예(티켓 12):

> 그래서 두께 후보 형상도 묶음마다 필요하다.

앞 문장이 "위상 묶음"이었다는 기억에 기댄 문장이다. 한 번 읽어서는 무엇의 묶음인지 알 수 없다.

같은 부류의 불일치:

- **샘플 352회 / 표본 12회**: 같은 뜻인데 섞여 쓰인다. 배경 설명에서는 "형상 표본"(티켓 01)이라고 하고 본문에서는 "샘플"이라고 해서, 같은 것인지 따로 확인해야 한다.
- **기본 형상 101회 / 기준 형상 24회**: 티켓 12 이후에는 "기준 형상"이 "위상 묶음마다의 기본 형상"이라는 다른 뜻으로 쓰이는데, 정의 없이 두 말이 섞여 나온다.
- "이동량", "위상", "스윕", "슬롯", "토폴로지/위상", "오커런스"처럼 CAD·그래픽스 전문용어가 처음 나올 때 풀이가 없거나, 접힌 "배경" 상자 안에만 풀이가 있다. 상자를 안 연 독자에게는 본문이 곧바로 암호가 된다.

### 2.2 한 문장에 정보를 너무 많이 눌러 담는다

평균은 짧지만 꼬리가 길다. 가장 긴 열두 문장 중 상당수가 "흐름:" 줄이거나 괄호 안에 파일 경로와 행 번호를 줄줄이 단 문장이다.

- "흐름:" 줄 최장 489자: `결정의 모양(…) → 최종 승인 화면(…) → 양식 읽기(…) → …`처럼, 화살표 사이마다 괄호로 경로가 붙어 있다. 읽는 사람은 흐름(한국어)을 읽다가 경로(코드)에 매번 막힌다.
- 의미 문장도 마찬가지다. 예(티켓 19 계열):

  > `writeVerifiedSpec`의 시도 루프(처음 시도와 다시 쓰기 3번을 합쳐 최대 4시도) 끝에서, 앞선 검증(두께 고정 실측·수치 검증·축 반응·교차 검증과 격자 보강)에서 피드백이 하나도 없을 때만 실행기 안의 함수 `judge`(아래 4절, AI 모델 포트의 `ai.judge`를 부른다)를 부른다(487행).

  "부른다"가 두 번, 괄호가 네 번, 조건이 두 겹이다. 영어라면 문장 둘로 갈랐을 내용이다.
- 후보 카드를 설명하는 문장(티켓 17): "각 부모 후보에 대해 `alsoChanges`를 계산해 붙인다(136~140행). … 읽고, … 이름을 붙여 … 이름으로 바꾼 뒤 슬라이더 자기 이름을 뺀다" — 동사 다섯 개가 연결어미로 이어진 한 문장이다.

### 2.3 영어 개념을 직역한 동사

문법 번역투는 적은데 **동사 선택**에 영어 어휘가 비친다. 한국어 본래 쓰임과 어긋나서, 개발자가 아니면 낯설다.

| 문서의 표현 | 영어 원형 | 더 자연스러운 한국어 |
|---|---|---|
| "이 티켓은 티켓 11이 만든 … **위에 선다**" | builds on top of | "티켓 11의 결과를 바탕으로 한다" |
| "함수를 **부른다**"(26회) | call | "호출한다" (개발 문서의 표준 표현. "부른다"는 사람을 부르는 느낌) |
| "시험을 **돌린다**"(167회, "돌아가다" 포함) | run | "실행한다" (맥락에 따라 "돌린다"는 구어로는 허용) |
| "범위가 **닿는** 위상 묶음" | the range reaches | "범위가 미치는 / 걸치는" |
| "AI에게 길을 **일러 준다**" | instruct | "알려 준다" |
| "이름을 **붙든다**", "어댑터를 **꽂는다**" | hold / plug in | "보관한다", "연결한다" |
| "점을 **뽑는다**"(32회) | sample/extract | "추출한다/읽어 온다" |

한 낱말씩 보면 용납되지만, 문서 하나에 여러 개가 겹치면 "한국어 같은데 뜻이 바로 안 잡히는" 인상을 준다. 의심하신 "영어식"의 정체는 대부분 이것이다.

### 2.4 "곧 / 즉 / 바깥 / 몫" 류의 풀이 접속

"곧"(14회), "~ 몫"(17회), "바깥"(34회)이 정의 문장에서 많이 쓰인다. 예: "이 문서에는 28 몫만 넣었다", "~ 곧 슬라이더를 움직이면 …". 모두 맞는 한국어지만, "몫"과 "곧"은 문어체 성향이 강해서 비전문가에게는 한 박자 걸린다. "몫만" 대신 "28번 티켓 부분만", "곧" 대신 "즉"이나 문장 분리가 더 낫다.

### 2.5 문서마다 말투가 다르다

| 문서 | 종결형 |
|---|---|
| 티켓 01~31 (32개) | 해라체: "~한다/이다" |
| 커밋 `f00a11d` 설명 (1개) | 합쇼체: "~합니다/입니다" (99회, 해라체는 0회) |

같은 폴더에서 한 문서만 공손체다. 또한 같은 사람이 보는 문서인데 앞부분 설명은 "펼치세요"(티켓 12 요약), 다른 곳은 "펼쳐서 읽는다"로 명령형과 서술형이 섞인다. 내용의 난이도와는 별개지만, 한국어 독자는 말투가 바뀔 때마다 글쓴이가 바뀐 느낌을 받아 집중이 흐트러진다.

### 2.6 영어 틀이 그대로 남은 곳

- **모든 문서(33/33) 머리말**에 영어 문장 `References link to this commit.`가 한국어 문장 바로 뒤에 붙어 있다. 스킬 템플릿 문구가 번역되지 않은 것이다.
- 티켓 26 두 문서는 제목이 `Background / Intuition / Code walkthrough / Quiz` 영어, 나머지 31개는 `배경 / 핵심 아이디어 / 코드 따라가기 / 퀴즈`로 한국어다. 같은 목차 구조인데 언어가 다르다.
- `f00a11d` 문서의 "직관"과 다른 문서의 "핵심 아이디어"는 같은 절의 서로 다른 번역이다(Intuition → 직관/핵심 아이디어).
- 티켓 01·26 두 문서와 `f00a11d` 문서의 머리말: "at f526ec2, explained 2026-11-04" 같은 영어 조각이 한국어 문장 안에 박혀 있다.
- 문서 안 영문 식별자는 반드시 필요한 것(파일명, 함수명, `affects.shape` 같은 명세 필드)이 대부분이라 그대로 두어야 한다. 다만 `affects`·`move`·`shape`를 한국어 문장 속에서 풀이 없이 쓰는 곳이 있다. 퀴즈에는 "한 부품을 affects.shape와 affects.move 양쪽에 적은 명세는…"처럼 영어 필드명이 문장의 주어 자리까지 올라온다.

### 2.7 약어와 내부 번호

AGENTS.md는 "내부 약어 코드(A1, B3 등) 대신 이름으로 쓴다"고 정했고, 이 점은 대체로 지켜졌다. 그러나 `ADR-0002`, `ADR-0016` 같은 번호 인용이 문서 하나에 여러 번 나온다(전체 102회). 번호만 보고는 내용을 알 수 없으므로, 첫 등장에서는 "ADR-0016(경계 맞춤 격자)"처럼 이름을 함께 달아야 한다. 일부 문서(티켓 01, 12)는 이미 이렇게 하고 있고 일부는 번호만 쓴다.

## 3. 좋은 점 (고치지 않아도 되는 것)

- 문장 틀이 한국어답다. 주어-목적어-서술어 순서가 자연스럽고, 영어식 관계절 중첩이나 수동태 남발이 드물다.
- "배경 → 핵심 아이디어 → 코드 → 퀴즈"의 골격과, "이 프로젝트가 처음이라면" 접힘 상자는 한국어 독자에게도 좋은 설계다.
- 숫자 예시(W=400, 600, 800…)와 장난감 예가 있어서 추상적 설명이 구체화된다. 퀴즈의 오답 해설("Fusion 제약이나 슬롯 표시는 이유가 아니다")도 학습 효과가 좋다.
- 비교적 짧은 문장이 중심이다(중앙값 37자).

## 4. 판정

> 영어식 번역투 때문에 어렵다기보다는, **용어 하나가 여러 뜻을 지는 것**, **한 문장에 경로·괄호·조건이 겹치는 것**, **개발자 속어에 가까운 동사**, **문서마다 다른 말투와 남은 영어**가 합쳐져 난이도가 오른 것이다. 한국인 개발자는 읽을 수 있지만, 이 프로젝트를 처음 보는 사람에게는 "묶음"과 "기준/기본 형상" 때문에 매 절마다 앞으로 돌아가야 하는 부담이 남는다.

## 5. 권고 (효과 큰 순)

1. **용어집 하나를 정해 문서 전체에 적용한다.** 루트 `GLOSSARY.md`에 이미 정의된 말이 있으면 그 말만 쓴다. 최소한 아래 네 쌍은 풀어 쓰는 것이 좋다.
   - 업로드 묶음 → 그대로 두되, 다른 "묶음"은 이름을 바꾼다: **위상 묶음**은 "면 구성 그룹", **값 묶음**은 "파라미터 값 조합"(또는 "값 세트").
   - **샘플**로 통일(표본 제거).
   - **기본 형상**과 **기준 형상**의 뜻을 문서 첫머리에 한 줄씩 정의.
   - "이동량", "위상", "스윕"은 처음 나올 때 괄호로 한 줄 풀이.
2. **"흐름:" 줄에서 경로를 빼고 코드 블록으로 옮긴다.** 흐름은 한국어 화살표만 남기고, 경로는 아래 코드 인용에 이미 있으므로 중복이다.
3. **80자를 넘는 문장은 둘로 쪼갠다.** 특히 괄호가 3개 이상 들어간 문장, "부른다"가 두 번 이상 나오는 문장을 우선한다. 전체의 12%가량(약 540문장)이다.
4. **동사를 표준 개발 용어로 맞춘다.** 부른다 → 호출한다, 위에 선다 → 바탕으로 한다, 닿는 → 미치는/걸치는, 일러 준다 → 알려 준다, 꽂는다 → 연결한다.
5. **말투를 하나로 통일한다.** 32개가 해라체이므로 `f00a11d` 설명을 해라체로 바꾸는 편이 싸다. "펼치세요" 같은 명령형도 "펼쳐서 읽는다"로 맞춘다.
6. **영어 잔재를 정리한다.** `References link to this commit.` 삭제 또는 번역("이 문서의 참조 링크는 위 커밋을 가리킨다."), 티켓 26 두 문서의 영어 절 제목 번역, `explained` → "설명일".
7. **원인 해결: 스킬 템플릿 쪽을 고친다.** 이 문서들은 `explain-diff-html` 스킬이 만든다. 스킬 지침에 위 1·4·5·6번을 규칙으로 적어 두면 다음 문서부터 같은 문제가 반복되지 않는다. 이미 만든 33개를 모두 손보기보다, 이 방법이 비용 대비 효과가 가장 크다. 기존 문서는 자주 보는 것(티켓 01, 12, 26 등)부터 용어만 바꿔 갱신하면 된다.

## 6. 스킬 쪽 원인과 수정안 (`explain-diff-html`)

검토 대상 스킬: `~/.claude/skills/explain-diff-html/` 의 `SKILL.md`, `references/writing-quality.md`, `html-template.html`. (`diagrams.md`, `quiz-design.md`, `validation.md`는 읽지 않았다.)

### 6.1 원인: 스킬이 영어 전용이다

스킬 어디에도 언어, 한국어, 번역에 관한 지침이 없다. 문서가 한국어로 나온 것은 이 프로젝트의 AGENTS.md가 "문서는 한국어"라고 정했기 때문이다. 한국어로 어떻게 써야 하는지는 스킬에도 프로젝트에도 규칙이 없었고, 아래 증상은 그 빈자리에서 나왔다.

| 증상(2절) | 스킬 쪽 원인 | 근거 위치 |
|---|---|---|
| 모든 문서에 `References link to this commit.`, "explained 날짜" | 출력 규약이 이 영어 문구를 그대로 쓰라고 정함 | `SKILL.md` 124~133행 |
| 티켓 26 두 문서만 영어 절 제목 | 템플릿이 `lang="en"`에 영어 제목(`Background / Intuition / Code walkthrough / Quiz`)을 박아 둠. 31개는 번역했고 2개는 안 한 것 | `html-template.html` 2, 614, 633, 657, 703, 725행 |
| "Intuition"이 "직관"과 "핵심 아이디어"로 갈림 | 번역어를 정하지 않음 | 스킬 전체 |

스킬에서 잘 작동한 규칙도 있다. "이름은 쓰기 전에 정의하라"(410행)와 "근거 없는 동기를 지어내지 마라"(398행)는 33개 문서에서 대체로 지켜졌다.

### 6.2 수정안 (파일별)

**A. `html-template.html`**
1. `<html lang="en">`을 `lang="ko"`로 바꾼다. 영어와 한국어를 모두 지원하려면 `{{LANG}}` 자리표시자로 둔다.
2. 절 제목을 고정 번역한다: 배경 / 핵심 아이디어 / 코드 따라가기 / 퀴즈. 목차(614행 부근)도 같이 바꾼다. "Intuition"의 번역어는 "핵심 아이디어"로 확정한다(31개 문서가 이미 이 말을 쓴다).
3. 출처 줄 주석(624행)의 예시를 한국어 틀로 바꾼다.

**B. `SKILL.md` 출력 규약**
1. 출처 줄 문구를 한국어 버전으로 고정한다.
   - 기본 형식: `owner/repo 티켓 N, 기준 커밋 abc1234, 2026-11-04 작성.`
   - 링크한 경우의 닫는 문장: `참조는 이 커밋을 가리킨다.`
   - 링크하지 않은 경우: `참조는 링크하지 않았다: 호스트가 GitHub가 아니다.`
   - 검증 스크립트가 이 영어 문구를 찾는지 `validate-output.js`에서 확인하고, 찾는다면 같이 바꾼다(이번 검토에서는 스크립트를 열어 보지 않았다).
2. "흐름 지도" 규칙을 분리한다: 흐름 지도는 **이름만** 화살표로 잇고(예: `업로드 → 검사 → 저장`), 파일 경로는 각 단계 아래 `.filename` 라벨에만 둔다. 한 줄은 100자를 넘기지 않는다.
3. 본문 문장 안의 `file:line` 인용은 한 단락에 두 개를 넘기지 않는다. 더 필요하면 단계 아래 코드 블록의 라벨로 보낸다.

**C. `SKILL.md` 2단계(맥락 수집) — 프로젝트 용어 우선**
1. 읽을 자료 목록에 루트 `GLOSSARY.md`를 README보다 앞에 둔다. 용어집에 있는 낱말은 그 낱말만 쓰고, 새 낱말을 만들 때는 용어집에 없는지 먼저 확인한다.
2. **한 낱말 한 뜻의 범위를 "프로젝트 전체"로 넓힌다.** 같은 프로젝트의 이전 설명 문서(`code-explanations/`)에서 이미 쓴 용어와 어긋나면 이전 문서를 따른다.
3. 용어집에 없는 새 개념이 3개 이상이면, 보고 단계에서 "용어집에 추가할 말" 목록을 사용자에게 알린다. 위의 "묶음" 문제를 사전에 잡는 장치다.

**D. `references/writing-quality.md` — 한국어용 절 추가**
언어가 한국어일 때 쓸 점검표를 따로 둔다. 하위 에이전트의 냉독 점검(6단계)에 이 표를 같이 넘긴다.

1. 번역투: "~를 통해", "~에 의해/의한", "~에 대해/대한", "~를 위해"의 연쇄, 영어 수동태 직역.
2. 직역 동사: 부른다→호출한다, 돌린다→실행한다, 위에 선다→바탕으로 한다, 닿는다→미친다/걸친다, 일러 준다→알려 준다, 꽂는다→연결한다, 뽑는다→추출한다.
3. 한 낱말이 두 뜻으로 쓰이는지(특히 "묶음", "형상", "샘플", "기준/기본").
4. 한 문장 80자 초과, 괄호 3개 이상, 같은 동사 두 번 이상.
5. 문어체 접속("곧", "몫", "바깥")이 정의 문장에 쓰였는지.
6. 말투가 해라체 하나인지(합쇼체, 명령형 "~하세요" 혼입 금지).
7. 영어 조각("explained", "affects"가 주어 자리)이 한국어 문장 안에 풀이 없이 있는지.

기존 영어 점검표(em dash, rule of three 등)는 영어 문서용이므로 "언어가 영어일 때"로 구분해 둔다. 한국어에서는 에이전트가 이를 억지로 적용하다 엉뚱한 지적을 낼 수 있다.

**E. `SKILL.md` — 말투 규칙 한 줄**
> 한국어 문서는 해라체("~한다")를 쓴다. 문서 한 편 안에서도, 같은 프로젝트의 여러 문서 사이에서도 말투를 바꾸지 않는다.

(해라체를 고른 이유: 기존 32개가 이미 해라체이므로 일괄 변환 비용이 가장 낮다. 합쇼체로 바꾸려면 32개를 고쳐야 한다.)

### 6.3 우선순위와 주의

1. 가장 싸고 효과가 큰 것: A(템플릿 한국어화)와 B-1(출처 문구). 기계적으로 바꿀 수 있고 2.6절의 영어 잔재 대부분이 사라진다.
2. 가장 효과가 큰 것: C(용어집·문서 간 용어 통일). 가독성 문제의 핵심인 "묶음" 류를 막는다.
3. D·E는 문체 문제를 줄이지만 점검표를 늘리는 만큼 하위 에이전트의 점검 시간이 늘어난다.
4. 이 스킬은 저장소 밖(`~/.claude/skills/`)에 있고 다른 프로젝트에도 쓰이므로, 한국어 규칙은 "프로젝트 언어가 한국어일 때만" 켜지는 분기로 넣어야 한다. 영어 프로젝트에서 동작이 바뀌면 안 된다.
5. 템플릿을 바꿔도 이미 만든 33개 문서에는 반영되지 않는다(스킬 문서도 같은 경고를 한다, `SKILL.md` 681~684행). 기존 문서는 5절 권고 1·6번(용어 통일, 영어 문구 정리)을 따로 일괄 치환해야 한다.

## 7. 한계

- 코드 블록 안과 퀴즈 보기의 일부는 본문 통계에서 빠졌다.
- 수치는 정규식으로 센 근사값이다(예: "부른다"가 사람을 부르는 뜻으로 쓰인 경우는 걸러 내지 못했다).
- 33개 전체를 한 줄씩 읽지 않았고, 수치 분석 전체와 표본 약 열두 곳(티켓 01, 12, 26, `f00a11d` 중심)을 직접 읽었다. 위 2.1~2.7의 사례는 그 표본에서 나왔다.
- "읽기 어렵다"는 독자의 배경(CAD, three.js 경험)에 달려 있다. 이 프로젝트를 만든 사람 본인에게는 쉽고, 처음 보는 한국인 개발자에게는 위 문제가 크게 느껴질 수 있다.

티켓 16: 정보 입력, 후보 제시·선택

운영자가 정보 입력을 적으면, AI가 명세 작성 전에 슬라이더 구성 후보 2~4개를 업로드한 스윕으로 만든 미리보기와 함께 보여 주고, 운영자가 고른 후보가 명세 작성의 입력이 되게 한 변경이다.

jun-1993-p/threejs-configurator-ai 티켓 16 (커밋 414ea8d), 2026-11-04에 설명함. References link to this commit.

배경

이 프로젝트가 처음이라면: 깊은 배경을 펼치세요.

프로젝트는 Fusion CAD 모델을 쇼핑몰 페이지의 div 안에서 도는 three.js 구성기로 바꾼다. 파이프라인 실행기가 상품 하나를 정해진 순서로 진행한다(ADR-0014). CAD 애드인이 올린 업로드 묶음(파라미터, 부품, 기본 형상, 스윕)을 받고, 운영자가 적은 정보 입력을 받고, AI가 명세(슬라이더를 어떤 범위로 노출할지 적은 JSON)를 쓴다. 이어서 조립·검증을 거쳐 사람이 최종 승인한다.

같은 Fusion 모델에서도 슬라이더를 만드는 방법이 여러 가지다. 예를 들어 서랍장에서 전체 폭 하나만 노출할 수도 있고, 폭과 깊이를 함께 노출할 수도 있다. 정면 방향(고객이 가구를 마주하는 방향)을 어느 쪽으로 보느냐에 따라 폭 W·깊이 D·높이 H가 Fusion의 어느 축인지도 달라진다. 정면을 AI가 혼자 정하면 틀려도 드러나지 않는다. 티켓 15 기록에는 정면이 +X인데 axes.W가 X인 명세가 수동 확인에서 제출까지 간 사례가 있다. 이 티켓은 명세 작성 전에 후보를 보이고 사람이 고르게 한다(두 사실을 잇는 것은 내 추정이다).

이 티켓 전의 chooseCandidate는 후보 목록만 받았고, 정면은 지시문의 "확신이 없으면 후보끼리 정면을 다르게 둔다"는 문장에만 맡겨져 있었다. 후보끼리 다른지 보는 검사도 없었다. 티켓 15에서 AI 모델 포트에 LiteLLM 구현이 생겼고, 이 티켓은 그 위에 정보 입력 화면, 그림을 보는 부품 탐색, 후보끼리 달라야 한다는 검사, 후보 카드를 쌓는다.

용어

부품 탐색은 후보 제시 첫머리에 VLM(그림을 보는 모델)이 기본 형상을 여섯 방향에서 그린 그림을 보고 부품의 역할과 정면 후보, 위쪽 방향을 찾는 일이다. 정면 후보가 여럿이면 정면을 확신하지 못한 것이고, 후보끼리 그 정면을 모두 나눠 쓴다. 후보 카드는 후보 선택 화면에서 후보 하나를 보여 주는 칸이다. 다른 후보와의 차이 한 줄, 축 대응, 변형 미리보기가 붙는다.

핵심 아이디어

이 변경은 세 가지를 한다. VLM이 확신하지 못하는 것(정면)은 후보에 펼쳐서 사람이 고르게 한다. 후보가 서로 정말 다른지는 코드가 검사한다. 사람이 고르는 근거를 글이 아니라 그림으로 준다.

후보 선택까지의 길

정보 입력 (상품명·종류·메모·두께 노출)
여섯 방향 그림 + 부품 색
부품 탐색 (VLM)
부품 역할, 정면 후보, 위쪽
후보 제시 (2~4개)
후보 + 축 대응 + 미리보기
운영자가 카드 하나를 고름

정면이 불확실한 서랍장을 예로 들자. VLM이 정면 후보를 -Y, +X 두 개로 답하면 정면을 확신하지 못한 것이다. 후보 제시는 후보 두 개 이상이 이 두 정면을 모두 나눠 써야 한다. 운영자는 두 카드를 비교한다. 카드에는 정면에 따라 정해지는 축 대응이 적혀 있다.

후보정면위쪽D 깊이H 높이W 폭
c1-Y+ZY축Z축X축
c2+X+ZX축Z축Y축

규칙은 하나다. 깊이는 정면 방향의 축이고, 높이는 위쪽의 축이고, 폭은 남은 축이다. 정면 후보가 -Y와 +X로 나뉘는 상황을 가정한 값이고, 정면이 바뀌면 폭과 깊이의 축이 서로 바뀐다.

경계 사례

미리보기에는 두께 후보 그림이 없고, 카드에는 "두께 선택 보이기/숨김"이 글로만 표시된다. 두께 후보의 형상은 명세 작성 뒤에 추가 샘플 요청으로 받기 때문에 후보 제시 때는 아직 없다(티켓 기록). 또 이 티켓은 운영자 화면을 띄우는 호스트를 만들지 않았다. 화면 함수는 HTML 문장을 만들고 양식 값을 읽는 데까지다.

코드 따라가기

흐름: 정보 입력 양식과 검사 → 여섯 방향 그림 그리기 → 부품 탐색 → 후보 제시와 후보 검사 → 후보 카드 만들기 → 고른 카드가 명세 작성의 입력과 검사 기준이 됨.

1. 정보 입력: 양식과 형식 검사

정보 입력은 상품명, 상품 종류(목록), 범위 메모, 두께 선택 노출 여부 네 칸이다. 직업처럼 쓰이지 않는 항목은 받지 않는다(사용자 스토리 18). 형식은 configurator/pipeline/schemas.ts:55가 검사한다.

양식 화면은 intakeFormHtml(configurator/pipeline/operator-screens.ts:31), 보낸 값을 읽는 것은 readIntakeForm(configurator/pipeline/operator-screens.ts:47)다. 두께 노출을 비우면 "AI 판단"(ai)이다. 실행기는 정보 입력 단계에서 같은 검사를 다시 돌려, 틀리면 후보 제시 전에 멈춘다.

2. 여섯 방향 그림

VLM에게 보낼 그림은 서버가 그린다. WebGL 없이 직교 투영·깊이 버퍼·면 음영만으로 삼각형을 칠하는 소프트웨어 래스터라이저가 새 파일 render.ts에 있다. 부품마다 색이 달라 VLM이 색으로 부품을 가린다. partViews(configurator/pipeline/candidate-cards.ts:64)가 기본 형상을 ±X·±Y·±Z 여섯 방향에서 그리고 부품 색 목록을 만든다. X·Y 쪽 그림은 Z가 위, Z 쪽 그림은 Y가 위다.

configurator/pipeline/candidate-cards.ts:64-73

export function partViews(bundle: UploadBundle): { views: PartView[]; colors: PartColor[] } {
  const colorOf = colorsOf(bundle);
  const shape = createMorph(sweepSpec(bundle, []), bundle).shape({});
  const views = FRONTS.map((from) => {
    const view: View = { eye: directionOf(from), up: from[1] === "Z" ? [0, 1, 0] : [0, 0, 1] };
    return { from, image: renderPngs([shape], view, VIEW_SIZE, colorOf)[0].toString("base64") };
  });
  const parts = [...new Set(shape.faces.map((f) => f.part))];
  return { views, colors: parts.map((name) => ({ name, color: hex(colorOf(name)) })) };
}

부품 색은 정해 둔 6색 뒤로 색상환을 황금각씩 돌려 만든다. 부품이 많아도 색이 겹치지 않는다(리뷰 반영). 티켓 기록에 따르면 렌더링은 한 실행에 0.3초 안팎이다.

3. 부품 탐색

AI 단계가 셋에서 넷이 되었다. 새 단계 parts는 후보 제시 앞에 온다. 새 메서드 findParts는 그림과 부품 색을 받는다. 응답은 JSON Schema(PARTS_SCHEMA)로 검사한다. 부품 목록, 정면 후보(확신 순서, 1~4개), 위쪽이다.

LiteLLM 구현은 그림을 OpenAI 호환 조각 목록에 실어 보낸다. 문장 뒤에 image_url 조각(data URI)이 붙고, 문장에는 그림 순서대로 어느 쪽에서 본 것인지만 남긴다. 부품 탐색의 형식 오류는 단계 candidates로 기록된다. 티켓 기록에 따르면 처리 기록의 단계 순서(ADR-0014의 10단계)를 바꾸지 않으려는 것이다. partsReferenceChecker(configurator/pipeline/schemas.ts:215)는 답의 부품 이름이 업로드 묶음에 있는지, 정면 후보가 위쪽과 같은 축이 아닌지 본다.

4. 후보 검사: 서로 달라야 하고 정면은 부품 탐색을 따른다

candidateDiversityChecker(configurator/pipeline/schemas.ts:231)가 형식 검사를 통과한 후보에 규칙 다섯 가지를 건다. 표의 네 가지와, 위쪽과 같은 축은 정면이 될 수 없다는 규칙이다.

규칙어긋나면
두 후보는 정면·부모 파라미터(순서 무관)·두께 노출 중 하나 이상이 다르다같은 후보라고 알림
정면 후보가 하나면 모든 후보가 그 정면이다확신한 정면이어야 한다고 알림
정면 후보가 여럿이면 후보에 모두 나온다빠진 정면을 알림
정보 입력이 두께를 보이기·숨기기로 정했으면 후보가 따른다. "AI 판단"이면 후보마다 달라도 된다정해진 값을 알림

configurator/pipeline/schemas.ts:231-250

export function candidateDiversityChecker({ fronts, up }: { fronts: Front[]; up: Front }, thickness: ThicknessExposure) {
  return (candidates: { id: string; front: Front; parents: string[]; showThickness: boolean }[]): string[] => {
    const shape = (c: (typeof candidates)[number]) => JSON.stringify([c.front, [...c.parents].sort(), c.showThickness]);
    const errors = candidates.flatMap((c, i) => [
      ...frontOnUpAxis(`/${i}/front`, c.front, up),
      ...(fronts.length === 1 && c.front !== fronts[0] ? [`/${i}/front: 부품 탐색이 확신한 정면 ${fronts[0]}이어야 합니다`] : []),
      ...(thickness !== "ai" && c.showThickness !== (thickness === "show")
        ? [`/${i}/showThickness: 정보 입력이 두께 선택을 ${thickness === "show" ? "보이기" : "숨기기"}로 정해 ${thickness === "show"}이어야 합니다`]
        : []),
      ...candidates
        .slice(0, i)
        .filter((other) => shape(other) === shape(c))
        .map((other) => `/${i}: 후보 ${other.id}와 정면·부모 파라미터·두께 선택 노출이 모두 같습니다. 하나 이상을 다르게 하세요`),
    ]);
    const missing = fronts.length > 1 ? fronts.filter((f) => !candidates.some((c) => c.front === f)) : [];
    if (missing.length > 0) {
      errors.push(`${ROOT}: 정면을 확신하지 못해(정면 후보 ${fronts.join("·")}) 후보끼리 정면이 달라야 합니다. 빠진 정면: ${missing.join("·")}`);
    }
    return errors;
  };

다섯째 규칙의 검사는 frontOnUpAxis(configurator/pipeline/schemas.ts:209) 하나로 합쳐 후보 검사와 부품 탐색 검사가 같이 쓴다.

5. 후보 카드: 축 대응과 변형 미리보기

axesFor(configurator/pipeline/candidate-cards.ts:17)가 정면과 위쪽에서 축 대응을 정한다. 같은 축이면 오류다.

configurator/pipeline/candidate-cards.ts:17-21

export function axesFor(front: Front, up: Front): Record<Axis, string> {
  const [D, H] = [front[1], up[1]];
  if (D === H) throw new Error(`정면 ${front}과 위쪽 ${up}이 같은 축이라 축 대응을 정할 수 없습니다`);
  return { W: [..."XYZ"].find((a) => a !== D && a !== H)!, D, H };
}

미리보기는 업로드한 스윕으로 만든다. sweepSpec(configurator/pipeline/candidate-cards.ts:52)가 후보의 부모 파라미터마다 스윕 범위 전체를 슬라이더로 둔 임시 명세를 만들고, 변형 엔진이 그 명세로 형상을 낸다. 위상 묶음도 그대로 탄다(티켓 11). candidateCards(configurator/pipeline/candidate-cards.ts:76)는 부모 파라미터마다 범위 끝·기본값 세 곳을 그려 카드에 붙인다. 시점은 정면 쪽에서 오른쪽 위로 비켜 본다.

configurator/pipeline/candidate-cards.ts:84-90

    const previews = spec.sliders.map(({ id, min, max, default: value }) => {
      const values = [min, value, max];
      const images = renderPngs(values.map((v) => morph.shape({ [id]: v })), view, PREVIEW_SIZE, colorOf);
      return { parameter: id, values, images: images.map((png) => png.toString("base64")) };
    });
    return { ...candidate, axes: axesFor(candidate.front, up), previews };
  });

카드 화면은 candidateCardsHtml(configurator/pipeline/operator-screens.ts:79)이 만들고, 보낸 선택은 readCandidateChoice(configurator/pipeline/operator-screens.ts:93)가 읽는다. 사람 포트 chooseCandidate는 이제 후보 대신 카드를 받는다.

6. 고른 후보가 명세 작성의 입력이 된다

명세 작성 입력의 candidate는 카드에서 미리보기 그림과 축 대응을 뺀 후보다. AI 입력과 사례 기록에 그림이 실리지 않게 하려는 것이다.

configurator/pipeline/runner.ts:217

const candidateOf = ({ axes: _axes, previews: _previews, ...candidate }: CandidateCard): Candidate => candidate;

명세 검사에는 chosenCandidateChecker(configurator/pipeline/schemas.ts:257)가 더해졌다. 명세의 정면이 고른 후보의 정면이어야 하고, 축 대응이 카드에 보인 것과 같아야 한다. 카드가 보여 준 축과 다른 명세가 제출되지 않게 하는 검사다. 티켓 15가 더했던 정면·축 검사(axesChecker)는 이 안에 들어가고, 축 대응 자체가 틀렸으면 카드와의 축 비교는 하지 않고 axesChecker의 오류만 더한다.

configurator/pipeline/schemas.ts:257-268

export function chosenCandidateChecker({ front, axes }: { front: Front; axes: Spec["axes"] }) {
  return (spec: Pick<Spec, "front" | "axes">): string[] => {
    const errors = spec.front === front ? [] : [`/front: 고른 후보의 정면 ${front}이어야 합니다(지금 ${spec.front})`];
    const axesErrors = axesChecker(spec);
    if (axesErrors.length > 0) return [...errors, ...axesErrors];
    if (spec.front === front && (["W", "D", "H"] as const).some((a) => spec.axes[a] !== axes[a])) {
      errors.push(`/axes: 고른 후보 카드의 축 대응(W ${axes.W}, D ${axes.D}, H ${axes.H})이어야 합니다(지금 W ${spec.axes.W}, D ${spec.axes.D}, H ${spec.axes.H})`);
    }
    return errors;
  };
}

퀴즈

후보끼리 같은지 비교할 때 부모 파라미터 목록을 정렬하지 않고 그대로 비교한다고 하자. 무엇이 통과하게 되는가?

검사는 정면·정렬한 부모 목록·두께 노출을 묶어 비교한다. 정렬을 빼면 [body_w, body_d]와 [body_d, body_w]가 다른 값이 되어, 같은 구성이 두 장의 카드로 운영자에게 보인다. 정면이 다른 후보는 어차피 다르다.

부품 탐색이 정면 후보로 -Y와 +X, 위쪽으로 +Z를 냈다. 후보 c1(-Y, 부모 body_w)과 c2(-Y, 부모 body_d)가 제시되면?

두 후보는 부모가 달라 서로 다르다. 그러나 정면 후보가 둘이면 정면을 확신하지 못한 것이어서 후보끼리 두 정면을 모두 나눠 써야 한다. 두 후보 모두 -Y라 +X가 빠졌다는 오류가 난다.

정면이 +X이고 위쪽이 +Z인 후보 카드에 표시되는 폭 W의 축은?

깊이 D는 정면 방향의 축이라 X, 높이 H는 위쪽의 축이라 Z다. 폭 W는 남은 축 Y다. 오류는 정면과 위쪽이 같은 축일 때만 난다.

후보 카드의 변형 미리보기에는 두께 후보를 바꾼 그림이 없다. 그 이유로 가장 알맞은 것은?

티켓 기록의 설명이다. 두께 후보(표준 두께의 앞뒤 한 칸)는 명세 작성에서 정해지고 그 형상은 추가 샘플 요청으로만 받는다. 후보 제시 때는 그 형상이 없어서, 카드에는 두께 선택 보이기·숨김이 글로만 표시된다. 미리보기는 부모 파라미터가 여럿이어도 파라미터마다 만들어진다.

정보 입력에서 운영자가 두께 선택 노출을 "숨기기"로 골랐는데, AI가 낸 후보 하나의 showThickness가 참이다. 어떻게 되는가?

"보이기"나 "숨기기"는 모든 후보가 따라야 하고, 후보마다 달라도 되는 것은 "AI 판단"일 때뿐이다. 어긋나면 어느 후보의 어느 필드가 틀렸는지 알리는 오류가 나고 후보 제시를 다시 묻는다. 경고만 하고 통과시키는 경로는 없다.

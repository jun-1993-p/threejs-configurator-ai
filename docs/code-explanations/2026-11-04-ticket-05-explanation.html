티켓 05: 적응형 스윕과 범위 축소

애드인이 업로드 때 5점 균등 샘플에서 시작해 휘는 구간만 샘플을 늘리고, 17점으로도 못 맞추면 그 파라미터를 후보에서 빼며, Fusion 재계산이 실패하는 곳에서는 스윕 범위를 줄인다.

jun-1993-p/threejs-configurator-ai 티켓 05, 기준 커밋 83573d2 (포함한 커밋: 83573d2), 2026-11-04 작성. References link to this commit.

배경

처음 보는 사람을 위한 배경

이 프로젝트는 Fusion에서 만든 CAD 모델을 쇼핑몰용 three.js 구성기로 옮긴다. 브라우저는 Fusion을 돌릴 수 없으므로, 슬라이더를 움직였을 때의 모양은 미리 계산해 둔 표본으로 흉내 낸다. 파라미터(예: 선반 폭 shelf_w)를 여러 값으로 바꿔 보며 모델의 면 점들을 기록해 두는 일을 스윕이라 하고, 기록한 값 하나를 샘플이라 한다. 슬라이더가 두 샘플 사이에 놓이면 변형 엔진이 두 샘플의 점을 직선으로 섞는다(ADR-0002, ADR-0004).

직선으로 섞는 방식은 파라미터에 비례해 움직이는 부분에는 정확하다. 하지만 경사진 등판처럼 점이 원호를 그리며 움직이면 두 샘플의 한가운데 점은 직선 위가 아니라 원호 위에 있으므로 오차가 생긴다.

업로드는 Fusion 애드인이 모델의 사용자 파라미터를 하나씩 바꿔 가며 형상을 읽어 업로드 묶음을 만드는 단계다. 샘플을 몇 점, 어디에 둘지는 AI가 아니라 애드인이 정한다(ADR-0007). 이 티켓 이전에는 기본값의 50%, 75%, 100%, 125%, 150%에 5점을 고정으로 뽑고, 이웃 샘플 사이 가운데 값에서 검증점(그 값에서 Fusion이 계산한 실제 형상)을 하나씩 더 뽑았다.

용어

합격선(ADR-0012)은 보간 결과가 실제 형상과 얼마나 달라도 되는지의 한도다. 치수 오차(부품별 가로·세로·높이 차이)는 0.2 mm, 형상 오차(같은 꼭짓점끼리의 거리)는 1 mm와 상품 전체 바운딩 박스 대각선의 0.1% 중 큰 값이다. 위상 묶음(ADR-0005)은 개수형 파라미터 때문에 면 구성이 달라지는 구간을 나눈 묶음이고, 처리 기록은 파이프라인이 단계마다 남기는 로그다. 슬라이더 후보는 AI가 제안하고 사람이 고르는 슬라이더 구성안이다.

티켓 파일은 이 변경이 할 일을 다섯 가지로 적었다. 선형 파라미터는 5점에서 멈출 것, 비선형 구간만 늘릴 것, 17점으로도 못 맞춘 파라미터는 실패로 보고해 후보에서 뺄 것, 재계산 실패 지점 안쪽으로 범위를 줄일 것, 위상 묶음 안에서 부피가 튀면 volume_jump 경고를 남길 것이다.

주의

합격선 비교는 "검증점의 실제 형상"과 "이웃 샘플 둘을 직선으로 섞은 형상"을 견주는 일이다. 그래서 애드인(Python)이 계산하는 섞기 규칙이 브라우저의 변형 엔진(TypeScript)과 같아야 한다. 규칙이 다르면 애드인이 통과시킨 구간이 브라우저에서는 틀린다.

핵심 아이디어

핵심 아이디어는 "의심스러운 구간만 반으로 쪼갠다"이다. 5점으로 시작해, 이웃한 샘플 두 개의 직선 보간이 그 사이 검증점을 합격선 안으로 맞히면 그 구간은 끝이다. 못 맞히면 그 검증점을 새 샘플로 삼아 구간을 둘로 나눈다. 나뉜 두 구간에는 다시 검증점이 생기고, 같은 검사를 반복한다. 샘플은 17점까지만 늘린다(5점에서 모든 구간을 두 번 반으로 나눈 수).

작은 예: 등판 각도 A가 50도를 넘어야 기울어지는 모델

시험 모델(_Tilt)에서 각도 A의 기본값은 40도다. 처음 샘플은 20, 30, 40, 50, 60도다. 50~60도 구간만 점이 원호를 그린다. 10도 폭 구간의 형상 오차는 1.5 mm로 합격선을 넘고, 5도 폭 구간은 상판 높이의 치수 오차 0.30 mm로 넘으며, 2.5도 폭 구간은 0.08 mm로 통과한다. 그래서 샘플은 50과 60 사이에서만 늘어난다.

두 번째 이야기: 재계산이 실패하는 곳

파라미터를 너무 크게 바꾸면 Fusion이 모델을 재계산하지 못할 수 있다. 그런 지점은 샘플로 쓸 수 없으니, 기본값에서 그쪽으로 가며 처음 실패한 점부터 바깥을 버린다. 남는 가장 안쪽 점이 새 범위 끝이다. 시험에서 W가 1200에서 실패하면 범위는 400~1100이 되고, 안쪽 검증점 1100이 샘플로 올라가며, 그 이유는 reason: "recompute_failed"로 업로드 묶음에 남는다.

17점으로도 합격선을 못 맞추면 업로드 묶음에 interpolation_failure(어디에서, 어떤 오차가, 어느 부품에서, 얼마나)가 담기고, 파이프라인은 그 파라미터를 슬라이더 후보에서 뺀다. 예를 들어 등판이 47.3도에서 0도에서 30도로 튀는 모델은 아무리 나눠도 맞지 않는다. 시험은 이때 샘플이 17개이고 합격선과의 비율이 가장 큰 것이 상판 높이의 치수 오차(0에서 200 mm)임을 확인한다.

코드 따라가기

흐름: 애드인의 스윕 시작(_single_sweep, _sweep) → 적응형 샘플 뽑기(_adaptive_points, _refine) → 보간 오차 계산 → 업로드 묶음 JSON → 파이프라인의 업로드 단계 알림 → 후보·명세 검사에서 파라미터 제외.

1. 합격선과 보간 오차

상한 17점과 치수 합격선 0.2 mm는 상수로 둔다. 형상 합격선은 점들의 바운딩 박스 대각선에서 계산한다(addin/ConfiguratorUploader/uploader/core.py:285의 SAMPLE_LIMIT, core.py:289의 DIMENSION_TOLERANCE). 핵심은 _interpolation_error다. 변형 엔진의 addDelta와 같은 규칙으로 면을 (바디, 면 이름)으로 짝짓고 점마다 lo + (hi - lo) * t를 계산한다. 부품마다 형상 오차와 치수 오차를 합격선으로 나눈 비율을 구해 가장 큰 것을 돌려준다.

addin/ConfiguratorUploader/uploader/core.py:315-337

def _interpolation_error(
    lo: dict[str, Any], hi: dict[str, Any], check: dict[str, Any], part_of: dict[str, str]
) -> _Miss | None:
    """검증점에서 이웃 두 샘플의 선형 보간이 빗나간 양. 변형 엔진의 단독 스윕 보간과 같은 규칙이다:
    면은 (바디, 면 이름)으로 짝짓고, 점마다 lo + (hi - lo) * t로 섞는다(configurator/src/engine.ts의 addDelta).

    부품마다 형상 오차와 W·D·H 치수 오차를 재서 오차 / 합격선이 가장 큰 것을 돌려준다. 점이 짝지어지지 않으면 None.
    """
    t = (check["value"] - lo["value"]) / (hi["value"] - lo["value"])
    faces_lo = {(f["body"], f["name"]): f["points"] for f in lo["faces"]}
    faces_hi = {(f["body"], f["name"]): f["points"] for f in hi["faces"]}
    predicted: dict[str, list[Point]] = {}
    actual: dict[str, list[Point]] = {}
    distance: dict[str, float] = {}
    for face in check["faces"]:
        key = (face["body"], face["name"])
        a, b = faces_lo.get(key), faces_hi.get(key)
        if a is None or b is None or not len(a) == len(b) == len(face["points"]):
            return None
        part = part_of.get(face["body"], face["body"])
        for pa, pb, pc in zip(a, b, face["points"]):
            p = (pa[0] + (pb[0] - pa[0]) * t, pa[1] + (pb[1] - pa[1]) * t, pa[2] + (pb[2] - pa[2]) * t)
            predicted.setdefault(part, []).append(p)

비율이 1을 넘으면 그 구간은 합격선을 못 맞춘 것이다. 면 구성이 달라 짝이 안 맞는 구간은 None을 돌려주고 보간하지 않는다. 그 구간은 위상 묶음의 몫이다.

2. 반으로 쪼개는 반복

_adaptive_points(core.py:368)가 5점 샘플을 만들고 _refine에 넘긴다. _refine의 반복은 검증점이 없는 구간에 검증점을 뽑고, 재계산 실패를 정리하고(범위 축소일 때), 합격선을 넘은 구간을 모은 뒤, 상한 안에서 비율이 큰 구간부터 나눈다.

끝 조건이 둘이다. 넘은 구간이 없으면 None(성공), 샘플이 이미 limit개인데도 넘은 구간이 있으면 비율이 가장 큰 검증점을 interpolation_failure 형식으로 돌려준다(addin/ConfiguratorUploader/uploader/core.py:427-429). 상한 근처에서는 limit - len(samples)개만 나눈다(addin/ConfiguratorUploader/uploader/core.py:431).

3. 재계산 실패에서 범위 줄이기

_trim_failures(core.py:439)는 기본값에서 쪽마다 처음 실패한 점부터 바깥을 지우고 그 안쪽 가장 먼 점이 검증점이면 샘플로 올린다. 줄인 쪽마다 recompute_failed 기록을 하나 돌려준다. 줄이고 나면 바깥 구간이 새로 생기므로 _refine은 continue로 처음부터 다시 돈다. 이것이 "범위를 줄여 새로 뽑은 검증점에서도 실패하면 더 안쪽으로 줄인다"는 시험(1200과 1050이 실패하면 최대 1000)의 근거다.

4. 스윕 두 종류에 연결하고 JSON으로

단독 스윕(_single_sweep, core.py:504)은 적응형 샘플을 뽑은 뒤 위상 변화로 줄일 쪽을 정하고, 위상 변화가 재계산 실패 기록을 덮는다. 이유는 코드 주석이 적었다: 면 구성이 바뀐 지점이 재계산 실패 지점보다 안쪽이기 때문이다. 위상 묶음을 나누는 _sweep은 경계 양쪽의 샘플을 더한 뒤 그 샘플과 이웃 샘플 사이 구간도 _refine으로 다듬는다. 경계 샘플은 상한 계산에서 빠진다(addin/ConfiguratorUploader/uploader/core.py:640-641의 SAMPLE_LIMIT + len(edges)).

5. 파이프라인: 알리고 후보에서 빼기

업로드 단계에서 runner.ts가 기존 범위 알림에 새 알림을 합쳐 처리 기록에 남긴다(configurator/pipeline/runner.ts:633).

configurator/pipeline/verify-sweep.ts:73-75

export function uploadSweepFeedback(bundle: UploadBundle): Feedback[] {
  return scopes(bundle).flatMap((scope) => [...interpolationFeedback(scope), ...volumeFeedback(scope)]);
}

새 파일 verify-sweep.ts의 interpolationFeedback(verify-sweep.ts:15)이 보간 실패를, volumeFeedback(verify-sweep.ts:38)이 부피 튐을 만든다. 부피 튐은 같은 위상 묶음 안의 이웃 세 샘플에서 가운데 바디의 부피가 양옆을 직선으로 이은 값에서 20%(VOLUME_JUMP, configurator/pipeline/verify-sweep.ts:11) 넘게 벗어나면 낸다. 20%로 잡은 이유는 코드 주석이 적었다: 판 크기가 두 치수에 따라 바뀌면 부피가 파라미터의 제곱이라 5점 스윕의 가운데 샘플도 11%쯤 벗어난다. 실패가 아니라 경고다.

두 알림이 같이 쓰는 도우미(기본 묶음의 단독 스윕과 위상 묶음 안의 단독 스윕을 하나씩 도는 scopes)는 verify-range.ts에서 새 파일 sweep-scopes.ts로 옮겼다(sweep-scopes.ts:21). verify-range.ts는 recompute_failed의 문장만 추가한다.

후보에서 빼는 규칙은 unmixableSweeps에 모았다.

configurator/pipeline/parameter-relations.ts:31-43

export function unmixableSweeps(bundle: BundleParameters): Map<string, string> {
  const all = bundle.sweeps.flatMap((s) => [s, ...(s.groups ?? []).flatMap((g) => g.sweeps)]);
  const out = new Map<string, string>();
  for (const s of all) {
    if (out.has(s.parameter)) continue;
    if (s.interpolation_failure !== undefined) {
      out.set(s.parameter, `${s.parameter}는 적응형 스윕을 ${SAMPLE_LIMIT}점까지 늘려도 보간 오차가 합격선을 넘어(보간 실패) 슬라이더 후보가 될 수 없습니다`);
    } else if (s.samples.filter((x) => x.status === "ok").length < 2) {
      out.set(s.parameter, `${s.parameter}는 재계산에 성공한 스윕 샘플이 2개보다 적어 보간할 수 없으므로 슬라이더 후보가 될 수 없습니다`);
    }
  }
  return out;
}

보간 실패한 파라미터뿐 아니라 재계산 실패로 범위가 줄어 성공한 샘플이 2개보다 적은 파라미터도 섞을 수 없다. 이 목록은 sliderable(parameter-relations.ts:56)과 후보 검사(configurator/pipeline/schemas.ts:399), 명세 검사(configurator/pipeline/schemas.ts:223)가 같이 쓰므로 같은 문장이 AI에게 돌아간다.

6. 스키마와 합성 녹화본

업로드 묶음 스키마에 interpolation_failure가 생기고 reductions[].reason에 recompute_failed가 더해졌다. SolidCraft 어댑터가 각도 파라미터를 바꿀 수 있게 되어, 합성 녹화본 fixtures/synthetic/bench-tilt.json이 추가되었다. 티켓에 적힌 "실제 상품 녹화본"은 이 합성 녹화본으로 대신하고 Fusion 실물 확인은 티켓 26으로 넘겼다.

티켓이 남긴 한계

티켓의 구현 기록에 따르면 17점 상한은 파라미터 하나의 스윕 전체(양쪽 끝과 모든 위상 묶음)가 나눠 쓴다. ADR-0007이 "파라미터마다" 상한을 두었기 때문이다. 그래서 기본 묶음 밖의 위상 묶음에서 보간이 실패해도 파라미터 전체가 후보에서 빠진다. volume_jump는 바디 부피가 있는 합성 녹화본에서만 나오고, Fusion 어댑터에는 아직 바디 측정이 없다.

5점 균등으로 끝내지 않고 합격선을 넘은 구간만 반으로 나누는 까닭은?

샘플 위치는 AI가 정하지 않는다(ADR-0007). 선형 구간은 5점이면 충분하고, 늘리는 비용(Fusion 재계산)을 오차가 큰 구간에만 쓴다.

등판 각도 A의 검증점 오차가 처음 샘플 사이에서 모두 합격선 안이었다. 어떤 일이 일어나는가?

_refine은 넘은 구간이 없으면 None을 돌려주고 끝난다. 선형 파라미터 W가 5점에서 멈춘 시험이 이 경우다.

재계산이 1200에서 실패했다. 그 안쪽 검증점 1100은 어떻게 쓰이는가?

_trim_failures는 실패 지점 안쪽의 가장 먼 점이 검증점이면 샘플로 올린다. 그래서 시험의 범위는 400~1100이 된다.

위상 묶음 안에서 면 구성이 바뀌는 경계의 두 샘플이 상한 17점 계산에서 빠지는 까닭으로 가장 알맞은 것은?

코드 주석은 "경계 샘플은 상한에 넣지 않는다"고만 적었다. 경계는 위상 묶음이 요구하는 샘플이라 보간 정확도를 올리려는 17점과는 목적이 다르다고 읽을 수 있다(해석). 실제로 SAMPLE_LIMIT + len(edges)를 상한으로 넘긴다.

두 번째 단독 스윕이 보간 실패인데 같은 파라미터가 다른 위상 묶음에서는 통과했다. 파이프라인은 어떻게 하는가?

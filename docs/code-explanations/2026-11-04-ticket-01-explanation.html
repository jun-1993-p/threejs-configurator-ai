티켓 01: 애드인 업로드와 녹화

Fusion 애드인이 서버 연결을 확인한 뒤 모델의 파라미터, 부품, 기본 형상, 단독 스윕을 업로드 묶음 하나로 만들어 서버에 보내고, 서버는 그 묶음을 검사해 저장하고 녹화본으로 내보낸다. 이후 모든 티켓이 쓰는 데이터 형식이 이 티켓에서 정해졌다.

jun-1993-p/threejs-configurator-ai 티켓 01 (커밋 ca03a34, f526ec2) at f526ec2, explained 2026-11-04. References link to this commit.

배경

이 프로젝트가 처음이라면 펼쳐서 읽는다.

프로젝트의 목표는 Fusion으로 만든 CAD 모델을 쇼핑몰 페이지의 div 하나 안에서 도는 three.js 구성기로 바꾸는 것이다. 고객은 슬라이더로 서랍 폭 같은 값을 바꾸고, 구성기는 모델 형태를 그에 맞게 변형해 보여준다.

브라우저는 Fusion의 파라메트릭 모델을 다시 계산할 수 없다. 그래서 변형은 미리 뽑아 둔 형상 표본을 섞어서 흉내 낸다(ADR-0002). 이 표본이 스윕이다. Fusion에서 사용자 파라미터 값을 바꿔 가며 형상을 뽑은 결과의 묶음이다. 이 티켓은 그 표본을 뽑는 쪽, 곧 Fusion 애드인과, 그것을 받는 서버를 만든다.

Fusion 애드인은 Fusion 안에서 도는 Python 프로그램이다. Fusion의 Python에는 외부 패키지를 설치할 수 없어서, 애드인은 표준 라이브러리만 쓴다. 서버는 일반 Python 프로젝트(FastAPI)다.

이 티켓이 다루는 용어는 루트 GLOSSARY.md의 말을 따른다.

  • 업로드 묶음: 애드인이 서버로 보내는 상품 하나의 파라미터, 부품, 기본 형상, 스윕.
  • 기본 형상: 파라미터를 기본값 그대로 둔 형상. 코드에서는 baseline이다.
  • 단독 스윕: 부모 파라미터 하나만 움직이고 나머지는 기본값으로 둔 스윕.
  • 부품: Fusion 컴포넌트 하나에 해당하는 구성 단위. 컴포넌트가 없는 모델에서는 바디 하나(ADR-0006).
  • 녹화본: 시험 데이터로 쓰려고 저장해 둔 업로드 묶음. 실제 상품 데이터이므로 공개 저장소에 올리지 않는다.

샘플 하나는 파라미터 값 하나에서 뽑은 형상이다. 형상은 메쉬가 아니라 면마다 n×n 격자 점으로 기록한다(GRID_N = 9이므로 면당 81점). 같은 면 구성이면 샘플끼리 점 수가 같으므로, 뒤 티켓에서 꼭짓점을 1:1로 짝지을 수 있다는 것이 이 방식의 이유다.

핵심 개념 업로드 묶음의 형식은 schema/upload-bundle.schema.json 하나가 정한다. 애드인은 이 형식으로 만들고 서버는 이 형식으로 검사하므로, 두 쪽이 서로의 코드를 모른 채 같은 계약을 지킨다.
알려진 한계 면의 매개변수 범위는 트림 전 표면의 사각 범위다. 구멍이 있거나 둥근 면에서는 격자 점 일부가 면 밖에 찍힌다. 티켓 파일은 이것을 후속 과제로 적어 두었고, 이 문제는 뒤에 나온 경계 맞춤 격자(ADR-0016)로 풀린다.

핵심 아이디어

업로드는 "연결 확인 → 기본 형상 한 번 → 사용자 파라미터마다 5번 재계산 → 서버로 전송" 순서다. 사용자 파라미터가 W와 D 둘이면 Fusion은 재계산을 10번 한다.

W의 기본값이 800 mm라면 샘플 값은 기본값에 0.5, 0.75, 1.0, 1.25, 1.5를 곱한 400, 600, 800, 1000, 1200이다. 각 값에서 Fusion이 면마다 격자 점을 찍어 주면 샘플이 된다. 재계산이 실패한 값(예: 1200)은 점 없이 recompute_failed로만 기록하고 다음 값으로 간다.

업로드 한 번의 흐름(예시 데이터)

운영자가 "구성기 업로드" 클릭
GET /health
서버 연결 시험
W=400, 600, 800, 1000, 1200
Fusion 재계산과 격자 점 찍기
업로드 묶음 JSON
POST /uploads: 스키마와 점 수 검사
id: 3f9a…
저장, 이어서 녹화 요청
Fusion 없이 시험하는 방법 Fusion API를 쓰는 코드는 얇은 어댑터에만 있다. 애드인 핵심(run_upload)은 FusionModel과 ServerClient라는 두 인터페이스(Protocol)에만 기대므로, 시험에서는 가짜 모델과 가짜 서버를 끼워 Fusion 없이 돌린다. 반대로 실제 Fusion 어댑터는 이 환경에서 한 번도 실행하지 못했다. 티켓은 이 점을 사람이 확인할 남은 인수 조건으로 남겼다.
값이 아니라 수식을 되돌린다 스윕이 끝나면 파라미터를 값(800)이 아니라 원래 수식(W / 2 같은 것)으로 되돌린다. 값으로 덮어쓰면 자식 치수와 부모 치수의 수식 관계가 상수로 굳어 버린다(ADR-0003).

코드 따라가기

흐름: 애드인 진입점 → 연결 시험 → 파라미터와 부품 수집 → 단독 스윕 → HTTP 전송 → 서버의 스키마와 점 수 검사 → 저장 → 녹화본 복사 → 안내서.

1. 진입점: 버튼과 실행 핸들러

애드인 진입점은 "구성기 업로드" 버튼을 추가한다. 눌렀을 때 실행되는 핸들러는 활성 문서가 디자인인지 확인하고, 실제 Fusion 어댑터와 HTTP 클라이언트를 run_upload에 꽂는다. 예외는 메시지 상자로 보여 준다.

addin/ConfiguratorUploader/ConfiguratorUploader.py:21-36

class _ExecuteHandler(adsk.core.CommandEventHandler):

핸들러 참조를 모듈 전역 목록 _handlers(addin/ConfiguratorUploader/ConfiguratorUploader.py:18)에 붙들어 두는 것은 코드 주석이 적은 대로 가비지 컬렉션으로 이벤트가 멈추지 않게 하려는 것이다.

2. 애드인 핵심: 연결 시험부터 묶음 조립까지

run_upload는 이 티켓의 중심이다. 서버가 응답하지 않으면 스윕을 시작하지 않고 운영자에게 알린 뒤 None을 돌려준다. 재계산이 수십 번 일어나는 긴 작업을 연결도 안 된 채로 시작하지 않으려는 순서다(이 이유는 코드 주석이 아니라 첫 인수 조건에서 읽은 것이다).

addin/ConfiguratorUploader/uploader/core.py:97-125

def run_upload(
    model: FusionModel,
    server: ServerClient,
    notify: Callable[[str], None],
) -> str | None:
    if not server.ping():
        notify("서버에 연결할 수 없습니다. 스윕을 시작하지 않았습니다.")
        return None
    parameters = model.parameters()
    baseline = model.sample_faces(GRID_N)
    bundle = {
        "schema_version": SCHEMA_VERSION,
        "units": "mm",
        "grid": {"n": GRID_N},
        "parts": _parts(model.bodies(), baseline),
        "baseline": {"faces": _faces_json(baseline)},
        "sweeps": [_sweep(model, p) for p in parameters if p.is_user],
        "parameters": [
            # elided: 파라미터마다 name, value, unit, expression, is_user를 담은 딕셔너리
        ],
    }
    return server.upload(bundle)

스윕은 is_user가 참인 파라미터에만 한다. 모델 파라미터(스케치 치수 d12 같은 것)는 묶음의 parameters에는 들어가지만 스윕하지 않는다.

3. 부품 만들기

부품은 기본 형상 면 목록의 위치로 면을 가리킨다. 컴포넌트가 있으면 컴포넌트 이름이 부품 이름이고(kind: "component"), 컴포넌트가 없는 바디는 바디 이름이 부품 이름이다(kind: "body").

addin/ConfiguratorUploader/uploader/core.py:52-61

def _parts(bodies: list[BodyInfo], faces: list[FaceSample]) -> list[dict[str, Any]]:
    """부품은 컴포넌트 단위, 컴포넌트가 없는 바디는 바디 단위다(ADR-0006)."""
    component_of = {b.name: b.component for b in bodies}
    parts: dict[str, dict[str, Any]] = {}
    for index, face in enumerate(faces):
        component = component_of[face.body]
        name, kind = (component, "component") if component is not None else (face.body, "body")
        part = parts.setdefault(name, {"name": name, "kind": kind, "faces": []})
        part["faces"].append(index)
    return list(parts.values())

실제 Fusion 어댑터는 이름 충돌을 피하려고 오커런스(컴포넌트 인스턴스)의 전체 경로 이름을 부품 이름으로 쓴다(addin/ConfiguratorUploader/uploader/fusion_model.py:41-62). 그래서 같은 컴포넌트를 좌·우 측판으로 두 번 넣으면 서로 다른 부품이 된다. 티켓은 이것이 ADR-0006의 "컴포넌트 단위"를 인스턴스 단위로 해석한 것이라 확인이 필요하다고 적었다.

4. 단독 스윕

스윕 위치는 기본값에 곱하는 비율 다섯 개로 고정이다. 값마다 재계산이 성공했는지 확인하고, 성공한 값에서만 격자 점을 찍는다. 끝나면 수식을 되돌린다.

addin/ConfiguratorUploader/uploader/core.py:76-94

def _sweep(model: FusionModel, parameter: ParameterInfo) -> dict[str, Any]:
    values = [parameter.value * factor for factor in SWEEP_FACTORS]
    samples = []
    for value in values:
        recomputed = model.set_parameter(parameter.name, value)
        samples.append(
            {
                "value": value,
                "status": "ok" if recomputed else "recompute_failed",
                "faces": _faces_json(model.sample_faces(GRID_N)) if recomputed else [],
            }
        )
    # 값이 아니라 원래 수식을 되돌린다. 수식으로 묶인 자식 관계를 상수로 덮지 않기 위해서다(ADR-0003).
    model.restore_parameter(parameter)
    return {
        "parameter": parameter.name,
        "range": {"min": values[0], "max": values[-1]},
        "samples": samples,
    }

비율 SWEEP_FACTORS = (0.5, 0.75, 1.0, 1.25, 1.5)는 addin/ConfiguratorUploader/uploader/core.py:66에 있다. 주석대로 비선형 구간을 더 나누는 적응형 샘플과 재계산 실패에 따른 범위 축소는 이 티켓의 범위가 아니다(티켓 05).

5. Fusion 어댑터: 재계산 판정과 격자 점

Fusion에서는 파라미터를 바꾼 뒤 타임라인에서 오류 상태인 피처 수를 센다. 업로드 시작 때의 오류 수보다 늘었으면 재계산 실패로 본다. 이미 있던 오류는 실패로 세지 않는다.

addin/ConfiguratorUploader/uploader/fusion_model.py:67-77

    def set_parameter(self, name: str, value: float) -> bool:
        parameter = self._design.allParameters.itemByName(name)
        unit = self._bundle_unit(parameter.unit)
        try:
            if unit in ("mm", "deg"):
                parameter.expression = f"{value} {unit}"
            else:
                parameter.value = value
        except Exception:
            return False
        return self._error_count() <= self._initial_errors

격자 점은 면의 매개변수 범위 (u0..u1, v0..v1)를 n등분한 (u,v)마다 getPointsAtParameters로 구한다. Fusion의 길이는 내부 단위 cm이므로 10을 곱해 mm로 담는다.

addin/ConfiguratorUploader/uploader/fusion_model.py:128-143

    evaluator = face.evaluator
    box = evaluator.parametricRange()
    u0, v0 = box.minPoint.x, box.minPoint.y
    u1, v1 = box.maxPoint.x, box.maxPoint.y
    params = [
        adsk.core.Point2D.create(
            u0 + (u1 - u0) * i / (grid_n - 1),
            v0 + (v1 - v0) * j / (grid_n - 1),
        )
        for i in range(grid_n)
        for j in range(grid_n)
    ]
    ok, points = evaluator.getPointsAtParameters(params)
    if not ok:
        raise RuntimeError(f"면의 격자 점을 계산하지 못했습니다: {face.body.name}")
    return [(p.x * _CM_TO_MM, p.y * _CM_TO_MM, p.z * _CM_TO_MM) for p in points]

이 함수는 Fusion 밖에서 실행해 본 적이 없다. 티켓의 구현 기록은 처음 Fusion에서 돌릴 때 확인할 것으로 어셈블리 프록시 면의 좌표, getPointsAtParameters 반환 형식, 재계산 실패 판정이 맞는지를 꼽았다.

6. 전송: 표준 라이브러리 HTTP 클라이언트

연결 시험은 5초, 업로드는 120초 제한이다. 연결 시험 실패는 예외 대신 False로 돌려서 핵심이 운영자에게 메시지를 줄 수 있게 한다.

addin/ConfiguratorUploader/uploader/server_client.py:16-31

    def ping(self) -> bool:
        try:
            with urllib.request.urlopen(f"{self._base_url}/health", timeout=_PING_TIMEOUT_S) as r:
                return bool(r.status == 200)
        except (urllib.error.URLError, OSError):
            return False

    def upload(self, bundle: dict[str, Any]) -> str:
        request = urllib.request.Request(
            f"{self._base_url}/uploads",
            data=json.dumps(bundle, ensure_ascii=False).encode("utf-8"),
            headers={"Content-Type": "application/json"},
            method="POST",
        )
        with urllib.request.urlopen(request, timeout=_UPLOAD_TIMEOUT_S) as r:
            return cast(str, json.loads(r.read())["id"])

7. 서버: 검사하고 저장한다

서버는 두 단계로 묶음을 검사한다. 먼저 공유 JSON Schema로 형식을 보고, 형식이 맞으면 면마다 점 수가 grid.n의 제곱인지 확인한다. 스키마만으로는 "배열 길이가 다른 필드 값의 제곱"이라는 관계를 적을 수 없어서 점 수는 코드로 본다(이 이유는 모듈 docstring의 "형식은 공유 JSON Schema, 격자 점 수는 여기서 확인한다"에서 읽었다).

server/bundle.py:22-35

def bundle_errors(bundle: dict[str, Any]) -> list[str]:
    """업로드 묶음의 문제를 사람이 읽을 문장으로 돌려준다. 문제가 없으면 빈 목록."""
    errors = [
        f"{'/'.join(str(p) for p in e.absolute_path) or '(최상위)'}: {e.message}"
        for e in _validator.iter_errors(bundle)
    ]
    if errors:
        return errors
    expected = bundle["grid"]["n"] ** 2
    return [
        f"{where} 바디 {face['body']}: 면의 점 {len(face['points'])}개가 격자 {expected}개와 다릅니다"
        for where, face in _all_faces(bundle)
        if len(face["points"]) != expected
    ]

검사를 통과한 묶음은 무작위 id(uuid4().hex)로 uploads/ 아래에 저장하고, 실패하면 422와 오류 문장 목록을 돌려준다.

server/app.py:33-43

    @app.post("/uploads", status_code=201)
    def create_upload(bundle: dict[str, Any] = Body()) -> dict[str, str]:
        errors = bundle_errors(bundle)
        if errors:
            raise HTTPException(status_code=422, detail=errors)
        upload_id = uuid.uuid4().hex
        uploads_dir.mkdir(parents=True, exist_ok=True)
        (uploads_dir / f"{upload_id}.json").write_text(
            json.dumps(bundle, ensure_ascii=False), encoding="utf-8"
        )
        return {"id": upload_id}

8. 녹화본 내보내기와 저장 위치

녹화는 저장된 업로드를 녹화 폴더에 복사하는 것이다. 요청의 name은 영문, 숫자, _, -, 한글만 허용해서 경로 문자(/, .)가 들어가 저장 폴더 밖에 쓰는 일을 막는다(정규식 server/app.py:16).

server/app.py:49-55

    @app.post("/uploads/{upload_id}/recording", status_code=201)
    def record_upload(upload_id: str, request: RecordingRequest) -> dict[str, str]:
        source = upload_path(upload_id)
        recordings_dir.mkdir(parents=True, exist_ok=True)
        target = recordings_dir / f"{request.name}.json"
        target.write_text(source.read_text(encoding="utf-8"), encoding="utf-8")

업로드를 시작하자마자 server.ping()을 호출하고 실패하면 곧바로 끝낸다. 이 순서의 이유로 가장 알맞은 것은?

사용자 파라미터마다 재계산이 5번이고 그동안 Fusion 화면이 멈춘다. 긴 작업을 끝낸 뒤에야 연결 실패를 아는 일을 피하는 순서다. 스키마 검사는 서버 쪽 일이고, 파라미터 읽기는 서버와 무관하다.

파라미터 D의 수식이 W / 2이고, 스윕 뒤 restore_parameter가 수식 대신 값 400으로 D를 되돌렸다고 하자. 그 뒤 W를 바꾸면 D는 어떻게 될까?

값으로 덮으면 D의 수식이 상수 400으로 바뀌어 W와의 관계가 끊긴다. 그래서 코드는 값이 아니라 원래 수식 문자열을 되돌린다(ADR-0003).

서버는 JSON Schema 검사를 통과한 뒤에도 면마다 점 수가 grid.n의 제곱인지 따로 센다. 스키마에 넣지 않은 이유로 가장 알맞은 것은?

면의 점 수는 같은 문서 안의 다른 필드 값(grid.n)에 따라 정해진다. JSON Schema의 길이 제한은 고정된 숫자만 받으므로 이 관계는 코드가 센다.

녹화 요청의 name이 ../../app이었다면 어떻게 될까?

name은 ^[A-Za-z0-9_\-가-힣]+$만 허용한다. 점과 슬래시가 들어 있으면 요청 모델 검사에서 거절되어 녹화 폴더 밖에는 아무것도 쓰이지 않는다.

어떤 사용자 파라미터의 기본값이 0이면 _sweep이 만드는 범위는 어떻게 될까?

샘플 값은 기본값에 비율을 곱해 만드므로 0에 무엇을 곱해도 0이다. 범위가 한 점으로 퇴화한다. 녹화 안내서가 기본값이 0이 아닐 것을 필수 조건으로 적은 이유다.

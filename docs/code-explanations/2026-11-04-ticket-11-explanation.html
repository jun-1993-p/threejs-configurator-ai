티켓 11: 위상 묶음

폭 슬라이더를 끌다가 칸막이 수가 바뀌는 지점을 넘으면, 구성기가 형상을 섞지 않고 새 면 구성으로 한 번에 바꿔 끼우도록 스윕을 위상 묶음으로 나눈 변경이다.

jun-1993-p/threejs-configurator-ai 티켓 11 (커밋 771e02e), 2026-11-04에 설명함. References link to this commit.

배경

이 프로젝트가 처음이라면: 깊은 배경을 펼치세요.

프로젝트는 Fusion CAD 모델을 쇼핑몰 페이지의 div 안에서 도는 three.js 구성기로 바꾼다. 고객이 슬라이더를 움직이면 상품 형태가 바뀐다. 구성기는 업로드 때 CAD 애드인이 파라미터 값을 바꿔 가며 Fusion에서 미리 뽑아 둔 형상을 쓴다. 이 묶음이 스윕이다. 파라미터 하나만 움직이고 나머지는 기본값으로 둔 것이 단독 스윕이다.

구성기는 샘플 사이를 보간한다. 샘플마다 꼭짓점이 몇 개 있는지, 어느 꼭짓점이 어느 꼭짓점과 짝인지 알아야 하므로, 모든 샘플은 같은 면 구성(바디와 면 이름의 집합, 그리고 면마다 점 수)을 가져야 한다. 슬라이더 두 개를 함께 움직이면 각 단독 스윕에서 읽은 꼭짓점 이동량을 더해 형상을 만든다(ADR-0004). 이 계산을 하는 모듈이 변형 엔진이다. 엔진은 구성기(브라우저)와 검증기(Node)가 같은 파일을 쓴다.

이 변경이 건드리는 좁은 범위는 이렇다. 칸막이 선반처럼 폭에 따라 칸막이 개수가 달라지는 상품은 폭 슬라이더의 범위 안에서 면 구성이 바뀐다. 칸막이가 새 바디로 생기기 때문이다. 이전 커밋(티켓 10)까지는 이런 지점을 만나면 애드인이 범위를 그 앞에서 잘라 버리거나 엔진이 오류를 던졌다. 엔진 코드에 그 자리 표시가 남아 있었다. 

function topologyChanged(id: string, value: number) {
  // 위상 묶음(ADR-0005)은 티켓 11에서 다룬다. 범위 끝의 위상 변화는 애드인이 범위를 줄여 샘플에서 뺀다(티켓 10). 그 전까지는 면 구성이 다른 샘플을 받지 않는다.
  return new Error(`슬라이더 ${id}: 값 ${value}의 샘플이 기본 형상과 면 구성이 다릅니다(위상 묶음은 아직 지원하지 않음)`);
}

ADR-0005가 정한 방향은 이렇다. 연속 슬라이더가 범위 안에서 위상 경계를 넘으면 스윕을 위상 묶음으로 나누고, 이동량은 같은 묶음 안에서만 섞고, 경계에서는 형상이 페이드 없이 바로 바뀐다. 슬라이더는 매끄럽게 계속 움직이지만 칸막이는 한 번에 나타난다.

용어

위상 묶음은 면 구성이 같은 스윕 결과의 모음이다. 기본값이 든 묶음이 기본 묶음이다. 기준 형상은 이동량을 재는 출발점이다. 기본 묶음에서는 기본 형상이고, 다른 묶음에서는 그 묶음 가운데에 가장 가까운 샘플의 형상이다. 삼각형 연결도 기준 형상에서 정한다. 위상 경계는 개수형 파라미터 값과 함께 면 구성이 바뀌는 슬라이더 값이다.

핵심 아이디어

꼭짓점 수가 다른 형상끼리는 이동량을 더할 수 없다. 그래서 면 구성이 같은 묶음마다 자기 기준 형상과 이동량을 따로 두고 묶음 안에서만 섞으며, 경계에서는 섞지 않고 형상을 통째로 바꾼다. 시험용 합성 녹화본인 칸막이 선반으로 보자. 칸 수는 bays = floor(shelf_w / 400 mm) + 1이다. 슬라이더 shelf_w(전체 폭)의 기본값은 900 mm이고 명세 범위는 500~1300 mm다. 폭 800과 1200에서 칸 수가 바뀐다. 티켓 기록에 따르면 애드인이 450~1350을 스윕하고(용어집의 스윕 범위는 기본값의 ±50%) 이렇게 나눈다.

묶음마다 필요한 것은 두 가지다. 기준 형상과, 그 기준 형상에서 다시 뽑은 나머지 슬라이더(여기서는 shelf_d, 전체 깊이)의 단독 스윕이다. 4칸 형상에 깊이 변화를 더하려면 깊이 이동량이 4칸 형상의 꼭짓점 기준이어야 하기 때문이다. 기본 형상 기준의 이동량은 꼭짓점 수가 달라 더할 수 없다.

경계에는 두 규칙이 있다. 애드인은 경계를 0.2 mm 안으로 좁혀서 경계 양쪽에 샘플을 하나씩 둔다. 코드 주석은 이 폭을 치수 합격선(0.2 mm)과 같은 값이라고 적는다. 엔진은 틈에 든 값을 가까운 쪽 묶음에 넣는다. 틈 가운데가 경계가 된다.

묶음 상한

묶음은 파라미터당 4개(기본 묶음 포함)까지다. 묶음마다 나머지 슬라이더의 단독 스윕을 따로 뽑아야 하기 때문이다(ADR-0005, 위상 변화는 위상 묶음으로 나눠 다룬다). 넘으면 기본값에서 먼 묶음부터 빼고 범위를 그 경계 앞에서 줄이며, 피드백 종류 topology_group_limit을 남긴다. 위상 묶음은 명세에는 적히지 않는다. 명세는 슬라이더 범위만 말하고, 묶음은 스윕 데이터에 있다.

코드 따라가기

흐름: 애드인이 스윕을 묶음으로 나눔 → 서버가 묶음별 기준 형상으로 업로드 묶음을 검사 → 조립이 슬라이더가 닿는 묶음만 추림 → 엔진이 묶음마다 기준 형상과 이동량을 만듦 → 구성기가 묶음이 바뀔 때 메쉬를 교체.

2. 서버: 샘플을 자기 묶음의 기준 형상과 짝짓는다

업로드 묶음 스키마에 groups가 생겼다. 서버는 샘플의 점 수를 검사하려고 샘플의 면을 기준 형상의 면과 짝짓는다. 4칸 묶음의 샘플은 기본 형상과 면 구성이 달라 짝지어지지 않으므로, 이제 서버는 샘플 값이 든 묶음을 찾아 그 묶음의 기준 형상과 짝짓는다.

4. 변형 엔진: 묶음마다 하나씩 만들고, 값이 든 묶음으로 계산한다

이전의 createMorph는 기본 형상 하나만 알았다. 이 변경에서 묶음 하나를 만드는 일은 createGroupMorph(configurator/src/engine.ts:157)로 분리됐다. 인자 samplesOf가 슬라이더마다 이 묶음의 단독 스윕 샘플을 돌려준다. 기본 묶음에서는 위상 묶음에 든 샘플을 뺀다.

createMorph(configurator/src/engine.ts:258)는 기본 묶음을 만들고, 묶음이 있는 슬라이더마다 묶음별 범위(GroupSpan)를 모은다. 값이 어느 묶음에 드는지는 groupFor(configurator/src/engine.ts:301)가 정한다.

configurator/src/engine.ts:301-309

  const groupFor = (values: Record<string, number>): GroupMorph => {
    for (const { id, defaultValue, spans } of grouped) {
      const value = values[id] ?? defaultValue;
      const gap = (span: GroupSpan) => Math.max(span.min - value, value - span.max, 0);
      const nearest = spans.reduce((best, span) => (gap(span) < gap(best) ? span : best));
      if (nearest.morph !== main) return nearest.morph;
    }
    return main;
  };

gap이 0이면 값이 묶음 안이다. 경계 양쪽 샘플 사이 틈에서는 gap이 작은 쪽이 이기므로 틈의 가운데가 경계가 된다. 슬라이더가 둘 이상 기본 묶음 밖일 때는 명세 순서로 앞 슬라이더의 묶음을 따른다. 티켓 기록은 두 슬라이더가 동시에 경계를 넘는 명세를 범위 검증이 거른다고 적었다.

마지막으로 shape(configurator/src/engine.ts:311)이 값이 든 묶음의 기준 위치에 그 묶음의 이동량을 더해 MorphShape를 낸다. 같은 묶음이면 faces와 triangles는 매번 같은 객체다. 구성기는 이 동일성으로 묶음이 바뀌었는지 안다.

configurator/src/engine.ts:311-317

  const shape = (values: Record<string, number>): MorphShape => {
    const morph = groupFor(values);
    const out = Float64Array.from(morph.base);
    for (const track of morph.tracks) addDelta(out, track, values[track.id] ?? track.defaultValue);
    for (const grid of morph.grids) addResidual(out, grid, grid.ids.map((id, k) => values[id] ?? grid.defaults[k]) as [number, number]);
    return { faces: morph.faces, triangles: morph.triangles, base: morph.base, positions: out };
  };

칸막이 선반 결과물을 Chrome에서 열어 폭 600, 900, 1300에서 칸막이가 1, 2, 3개로 바뀌고 콘솔 오류가 없음을 확인했다고 티켓 기록에 적혀 있다.

6. 시험: 경계 양쪽에서 실제 녹화 형상과 맞는다

엔진 시험은 칸막이 선반 합성 녹화본에서 경계 바로 안팎의 바디 목록을 확인한다.

퀴즈

애드인은 위상 경계를 0.2 mm 안으로 좁히고 경계 양쪽에 샘플을 하나씩 남긴다. 경계에서 형상을 섞지 않고 바로 바꾸는 구성기에서, 이렇게 좁게 잡는 이유로 가장 맞는 것은?

경계에서는 보간하지 않고 가까운 쪽 샘플 형상으로 바뀌므로, 샘플과 경계 사이 거리가 곧 화면의 오차다. 좁은 폭은 샘플과 경계 사이 거리를 줄인다(이 풀이는 내 해석이다). 코드 주석은 이 폭을 치수 합격선(0.2 mm)과 같은 값으로 잡았다고 적는다. 칸막이는 서서히 나타나지 않고 한 번에 나타난다(ADR-0005). 면 짝짓기 비용은 폭과 상관없다.

엔진이 4칸 묶음에서도 깊이 슬라이더(shelf_d)의 이동량을 기본 형상 기준 단독 스윕에서 가져온다고 하자. 폭 1250에서 깊이를 바꾸면 어떻게 되는가?

이동량은 기준 형상의 꼭짓점 순서에 맞춘 숫자 배열이다. 기본 형상(3칸)과 4칸 형상은 바디 수가 달라 꼭짓점 수와 짝이 다르므로 배열이 대응하지 않는다. 엔진에는 꼭짓점을 다시 짝짓는 기능이 없고, 그래서 묶음마다 자기 기준 형상에서 단독 스윕을 따로 뽑는다.

구성기의 update에서 shape.faces !== shown.faces 분기를 지우고 항상 위치 버퍼만 갱신하게 하면, 폭 슬라이더가 800을 넘는 순간 무엇이 깨지는가?

메쉬는 면 구성마다 만든 인덱스와 위치 버퍼를 가진다. 묶음이 바뀌면 꼭짓점 수와 연결이 달라지는데, 이전 메쉬를 그대로 두고 값만 덮어쓰면 새 칸막이 바디가 없거나 배열 길이가 맞지 않는다. 슬라이더 입력은 별개의 UI이므로 멈추지 않고, 서서히 나타나는 일도 없다.

기본값 900인 폭 슬라이더에서, 왼쪽으로 600과 450에서 시작하는 묶음 둘, 오른쪽으로 1100과 1300에서 시작하는 묶음 둘이 발견되었다. 기본 묶음까지 5개다. 상한 4를 맞추려면 어떻게 되는가?

애드인은 기본값에서 먼 묶음부터 하나씩 뺀다. 거리는 묶음 안 첫 점과 기본값 사이로 재며, 450 묶음이 기본값에서 450 mm로 가장 멀다(1300 묶음은 400 mm). 뺀 쪽 범위는 그 경계 안쪽 점으로 줄고 topology_group_limit 기록이 검증 피드백으로 나온다. 업로드가 거절되지는 않는다.

칸막이 선반 명세의 폭 슬라이더 범위를 600~1000으로 좁혔다. 4칸 묶음(1200.04~1350)은 조립 때 어떻게 다뤄지는가?

조립의 engineSweeps는 reaches가 참인 묶음만 남긴다. 4칸 묶음은 범위 1200.04~1350이 슬라이더 최댓값 1000보다 커서 닿지 않으므로 빠지고, 수치 검증과 범위 검증도 그 묶음을 보지 않는다. 오류나 피드백 대상이 아니라 정상적인 걸러내기다.

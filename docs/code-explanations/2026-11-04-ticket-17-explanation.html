티켓 17: 자식 치수의 부모 고르기와 슬라이더 이름

고객이 바꾸길 원하는 치수가 수식에 묶인 자식 파라미터일 때, 운영자가 후보 선택에서 움직일 부모를 고르게 하고, 슬라이더 이름은 Fusion 파라미터 이름 대신 고객이 보는 치수의 뜻으로 짓게 한다.

배경

이 영역이 처음이면 펼쳐서 읽는 기본 배경

이 프로젝트는 Fusion 360 CAD 모델을 쇼핑몰 페이지의 three.js 구성기(div)로 바꾼다. 고객은 슬라이더로 상품 형태를 바꾼다. 슬라이더 하나는 Fusion의 사용자 파라미터 하나(부모 파라미터)에 연결된다.

Fusion에서는 파라미터의 값을 수식으로 쓸 수 있다. 예를 들어 d5 = body_w - 40 mm라고 쓰면 d5는 body_w를 따라 자동으로 바뀐다. 이 문서는 따라 바뀌는 쪽을 자식 파라미터, 따라가는 쪽을 부모 파라미터라고 부른다(용어집 기준).

업로드할 때 CAD 애드인은 파라미터 값을 바꿔 가며 형상을 뽑아 둔다. 이 묶음을 스윕이라 하고, 파라미터 하나만 움직인 것을 단독 스윕이라 한다. 구성기의 변형 엔진은 스윕에서 꼭짓점 이동량을 읽어 섞을 뿐이고(ADR-0002), Fusion 수식은 풀지 않는다(ADR-0003).

서버 쪽 파이프라인은 상품 하나를 정해진 순서의 단계로 처리하고, AI는 단계 안에서만 일한다(ADR-0014). 이 변경이 닿는 단계는 후보 제시, 후보 선택, 명세 작성이다. 후보 제시에서 AI가 슬라이더 구성 후보 2~4개를 내면, 후보 선택에서 사람(운영자)이 하나를 고른다. 화면의 후보 한 칸을 후보 카드라 부른다.

변경 전 후보는 parents, 곧 움직일 부모 파라미터 이름 목록이었다. 이전의 후보 검사는 스윕하지 않은 파라미터를 반려했으므로, 고객이 원하는 치수가 d5처럼 스윕하지 않는 자식 파라미터이면 후보에 담을 수 없었다. 후보에는 슬라이더 이름이 없었고 이름은 명세에만 있었다. 명세는 AI가 쓰는 JSON이고, 슬라이더마다 id(움직일 부모 파라미터), name, children을 가진다.

이 문서에서 쓰는 말은 다섯 가지다. 먼저 자식 치수는 고객이 원하는 치수가 자식 파라미터인 경우다. 부모 후보는 그 자식을 바꾸려고 움직일 수 있는 스윕한 부모들이고, 운영자가 후보 선택에서 하나를 고른다. 같이 변하는 치수는 부모를 움직였을 때 슬라이더 자신의 치수 말고 함께 바뀌는 치수다. 축 반응은 이 변경에서는 AI 입력에 실린 값(response), 곧 단독 스윕에서 상품 전체와 부품의 Fusion 축별 크기·위치 변화량을 가리킨다. 마지막으로 명세의 children는 슬라이더 부모를 따르는 파라미터를 적는 기록용 칸이다.

핵심 개념

수식은 읽기만 하고 풀지 않는다. 부모 후보를 찾는 일도 같이 변하는 치수를 찾는 일도, 수식의 낱말을 파라미터 이름과 맞춰 관계를 잇고 스윕이 담은 형상으로 변화를 재는 방식으로만 한다(ADR-0003).

핵심 아이디어

서랍 폭 예시로 보자. 용어집의 예처럼 서랍 폭이 d5 = body_w - 40 mm라는 자식 파라미터이고, 스윕한 파라미터는 부모인 body_w라고 하자(티켓 기록의 서랍장 합성 녹화본에서도 d5의 부모 후보는 body_w다). 고객이 "서랍 폭"을 바꾸고 싶다면 실제로 움직이는 것은 body_w다. 예를 들어 서랍 폭만이 아니라 서랍장 전체 폭도 같이 바뀐다고 하자(가정이다. 티켓의 카드 예시는 "전체 폭, 몸통 폭도 같이 변함"이다).

이 변경은 그 사실을 후보 카드에 드러내고 운영자에게 확인받는다. 명세에는 슬라이더 id가 부모 body_w로, children에 d5로 기록된다. 수식은 이번에도 읽기만 하고 풀지 않는다. 후보의 sliders는 [{ parameter, name }] 모양이고, 순서는 다음과 같다.

후보 제시: AI가 sliders 낸다
{ parameter: d5, name: 서랍 폭 }
후보 카드: 부모 후보와 같이 변하는 치수
부모 body_w 선택
후보 선택: 운영자가 부모 고름
{ parameter: d5, name, parent: body_w }
명세 작성: id는 부모, children에 d5

부모 후보가 여럿이면 선택이 필요하다. 합성 녹화본에서 d9의 부모 후보는 drawer_d와 body_d 두 개다. 카드에는 부모마다 같이 변하는 치수가 적히므로, 운영자는 그것을 보고 고른다.

경우부모 후보운영자가 할 일
파라미터가 스윕한 부모자기 하나없음
자식인데 스윕한 부모가 하나그 부모 하나없음(글로만 표시)
자식인데 스윕한 부모가 여럿예: drawer_d, body_d단추로 하나를 고름
자식인데 스윕한 부모가 없음없음후보 검사에서 반려

이름 쪽 규칙이다. 슬라이더 이름에 Fusion 파라미터 이름이 낱말로 들어 있으면 오류로 보고 AI에게 다시 묻는다. d6처럼 이름만으로는 무엇인지 알 수 없는 파라미터는, 단독 스윕의 축 반응을 AI에게 함께 보내 그 반응(예: 서랍 Z 치수만 100 mm 변함)을 보고 이름을 짓게 한다.

남긴 한계

같이 변하는 치수에서 슬라이더 자신을 빼는 비교는 이름이 같은지로만 한다. 자식 치수가 어느 부품의 어느 치수인지는 수식을 풀어야 알 수 있기 때문이다. AI가 지은 이름이 부품 역할 이름과 다르면("서랍 너비" 대 "서랍 폭") 자기 치수가 같이 변하는 목록에 한 번 더 적힐 수 있다. 티켓 리뷰 기록에 남긴 항목이다.

1. 수식에서 부모 후보 찾기

새 파일 parameter-relations.ts의 parameterRelations가 모든 관계의 출발점이다. 수식의 낱말 중 파라미터 이름과 같은 것을 "이 파라미터가 쓰는 파라미터"로 모으고(25행), 스윕했으며 개수형이 아닌 파라미터를 슬라이더가 될 수 있는 것으로 본다(28행). parentOptions는 이름이 이미 슬라이더가 될 수 있으면 자기 하나를, 아니면 수식을 거슬러 닿는 슬라이더 후보를 가까운 것부터 돌려준다(46행). 수식을 읽기만 하고 어느 값도 바꾸지 않는다.

configurator/pipeline/parameter-relations.ts:23-28

export function parameterRelations(bundle: BundleParameters) {
  const names = new Set(bundle.parameters.map((p) => p.name));
  const uses = new Map(bundle.parameters.map((p) => [p.name, wordsOf(p.expression).filter((w) => names.has(w) && w !== p.name)]));
  const counts = new Set(bundle.parameters.filter((p) => p.is_count).map((p) => p.name));
  const swept = new Set(bundle.sweeps.map((s) => s.parameter));
  const sliderable = (name: string) => swept.has(name) && !counts.has(name);

configurator/pipeline/parameter-relations.ts:44-51

후보 응답의 JSON Schema에서 parents(이름 문자열 목록)가 사라지고, parameter와 name을 가진 sliders가 들어왔다. 변경 전 줄은 아래와 같다.

후보 응답 스키마의 변경 전후 (일부 줄은 줄여 적음, 현재 코드는 schemas.ts:98 이후)

후보끼리 달라야 한다는 검사도 parents 대신 sliders의 parameter 집합을 본다(configurator/pipeline/schemas.ts:270-290).

3. 후보 검사: 쓸 수 없는 치수 걸러내기

candidateReferenceChecker의 parameterErrors는 슬라이더 하나가 쓸 수 있는 치수인지 순서대로 본다. 이미 쓴 파라미터, 개수형(값이 바뀌면 위상이 바뀌는 정수 파라미터), 업로드 묶음에 없는 이름, 스윕한 부모가 없는 자식을 거르고(341~345행), 마지막으로 그 자식의 부모 후보가 모두 같은 후보의 다른 슬라이더이면 움직일 부모가 없다고 반려한다(346~347행). 이름 검사 fusionNameError는 같은 위치에서 슬라이더 이름마다 돈다(353행).

configurator/pipeline/schemas.ts:339-348

  function parameterErrors(sliders: { parameter: string }[], k: number): string[] {
    const { parameter } = sliders[k];
    if (sliders.findIndex((s) => s.parameter === parameter) < k) return [`${parameter}를 이 후보에서 이미 썼습니다`];
    if (counts.has(parameter)) return [`${parameter}는 개수형 파라미터라 슬라이더 후보가 될 수 없습니다`];
    if (!parameterNames.has(parameter)) return [`${parameter}는 업로드 묶음의 파라미터가 아닙니다`];
    const options = relations.parentOptions(parameter);
    if (options.length === 0) return [`${parameter}는 스윕한 파라미터가 아니고, 수식으로 따르는 스윕한 부모도 없습니다`];
    const others = sliders.map((s) => s.parameter).filter((p) => p !== parameter && relations.sliderable(p));
    return options.every((o) => others.includes(o)) ? [`${parameter}를 바꿀 부모(${options.join(", ")})가 모두 이 후보의 다른 슬라이더입니다`] : [];
  }

fusionNameError(configurator/pipeline/schemas.ts:145-151)는 이름의 낱말을 대소문자 없이 파라미터 이름과 비교한다. 리뷰 뒤 이 검사를 넓혀 "D6 높이" 같은 이름도 걸리게 했다. 명세 검사(configurator/pipeline/schemas.ts:159-179)도 같은 함수를 쓴다.

4. 후보 카드: 부모 후보와 같이 변하는 치수

candidateCards는 슬라이더마다 choices를 만든다. 각 부모 후보에 대해 alsoChanges를 계산해 붙인다(136~140행). alsoChanges(configurator/pipeline/candidate-cards.ts:114-123)는 그 부모의 단독 스윕 반응에서 상품 전체와 부품의 W·D·H 크기 변화를 읽고, 부품 탐색이 찾은 역할 이름을 붙여 "전체 폭", "몸통 폭" 같은 이름으로 바꾼 뒤 슬라이더 자기 이름을 뺀다. 반응값은 0.2 mm를 넘을 때만 변화로 친다(sweepResponse, configurator/pipeline/parameter-relations.ts:82-104).

configurator/pipeline/candidate-cards.ts:126-152

export function candidateCards(candidates: Candidate[], bundle: UploadBundle, parts: PartsFound): CandidateCard[] {
  const colorOf = colorsOf(bundle);
  const relations = parameterRelations(bundle);
  const roles = new Map(parts.parts.map((p) => [p.name, p.role]));
  const roleOf = (part: string) => roles.get(part) ?? part;
  return candidates.map((candidate) => {
    const axes = axesFor(candidate.front, parts.up);
    const [front, top] = [directionOf(candidate.front), directionOf(parts.up)];
    const side = cross(top, front);
    const view: View = { eye: [0, 1, 2].map((c) => front[c] + 0.6 * side[c] + 0.5 * top[c]) as Vector, up: top };
    const choices = candidate.sliders.map(({ parameter, name }) => ({
      parameter,
      name,
      options: relations.parentOptions(parameter).map((parent) => ({ parent, alsoChanges: alsoChanges(bundle, parent, name, axes, roleOf) })),
    }));
    // 미리보기는 움직일 수 있는 부모마다 하나다. 자식 치수는 부모 후보마다 그려 운영자가 비교하고 고른다.
    const parents = [...new Set(choices.flatMap((c) => c.options.map((o) => o.parent)))];
    const spec = sweepSpec(bundle, parents);
    const morph = createMorph(spec, bundle);
    const previews = spec.sliders.map(({ id, min, max, default: value }) => {
      const values = [min, value, max];
      const images = renderPngs(values.map((v) => morph.shape({ [id]: v })), view, PREVIEW_SIZE, colorOf);
      return { parameter: id, values, images: images.map((png) => png.toString("base64")) };
    });
    return { ...candidate, axes, previews, choices };
  });
}

미리보기는 슬라이더마다가 아니라 움직일 수 있는 부모마다 하나를 그린다(141~143행). 운영자가 부모 후보를 눈으로 비교하고 고를 수 있게 하려는 것이다(티켓 기록).

5. 화면: 고르기 단추와 읽기

sliderHtml은 부모 후보가 하나면 글로만 적고, 여럿이면 부모마다 라디오 단추를 만들되 처음 것을 고른 상태로 둔다. 각 단추 옆에 그 부모가 바꾸는 치수가 같이 적힌다. readCandidateChoice는 부모 후보가 여럿인 슬라이더만 양식에서 읽고, 잘못된 값이면 pickParent의 오류 문장을 모아 돌려준다.

configurator/pipeline/operator-screens.ts:116-130

export function readCandidateChoice(
  form: URLSearchParams,
  cards: CandidateCard[],
): { candidate: string; parents: Record<string, string> } | { errors: string[] } {
  const card = cards.find((c) => c.id === form.get("candidate"));
  if (!card) return { errors: ["제시된 후보 중 하나를 고르세요"] };
  const parents: Record<string, string> = {};
  const errors: string[] = [];
  for (const choice of card.choices.filter((c) => c.options.length > 1)) {
    const picked = pickParent(choice, form.get(parentField(card.id, choice.parameter)) ?? undefined);
    if ("error" in picked) errors.push(picked.error);
    else parents[choice.parameter] = picked.parent;
  }
  return errors.length > 0 ? { errors } : { candidate: card.id, parents };
}

오류 문장을 만드는 pickParent(configurator/pipeline/candidate-cards.ts:72-78)는 화면과 실행기가 함께 쓴다. 부모 후보가 하나면 고르지 않아도 그 부모가 되고, 고르지 않았거나 후보 밖이면 "무엇을 움직일지 고르세요" 문장을 낸다.

6. 실행기: 고른 후보 만들기

chosenOf는 후보 카드와 운영자가 고른 부모로 ChosenCandidate를 만든다. 각 슬라이더에 parent를 붙이며, 두 슬라이더가 같은 부모를 움직이게 되면 오류 문장을 돌려준다(명세의 슬라이더 id는 겹칠 수 없기 때문이다). 실행기는 이 문장을 후보 선택 단계의 정지 사유로 쓴다(configurator/pipeline/runner.ts:506-507).

configurator/pipeline/runner.ts:238-248

function chosenOf({ previews: _previews, choices, ...candidate }: CandidateCard, parents: Record<string, string> = {}): ChosenCandidate | string {
  const sliders: ChosenSlider[] = [];
  for (const choice of choices) {
    const picked = pickParent(choice, parents[choice.parameter]);
    if ("error" in picked) return picked.error;
    // 명세의 슬라이더 id는 겹칠 수 없다
    if (sliders.some((s) => s.parent === picked.parent)) return `${picked.parent}를 두 슬라이더가 같이 움직이게 됩니다`;
    sliders.push({ parameter: choice.parameter, name: choice.name, parent: picked.parent });
  }
  return { ...candidate, sliders };
}

고른 후보를 따르는지는 chosenCandidateChecker가 슬라이더마다 본다. 슬라이더 id가 고른 부모여야 하고, name이 카드의 이름이어야 하며, 부모가 자식 치수와 다르면 children에 그 자식이 있어야 한다. 명세 검사 specReferenceChecker는 거기에 더해, children이 수식으로 그 슬라이더를 실제로 따르는 파라미터만 담는지 본다(descendants, configurator/pipeline/schemas.ts:159-179). 변형 엔진은 children을 읽지 않는다(엔진 시험이 확인).

퀴즈

자식 치수 d5(d5 = body_w - 40 mm)를 슬라이더로 노출하려는 후보가 있다. 명세의 슬라이더 id는 무엇이어야 하는가?

변형 엔진은 스윕한 파라미터의 이동량만 섞는다. 그래서 움직이는 것은 스윕한 부모 body_w이고, 고객이 보는 치수인 d5는 기록용 children에 적는다. chosenCandidateChecker가 정확히 이 대응을 본다.

한 후보가 슬라이더 "서랍 폭"(d5)과 "몸통 폭"(body_w)을 함께 노출한다. d5의 부모 후보는 body_w 하나뿐이다. 후보 검사 결과는?

d5를 바꿀 부모가 모두 같은 후보의 다른 슬라이더이므로 움직일 부모가 없다. 같은 부모를 두 슬라이더가 움직이면 명세의 슬라이더 id가 겹치기도 한다. 이 반려는 parameterErrors의 마지막 검사다.

운영자가 부모 후보 drawer_d와 body_d 중에서 고른다. 이 선택에 쓰는 정보로 가장 알맞은 것은?

화면의 단추 옆에는 부모마다 같이 변하는 치수가 적힌다. 부모마다 뜻 이름을 짓게 하면 AI가 고르지도 않은 부모의 이름까지 지어야 해서 두었고(티켓 기록), 수식을 풀어 계산하는 방식은 ADR-0003이 막는다.

파라미터 d6는 이름만으로 무엇인지 알 수 없다. AI가 이 슬라이더 이름을 지을 근거로 가장 알맞은 것은?

bundleForPrompt가 스윕마다 싣는 response에는 상품 전체와 부품의 축별 크기·위치 변화가 있다. d6를 움직였을 때 서랍 Z 치수만 100 mm 바뀐다면 이름을 서랍 높이로 지을 근거가 된다. 기본값은 어느 치수인지 말해 주지 않는다.

이 변경이 반복해서 지키는 원칙은?

부모 후보는 수식 낱말 매칭으로, 같이 변하는 치수는 스윕 형상으로 얻는다. 어느 쪽도 수식을 풀어 자식을 독립 파라미터로 바꾸지 않는다(ADR-0003). 자식을 스윕하지 않는 것은 결과이지 원칙이 아니고, 한 부모에 슬라이더를 모으지도 않는다.

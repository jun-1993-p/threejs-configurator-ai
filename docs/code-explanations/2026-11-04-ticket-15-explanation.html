티켓 15: LiteLLM 포트와 실제 명세 작성

각본으로 답하던 가짜 AI 대신 LiteLLM 프록시를 거친 실제 LLM이 명세를 쓰고, 검증 피드백을 받아 고치게 한 변경이다. 형식이 틀린 응답을 다시 묻는 기존 고리에 직전 답(rejected)과 직전 명세(previous)를 싣는다.

jun-1993-p/threejs-configurator-ai 티켓 15 (커밋 193f777), 2026-11-04에 설명함. References link to this commit.

배경

이 프로젝트가 처음이라면: 깊은 배경을 펼치세요.

프로젝트는 Fusion CAD 모델을 쇼핑몰 페이지의 div 안에서 도는 three.js 구성기로 바꾼다. 고정 코어와 변형 엔진은 사람이 관리하는 고정 코드이고, AI가 상품마다 쓰는 것은 명세(JSON)와 스타일 선택뿐이다(ADR-0001). 명세는 어떤 슬라이더를 어떤 범위로 노출할지 적은 파일이다. 파이프라인 실행기가 상품 하나를 정해진 단계 순서로 진행하며, AI는 단계 안에서 정해진 형식으로만 답한다(ADR-0014).

실행기에 넘기는 ports는 Fusion 연결, AI 모델, 저장소 셋이고, 사람 결정은 별도의 HumanPort가 맡는다. 시험에서는 포트를 가짜로 바꿔 끼운다. 이 티켓 전까지(부모 커밋 기준) AI 모델 포트의 구현은 단계마다 정해 둔 답을 차례로 내는 각본 AI(scripted-ai.ts)뿐이었다.

ADR-0015는 AI 모델을 외부 API(Cerebras의 무료 등급, 예비로 Groq)로 부르고, 외부 API를 쓸 수 없게 되면 로컬 모델로 바꿀 수 있게 하자고 정했다. 이 호출을 LiteLLM이 중계한다. LiteLLM 프록시는 OpenAI 호환 채팅 API 하나로 모델 호출을 중계한다. 그래서 코드가 모델을 직접 알 필요 없이 LiteLLM 설정의 model_name만 안다. ADR는 특정 외부 API나 로컬 환경에만 있는 기능에 기대지 말라고 요구한다.

AI 모델 포트에는 단계가 셋 있다. 후보 제시(candidates), UI 스타일 고르기(style), 명세 작성(spec). 이 티켓의 중심은 명세 작성이지만, 포트를 통째로 바꿔 끼우려면 세 메서드가 모두 있어야 하므로 후보 제시와 스타일 지시문도 함께 넣었다고 티켓 기록에 적혀 있다.

용어

형식 검사는 AI 응답을 JSON Schema와 명세 검사(상품명, 참조, 범위, 두께, 정면·축 대응)로 검사하는 일이다. 실패하면 오류 문장(schemaErrors)을 붙여 다시 묻는다. 검증 피드백은 형식은 맞는 명세를 조립해 재 본 뒤, 틀린 곳(path)과 고칠 값을 알리는 것이다. 둘은 단계가 다르다.

핵심 아이디어

실제 모델은 JSON을 코드 블록으로 감싸거나 {"$ref": …}를 값처럼 옮겨 적기도 했다(코드 주석, 티켓 기록). 이 변경의 핵심은 LiteLLM 포트가 모델의 문장을 JSON으로 읽기만 해서 실행기에 돌려주고, 판단은 모두 실행기의 형식 검사와 다시 묻기에 맡기는 것이다. 포트는 형식 검사와 다시 묻기를 하지 않는다. 입력을 요약해 지시문과 함께 묻고, 답을 JSON으로 읽어 돌려줄 뿐이다.

명세 작성 한 번의 길

실행기 writeSpec 호출
bundle 요약, intake, candidate, rules, previous, feedback, rejected
LiteLLM 프록시 (v1/chat/completions)
모델이 낸 문장
포트: 코드 블록을 벗기고 JSON으로 읽음
객체 또는 읽을 수 없는 문장
실행기: 형식 검사, 틀리면 다시 묻기

티켓 기록은 직전 명세가 없으면 실제 모델이 path가 가리키는 곳을 고칠 수 없다고 적었다. 그래서 입력에 previous와 rejected가 더해졌다. rejected를 더한 까닭은 기록에 없고, 지시문이 "rejected가 형식 검사에 걸린 직전 답이니 오류 위치를 고쳐 전체 답을 다시 낸다"고 안내하는 것으로 보아 같은 목적으로 보인다(내 추정).

입력 이름뜻어느 단계
rejected형식 검사에 걸린 직전 답세 단계 모두
previous검증 피드백을 받은 직전 명세명세 작성만

형식 재요청이 끼어도 previous는 피드백을 받은 명세 그대로다. 형식이 틀린 답은 rejected에만 들어간다.

수동 확인과 한계

티켓 기록에 따르면 합성 서랍장 녹화본과 로컬 Ollama의 qwen2.5:7b(LiteLLM 프록시 뒤)로 돌려 보았다. 7b 모델은 메모를 무시하고 슬라이더 여러 개짜리 후보만 내거나, 정면을 +X로 잡고 축 오류를 세 번 다시 물어도 못 고쳐 명세 단계에서 멈췄다. 형식 오류는 매번 다음 단계로 새지 않았다. 실제 상품과 실제 모델로 수치 검증까지 통과하는지 보는 확인은 이 커밋 시점에는 되어 있지 않다. 티켓 15의 마지막 체크박스가 비어 있고 상태는 사람 확인 대기(ready-for-human)다.

코드 따라가기

흐름: 실행기가 입력을 만듦 → LiteLLM 포트가 지시문과 함께 요청 → 모델의 문장을 JSON으로 읽음 → 실행기가 형식 검사 → 틀리면 직전 답과 오류를 붙여 다시 묻기 → 명세 검사에 정면·축 검사 추가.

3. 형식 오류 문장을 고칠 수 있게 쓴다

오류 문장 만드는 configurator/pipeline/schemas.ts:26에서, 값 목록(enum) 밖이면 고를 수 있는 값을 괄호로 붙인다. 실제 모델이 값 목록을 모른 채 같은 오류를 되풀이했기 때문이다(티켓 기록). 읽을 수 없는 답의 문장 UNREADABLE_ANSWER도 이 파일에 모았다.

configurator/pipeline/schemas.ts:26-36

function checker(schema: object): Check {
  const validate = ajv.compile(schema);
  return (value) =>
    validate(value)
      ? []
      : (validate.errors ?? []).map((e) => {
          // 값 목록 밖이면 고칠 수 있게 고를 수 있는 값을 붙인다
          const allowed = e.keyword === "enum" ? ` (${(e.params as { allowedValues: unknown[] }).allowedValues.join(", ")})` : "";
          return `${e.instancePath || ROOT}: ${e.message}${allowed}`;
        });
}

4. LiteLLM 포트: 묻고, 읽고, 돌려준다

configurator/pipeline/litellm-ai.ts:105는 OpenAI 호환 채팅 API 하나만 부른다. 단계마다 LiteLLM 설정의 model_name을 받는다. 주소에 경로가 붙어도(예: /litellm) 그 아래 채팅 API를 부르도록 주소 끝을 /로 맞춘다.

configurator/pipeline/litellm-ai.ts:105-123

export function liteLlmAi({ baseUrl, apiKey, models }: LiteLlmOptions): AiPort {
  // 주소에 붙은 경로(예: /litellm) 아래의 채팅 API를 부르도록 끝을 /로 맞춘다
  const chat = new URL("v1/chat/completions", baseUrl.endsWith("/") ? baseUrl : `${baseUrl}/`);
  async function ask(stage: AiStage, instructions: string, input: unknown): Promise<unknown> {
    const response = await fetch(chat, {
      method: "POST",
      headers: { "content-type": "application/json", ...(apiKey ? { authorization: `Bearer ${apiKey}` } : {}) },
      body: JSON.stringify({
        model: models[stage],
        messages: [
          { role: "system", content: instructions },
          { role: "user", content: JSON.stringify(input) },
        ],
      }),
    });
    if (!response.ok) throw new Error(`LiteLLM 호출 실패(${models[stage]}): ${response.status} ${await response.text()}`);
    const body = (await response.json()) as { choices: { message: { content: string } }[] };
    return readJson(body.choices[0].message.content);
  }

지시문은 단계마다 있고(후보 제시, 스타일, 명세 작성) 공통 출력 규칙이 뒤에 붙는다. 출력 규칙은 JSON Schema를 지시문 안에 적어 알린다. JSON 모드 같은 특정 API 기능에 기대지 않기 위해서다(ADR-0015). 스키마의 $ref는 풀어서 넣는다. configurator/pipeline/litellm-ai.ts:44가 같은 스키마 안의 참조를 값으로 바꾸고 $defs를 뺀다.

configurator/pipeline/litellm-ai.ts:44-54

function inlineRefs(schema: object): object {
  const defs = (schema as { $defs?: Record<string, unknown> }).$defs ?? {};
  const inline = (node: unknown): unknown => {
    if (Array.isArray(node)) return node.map(inline);
    if (node === null || typeof node !== "object") return node;
    const ref = (node as { $ref?: string }).$ref?.match(/^#\/\$defs\/(.+)$/);
    if (ref) return defs[ref[1]];
    return Object.fromEntries(Object.entries(node).filter(([key]) => key !== "$defs").map(([key, value]) => [key, inline(value)]));
  };
  return inline(schema) as object;
}

5. 업로드 묶음은 줄여서 보낸다

업로드 묶음은 4MB라 그대로 보내지 않는다. configurator/pipeline/litellm-ai.ts:21가 파라미터(이름·값·수식·사용자/개수형 여부), 부품별 기본 형상 바운딩 박스, 스윕 범위와 범위 축소 기록, 위상 묶음 수만 남긴다. 티켓 기록은 서랍장 녹화본 요청이 20KB 아래라고 적었다. 위상 묶음 수의 groups.length + 1은 groups가 기본 묶음 밖의 묶음이라서 기본 묶음 몫을 더한 것이다(코드 주석).

6. 모델의 문장을 JSON으로 읽는다

지시해도 답을 코드 블록으로 감싸는 모델이 있어, configurator/pipeline/litellm-ai.ts:97는 감싼 것을 벗긴다. 읽을 수 없으면 문장 그대로 돌려주어, 실행기의 형식 검사에 걸려 다시 묻게 한다.

configurator/pipeline/litellm-ai.ts:97-103

function readJson(content: string): unknown {
  try {
    return JSON.parse(content.match(CODE_BLOCK)?.[1] ?? content);
  } catch {
    return content;
  }
}

7. 명세 검사: 정면과 축 대응

수동 확인에서 정면이 +X인데 axes.W가 X인 명세가 제출까지 갔다. 축 반응 검증은 명세의 axes로 재기 때문에 어긋난 대응도 스스로 통과한다. 그래서 configurator/pipeline/schemas.ts:136를 명세 검사에 더했다. 깊이(D)는 정면 방향의 축이고, W·D·H는 서로 다른 축이어야 한다.

configurator/pipeline/schemas.ts:136-141

export function axesChecker(spec: Pick<Spec, "front" | "axes">): string[] {
  const { W, D, H } = spec.axes;
  if (new Set([W, D, H]).size < 3) return [`/axes: W·D·H는 서로 다른 축이어야 합니다(W ${W}, D ${D}, H ${H})`];
  const frontAxis = spec.front.slice(1);
  return D === frontAxis ? [] : [`/axes/D: 정면 ${spec.front} 쪽에서 보면 깊이는 ${frontAxis}축입니다(지금 ${D})`];
}

8. 시험과 수동 실행 도구

시험은 AI 모델 포트만 LiteLLM 구현으로 바꾸고 OpenAI 호환 가짜 HTTP 서버를 둔다. 서버는 단계별로 정해 둔 문장을 차례로 내고 받은 요청을 남긴다. 제출까지, 요청 내용, 읽을 수 없는 답, 검증 피드백, 피드백 중 형식 오류, 주소 경로, 코드 블록, LiteLLM 오류를 본다. 수동 실행은 node scripts/run-pipeline.ts에 환경 변수 LITELLM_URL·LITELLM_API_KEY·LITELLM_MODEL을 주어 돌린다.

퀴즈

LiteLLM 포트는 지시문에 넣을 JSON Schema에서 $ref를 풀어 값으로 바꾸고 $defs를 뺀다. 이렇게 하는 이유로 가장 알맞은 것은?

코드 주석과 티켓 기록의 설명이다. 작은 모델은 {"$ref": …}를 그 자리의 값 모양인 것처럼 답에 옮겨 적었다. 프록시가 거절한다는 근거나 속도 측정은 기록에 없다.

모델이 JSON 앞뒤에 마크다운 코드 블록 표시를 붙여 답했다. 내용은 스키마에 맞는다. 어떻게 처리되는가?

readJson이 답 전체를 감싼 코드 블록을 벗기고 JSON으로 읽는다. 읽은 결과가 스키마에 맞으면 실행기의 형식 검사도 통과한다. 읽을 수 없는 문장이어야만 문자열로 돌아가 다시 묻게 된다.

검증 피드백을 받은 뒤 AI가 새 명세를 냈는데 형식 검사에 걸려 다시 묻는다. 이때 writeSpec 입력의 previous와 rejected는 무엇인가?

previous는 검증 피드백을 받은 명세로 고정되어 있다. 형식 재요청 중에도 바뀌지 않는다. rejected는 형식 검사에 걸린 직전 답이다. 티켓 기록은 직전 명세(previous)가 있어야 모델이 path가 가리키는 곳을 고칠 수 있다고 적었다.

축 반응 검증이 있는데도 명세 검사에 정면과 축 대응(axesChecker)을 따로 더한 이유는?

축 반응 검증은 명세에 적힌 axes를 기준으로 형상을 잰다. 그래서 정면과 맞지 않는 axes도 그 기준으로 자기 일관되게 통과한다. 수동 확인에서 정면 +X인데 W가 X인 명세가 제출까지 갔고, 그 사례가 검사를 더하게 했다.

포트가 JSON Schema를 지시문에 적는 대신 한 제공자만 지원하는 JSON 모드로 출력을 강제한다고 하자. ADR-0015의 목적에 비추어 가장 큰 문제는?

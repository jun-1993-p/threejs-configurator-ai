티켓 30: 지시문의 개수를 응답 스키마에서 가져오기

후보 제시와 부품 탐색 지시문이 후보 수와 정면 수를 문장으로 따로 적던 것을 응답 스키마의 minItems와 maxItems에서 만들게 바꿔, 둘이 어긋나지 못하게 하고 그것을 시험이 지키게 한다.

배경

처음 보는 사람을 위한 배경

AI에게 JSON으로 답하게 하려면 두 가지를 함께 준다. 하나는 사람이 읽는 지시문(프롬프트)이고, 다른 하나는 코드가 답을 검사하는 응답 스키마(JSON Schema)다. 답이 스키마를 통과하지 못하면 실행기가 오류 문장을 붙여 다시 묻는다. 두 곳이 같은 사실(예: 후보는 몇 개까지)을 말하는데 하나만 고치면, 모델은 모순된 지시를 받는다.

후보 제시 단계는 후보 수의 하한을 2에서 1로 바꿨다(티켓 28). 그때 스키마의 minItems만 고치고 지시문의 "2~4개"가 남아서, 바로 다음 줄에 "후보 하나만 낸다"는 문장과 부딪쳤다. 티켓 28 리뷰가 이를 잡았고, 티켓 28·29 회고 3번이 근본 원인으로 "같은 수를 두 곳에 적은 것"을 꼽았다고 티켓 30에 적혀 있다.

용어

부품 탐색은 후보 제시 첫머리에 VLM이 그림으로 부품과 정면 후보를 찾는 일이다. 정면 후보 수는 PARTS_SCHEMA의 fronts maxItems(4)이고, 확신하면 하나, 확신하지 못하면 여러 개를 낸다. 후보 제시의 응답 스키마는 CANDIDATES_SCHEMA이고 minItems 1, maxItems 4다.

핵심 아이디어

핵심 아이디어는 "한 사실은 한 곳에서 만들고, 다른 곳은 그것을 가져다 쓴다"이다. 지시문은 JavaScript 템플릿 문자열이므로 문장에 숫자를 직접 쓰는 대신 스키마의 값을 끼워 넣으면 된다.

지시문의 문장이전이후
답은 후보 객체 N~M개1~4를 문장에 직접 씀minItems~maxItems에서 만듦
보통 2~M개2~4를 직접 씀2는 문장, M은 maxItems
부품 탐색: 확신하지 못하면 2~M개2~4를 직접 씀2는 문장, M은 fronts의 maxItems

"보통 2"의 2는 스키마 값이 아니다. 서로 다른 후보를 낼 수 있을 때의 하한이라 스키마의 minItems(1)와 뜻이 다르기 때문에 문장에 남겼다고 티켓에 있다. 시험은 이 2를 따로 적지 않고, 모든 "N~M개"가 스키마의 최대에서 끝나고 최소보다 작지 않은지만 본다.

예를 들어 누군가 CANDIDATES_SCHEMA.maxItems를 3으로 바꾸면 지시문은 "1~3개, 보통 2~3개"로 저절로 바뀐다. 옛 방식이면 "1~4개"가 남아 모델이 4개를 내고 스키마 검사에서 떨어져 다시 묻게 된다.

코드 따라가기

흐름: 스키마 상수 → 지시문 템플릿에 끼워 넣음 → 모델에게 가는 요청 → 시험이 요청에서 숫자 범위를 읽어 스키마와 대조.

1. 지시문이 스키마를 읽는다

후보 제시 지시문의 개수 두 곳과 부품 탐색 지시문의 개수 한 곳이 바뀌었다. 먼저 후보 제시다.

- 답은 후보 객체 1~4개를 담은 JSON 배열 하나([ … ])다. 보통 2~4개이고, …
- 답은 후보 객체 ${CANDIDATES_SCHEMA.minItems}~${CANDIDATES_SCHEMA.maxItems}개를 담은 JSON 배열 하나([ … ])다. 보통 2~${CANDIDATES_SCHEMA.maxItems}개이고, …

이 줄은 지금 configurator/pipeline/litellm-ai.ts:98에 있다. 부품 탐색은 이렇게 바뀌었다. 생략한 부분은 줄의 나머지 문장이다.

... 확신하지 못하면 가능성 높은 순서로 2~4개 낸다. ...
... 확신하지 못하면 가능성 높은 순서로 2~${PARTS_SCHEMA.properties.fronts.maxItems}개 낸다. ...

부품 탐색 줄은 configurator/pipeline/litellm-ai.ts:94다. 스키마의 후보 응답 주석에서도 "2~4개"를 빼고 개수 범위를 minItems·maxItems가 정한다고 고쳤다(configurator/pipeline/schemas.ts:104).

2. 시험: 요청에 실린 문장에서 범위를 읽는다

시험은 모델에게 실제로 간 요청의 지시문 본문에서 "N~M개" 꼴을 모두 찾아 스키마와 대조한다. 요청을 읽는 까닭은 상수를 직접 비교하면 지시문이 어떤 문장으로 만들어졌는지가 검사되지 않기 때문이다(내 해석이다. 코드 주석은 "지시문과 스키마에 후보 수를 따로 적었다가 어긋났다"고만 적었다).

configurator/test/litellm-ai.test.ts:465-480

test("후보 제시·부품 탐색 지시문이 알리는 개수는 응답 스키마의 개수를 넘지 않는다", async () => {
  // 지시문과 스키마에 후보 수를 따로 적었다가 어긋났다(티켓 28 리뷰)
  const { llm } = await run({});
  const promptOf = (model: string) => textOf(llm.requests.find((r) => r.body.model === model)!.body.messages[0].content);
  const ranges = (prompt: string) => [...prompt.matchAll(/(\d+)~(\d+)개/g)].map(([, low, high]) => [Number(low), Number(high)]);

  const { minItems, maxItems } = CANDIDATES_SCHEMA;
  const candidateRanges = ranges(promptOf(MODELS.candidates));
  assert.deepEqual(candidateRanges[0], [minItems, maxItems]);
  for (const [low, high] of candidateRanges) assert.ok(low >= minItems && high === maxItems, `후보 제시 ${low}~${high}개`);

  const fronts = PARTS_SCHEMA.properties.fronts;
  const frontRanges = ranges(promptOf(MODELS.parts));
  assert.ok(frontRanges.length > 0);
  for (const [low, high] of frontRanges) assert.ok(low >= fronts.minItems && high === fronts.maxItems, `부품 탐색 ${low}~${high}개`);
});

후보 제시는 첫 범위가 스키마의 범위 그대로([minItems, maxItems])인지, 나머지 범위는 하한이 최소 이상이고 상한이 최대와 같은지 본다. 부품 탐색은 하한이 최소 이상이고 상한이 최대인지 본다. 티켓 기록에 따르면 스키마 최대를 잠시 3으로 바꾸면 옛 지시문에서는 실패하고 고친 지시문에서는 통과함을 확인했다.

티켓이 남긴 한계

시험은 "N~M개" 꼴만 본다. "최대 4개"처럼 다른 꼴로 숫자를 적으면 놓친다. 또 "후보 하나만 낸다"는 문장은 minItems가 1이라는 데 기댄다. 최소값을 바꾸면 후보 하나 허용(티켓 28) 자체가 바뀌는 일이라 그때 이 문장도 같이 고친다.

퀴즈

지시문의 "보통 2~M개"에서 2를 스키마 minItems로 바꾸지 않은 까닭은?

스키마의 minItems는 후보 하나를 허용하는 1이다. "보통 2"는 구성이 여럿일 때의 하한이라 같은 값이 아니다. 그래서 문장으로 남기고 시험도 이 2를 따로 적지 않는다.

누군가 CANDIDATES_SCHEMA의 maxItems를 4에서 3으로 바꿨다. 이 변경 후 후보 제시 지시문은?

지시문이 ${CANDIDATES_SCHEMA.maxItems}를 읽어 만들어지므로 값이 함께 바뀐다. 둘째 보기의 상황이 이 티켓 전에 일어날 수 있던 어긋남이다.

새 지시문 줄에 누군가 "최대 4개까지 낸다"라고 숫자를 적었다. 이 티켓의 시험은?

시험은 정규식 (\d+)~(\d+)개로 범위만 찾는다. 티켓이 남긴 한계로 적은 부분이다. 이번에 어긋났던 꼴을 막는 것이 목적이다.

부품 탐색의 확신하지 못하는 경우 2~M개에 대해, 스키마의 fronts maxItems를 3으로 바꾸고 지시문을 옛 문장으로 두면 시험은?

시험은 부품 탐색 지시문의 모든 범위에서 하한이 최소 이상이고 상한이 최대와 같은지 본다. 옛 지시문은 상한 4를 직접 적어 3과 어긋나므로 실패하고, 고친 지시문은 값을 가져와 통과한다.

이 티켓이 적용한 원칙은?

지시문과 스키마가 같은 사실을 따로 말하면 한쪽을 고칠 때 다른 쪽이 남는다. 티켓 28에서 실제로 그렇게 어긋났다. 오류 문장을 붙여 다시 묻는 것은 어긋남이 생긴 뒤의 복구 수단이고 이 티켓의 대상이 아니다.

티켓 09: 격자 보강

명세를 고쳐 다시 써도 덧셈이 틀리는 슬라이더 쌍만 3x3 격자 샘플로 보강하고, 변형 엔진이 그 쌍을 격자의 나머지를 쌍선형으로 섞어 맞추는 변경이다. 보강한 쌍은 명세가 아니라 결과물의 스윕 데이터에 담긴다.

배경

이 영역이 처음이면 펼쳐서 읽는 깊은 배경

변형 엔진은 슬라이더마다 단독 스윕의 꼭짓점 이동량을 기본 형상에 더해 형상을 만든다(ADR-0004). 슬라이더 둘이 서로 영향을 주지 않으면 합이 Fusion과 맞는다. 하지만 한 파라미터가 Fusion 수식으로 다른 파라미터를 따라가는 쌍(예: 서랍 깊이 drawer_d = body_d - 20 mm)은 둘을 함께 움직일 때 덧셈이 틀린다. 앞 티켓의 교차 검증은 쌍마다 범위 모서리 4곳에서 Fusion 형상을 받아 덧셈과 비교해 이런 쌍을 찾는다.

ADR-0008은 이 쌍을 두 단계로 다룬다. 먼저 AI가 명세를 고쳐 다시 쓰게 한다(한쪽을 다른 쪽의 자식으로 바꾸거나 범위를 줄임). 그래도 넘으면 그 쌍만 작은 격자 스윕(3x3)으로 보강하고, 변형 엔진이 그 쌍을 격자 보간으로 섞는다. 전체 폭과 서랍 폭처럼 서로 영향을 주는 쌍은 가구에서 흔해서 명세 수정만으로는 상품이 막히므로, 고정 코어에 격자 보간을 하나 더 넣는 비용을 받아들였다고 ADR이 밝힌다. 상품당 2쌍까지만 허용한다.

이 문서의 이름을 먼저 정리한다. 마디는 3x3 격자의 점 9개, 칸은 마디 네 개가 이루는 사각형, 기본값 줄은 한 슬라이더가 기본값에 있는 선, 쌍선형은 두 축 방향으로 차례로 선형 보간하는 방식이다.

  • 격자 보강: 쌍을 이루는 두 슬라이더의 min, default, max를 엇걸어 뽑은 3x3 샘플. default가 범위 끝이면 그 축은 값이 둘이다. 명세가 아니라 결과물 sweeps.json의 grids에 담긴다.
  • 나머지(residual): 격자 마디의 Fusion 샘플 이동량에서 두 단독 스윕 이동량의 합을 뺀 값. 덧셈이 못 맞추는 몫이다.
  • GridTrack: 엔진 안에서 격자 보강 쌍 하나를 담는 구조. 마디마다 나머지를 갖는다.
  • Pair: 슬라이더 쌍(두 부모 파라미터 이름, 명세 순서).
  • verifyCross, gridValues, verifyGrid, checkGridSamples: 교차 검증, 격자 요청 값 만들기, 격자 검증점 비교, 격자 샘플 사용 가능 여부 검사.
  • GRID_PAIR_LIMIT: 상품당 격자 보강 쌍 상한(2).
핵심 개념: 나머지를 더한다 엔진은 격자를 따로 섞지 않는다. 먼저 평소처럼 두 단독 스윕 이동량을 더하고, 덧셈이 틀리는 만큼인 나머지를 격자 마디 네 개에서 쌍선형으로 섞어 그 위에 더한다. 그래서 격자 마디에서는 덧셈과 나머지의 합이 Fusion 샘플과 정확히 같아진다.

핵심 아이디어

덧셈이 틀리는 쌍은 단독 스윕을 더한 뒤, 틀린 만큼(나머지)을 격자 마디에서 쌍선형으로 섞어 더한다. 작은 예시는 티켓 파일이 쓴 합성 서랍장의 전체 깊이 x 서랍 깊이 쌍이다. 전체 깊이는 300, 450, 600, 서랍 깊이는 300, 430, 600을 엇걸어 격자 9곳을 만든다. 서랍장 합성 모델에는 서랍 폭 파라미터가 없어서 같은 성격의 이 쌍으로 시험했다고 티켓 파일이 적는다.

한 번의 격자 요청은 격자 9곳과 검증점 8곳을 합쳐 값 묶음 17개를 보낸다. 검증점이 8곳인 것은 gridValues가 칸 가운데 2x2, 기본값 줄의 두 방향 각 2개를 만들기 때문이다.

코드 따라가기

흐름: 실행기가 실패한 쌍을 추려 격자를 요청 → 받은 격자를 결과물의 스윕 데이터에 담아 조립 → 엔진이 나머지를 만들어 덧셈 위에 더함 → 격자 검증점으로 확인.

1. 검증기: 실패를 쌍 단위로 돌려준다

verifyCross는 이전에는 피드백 목록 하나를 돌려줬지만 이제 쌍별 실패(PairFailure)를 돌려준다. 실행기가 어느 쌍이 실패했는지 알아야 하기 때문이다(configurator/pipeline/verify-cross.ts:113). 격자를 쓸 수 없는 실패도 구분한다. 재계산 실패와 위상 변화는 격자로 섞을 수 없다.

configurator/pipeline/verify-cross.ts:129

export const fixableByGrid = ({ feedback }: PairFailure) => feedback.every((f) => !UNMIXABLE.has(f.kind));

gridValues가 격자 9곳과 검증점 8곳의 값 묶음을 만든다(configurator/pipeline/verify-cross.ts:66). 쌍이 아닌 슬라이더는 default다. 격자를 받은 뒤에는 checkGridSamples가 재계산 실패나 위상 변화를 검사해, 있으면 보강하지 않고 그 피드백을 낸다. verifyGrid는 격자를 넣은 엔진으로 검증점을 수치 검증과 같은 측정과 합격선으로 재고, 쌍이 상한을 넘으면 gridLimitFeedback이 grid_limit 종류의 피드백을 만든다. 이 피드백은 한 슬라이더나 부품의 실패가 아니라서 slider와 part가 빈 문자열이다.

2. 실행기: 두 번째 실패에서 격자

writeVerifiedSpec가 쌍마다 지난 명세에서 실패했는지 기억한다(pairsFailedBefore). 처음 실패한 쌍은 피드백으로 명세를 다시 쓰게 하고, 다음 명세에서도 실패하면서, 아직 격자가 없고, 격자로 고칠 수 있는 쌍만 toReinforce에 든다.

    feedback.push(gridLimitFeedback(needed));

이미 보강한 쌍까지 세어 2쌍을 넘으면 요청하지 않고 grid_limit를 낸다. 티켓 파일은 처음부터 세 쌍이 실패해도 상한 피드백은 다음 명세에서 나온다고 적는다. 처음 실패한 쌍은 아직 보강이 필요한 쌍이 아니라 명세 수정 대상이기 때문이다. 넘지 않으면 reinforce가 쌍마다 kind: "grid" 요청을 보낸다(configurator/pipeline/runner.ts:323). 같은 요청은 다시 보내지 않도록 응답을 answered 맵에 캐시한다(configurator/pipeline/runner.ts:191). 받은 격자는 요청한 값 묶음(범위와 기본값)이 지금 명세와 같을 때만 쓴다(configurator/pipeline/runner.ts:242). 범위가 바뀌면 격자 마디가 슬라이더 범위 끝과 어긋나기 때문이다.

보강 뒤 같은 명세를 assembleAndVerify로 다시 조립해 검증한다(configurator/pipeline/runner.ts:249). 이 함수가 조립, 수치 검증, 축 반응 검증, 교차 검증, 격자 검증점을 차례로 부른다.

3. 조립: 격자는 명세가 아니라 스윕 데이터에

sweepDataFor가 명세의 슬라이더에 모두 속하는 격자만 남겨 sweeps.json의 grids로 넣는다(configurator/pipeline/assemble.ts:32). 엔진이 쓰는 면 필드만 남기는 engineFaces도 샘플과 격자가 함께 쓰도록 분리되었다.

4. 엔진: 나머지를 만들고 쌍선형으로 섞는다

createMorph는 data.grids에서 명세의 두 슬라이더를 잇는 격자마다 GridTrack을 만든다. 마디마다 샘플의 기본 형상 대비 이동량(deltaOf)에서 두 단독 스윕 이동량을 addDelta로 더한 값을 빼 나머지를 얻는다(configurator/src/engine.ts:186). 주석은 서로 독립이면 기본값 줄의 나머지가 0이고, 한쪽이 수식으로 다른 쪽을 따르면 기본값 줄에도 나머지가 남는다고 설명한다. 샘플이 재계산에 실패했거나 면 구성이 다르면 예외를 던진다.

이어서 positions가 단독 스윕을 모두 더한 뒤 격자 쌍마다 addResidual을 부른다. 값이 격자 밖이면 가장자리 마디에 붙는다.

configurator/src/engine.ts:223-230

function addResidual(out: Float64Array, grid: GridTrack, [va, vb]: [number, number]) {
  const u = bracket(grid.values[0], va);
  const v = bracket(grid.values[1], vb);
  const r = grid.residuals;
  const [r00, r01, r10, r11] = [r[u.lo][v.lo], r[u.lo][v.hi], r[u.hi][v.lo], r[u.hi][v.hi]];
  const [w00, w01, w10, w11] = [(1 - u.t) * (1 - v.t), (1 - u.t) * v.t, u.t * (1 - v.t), u.t * v.t];
  for (let i = 0; i < out.length; i++) out[i] += r00[i] * w00 + r01[i] * w01 + r10[i] * w10 + r11[i] * w11;
}

값을 감싸는 두 샘플 번호와 비율을 구하는 일은 bracket으로 빠져 addDelta와 addResidual이 함께 쓴다(configurator/src/engine.ts:206). 샘플의 이동량을 계산하는 deltaOf도 단독 스윕과 격자가 같이 쓰도록 안쪽 함수로 분리되었다.

5. 수치 검증: 격자 보강 쌍의 슬라이더는 단독 검증점을 건너뛴다

격자에 속한 슬라이더를 모아(gridded) 단독 스윕 검증점 검사를 통째로 건너뛴다(configurator/pipeline/verify-numeric.ts:72). 앞의 설계 판단이 그 이유다.

6. 시험

엔진 시험은 덧셈이 틀리는 쌍이 격자 마디 사이 8곳에서 합격선 안에서 맞는지, 격자 마디에서 녹화 샘플과 일치하는지, 격자 쌍이 아닌 슬라이더는 덧셈 그대로인지 본다. 실행기 시험은 처음 실패는 피드백만, 두 번째 실패에서 격자를 요청하고 제출, 격자에는 명세가 아닌 스윕 데이터에 담김, 격자 검증점 실패, 격자 샘플 재계산 실패, 세 쌍이면 grid_limit를 확인한다. 서버와 애드인은 바꾸지 않았다. 앞 티켓에서 요청 종류에 grid를 미리 두었고 애드인은 종류와 무관하게 값 묶음마다 교차 검증 샘플로 답하기 때문이다.

퀴즈

같은 후보의 첫 명세에서 쌍 하나가 교차 검증에 처음 실패했다. 실행기는 무엇을 하는가?

격자는 앞선 명세에서도 실패한 쌍에만 쓴다(pairsFailedBefore). 처음 실패한 쌍은 ADR-0008의 순서대로 명세 수정을 먼저 시도하고, 처음 실패 기록만 남긴다.

격자 마디에서 엔진 결과가 녹화된 격자 샘플과 일치하는 까닭은?

나머지는 샘플 이동량에서 두 단독 스윕 이동량을 뺀 값이다. 엔진은 덧셈을 하고 나머지를 더하므로 마디에서 합이 샘플이 된다. 마디 사이는 쌍선형으로 섞는다.

한 상품에서 세 쌍이 처음부터 모두 교차 검증에 실패한 첫 명세는 어떻게 처리되는가?

처음 실패한 쌍은 보강이 필요한 쌍으로 세지 않는다. 세 쌍이 다음 명세에서도 실패하면 그때 보강할 쌍이 상한 2를 넘어 grid_limit 피드백이 난다.

수치 검증이 격자 보강 쌍의 슬라이더에는 단독 스윕 검증점을 재지 않는 까닭은?

주석의 설명이다. 짝 슬라이더가 수식으로 따라가는 단독 스윕은 짝 값을 고정한 구성기 상태가 아니다. 그래서 이 쌍은 교차 검증에서 격자 칸 가운데와 기본값 줄 위 검증점으로 잰다.

격자를 받은 뒤 명세가 슬라이더 범위를 바꿔 다시 쓰이면 그 격자는 어떻게 되는가?

gridKey는 요청한 값 묶음이고 gridsFor는 지금 범위와 기본값에서 만든 키와 같을 때만 격자를 쓴다. 격자 마디가 슬라이더 범위 끝과 맞아야 보간 범위가 맞기 때문이다.

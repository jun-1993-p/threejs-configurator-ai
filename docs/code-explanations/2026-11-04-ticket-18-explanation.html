티켓 18: UI 스타일 선택

AI가 정해 둔 UI 스타일 목록에서 id 하나만 고르고, 고정 코어가 그 스타일의 색·글꼴·슬라이더 모양을 구성기에 입힌다. 목록 밖의 스타일은 만들 수 없다.

배경

이 영역이 처음이면 펼쳐서 읽는 기본 배경

이 프로젝트의 구성기는 쇼핑몰 페이지의 div 안에서 도는 three.js 3D 뷰어다. 구성기를 움직이는 코드는 상품마다 바뀌지 않는 고정 코어(configurator/src/)이고, 상품마다 달라지는 것은 JSON 파일뿐이다(ADR-0001). 쇼핑몰 쪽은 div 하나와 스크립트 한 줄만 붙인다.

파이프라인은 상품 하나를 정해진 순서의 단계로 처리하며, AI는 각 단계 안에서 정해진 JSON 형식으로만 답한다(ADR-0014). AI가 만드는 것은 코드가 아니라 명세 같은 데이터이고, 그 데이터는 JSON Schema로 검사한다.

변경 전의 파이프라인에는 이미 "스타일 고르기" 단계 자리가 있었다. 그 단계는 styleChoiceSchema로 응답이 목록의 id 중 하나인지 검사했지만, 스타일이 무엇을 뜻하는지는 아직 비어 있었다. 고른 스타일은 결과물에 담기지 않았고, 고정 코어는 부품 색 배열(PART_COLORS)과 배경색을 코드 안에 직접 적어 두고 있었다. 코어 안의 주석은 "스타일 선택(티켓 18)이 들어오면 그쪽에서 정한다"고 적고 있었다.

이 문서의 용어는 다음과 같다. UI 스타일 목록은 사람이 관리하는 스타일 모음이다(저장소 포트가 단계에 내준다). 스타일 하나는 id, 분위기 설명(summary), 색(바탕·글자·강조·부품), 글꼴, 슬라이더 모양으로 이뤄진다. 슬라이더 모양은 thin, bold, square 셋 중 하나다. 결과물은 쇼핑몰에 그대로 올리는 파일 묶음이다(변경 전에는 configurator.js, spec.json, sweeps.json, index.html 넷이었고, 이 변경이 style.json을 더한다).

핵심 개념

AI는 스타일의 값을 쓰지 않고 id만 고른다. 값은 사람이 관리하는 목록에만 있고 AI의 응답은 그 목록의 id 열거(enum)로 검사한다. ADR-0001(코어와 변형 엔진은 고정하고 AI는 JSON 명세만 쓴다)은 AI가 쓰는 출력을 JSON으로 좁혀 스키마로 검증하는 방침이다. 색 코드나 CSS를 AI가 쓰면 목록 밖의 값이 코어에 들어갈 수 있다는 점은 이 방침을 이 변경에 적용한 저자의 추론이다.

핵심 아이디어

고정 코어는 상품마다 바뀌지 않는 구성기 코드다(configurator/src/). 세 부분이 한 줄로 이어진다. 스타일 목록은 사람이 쓰는 데이터이고, AI의 답은 id 한 줄이며, 고정 코어는 그 id가 가리키는 스타일 객체를 CSS 속성과 재질 색에 그대로 넣을 뿐이다.

UI 스타일 목록 (natural, dark, minimal)
styles: [{id, summary, colors, ...}]
스타일 고르기: AI가 id 응답
{ style: dark }
목록에서 스타일 찾기
style.json
결과물에 담김
data-style=style.json
고정 코어가 색·글꼴·슬라이더 모양 적용

목록 밖의 id를 답하면(예: { "style": "neon" }) JSON Schema 검사에서 걸린다. 이때 실행기는 고를 수 있는 id를 붙여 다시 묻고, 3번 다시 물어도 맞지 않으면 스타일 단계에서 멈춘다. 명세 작성 단계로는 넘어가지 않는다.

티켓 기록에 따르면 서랍장 합성 녹화본으로 세 스타일의 결과물을 만들어 Chrome에서 띄워 보았다. 바탕과 부품 색이 스타일대로 바뀌었고, 슬라이더는 natural에서 가는 둥근 갈색, dark에서 굵은 둥근 금색, minimal에서 각진 검정으로 나왔다.

id바탕강조슬라이더
natural#f4f1ea#a47551thin
dark#26262a#c8a24abold
minimal#ffffff#1d1d1fsquare
티켓에 없던 목록 형식 검사

티켓 본문에는 없었지만, 목록 형식 검사(checkStyles, 목록이 색·글꼴·슬라이더 모양 규칙을 지키는지 보는 JSON Schema 검사)를 AI에게 묻기 전 단계에 두었다. 목록은 사람이 고치는 자료이고 고정 코어가 그 값을 그대로 CSS와 재질 색에 넣기 때문에, 틀린 색이나 모르는 슬라이더 모양은 브라우저에서 조용히 무시되거나 예외가 난다. 그래서 위치를 짚어 단계에서 멈추게 했다(티켓의 리뷰 기록).

코드 따라가기

흐름: 스타일 목록(configurator/pipeline/ui-styles.ts:6-28) → 목록 형식 검사(configurator/pipeline/schemas.ts:128-154) → 스타일 고르기(configurator/pipeline/runner.ts:508-519) → 조립(configurator/pipeline/assemble.ts:109-117) → 결과물 div가 style.json을 불러옴(configurator/src/core.ts:241-257) → 고정 코어가 스타일을 입힘(configurator/src/core.ts:59-71).

1. 값 목록은 고정 코어 쪽에 둔다

새 파일 src/style.ts가 스타일의 모양을 정한다. 슬라이더 모양 이름 세 개와 Style 타입이 여기에 있다. 파일 맨 위 주석이 이유를 적는다: 고정 코어 번들에 들어가므로 ajv를 끌어오는 pipeline/schemas.ts에 두지 않고 여기에 둔다. 두께 표준 목록 STANDARD_THICKNESSES가 같은 방식의 선례이고, 이 예외는 CODING_STANDARDS.md에도 적었다.

configurator/src/style.ts:4-20

/** 슬라이더 모양. 고정 코어가 모양마다 정해 둔 CSS만 쓴다. */
export const SLIDER_SHAPES = ["thin", "bold", "square"] as const;
export type SliderShape = (typeof SLIDER_SHAPES)[number];

/** "#rrggbb". UI 스타일 목록 검사(pipeline/schemas.ts의 checkStyles)가 형식을 본다. */
export type HexColor = string;

export interface Style {
  id: string;
  /** AI가 고를 때 읽는 한 줄 설명 */
  summary: string;
  /** parts는 부품마다 돌려 쓰는 색이다 */
  colors: { background: HexColor; text: HexColor; accent: HexColor; parts: HexColor[] };
  /** CSS font-family */
  font: string;
  slider: SliderShape;
}

checkStyles의 스키마는 색을 #rrggbb만, 글꼴은 CSS 규칙을 끊는 글자(; { } < > \)가 없는 문자열만, 슬라이더 모양은 SLIDER_SHAPES 중 하나만 받는다.

configurator/pipeline/schemas.ts:128-154

const HEX_COLOR = { type: "string", pattern: "^#[0-9a-fA-F]{6}$" };

/**
 * 저장소의 UI 스타일 목록. 고정 코어가 그대로 CSS와 재질 색에 넣으므로, 색은 "#rrggbb"만, 글꼴은 CSS 규칙을 끊는 글자 없이 받는다.
 */
const STYLES_SCHEMA = {
  type: "array",
  minItems: 1,
  items: {
    type: "object",
    required: ["id", "summary", "colors", "font", "slider"],
    additionalProperties: false,
    properties: {
      id: { type: "string", minLength: 1 },
      summary: { type: "string" },
      colors: {
        type: "object",
        required: ["background", "text", "accent", "parts"],
        additionalProperties: false,
        properties: { background: HEX_COLOR, text: HEX_COLOR, accent: HEX_COLOR, parts: { type: "array", minItems: 1, items: HEX_COLOR } },
      },
      font: { type: "string", pattern: "^[^;{}<>\\\\]+$" },
      slider: { enum: SLIDER_SHAPES },
    },
  },
};
export const checkStyles = checker(STYLES_SCHEMA);

3. 실행기: 형식 검사, id 고르기, 스타일 객체 찾기

후보 선택 직후 실행기는 저장소에서 목록을 받아 먼저 checkStyles로 목록 자체를 검사한다. 목록이 틀렸으면 스타일 단계에서 멈춘다. 그 다음 AI에게 목록을 복사해 보내고(structuredClone) 응답이 목록의 id인지 styleChoiceChecker로 검사하며, 통과하면 그 id의 스타일 객체를 찾아 명세 작성과 검증으로 넘긴다.

configurator/pipeline/runner.ts:508-519

      // 고정 코어가 UI 스타일 목록의 값을 그대로 CSS와 재질 색에 넣으므로, 형식에 맞지 않는 목록으로는 고르지 않는다
      const styles = await store.styles();
      const styleErrors = checkStyles(styles);
      if (styleErrors.length > 0) throw new PipelineStop("style", `UI 스타일 목록 형식 오류: ${styleErrors.join("; ")}`);
      const { style: styleId } = await askUntilValid<{ style: string }>(
        "style",
        styleChoiceChecker(styles.map((s) => s.id)),
        (schemaErrors, rejected) => ai.chooseStyle({ intake, candidate, styles: structuredClone(styles), rejected, schemaErrors }),
      );
      await log("style", styleId);

      const written = await writeVerifiedSpec(candidate, styles.find((s) => s.id === styleId)!);

AI 지시문(STYLE_PROMPT)도 바뀌었다. 변경 전에는 "styles 목록의 id 하나만 고른다"가 전부였고, 이제는 목록 필드의 뜻을 적고 상품 종류와 상품명에 어울리는 스타일을 summary와 colors로 판단해 id 하나를 고르라고 한다.

4. 조립: style.json과 data-style

assembleProduct에 style 인자가 생기고, 결과물에 style.json이 하나 더 담긴다. 쇼핑몰에 붙이는 div도 data-style="style.json"을 갖는다. 같은 인자가 실행기의 writeVerifiedSpec과 assembleAndVerify를 거쳐 내려온다. 검증 중에 조립이 여러 번 일어나도 같은 스타일이 쓰인다.

configurator/pipeline/assemble.ts:102-117

/** 결과물 파일 이름과 내용. 쇼핑몰에는 이 파일들을 그대로 올린다. */
export type ProductFiles = Record<"configurator.js" | "spec.json" | "sweeps.json" | "style.json" | "index.html", string>;

/**
 * 고정 코어 번들과 명세·스윕 데이터·스타일 선택·붙여 넣을 div를 메모리에서 만든다. bundle.grids·thickness는 검증 중에 받은 격자 보강·두께 후보 형상이다.
 * style은 UI 스타일 목록에서 고른 스타일 그대로다.
 */
export async function assembleProduct(spec: Spec, bundle: SweepData, style: Style): Promise<ProductFiles> {
  return {
    "configurator.js": await buildCore(),
    "spec.json": JSON.stringify(spec, null, 2),
    "sweeps.json": JSON.stringify(sweepDataFor(spec, bundle)),
    "style.json": JSON.stringify(style, null, 2),
    "index.html": SNIPPET,
  };
}

6. 슬라이더 모양은 이름만 고르고 CSS는 코어가 만든다

SLIDER_SHAPE_SIZES가 모양마다 트랙 두께·손잡이 크기·둥근지를 정하고, sliderCss가 이 값으로 CSS를 만든다. 스타일 목록은 모양 이름만 말하므로 AI도 목록 편집자도 CSS를 쓰지 못한다. 색은 컨테이너의 강조색 변수를 따른다. 트랙에는 color-mix를 모르는 브라우저가 쓰도록 회색 값을 앞에 하나 더 둔다(리뷰 뒤 반영).

configurator/src/core.ts:19-42

/** 슬라이더 모양마다 트랙 두께·손잡이 크기(px)와 둥근지. 스타일 선택은 모양 이름만 고르고 CSS는 여기서만 만든다. */
const SLIDER_SHAPE_SIZES: Record<SliderShape, { track: number; thumb: number; round: boolean }> = {
  thin: { track: 4, thumb: 16, round: true },
  bold: { track: 10, thumb: 22, round: true },
  square: { track: 6, thumb: 16, round: false },
};

const sliderClass = (shape: SliderShape) => `configurator-slider-${shape}`;

/** 슬라이더 모양의 CSS. 색은 구성기 div의 --configurator-accent를 따른다. */
function sliderCss(shape: SliderShape): string {
  const { track, thumb, round } = SLIDER_SHAPE_SIZES[shape];
  const selector = `.${sliderClass(shape)}`;
  // color-mix를 모르는 브라우저는 앞의 회색 트랙을 쓴다
  const trackRule = `height:${track}px;border-radius:${round ? `${track / 2}px` : "0"};background:#8888;background:color-mix(in srgb,var(--configurator-accent) 25%,transparent)`;
  const thumbRule = `width:${thumb}px;height:${thumb}px;border:none;border-radius:${round ? "50%" : "0"};background:var(--configurator-accent)`;
  return [
    `${selector}{-webkit-appearance:none;appearance:none;width:100%;height:${thumb}px;margin:0;background:transparent}`,
    `${selector}::-webkit-slider-runnable-track{${trackRule}}`,
    `${selector}::-moz-range-track{${trackRule}}`,
    `${selector}::-webkit-slider-thumb{-webkit-appearance:none;${thumbRule};margin-top:${(track - thumb) / 2}px}`,
    `${selector}::-moz-range-thumb{${thumbRule}}`,
  ].join("\n");
}

퀴즈

AI의 스타일 응답을 JSON Schema로 검사하는 가장 큰 이유는?

스타일 응답의 스키마는 목록 id의 열거(enum)다. AI는 id만 답하고 값은 사람이 관리하는 목록이 가진다. AI가 직접 쓴 색 코드나 CSS는 스키마로 검증되지 않은 채 코어에 들어갈 수 있다는 것이 ADR-0001의 방침을 적용한 추론이다.

UI 스타일 목록 파일 안의 색이 #12345(다섯 자리)로 잘못 적혀 있다. 파이프라인은 어떻게 되는가?

목록 검사(checkStyles)는 AI에게 묻기 전에 한다. 목록은 사람이 고치는 자료이므로 AI에게 다시 물어도 고쳐지지 않는다. 그리고 브라우저는 틀린 색을 조용히 무시하므로 조립까지 가면 문제가 보이지 않는다. 그래서 파이프라인에서 위치를 짚어 멈춘다.

슬라이더 모양을 스타일에서 CSS 문자열이 아니라 thin·bold·square 이름으로만 받는 까닭은?

코어는 모양 이름마다 트랙·손잡이 크기를 SLIDER_SHAPE_SIZES에 갖고 있고, CSS를 만드는 일도 코어에서만 한다. 그러면 목록 편집자도 AI도 CSS를 끼워 넣을 수 없다. 브라우저 호환은 이 결정과 별개로 코어가 앞의 회색 트랙 같은 방법으로 다룬다.

SLIDER_SHAPES를 pipeline/schemas.ts가 아니라 src/style.ts에 둔 이유로 맞는 것은?

schemas.ts는 불러올 때 ajv로 스키마를 컴파일한다. 고정 코어 번들이 schemas.ts를 가져오면 ajv가 번들에 들어간다. 그래서 코어도 읽는 값 목록은 src/에 두고 schemas.ts가 가져다 쓰는 선례(STANDARD_THICKNESSES)를 따랐다.

같은 방식을 다른 곳에 적용한다면, 고정 코어가 새로 읽을 값(예: 버튼 글자 크기 단계)도 어떻게 두는 것이 맞는가?

이 변경의 원칙은 AI가 만드는 데이터가 열거형으로 좁혀지고, 값을 CSS나 재질에 옮기는 일은 코어가 한다는 것이다. 새 값도 이름 목록과 코어 쪽 대응표로 두면 같은 검사 구조를 그대로 쓸 수 있다.

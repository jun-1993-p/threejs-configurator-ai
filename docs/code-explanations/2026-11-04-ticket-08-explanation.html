티켓 08: 추가 샘플 요청과 교차 검증

검증 중에 서버가 업로드 뒤에도 연결된 Fusion 애드인에 추가 샘플을 요청하고, 슬라이더 쌍마다 범위 모서리 4곳에서 단독 스윕 덧셈과 Fusion 형상을 비교하는 변경이다. 애드인 연결이 끊기면 실패로 세지 않고 다시 연결될 때까지 기다린다.

배경

이 영역이 처음이면 펼쳐서 읽는 깊은 배경

구성기는 슬라이더를 여러 개 함께 움직일 때 각 슬라이더의 단독 스윕 이동량을 더해서 형상을 만든다(ADR-0004). 앞 티켓에서 확인했듯 서로 영향이 없는 슬라이더 쌍은 덧셈이 맞는다. 그러나 한 파라미터가 다른 파라미터를 Fusion 수식으로 따르는 쌍은 틀릴 수 있다. 이를 찾으려면 두 파라미터를 동시에 움직인 교차 검증 샘플을 Fusion에서 새로 뽑아야 한다.

문제는 어느 슬라이더 쌍이 필요한지가 후보 선택 뒤에야 정해진다는 점이다. 업로드 때 모든 파라미터 쌍(n(n-1)/2개)을 미리 뽑으면 업로드가 크게 늦어진다. 그래서 ADR-0013은 업로드부터 최종 승인까지 CAD 애드인을 서버에 연결해 두고, 검증 중에 서버가 추가 샘플을 요청하게 했다. 1인 운영·LAN 로컬 서버이므로 Fusion을 켜 두는 부담은 작다고 ADR이 적는다.

이 문서에 나오는 이름을 먼저 정리한다.

  • 추가 샘플 요청: 파라미터 이름과 값을 짝지은 값 묶음 여러 개를 보내고, 애드인이 값 묶음마다 교차 검증 샘플 형식으로 답하는 요청. 종류(kind)는 cross(교차 검증), grid, thickness 세 가지로 정해져 있고 이 티켓은 cross만 쓴다.
  • Fusion 연결 필요: 추가 샘플 요청 중 애드인 연결이 끊긴 상태. 검증 실패로 세지 않고 다시 연결될 때까지 검증을 멈춘다.
  • FusionPort: 실행기가 Fusion에 샘플을 요청하는 인터페이스. requestSamples의 답은 answered, disconnected, failed 셋 중 하나이고, reconnected()는 연결이 돌아올 때까지 기다리는 함수다.
  • shapeComparer: 값 묶음 하나에서 변형 엔진 결과와 Fusion 형상을 부품마다 비교하는 함수. 수치 검증의 계산을 떼어 낸 것이다.
범위: 파이프라인 쪽 HTTP 포트는 아직 없다 커밋 설명에 따르면 파이프라인 쪽에서 서버의 요청 경로를 부르는 HTTP Fusion 연결 포트는 실행기 운영 호스트(티켓 22)에서 붙인다. 이 티켓의 실행기 시험은 가짜 포트로 돌고, 서버와 애드인 쪽은 각자 시험이 있다. 또 README는 Fusion 안에서의 연결 동작을 아직 사람이 확인하지 않았다고 적는다.

핵심 아이디어

세 가지가 합쳐진 변경이다. 첫째, 파이프라인이 애드인에 직접 말할 수 없으므로 서버가 대기 중인 요청 목록을 보관한다. 애드인이 몇 초마다 가져가 답한다. 둘째, 쌍마다 범위의 네 모서리를 확인한다. 셋째, 애드인이 안 보이면 실패가 아니라 대기다.

모서리 4곳

슬라이더 쌍 (a, b)마다 a의 min·max와 b의 min·max를 조합한 4곳을 만들고, 나머지 슬라이더는 기본값에 둔다. 토이 예로 슬라이더가 body_w, body_h, drawer_d 셋이면 쌍은 세 개이고 요청하는 값 묶음은 12개다.

쌍모서리 (a, b)
body_w, body_h(min, min) (min, max) (max, min) (max, max)
body_w, drawer_d같은 4곳
body_h, drawer_d같은 4곳

코드와 ADR은 모서리 4곳을 고른 이유를 적지 않는다. 범위 끝에서 덧셈이 가장 크게 틀릴 것이라 골랐으리라는 것은 이 문서의 추론이다.

한 번의 요청이 오가는 순서

sequenceDiagram
    participant P as "파이프라인 실행기"
    participant S as "서버"
    participant A as "Fusion 애드인"
    P->>S: POST sample-requests (kind cross, 값 묶음 4개)
    S-->>P: 201 요청 id
    loop 3초마다
        A->>S: GET sample-requests/next
    end
    S-->>A: 요청 id와 값 묶음
    Note over A: 주 스레드에서 샘플을 뽑는 동안 연결 신호를 보낸다
    A->>S: POST fusion 연결 신호
    A->>S: POST response (samples 4개)
    Note over S: 응답의 형식과 값 묶음 순서를 검사한다
    P->>S: GET sample-requests/id
    S-->>P: answered와 response

서버는 애드인 소식(요청 가져가기, 응답, 연결 신호)이 15초 넘게 없으면 연결이 끊긴 것으로 판정한다. 애드인의 확인 간격 3초는 이 판정 시간보다 짧아야 한다고 코드 주석이 적는다. 이 판정은 파이프라인이 요청 상태를 물을 때 fusion: connected | disconnected로 함께 알려 준다.

끊김과 실패는 다르다 애드인 연결이 끊기면 실행기는 단계별 처리 기록에 "Fusion 연결 필요"를 남기고 reconnected()가 끝나기를 기다린 뒤 같은 요청을 다시 보낸다. 반대로 애드인이 "샘플을 뽑지 못했다"고 이유를 알리면 실행기는 검증 단계에서 멈춘다. 끝없이 기다리지 않게 하기 위해서라고 애드인 함수의 주석이 설명한다.

덧셈이 틀린 쌍은 검증 피드백이 된다. path는 쌍의 앞 슬라이더(sliders[i])이고, measured.values에 쌍의 두 값이 들어 있으며, 힌트는 한쪽을 다른 쪽의 자식으로 두거나 두 범위를 좁히라고 한다. 시험의 예는 서랍 깊이가 수식으로 전체 깊이를 따르는 쌍이다.

코드 따라가기

흐름: 실행기가 쌍과 모서리를 정함 → 포트로 요청 → 서버가 요청을 보관하고 연결 상태를 판정 → 애드인이 가져가 Fusion에서 뽑아 답 → 실행기가 응답을 검사하고 덧셈과 비교 → 실패한 쌍은 피드백으로 명세 다시 쓰기.

1. 실행기: 모서리를 만들고 요청한다

corners는 슬라이더 쌍마다 네 모서리를 만든다. 쌍의 두 슬라이더만 범위 끝에 두고 나머지는 default다. 슬라이더가 하나면 쌍이 없어 빈 목록이 된다.

configurator/pipeline/verify-cross.ts:23-34

function corners(spec: Spec): Corner[] {
  const defaults = Object.fromEntries(spec.sliders.map((s) => [s.id, s.default]));
  const out: Corner[] = [];
  spec.sliders.forEach((a, i) => {
    spec.sliders.slice(i + 1).forEach((b, k) => {
      for (const va of [a.min, a.max]) {
        for (const vb of [b.min, b.max]) out.push({ pair: [i, i + 1 + k], values: { ...defaults, [a.id]: va, [b.id]: vb } });
      }
    });
  });
  return out;
}

검증의 마지막 단계로 verifyCrossChecks가 붙는다. 수치 검증과 축 반응 검증이 모두 통과해야 불린다(configurator/pipeline/runner.ts:202).

2. 실행기: 끊김은 기다리고, 실패는 멈춘다

requestSamples는 for (;;) 고리다. 응답이 오면 스키마와 값 묶음 순서를 검사해 어긋나면 검증 단계에서 멈춘다. 서버도 같은 검사를 하지만 포트 구현이 서버를 거치지 않을 수 있어서 한 번 더 본다고 주석이 적는다. 애드인이 실패를 알렸다면 멈추고, 그 밖의 경우(끊김)에는 처리 기록에 대기를 남기고 reconnected()를 기다린 뒤 고리의 처음으로 돌아가 다시 요청한다.

configurator/pipeline/runner.ts:181-199

async function requestSamples(request: SampleRequest): Promise<CrossSample[]> {
  for (;;) {
    const answer = await fusion.requestSamples(request);
    if (answer.status === "answered") {
      // elided: 응답 스키마 검사와 값 묶음 순서 검사. 어긋나면 검증 단계에서 멈춘다
      return samples;
    }
    if (answer.status === "failed") throw new PipelineStop("verification", `애드인이 추가 샘플을 뽑지 못했습니다: ${answer.reason}`);
    await log("verification", { fusion: FUSION_NEEDED });
    await fusion.reconnected();
    await log("verification", { fusion: FUSION_RECONNECTED });
  }
}

3. 비교: 수치 검증의 계산을 공유한다

수치 검증이 검증점마다 하던 "변형 엔진 결과 대 Fusion 형상" 비교는 shapeComparer로 분리되었다(configurator/pipeline/verify-numeric.ts:46). 값 묶음과 면 목록, 피드백에 붙일 말(ComparisonContext)을 받아 부품별 실패를 돌려주고, 면 구성이 다르면 undefined다. verifyNumeric도 verifyCross도 이것을 부른다. 합격선과 재는 방법이 같다는 뜻이다(ADR-0012). verifyCross는 모서리 순서대로 받은 샘플과 비교하고, 재계산 실패와 위상 변화는 부품이 없는 실패로 낸다(configurator/pipeline/verify-cross.ts:44).

4. 서버: 요청함과 연결 판정

서버는 업로드마다 요청 목록과 애드인이 마지막으로 찾아온 시각을 메모리에 둔다. 업로드부터 최종 승인까지만 쓰기 때문이라고 주석이 밝힌다. 답이 오지 않은 요청은 애드인이 다시 붙으면 또 내준다. 시계는 clock 매개변수로 바꿔 끼울 수 있어서 연결 판정 시험이 실제로 15초를 기다리지 않는다.

server/app.py:121-130

def get_sample_request(upload_id: str, request_id: str) -> dict[str, Any]:
    request = find_request(upload_id, request_id)
    last = fusion_seen.get(upload_id)
    connected = last is not None and clock() - last <= FUSION_TIMEOUT_S
    out: dict[str, Any] = {"status": "pending", "fusion": "connected" if connected else "disconnected"}
    if request.response is not None:
        out.update(status="answered", response=request.response)
    if request.failure is not None:
        out.update(status="failed", reason=request.failure)
    return out

응답을 받을 때(server/app.py:133) 서버는 sample_response_errors로 스키마와 요청한 값 묶음의 수와 순서를 검사하고, 어긋나면 422로 거절한다. 라우트 등록 순서에도 이유가 있다. next 경로를 요청 id 경로보다 먼저 등록해야 next가 id로 잡히지 않는다고 주석이 적는다.

5. 애드인: 요청에 답하고, 예외가 나도 수식을 되돌린다

serve_sample_request는 요청 하나를 가져와 값 묶음마다 cross_check_sample을 부르고 답한다. 하나라도 예외가 나면 답 대신 실패 이유를 알린다. 앞 티켓의 cross_check_sample은 이 커밋에서 try/finally가 되어, 업로드 뒤에도 사용자가 연 모델이므로 예외가 나도 수식을 되돌린다.

addin/ConfiguratorUploader/uploader/core.py:167-182

def serve_sample_request(model: FusionModel, server: SampleRequestClient, upload_id: str) -> bool:
    # elided: 요청과 응답 형식을 설명하는 docstring
    request = server.next_sample_request(upload_id)
    if request is None:
        return False
    try:
        samples = [cross_check_sample(model, values) for values in request["values"]]
    except Exception as error:
        server.fail_sample_request(upload_id, request["id"], f"{type(error).__name__}: {error}")
        return True
    server.answer_sample_request(upload_id, request["id"], {"samples": samples})
    return True

Fusion API는 주 스레드에서만 부를 수 있다. 그래서 진입점은 별도 스레드(일꾼 스레드)가 POLL_S(3초)마다 사용자 이벤트를 쏘고 주 스레드의 처리기가 요청 하나에 답한다. 주 스레드가 샘플을 뽑는 중(busy)이면 일꾼 스레드는 이벤트 대신 연결 신호만 보낸다(addin/ConfiguratorUploader/ConfiguratorUploader.py:29).

퀴즈

업로드 때 모든 파라미터 쌍의 교차 검증 샘플을 미리 뽑지 않고 검증 중에 요청하는 까닭은?

ADR-0013이 밝힌 이유다. 후보 선택 전에는 어느 슬라이더 쌍을 쓸지 모르고, 모든 쌍을 미리 뽑으면 업로드가 크게 늦어진다. 애드인은 cross_check_sample로 여러 파라미터를 함께 바꿀 수 있다.

슬라이더가 body_w, body_h, drawer_d 셋이면 교차 검증으로 요청하는 값 묶음은 모두 몇 개인가?

쌍이 세 개(w-h, w-d, h-d)이고 쌍마다 두 슬라이더의 min·max를 조합한 4곳이라 3 x 4로 12개다. 나머지 슬라이더는 default에 둔다.

검증 중 Fusion 연결이 끊긴 경우와 애드인이 "샘플을 뽑지 못했다"고 알린 경우, 실행기는 각각 어떻게 하는가?

끊김은 실패로 세지 않고 Fusion 연결 필요로 기다린다. 못 뽑음은 기다려도 달라지지 않으므로 이유를 붙여 검증 단계에서 멈춘다.

샘플을 뽑는 동안 일꾼 스레드가 연결 신호를 보내지 않으면 무엇이 문제가 되는가?

서버는 애드인 소식이 15초 넘게 없으면 끊김으로 본다. 주 스레드가 샘플을 뽑는 동안은 요청을 가져가지 못하므로, 연결 신호가 그 공백을 메운다. 시간이 오래 걸리는 모델에서 거짓 끊김을 막는 것으로 읽히지만, 걸리는 시간은 코드에 없다.

cross_check_sample을 try/finally로 바꾸지 않고 예외가 나면 수식을 되돌리는 줄이 건너뛰어진다면 무엇이 남는가?

파라미터를 바꾼 뒤 수식을 되돌리지 못하면 자식 관계가 상수로 덮인 채 남는다(ADR-0003). 업로드 뒤에도 사용자가 연 모델이라 예외 경로에서도 되돌린다.

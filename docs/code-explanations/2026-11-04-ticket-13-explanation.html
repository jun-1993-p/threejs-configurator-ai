티켓 13: 두께 고정 실측과 두께 교차 검증

슬라이더를 움직이는 동안 고른 두께가 정말 그대로인지 Fusion 형상으로 재고, 두께 후보와 각 슬라이더를 함께 바꾼 조합에서도 변형 엔진의 덧셈이 맞는지 확인하며, 틀리면 격자 보강으로 고치게 한 변경이다.

jun-1993-p/threejs-configurator-ai 티켓 13 (커밋 2a98730), 2026-11-04에 설명함. References link to this commit.

배경

이 프로젝트가 처음이라면: 깊은 배경을 펼치세요.

프로젝트는 Fusion CAD 모델을 쇼핑몰 페이지의 div 안에서 도는 three.js 구성기로 바꾼다. 구성기의 변형 엔진은 CAD 애드인이 미리 뽑아 둔 형상 샘플에서 꼭짓점 이동량을 읽어, 슬라이더 값에 맞춰 섞는다. 슬라이더 둘을 함께 움직이면 두 단독 스윕의 이동량을 더하는데, 이 덧셈이 맞는다는 보장은 없다. 그래서 파이프라인은 교차 검증을 한다. 서버가 애드인에 슬라이더 쌍의 교차 검증 샘플을 요청하고(ADR-0004, 범위 모서리 4곳이라는 값 묶음은 docs/spec-schema.md), 받은 Fusion 형상을 엔진의 덧셈 결과와 비교한다.

덧셈이 틀리는 쌍은 격자 보강으로 고친다(ADR-0008). 명세를 고쳐 쓰고도 계속 틀리는 쌍은 3×3 격자 샘플(두 슬라이더의 최솟값·기본값·최댓값)을 받아, 덧셈이 틀린 만큼을 나머지 이동량으로 담는다. 상품당 2쌍까지다. 검증이 틀린 곳을 알리는 것이 검증 피드백이고, 실패 종류(kind)와 명세 위치(path), 잰 값, 고치는 방법(hint)을 담는다.

티켓 12는 고객이 판재 두께를 표준 두께 목록의 후보 중에서 고르게 했다(ADR-0010). 그 설계에는 약속이 하나 있다. 슬라이더를 움직이는 동안 두께는 변하지 않는다. 엔진은 고른 후보의 이동량을 슬라이더 이동량에 그대로 더할 뿐이라, 모델이 지켜 주지 않으면 화면이 틀린다. 티켓 12는 두께 고정을 명세 검사로 확인했다. 고정 두께 파라미터를 슬라이더의 children에 못 두게 한 것이다. 티켓 12 기록은 두께 고정 실측과 두께 후보 × 슬라이더 교차 검증을 티켓 13의 몫으로 남겼다. 이 페이지는 이 둘을 "두 구멍"이라 부른다.

두 구멍

첫째, 명세 검사는 Fusion 안의 수식을 보지 못한다. 두께가 슬라이더의 비율 수식이면(예: 몸통 셸 두께 = body_w * 0.03) 명세 검사는 통과하지만 슬라이더를 움직이면 판이 얇아진다. 둘째, 두께 후보와 슬라이더를 함께 바꾸었을 때의 덧셈을 아직 확인하지 않았다. 두께 쌍은 두께 선택과 슬라이더 하나의 짝이다.

핵심 아이디어

이 변경의 요점은 두 가지다. 고른 두께가 슬라이더로 바뀌지 않는다는 약속을 엔진의 계산이 아니라 Fusion 형상에서 판 두께를 재서 확인하고(두께 고정 실측), 두께 후보와 슬라이더를 함께 바꾼 Fusion 형상을 받아 엔진의 덧셈과 비교한다. 티켓 기록이 든 두 합성 녹화본이 두 구멍에 하나씩 대응한다. 둘 다 서랍장이고 SolidCraft로 만든 합성 녹화본이다.

구멍 1: 슬라이더가 두께를 바꾼다

몸통 셸 두께가 body_w * 0.03인 녹화본이다. 문서의 예에서 판 두께는 기본값에서 18 mm이고, body_w가 300이면 9 mm다. 비율 수식은 선형이라서 엔진의 보간이 Fusion 형상과 맞는다. 그래서 수치 검증(엔진 결과와 Fusion 형상을 검증점마다 견주는 검사)은 통과한다. 두께가 변한 사실은 형상을 판 두께로 직접 재야 드러난다. 이것이 두께 고정 실측이다.

두께 고정 실측

슬라이더 body_w의 단독 스윕 샘플·검증점
판 두께를 재서 기준 형상과 비교

구멍 2: 두께와 슬라이더의 덧셈이 어긋난다

다른 녹화본은 두께 t(기본 18 mm)가 몸통 셸 두께이고, 서랍 폭이 d5 = body_w - 40 + (body_w - 600) * (t - 18) / 60(단위 mm)이다. 마지막 항이 두께와 폭의 곱이라서, 두께를 바꾸면 폭 슬라이더의 효과가 달라진다. 기본 두께 18에서는 그 항이 0이라 덧셈이 맞는다. 장난감 값으로 기본 전체 폭을 600이라 두고, 폭을 100 mm 늘린 상태에서 두께를 24로 고르면 이렇게 된다.

계산식서랍 폭 변화
폭 +100만 움직임(t=18)폭 항 (곱 항은 0)+100 mm
t=24만 움직임(폭은 기본)곱 항에 (600 - 600)이 들어감0 mm
엔진의 덧셈100 + 0+100 mm
Fusion의 실제 값100 + 100 × 6 / 60+110 mm

10 mm가 어긋난다. 일반식으로는 (폭 변화) × (두께 변화) / 60이다. 이 오차를 잡으려면 두께 후보와 슬라이더를 함께 움직인 형상을 Fusion에서 받아 와서 엔진의 덧셈과 비교해야 한다.

경계 사례

두께 쌍의 교차 검증은 슬라이더의 범위 끝 두 곳만 본다. 티켓 기록의 리뷰는 중간에서만 드러나는 수식을 놓칠 수 있다고 지적했고, 슬라이더 쌍도 모서리만 보는 것과 같은 방식(티켓 기록은 ADR-0004를 들었다)이라 반영하지 않았다고 적었다. 또 두 두께 선택을 함께 바꾼 조합은 이번에도 보지 않는다.

코드 따라가기

흐름: 실행기의 검증 순서 → 두께 고정 실측 → 교차 검증 요청에 두께 쌍 추가 → 쌍을 읽는 공통 함수 → 어긋남 판정 → 두께 쌍 격자 보강 → 엔진이 격자 나머지를 더함.

1. 실행기: 두께 고정 실측을 수치 검증보다 먼저 본다

순서는 범위 검증, 두께 고정 실측, 수치 검증, 축 반응, 교차 검증이다. 코드 주석이 까닭을 적었다. 슬라이더가 판 두께를 바꾸면 수치 검증의 판 두께 치수 오차보다 "슬라이더 X가 부품 Y의 두께를 바꿈"이 원인을 바로 가리키고, 비율 수식이면 수치 검증은 통과하기 때문이다.

2. 두께 고정 실측

configurator/pipeline/verify-thickness.ts:38는 슬라이더마다 단독 스윕 전체의 샘플과 검증점을 돈다. 슬라이더 범위 밖도 포함한다. 위상 묶음이 있으면 묶음 안 단독 스윕도 잰다. 재계산에 실패했거나 면 구성이 다른 형상은 재지 않는다. 판 두께를 읽는 panelReader(configurator/pipeline/verify-numeric.ts:77)는 수치 검증의 판재 두께 계산과 같은 면 쌍을 쓰도록 이 티켓에서 수치 검증 코드에서 분리했다.

configurator/pipeline/verify-thickness.ts:38-47

export function verifyThicknessFixed(spec: Spec, sweeps: SweepData, bundle: UploadBundle): Feedback[] {
  const read = panelReader(spec, sweeps, bundle);
  const readings = spec.sliders.map((): Reading[] => []);
  for (const { i, sweep, fixed } of sliderSweeps(spec, bundle)) {
    for (const { value, status, faces } of [...sweep.samples, ...sweep.checks]) {
      if (status !== "ok") continue;

      for (const panel of read(values, faces) ?? []) readings[i].push({ measured, place, ...panel });
    }
  }

4. 쌍이 슬라이더 쌍인지 두께 쌍인지

격자 보강과 교차 검증이 같은 판정을 쓰도록 엔진 파일에 configurator/src/engine.ts:75가 생겼다. 둘째 이름은 반드시 슬라이더이고, 첫째가 슬라이더면 슬라이더 쌍, 두께 선택의 첫 파라미터면 두께 쌍이다. 어느 쪽도 아니면 명세에 없는 쌍이다.

configurator/src/engine.ts:75-82

export function findPair(spec: Spec, [a, b]: Pair): PairRef | undefined {
  const j = spec.sliders.findIndex((s) => s.id === b);
  if (j === -1) return undefined;
  const i = spec.sliders.findIndex((s) => s.id === a);
  if (i !== -1) return { kind: "sliders", i, j };
  const choice = spec.thickness.findIndex((c) => c.ids[0] === a);
  return choice === -1 ? undefined : { kind: "thickness", choice, j };
}

피드백이 가리킬 곳은 쌍 종류마다 다르다. configurator/pipeline/verify-cross.ts:87가 슬라이더 쌍이면 앞 슬라이더(sliders[i])를, 두께 쌍이면 그 두께 선택의 후보(thickness[i].options)를 path로 돌려주고, 힌트에 쓰는 이름과 고치는 방법도 함께 준다.

5. 어긋남을 판정하고 이름을 붙인다

두께 쌍에서 판 두께 치수가 어긋나면 dimension_error 대신 thickness_change를 낸다. 코드 주석의 논리는 이렇다. 엔진은 고른 두께를 그대로 두므로, 판 두께가 어긋났다면 그 두께 후보에서 슬라이더가 판 두께를 바꾸었다는 뜻이다. 기본 두께의 경우는 두께 고정 실측으로 확인했다.

6. 격자 보강: 두께 후보마다 슬라이더 방향으로만

처음 실패는 피드백이고, 같은 쌍이 다음 명세에서도 실패하면 보강한다. 두께 쌍의 격자는 configurator/pipeline/verify-cross.ts:115에서 정한다. 기본 두께가 아닌 후보마다 슬라이더의 최솟값·기본값·최댓값(후보가 바깥 고리)을 요청하고, 검증점은 후보마다 슬라이더 마디 사이 가운데다. 기본 두께에서는 덧셈이 그대로 맞으므로 요청하지 않는다. 2쌍 상한에 슬라이더 쌍과 함께 센다.

configurator/pipeline/verify-cross.ts:115-120

  if (ref.kind === "thickness") {
    const choice = spec.thickness[ref.choice];
    const s = spec.sliders[ref.j];
    const along = (vs: number[]) => nonDefaultOptions(choice).flatMap((o) => vs.map((v) => ({ ...defaults, ...thicknessValues(choice, o), [s.id]: v })));
    return { grid: along(gridAxis(s)), checks: along(midpoints(gridAxis(s))) };
  }

엔진은 configurator/src/engine.ts:524로 보정한다. 고른 후보의 나머지(격자 샘플에서 슬라이더 이동량과 두께 후보 이동량을 뺀 것)를 슬라이더 값에 대해 선형으로 보간해 더한다. 후보가 아니면(기본 두께면) 아무것도 더하지 않는다.

configurator/src/engine.ts:524-530

function addThicknessResidual(out: Float64Array, grid: ThicknessGridTrack, option: number, value: number) {
  const residuals = grid.residuals.get(option);
  if (!residuals) return;
  const { lo, hi, t } = bracket(grid.values, value);
  const [a, b] = [residuals[lo], residuals[hi]];
  for (let i = 0; i < out.length; i++) out[i] += a[i] + (b[i] - a[i]) * t;
}

티켓 기록은 두께 격자를 슬라이더 쌍 격자처럼 기본 묶음에서만 쓴다고 적었다. 슬라이더 범위가 다른 위상 묶음에 닿으면 범위 끝 격자 샘플의 면 구성이 기본 형상과 달라 보강하지 않고 topology_change가 나오기 때문이다.

퀴즈

서랍 폭이 body_w - 40 + (body_w - 600) * (t - 18) / 60인 모델에서, 전체 폭을 기본값보다 200 mm 줄이고 두께를 15로 고르면 엔진의 덧셈과 Fusion 서랍 폭은 몇 mm 차이 나는가?

오차는 (폭 변화) × (두께 변화) / 60의 크기다. 폭 변화는 -200, 두께 변화는 15 - 18 = -3이므로 곱이 600이고 60으로 나누면 10 mm다. 기본 폭이 얼마든 같다. 한쪽이 기본이면 오차가 0이다. 두 값이 함께 바뀔 때만 생기므로 단독 스윕만 보는 검증은 이 항을 놓친다.

몸통 셸 두께가 body_w * 0.03인 모델은 수치 검증을 통과하는데도 별도의 두께 고정 실측이 필요하다. 수치 검증을 통과하는 이유는?

문서의 설명은 이렇다. 비율 수식이면 엔진의 보간이 Fusion과 맞아 수치 검증은 통과한다. 그래서 슬라이더가 두께를 바꾼다는 원인은 판 두께를 직접 재는 실측으로만 드러난다. 수치 검증은 엔진 결과와 Fusion 형상을 견주므로, 엔진 보간이 맞으면 두께가 변해도 통과한다. 판 두께 치수도 수치 검증이 재고 있어서 바깥 치수만 본다는 설명은 틀리다.

두께 쌍의 교차 검증에서 판 두께 치수가 어긋나면 dimension_error가 아니라 thickness_change가 나온다. 그렇게 부를 수 있는 근거는?

엔진은 고른 두께의 이동량을 그대로 더하고 보간하지 않으므로, 엔진이 낸 판 두께는 고른 두께와 같다(기본 두께에서는 두께 고정 실측이 통과했다는 전제). 거기서 Fusion과 어긋나면 그 두께에서 슬라이더가 판 두께를 바꾸었다는 뜻이고, 원인을 가리키는 이름이 더 쓸모 있다. 나머지 둘은 코드와 맞지 않는다. 후보 형상을 위상 묶음마다 받는 것은 맞지만 두께가 언제나 위상 변화로 나타나지는 않는다.

명세에 슬라이더가 둘이고 두께 선택이 하나이며 기본이 아닌 후보가 둘이다. 교차 검증 요청의 값 묶음은 모두 몇 개인가?

슬라이더 쌍 하나의 모서리가 2 × 2 = 4곳이다. 두께 쌍은 두께 선택 1개 × 후보 2개 × 슬라이더 2개 × 범위 끝 2곳 = 8곳이다. 합쳐서 12개다.

두께 쌍을 격자로 보강한 상품에서 고객이 기본 두께를 고르고 그 슬라이더를 움직인다. 격자의 나머지 이동량은 어떻게 쓰이는가?

addThicknessResidual은 고른 두께의 나머지가 격자에 없으면 곧바로 돌아온다. 격자는 기본이 아닌 후보에서만 만들어지기 때문이다. 기본 두께에서 슬라이더 효과는 단독 스윕이 담고, 수치 검증이 그 검증점을 잰다. 가까운 후보의 값을 빌리는 일은 없다.

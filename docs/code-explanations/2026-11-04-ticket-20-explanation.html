티켓 20: 최종 승인 편집과 반려

운영자가 최종 승인 화면에서 구성기를 직접 만져 보고, 슬라이더 이름을 고치거나 범위를 좁혀 승인하거나, 반려해서 다른 후보를 고르거나 거절 이유를 적어 후보 제시를 다시 받게 한다.

배경

이 영역이 처음이면 펼쳐서 읽는 기본 배경

이 프로젝트는 AI가 쓴 명세(JSON)와 업로드 때 뽑은 스윕으로, 쇼핑몰에 붙이는 구성기 결과물을 만든다. 파이프라인은 정해진 단계로 진행되고 AI는 단계 안에서만 일한다(ADR-0014). 이 문서가 다루는 사람(운영자)의 결정 자리는 후보 선택과 최종 승인이다. 최종 승인은 결과물을 제출하기 직전의 마지막 사람 결정이다.

명세의 슬라이더에는 이름, 최솟값, 최댓값, 기본값, 한 칸 크기(step)가 있다. 기본값은 업로드한 모델의 값이다. 고정 코어의 슬라이더는 최솟값에서 시작해 step씩 움직인다.

티켓 19까지의 최종 승인은 승인 단추 하나뿐이었다. 사람 결정 포트(HumanPort.finalApproval)는 { decision: "approve" }만 돌려주었고, 화면은 슬라이더 이름·범위를 읽기 전용 목록으로 보였다. 최종 승인 뒤에는 늘 제출로 끝났으므로, 운영자는 마음에 안 들어도 후보로 되돌아갈 방법이 없었다.

새로 쓰는 말은 다음과 같다. 고친 내용(SliderEdits)은 슬라이더 id마다 새 이름과 좁힌 최솟값·최댓값이다. 반려는 두 가지다. 하나는 이미 받은 후보 카드로 후보 선택에 돌아가는 back: "choice"(다른 후보)이고, 다른 하나는 거절 이유를 한 줄 적어 후보 제시를 다시 받는 back: "candidates"다. 거절 이유(rejections)는 새 후보를 만드는 AI 입력에 들어간다.

핵심 개념

최종 승인은 검증을 이미 통과한 명세를 사람이 다듬는 자리다. 그래서 고칠 수 있는 것은 이름과 범위의 좁히기로 한정되고, 기본값은 업로드한 모델의 값이라 고칠 수 없다(코드 주석). 범위 넓히기를 막는 이유는 티켓에 적혀 있지 않다. 이 문서의 추론으로는, 검증을 거치지 않은 범위가 제출에 들어가지 않게 하려는 것으로 보인다.

핵심 아이디어

서랍장 예시로 보자(값은 설명을 위해 정한 것이다). 슬라이더 body_w가 400~800 mm, 기본값 600, step 10이라고 하자. 운영자가 화면에서 최댓값 칸을 700으로 바꾸면, 화면 스크립트가 그 값으로 구성기를 다시 띄워 슬라이더가 400~700으로 보인다(티켓 기록에 확인한 기록이 있다). 승인 단추를 누르면 서버가 같은 값을 다시 검사한 뒤 제출한다.

운영자가 입력결과이유
최대 700승인검증한 범위 안이고 기본값에서 step의 배수
최대 900막힘범위는 좁히기만 할 수 있음
최소 650막힘기본값 600이 범위 밖으로 나감
최소 405막힘기본값에서 step 10의 배수가 아님
이름 "d5 폭"막힘Fusion 파라미터 이름이 들어 있음

표의 마지막 행은 이 상품에 Fusion 파라미터 d5가 있다고 가정한 예다. 막힌 답은 파이프라인을 멈추지 않는다. 같은 명세로 최종 승인을 다시 묻고, 오류 문장과 앞서 고친 값을 화면에 다시 채워 보인다. 티켓 기록은 후보 선택의 잘못된 답처럼 멈추지 않는 까닭을 "운영자가 칸 하나만 고치면 되는 일이라서"라고 적는다.

반려의 두 경로는 되돌아가는 곳이 다르다.

reject / candidates + reason
거절 이유가 rejections에 쌓이고 후보 제시 다시
남긴 한계

사례 기록에는 고친 내용·거절 이유·버려진 후보를 따로 담지 않았다. 사례 저장소는 티켓 21이라서, 지금은 고친 명세가 사례의 spec에 들어갈 뿐이다. 화면 스크립트의 범위 판정도 서버의 검사기와 겹친다. 브라우저 코드에 서버 모듈을 실을 수 없어서이고, 받아들일지는 서버가 정한다(티켓 리뷰 기록).

코드 따라가기

흐름: 결정의 모양(ApprovalDecision, configurator/pipeline/runner.ts:126-133) → 최종 승인 화면(finalApprovalHtml, configurator/pipeline/operator-screens.ts:196-237) → 양식 읽기(readFinalApproval, configurator/pipeline/operator-screens.ts:243-266) → 고친 내용 검사(approvalEditChecker, configurator/pipeline/schemas.ts:430-455) → 다시 묻기(finalApproval, configurator/pipeline/runner.ts:401-411) → 두 고리의 분기(configurator/pipeline/runner.ts:646-656) → 제출(configurator/pipeline/runner.ts:417-421).

1. 사람 결정의 모양

변경 전에는 finalApproval이 승인 한 가지만 돌려주었다. 이제 ApprovalDecision은 세 가지 경우를 판별 태그(decision·back 값으로 경우를 가르는 필드)로 나눈다. 승인은 고친 내용(edits)을 선택적으로 담고, 반려는 back이 choice인지 candidates인지에 따라 거절 이유가 필수가 된다.

configurator/pipeline/runner.ts:126-133

/**
 * 최종 승인의 사람 결정. 반려하면 이미 받은 후보 카드로 후보 선택에 돌아가거나(back: choice, 사용자 스토리 71),
 * 거절 이유를 붙여 후보 제시를 다시 한다(back: candidates, 사용자 스토리 72).
 */
export type ApprovalDecision =
  | { decision: "approve"; edits?: SliderEdits }
  | { decision: "reject"; back: "choice" }
  | { decision: "reject"; back: "candidates"; reason: string };

이 결정을 받는 입력에는 앞 결정이 막힌 까닭 errors와 그 결정이 고친 내용 edits가 더해졌다(configurator/pipeline/runner.ts:243-248).

2. 화면: 구성기를 띄우고 고치는 칸을 둔다

finalApprovalHtml은 구성기를 띄우는 previewHtml(아래 코드)과 고치는 칸 sliderEditHtml(configurator/pipeline/operator-screens.ts:151-163)을 붙여 화면을 만든다. previewHtml은 결과물의 고정 코어 번들(구성기를 그리는 고정 코드), 명세, 스윕 데이터, 스타일 선택을 화면 안에 싣고 구성기를 띄운다. 슬라이더마다 이름·최소·최대 칸이 있고, 범위 칸의 min·max 속성은 좁히기의 한계(승인 전 범위와 기본값)다. 칸 값이 바뀔 때마다 화면 스크립트가 그 값으로 구성기를 다시 띄우고, 범위가 맞지 않는 중간 상태이면 앞의 구성기를 그대로 둔다.

반려 단추 둘에는 formnovalidate가 붙어 고치는 칸의 브라우저 검사를 건너뛴다. 반려하면 고친 내용은 쓰지 않기 때문이다. 스크립트 안에 싣는 번들은 </script를 끊고, JSON은 <를 이스케이프해 요소가 닫히거나 주석이 열리지 않게 한다(configurator/pipeline/operator-screens.ts:136-140).

3. 양식 읽기

readFinalApproval은 단추의 값(decision)으로 경로를 나눈다. 승인이면 슬라이더마다 이름과 범위를 승인 전 명세와 비교해 달라진 것만 고친 내용에 담는다. 빈 칸은 NaN으로 읽는다. Number("")가 0이라서 빈 칸이 숫자 0으로 통과하는 일을 막으려는 처리이고, 코드 주석은 "빈 칸은 숫자가 아니다"라고만 적는다.

configurator/pipeline/operator-screens.ts:243-266

export function readFinalApproval(form: URLSearchParams, spec: Spec): ApprovalDecision | { errors: string[] } {
  const decision = form.get("decision");
  if (decision === "choice") return { decision: "reject", back: "choice" };
  if (decision === "candidates") {
    const reason = form.get("reason") ?? "";
    const errors = rejectionReasonErrors(reason);
    return errors.length > 0 ? { errors } : { decision: "reject", back: "candidates", reason: reason.trim() };
  }
  if (decision !== "approve") return { errors: ["/decision: 승인(approve)하거나 반려(choice, candidates)하세요"] };

  const edits: SliderEdits = {};
  for (const slider of spec.sliders) {
    const text = (field: "name" | "min" | "max") => (form.get(editField(field, slider.id)) ?? "").trim();
    // 빈 칸은 숫자가 아니다(Number("")는 0)
    const number = (field: "min" | "max") => (text(field) === "" ? NaN : Number(text(field)));
    const edit: SliderEdits[string] = {};
    if (text("name") !== slider.name) edit.name = text("name");
    if (number("min") !== slider.min) edit.min = number("min");
    if (number("max") !== slider.max) edit.max = number("max");
    if (Object.keys(edit).length > 0) edits[slider.id] = edit;
  }
  const errors = approvalEditChecker(spec)(edits);
  return errors.length > 0 ? { errors } : { decision: "approve", edits };
}

4. 고친 내용 검사

approvalEditChecker가 승인 전 명세 안에서의 변경인지 본다. 범위는 좁히기만 하고(newMin < slider.min이면 오류), 기본값이 범위 안에 남아야 하며(newMin > base 또는 newMax < base이면 오류), 고친 끝은 기본값에서 step의 배수만큼 떨어져 있어야 하고, 한 값뿐인 범위는 안 된다. 숫자로 읽지 못한 칸은 이름 오류를 가리지 않도록 따로 모은다(인용하지 않은 436~439행). 오류 문장은 JSON 경로(/body_w/max: …)로 시작한다.

configurator/pipeline/schemas.ts:421-424

const onStep = (value: number, { default: base, step }: { default: number; step: number }) => {
  const k = (base - value) / step;
  return Math.abs(k - Math.round(k)) < 1e-9;
};

      else if (max !== undefined && !onStep(newMax, slider)) errors.push(`/${id}/max: 기본값 ${base}에서 step ${step}의 배수만큼 떨어진 값으로 적으세요(예: ${near(newMax)})`);
      if (errors.length === 0 && newMin === newMax) errors.push(`/${id}/max: ${newMin + step} 이상으로 적으세요. 범위가 한 값뿐이면 슬라이더를 움직일 수 없습니다`);
      return errors;

5. 실행기: 받아들일 수 있을 때까지 다시 묻기

approvalErrors는 반려의 거절 이유를 한 줄 검사하고, 승인의 고친 내용은 위 검사기를 거친 뒤 고친 명세로 형식 검사(checkSpec)와 Fusion 파라미터 이름 검사(specReferenceChecker)까지 돌린다. 이름 검사가 여기서 다시 돈다. 운영자가 쓴 이름도 AI가 쓴 이름과 같은 규칙을 받는다. 실행기의 finalApproval 함수(포트 메서드와 이름이 같다)는 오류가 있으면 처리 기록(단계마다 남기는 log)에 { errors }를 남기고 같은 명세로 다시 묻는다.

configurator/pipeline/runner.ts:391-411

  function approvalErrors(spec: Spec, answer: ApprovalDecision): string[] {
    if (answer.decision === "reject") return answer.back === "choice" ? [] : rejectionReasonErrors(answer.reason);
    if (!answer.edits) return [];
    const errors = approvalEditChecker(spec)(answer.edits);
    if (errors.length > 0) return errors;
    const edited = applyEdits(spec, answer.edits);
    return [...checkSpec(edited), ...specReferenceChecker(uploaded)(edited)];
  }

  /** 받아들일 수 있는 결정이 올 때까지 최종 승인을 다시 묻는다. 다시 물을 때는 앞 결정의 오류와 고친 내용을 보인다. */
  async function finalApproval(spec: Spec, files: ProductFiles, judgment: Feedback[]): Promise<ApprovalDecision> {
    let errors: string[] = [];
    let edits: SliderEdits = {};
    for (;;) {
      const answer = await human.finalApproval({ spec, files, judgment, errors, edits });
      errors = approvalErrors(spec, answer);
      edits = answer.decision === "approve" ? (answer.edits ?? {}) : {};
      if (errors.length === 0) return answer;
      await log("approval", { errors });
    }
  }

6. 두 고리: 후보 선택과 후보 제시

변경 전의 실행기는 후보 제시 고리 하나였다. 이제 그 안에 후보 선택 고리가 하나 더 있다. 승인하면 고친 명세로 제출하고 끝난다. 반려 중 "다른 후보"는 continue로 같은 카드의 후보 선택으로 돌아가고, 거절 이유가 있는 반려는 rejections에 후보와 이유를 쌓은 뒤 break로 안쪽 고리를 나가 후보 제시를 다시 한다. 검증에 실패해 후보를 버리는 경우(failures)도 같은 break다.

configurator/pipeline/runner.ts:646-656

        const answer = await finalApproval(written.spec, files, judgment);
        await log("approval", answer);
        if (answer.decision === "reject") {
          if (answer.back === "choice") continue;
          rejections.push({ candidate, reason: answer.reason.trim() });
          break;
        }

        await submit(applyEdits(written.spec, answer.edits ?? {}), files, candidates, candidate);
        return { status: "submitted" };
      }

후보 제시 입력에는 rejections가 더해졌고({ candidate, reason } 목록, 이 상품에서 쌓인 것 모두), 지시문은 "그 거절 이유를 따르도록 구성을 고치고, 반려된 후보를 같은 구성으로 다시 내지 않는다"고 적는다(configurator/pipeline/litellm-ai.ts:82).

7. 제출: 좁힌 명세로 결과물 다시 만들기

퀴즈

최종 승인에서 슬라이더 범위를 넓힐 수 없게 한 가장 알맞은 이유는?

좁힌 범위는 검증을 거친 범위의 일부이므로 다시 검증하지 않고 제출한다. 넓힌 범위는 검증된 적이 없어 뚫림·겹침이나 덧셈 오차가 있을 수 있다. 그래서 넓히기는 막고 좁히기만 받는다.

기본값 500, step 10, 승인 전 범위 400~800인 슬라이더의 최솟값 칸에 405를 적고 승인했다. 결과는?

고정 코어의 슬라이더는 최솟값에서 step씩 움직이므로 405에서 시작하면 500에 닿지 못한다. 기본값에서 step의 배수만큼 떨어진 값(예: 400, 410)이어야 한다. 막힌 답은 멈춤이 아니라 오류 문장을 붙인 재질문이다.

운영자가 슬라이더 이름을 d5 폭으로 고쳐 승인했다. 어디서 걸리는가?

approvalErrors가 고친 명세에 specReferenceChecker를 돌린다. 이 검사는 명세 작성 때와 같아서 이름에 Fusion 파라미터 이름이 낱말로 있으면 오류를 낸다. 운영자가 쓴 이름도 AI가 쓴 이름과 같은 규칙을 받는다.

운영자가 "반려하고 다른 후보 고르기"를 눌렀다. 바로 이어지는 일은?

이 경로는 후보 선택 고리의 continue다. 후보 제시를 다시 하지 않고 이미 받은 카드를 그대로 쓴다. AI가 새 후보를 만드는 경로는 거절 이유를 적은 반려이고, 이때 고친 내용은 쓰이지 않는다.

승인 뒤 제출할 때 검증을 다시 하지 않고 sweeps.json만 다시 거르는 까닭은?

범위를 좁히기만 하므로 검증한 형상의 부분집합이다. 스윕 데이터는 좁힌 범위가 닿지 않는 위상 묶음을 빼려고 다시 거르며, 이 거르기는 업로드 묶음을 거르는 방법과 같다.

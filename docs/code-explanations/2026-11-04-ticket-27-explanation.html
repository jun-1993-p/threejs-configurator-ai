티켓 27: VLM에 보내는 그림을 모음 그림으로 묶기

VLM이 요청 하나에 받는 그림 수가 3장으로 제한되어 있어, 부품 탐색과 AI 판정이 보내는 여러 그림을 칸을 이어 붙인 모음 그림으로 묶고, 그래도 넘으면 AI 판정을 나눠 묻는다.

배경

처음 보는 사람을 위한 배경

VLM(그림을 읽는 언어 모델)은 글과 그림을 함께 받아 글로 답한다. 이 프로젝트는 AI를 외부 API로 부르고(ADR-0015), 그 사이에 LiteLLM 프록시를 둔다. 파이프라인 실행기는 AI를 "포트"(AiPort)로만 알고 있고, 포트 뒤에서 실제로 LiteLLM에 요청을 보내는 것이 liteLlmAi다. 그림은 요청에 base64 PNG로 붙는다.

AI가 그림을 보는 단계는 둘이다. 부품 탐색은 기본 형상을 여섯 방향에서 그린 그림을 보고 부품(서랍, 몸통, 상판 등)을 찾는다. AI 판정은 수치 검증을 모두 통과한 뒤 슬라이더 끝값과 모서리 조합을 그린 렌더링을 보고 뚫림, 겹침, 비례 깨짐만 찾는다(수치로 잡을 수 없는 것만 본다).

티켓 26 6절의 실행 기록에서 Groq VLM(qwen/qwen3.8-27b)이 요청 하나에 그림을 3장까지만 받는다는 것이 드러났다. 그런데 부품 탐색은 6장을 보내고, AI 판정은 슬라이더가 n개일 때 2n + 4·C(n,2)장을 보낸다. 슬라이더가 둘이면 8장, 셋이면 18장, 넷이면 32장이다. 그래서 파이프라인이 첫 단계에서 멈췄다.

용어(GLOSSARY.md)

모음 그림은 여러 장의 그림을 크기를 바꾸지 않고 칸으로 격자에 이어 붙인 그림 한 장이다. 한 장에 3×3칸까지다. 문장에는 칸마다 어떤 그림인지(몇째 모음 그림의 몇째 줄 몇째 칸)를 적는다.

주의

AI 판정은 슬라이더 끝값끼리 크기 차이가 보여야 의미가 있다. 렌더링은 모두 같은 축척으로 그려지므로, 모음 그림으로 묶을 때 크기를 바꾸면 이 차이가 사라진다. 티켓의 네 번째 조건이 이것이다.

핵심 아이디어

핵심 아이디어는 "그림 수 제한은 요청에 붙는 파일 수 제한이지, 보이는 칸 수 제한이 아니다"이다. 칸 아홉 개를 한 장에 붙이면 요청 하나로 최대 27장 분량(3장 × 9칸)을 보낼 수 있다. 대신 모델이 어느 칸이 무엇인지 알려면 문장에 칸 배치를 적어야 한다. 예컨대 부품 탐색의 여섯 방향 그림은 3칸 × 2줄 모음 그림 한 장이 되고, 문장에는 이렇게 간다.

입력 순서방향(from)sheetrowcolumn
1+X111
2-X112
3+Y113
4-Y121
5+Z122
6-Z123

(방향 이름과 순서는 이 설명을 위한 예시다. 실제 순서는 실행기가 정한다.) 320×240 칸이면 이 모음 그림은 3·320+2·4 = 968, 2·240+4 = 484로 968×484다. 칸 사이는 4픽셀 회색 경계다.

AI 판정은 한 걸음 더 간다. 모음 그림이 3장을 넘기면 렌더링을 순서대로 나눠 요청을 여러 번 보낸다. 슬라이더 넷, 렌더링 32장이면 첫 요청이 27장(모음 그림 3장), 둘째 요청이 5장(모음 그림 1장)이다. 각 요청의 답에서 나온 문제 목록(problems)을 하나로 합쳐 실행기에는 하나의 답으로 돌려준다.

렌더링 32장
27장 + 5장
나눔
모음 그림 3장 / 1장
VLM 요청 둘
problems 둘
합침
ok: 답 하
답 하나

이 변경은 포트 안에서 끝난다. 실행기의 단계, 형식 검사, 다시 묻기는 바뀌지 않는다.

코드 따라가기

흐름: liteLlmAi의 부품 탐색 또는 AI 판정 → 그림을 모음 그림으로 묶는 imageSheets → 칸 위치를 문장에 싣고 요청 → (AI 판정만) 나눈 답 합치기.

1. 모음 그림 만들기

새 파일 image-sheet.ts가 격자 크기(3×3칸)와 경계(4픽셀, 어두운 회색)를 정한다.

configurator/pipeline/image-sheet.ts:8-15

/** 모음 그림 한 장의 격자. 320×240 칸이면 한 장이 968×728이다. */
export const SHEET_COLUMNS = 3;
const SHEET_ROWS = 3;
export const SHEET_CELLS = SHEET_COLUMNS * SHEET_ROWS;

/** 칸 사이 경계(픽셀)와 색. 렌더링 바탕색(밝은 회색)과 구별되게 어둡게 둔다. */
const GAP = 4;
const GAP_COLOR: Rgb = [120, 120, 120];

imageSheets는 PNG(base64) 목록을 받아 모음 그림 목록과 칸 위치를 돌려준다. PNG를 읽어(decodePng, 8비트 RGB에 비월 없는 형식만 받는다. 입력이 이 프로젝트의 렌더러가 만든 그림뿐이기 때문이다) 크기를 바꾸지 않고 칸에 붙인다. 칸 크기는 가장 큰 그림에 맞추고 작은 그림은 칸 왼쪽 위에 그대로 놓는다.

configurator/pipeline/image-sheet.ts:68-95

export function imageSheets(images: string[]): { sheets: string[]; cells: Cell[] } {
  if (images.length === 0) return { sheets: [], cells: [] };
  const decoded = images.map((image) => decodePng(Buffer.from(image, "base64")));
  const cellWidth = Math.max(...decoded.map((d) => d.width));
  const cellHeight = Math.max(...decoded.map((d) => d.height));
  const cells = decoded.map((_, i) => ({
    sheet: Math.floor(i / SHEET_CELLS) + 1,
    row: Math.floor((i % SHEET_CELLS) / SHEET_COLUMNS) + 1,
    column: (i % SHEET_COLUMNS) + 1,
  }));
  const sheets: string[] = [];
  for (let start = 0; start < decoded.length; start += SHEET_CELLS) {
    const onSheet = decoded.slice(start, start + SHEET_CELLS);
    const columns = Math.min(SHEET_COLUMNS, onSheet.length);
    const rows = Math.ceil(onSheet.length / SHEET_COLUMNS);
    const width = columns * cellWidth + (columns - 1) * GAP;
    const height = rows * cellHeight + (rows - 1) * GAP;
    const rgb = new Uint8Array(width * height * 3);
    for (let i = 0; i < width * height; i++) rgb.set(GAP_COLOR, i * 3);
    onSheet.forEach((image, k) => {
      const { row, column } = cells[start + k];
      const [left, top] = [(column - 1) * (cellWidth + GAP), (row - 1) * (cellHeight + GAP)];
      for (let y = 0; y < image.height; y++) rgb.set(image.rgb.subarray(y * image.width * 3, (y + 1) * image.width * 3), ((top + y) * width + left) * 3);
    });
    sheets.push(encodePng(rgb, width, height).toString("base64"));
  }
  return { sheets, cells };
}

칸 위치는 입력 순서 i에서 정해진다: 모음 그림 번호는 ⌊i/9⌋+1, 줄은 ⌊(i mod 9)/3⌋+1, 칸은 (i mod 3)+1. 11번째 그림(i=10)이면 둘째 모음 그림의 첫째 줄 둘째 칸이다. 렌더러의 encodePng를 내보내 모음 그림을 같은 방식으로 다시 인코딩한다(configurator/pipeline/render.ts:135).

2. 설정: 그림 수 제한

liteLlmAi의 옵션 maxImages가 요청 하나에 붙일 모음 그림 수다. 기본값 3은 Groq VLM의 제한이다(configurator/pipeline/litellm-ai.ts:27). 실행 도구는 환경 변수 LITELLM_VLM_MAX_IMAGES로 바꾼다. 0이나 NaN을 막는 검사가 만들 때 있다(litellm-ai.ts:176). 티켓의 리뷰 기록에 따르면 0이면 판정이 끝나지 않거나 그림 없이 통과했다.

3. 부품 탐색: 한 장으로

configurator/pipeline/litellm-ai.ts:211-214

    findParts: ({ views, ...input }) => {
      const { sheets, cells } = imageSheets(views.map((v) => v.image));
      return ask("parts", `${PARTS_PROMPT}\n${OUTPUT_RULES(PARTS_SCHEMA)}`, { ...input, views: views.map((v, i) => ({ from: v.from, ...cells[i] })) }, sheets);
    },

여섯 방향 그림이 한 장으로 가고, views는 { from, sheet, row, column } 목록이 된다. 지시문도 바뀌어 칸마다 어느 쪽에서 본 그림인지와 모음 그림이 무엇인지(SHEET_RULE, litellm-ai.ts:86)를 알린다. 부품 탐색은 나누지 않는다. 여섯 칸은 늘 한 장이고 그림 수 제한은 1 이상이기 때문이다.

4. AI 판정: 나눠 묻고 합치기

configurator/pipeline/litellm-ai.ts:221-243

    judge: async ({ renders, ...input }) => {
      const problems: unknown[] = [];
      let merged = {};
      for (let start = 0; start < renders.length; start += maxImages * SHEET_CELLS) {
        const part = renders.slice(start, start + maxImages * SHEET_CELLS);
        const { sheets, cells } = imageSheets(part.map((r) => r.image));
        const answer = await ask(
          "judgment",
          `${JUDGMENT_PROMPT}\n${OUTPUT_RULES(judgmentSchema(part.map((r) => r.name)))}`,
          { ...input, renders: part.map(({ name, values }, i) => ({ name, values, ...cells[i] })) },
          sheets,
        );
        // 형식이 틀린 답은 그대로 돌려줘 실행기의 형식 검사에 걸리게 한다. 다시 물을 때는 나눈 요청을 모두 다시 묻는다.
        const found = (answer as { problems?: unknown } | null)?.problems;
        if (!Array.isArray(found)) return answer;
        // 이 요청에 보내지 않은 렌더링은 모델이 보지 못한 그림이라 짚은 문제를 버린다. 모르는 이름은 남겨 형식 검사에 걸리게 한다.
        const elsewhere = new Set(renders.filter((r) => !part.includes(r)).map((r) => r.name));
        problems.push(...found.filter((p) => !elsewhere.has((p as { image?: string } | null)?.image as string)));
        // problems 밖의 필드도 남겨, 출력 형식에 없는 필드는 실행기의 형식 검사에 걸리게 한다
        merged = { ...merged, ...(answer as object) };
      }
      return { ...merged, problems };
    },

반복은 요청마다 maxImages * SHEET_CELLS개(기본 27개) 렌더링을 잘라 묻는다. 출력 형식의 그림 이름은 그 요청의 렌더링 이름만 허용한다. 처리 중 결정이 셋 있다.

  • 형식이 틀린 답(problems가 목록이 아님)은 합치지 않고 그대로 돌려줘 실행기의 형식 검사에 걸리게 한다(litellm-ai.ts:235).
  • 그 요청에 보내지 않은 렌더링을 짚은 문제는 버린다(litellm-ai.ts:237). 티켓 기록에 따르면 실행기는 합친 답을 전체 렌더링 이름으로 검사하므로, 모델이 보지 못한 그림을 짚은 답이 걸리지 않고 지나가기 때문이다.
  • problems 밖의 필드와 모르는 이름은 남겨 형식 검사에 걸리게 한다(litellm-ai.ts:240).
티켓이 남긴 한계

실행기가 다시 물을 때 주는 rejected·schemaErrors는 합친 답 기준이라 나눈 요청 모두에 간다. 실행기의 다시 묻기를 바꾸지 않는다는 요구 때문이다. 오류 문장이 렌더링 이름을 짚으므로 모델이 자기 요청 몫을 가릴 수 있다고 본다(티켓의 판단). 실제 모델에서 다시 묻기가 늘면 요청별로 나눈다. 또 렌더링이 27장을 넘으면(슬라이더 넷부터) 끝값 렌더링과 일부 모서리 조합이 다른 요청으로 가는데, 끝값 렌더링이 앞에 있어 첫 요청에 함께 들어가므로 끝값끼리는 늘 나란히 본다.

5. 시험

litellm-ai.test.ts에 시험 다섯 개가 더해졌다. 32장 렌더링이 3장과 1장 두 요청으로 가는지, 둘째 모음 그림의 가운데 칸이 원래 픽셀 그대로인지(같은 축척), 나눈 답 하나가 형식이 틀리면 그 답을 돌려주는지, 보내지 않은 렌더링을 짚은 문제가 버려지는지, 그림 수 제한이 잘못되면 포트를 만들지 않는지를 본다.

퀴즈

슬라이더가 넷이라 렌더링이 32장일 때, 기본 설정에서 AI 판정은 몇 번 묻는가?

요청 하나에 모음 그림 3장 × 9칸 = 27칸까지 붙는다. 32장에서 27장을 잘라 첫 요청, 남은 5장이 둘째 요청이다. 그림 수 제한은 모음 그림 수에 걸리지 칸 수에 걸리지 않는다.

320×240 렌더링 아홉 장 사이에 200×100 렌더링이 하나 섞여 있다. 그 렌더링은 모음 그림에서 어떻게 놓이는가?

imageSheets는 칸 크기를 가장 큰 그림에 맞추고 작은 그림은 왼쪽 위에 붙인다. 크기를 바꾸면 슬라이더 끝값끼리 크기 차이가 사라지므로 같은 축척 요구가 깨진다.

입력 순서로 11번째 렌더링(i=10)이 놓이는 칸은?

한 장은 9칸이므로 i=10은 둘째 모음 그림(⌊10/9⌋+1)이고, 그 안에서 10 mod 9 = 1번째(0부터)이므로 첫째 줄(⌊1/3⌋+1)의 둘째 칸(1 mod 3 + 1)이다.

요청을 나눠 묻는 AI 판정에서, 어느 요청이 그 요청에 보내지 않은 렌더링을 짚은 문제를 돌려주면 버리는 까닭은?

형식 검사는 합친 답을 전체 렌더링 이름으로 검사하므로 보내지 않은 이름도 유효한 이름이다. 그래서 포트 안에서 버린다. 모르는 이름은 반대로 남겨 형식 검사에서 걸리게 한다. (중복 이유는 실행기가 별도로 ; 로 이어 붙인다.)

부품 탐색은 AI 판정과 달리 그림 수 제한을 넘는 경우를 나누지 않는다. 가장 알맞은 까닭은?

여섯 방향은 3×3칸 안에 들어가므로 모음 그림이 늘 한 장이고, 제한은 만들 때 1 이상의 정수로 검사한다. 어느 설정에서도 그림 수 제한을 넘지 않는다.

티켓 26: 실제 키로 예비 모델 전환을 확인하며 바뀐 것들

LLM·VLM을 실제 API 키로 돌려 보는 확인 절을 만들었더니, 첫 모델이 Cerebras에서 Groq로, VLM 이름과 속도 제한 처리가 바뀌고, 끝내 로컬 예비 모델이 빠졌다. 최종 상태를 기준으로 그 이유를 설명한다.

jun-1993-p/threejs-configurator-ai 8d7cf78, explained 2026-11-04. 포함한 커밋 7개: 422814e, 8d3a519, 0040614, 4c96ebe, 1d47b40, 86236f4, 8d7cf78 (모두 티켓 26의 예비 모델 전환·VLM 확인 부분). References link to this commit.

Background

New to this area? Expand for the deeper background.

이 프로젝트는 Fusion CAD 모델을 쇼핑몰용 three.js 구성기로 바꾼다. 중간의 파이프라인(상품 후보 제시, 부품 탐색, 명세 작성, AI 판정)은 단계마다 AI 모델에게 묻는다. 글만 읽는 모델을 LLM, 그림도 읽는 모델을 VLM이라고 부른다.

AI를 직접 부르지 않고 LiteLLM이라는 중계 서버(프록시)를 거친다. 파이프라인은 llm, vlm, embedding이라는 이름만 부르고, 그 이름이 실제로 어느 회사의 어느 모델인지는 LiteLLM 설정 파일이 정한다. 그래서 모델을 바꿀 때 파이프라인 코드는 건드리지 않는다.

외부 API 무료 등급에는 분당 처리량 제한이 있다. 제한을 넘으면 서버가 HTTP 429(속도 제한) 오류를 내고, 보통 얼마나 기다리라는 시간도 함께 알려 준다. 로컬 모델은 Ollama라는 프로그램이 Docker 안에서 돌린다. 모델이 클수록 메모리가 많이 들고, GPU가 없으면 CPU가 느리게 계산한다.

이 변경이 건드리는 약속은 ADR-0015다. 원문 제목은 「AI 모델은 외부 API를 쓰고 로컬 모델을 예비로 둔다」이다. LLM과 VLM은 외부 API의 무료 등급으로 부르고, 외부 API를 쓸 수 없게 되면 LiteLLM 설정만 바꿔 로컬 모델로 갈아탈 수 있게 한다는 내용이다. 용어집은 이때 대신 불리는 모델을 예비 모델이라고 정의한다.

티켓 22(Docker 구성과 예비 모델)는 이 전환을 가짜 응답과 작은 모델(qwen2.5:3b)로만 확인하고, 실제 키로 도는 확인은 티켓 26으로 넘겼다. 티켓 26은 Fusion이 필요한 사람 확인을 모아 둔 티켓이다. 그 6절 「실제 키로 예비 모델 전환 확인」이 이 문서의 주제다. 6절은 Docker 구성을 띄우고 .env에 실제 키를 넣은 뒤, 어느 모델이 답했는지를 LiteLLM 응답 헤더 x-litellm-model-group으로 본다.

확인에 쓰는 입력은 합성 서랍장 녹화본(fixtures/synthetic/drawer.json)이다. 실제 상품 대신 만든 가짜 녹화본이라 Fusion 없이 파이프라인을 끝까지 돌릴 수 있다. 돌린 기록은 처리 기록(log.json)에 남고, 모델의 답이 형식 검사(JSON Schema)에 걸려 다시 물은 횟수도 거기서 센다.

용어 몇 개를 먼저 정해 둔다. 위저드는 사람이 해야 하는 단계만 묻고 나머지는 스크립트가 하는 셸 스크립트다(6절 전용). 부품 탐색과 AI 판정은 VLM에 그림을 보여 주는 파이프라인 단계다. 모음 그림은 여러 그림을 격자로 이어 붙여 한 장으로 만든 그림이고(티켓 27), Groq VLM이 요청 하나에 받는 그림 수 제한 때문에 쓴다. 형식 오류는 모델의 답이 JSON Schema 검사에 걸리는 일이고, 그러면 파이프라인이 다시 묻는다.

Key concept 예비 모델은 외부 API가 응답하지 않거나 오류를 낼 때 LiteLLM이 대신 부르는 로컬 모델이다(GLOSSARY.md:221-223). 파이프라인은 어느 모델이 답했는지 모르고 입출력 형식은 같다. 최종 커밋에서는 이 정의 끝에 「개발 PC 사양으로는 돌지 않아 지금은 두지 않는다」가 붙는다.

Intuition

전환 설계는 가짜 응답으로만 확인되어 있었고(티켓 22), 6절은 그 설계를 실제 키와 실제 PC로 돌려 본 자리다. 부딪칠 때마다 가정 하나가 깨졌다. 큰 변경 셋을 한 줄씩 요약하면 이렇다.

결과적으로 바뀐 것은 모델 배치만이 아니다. 실패하면 다음 모델이 받던 방식에서, 속도 제한은 기다리고 나머지 실패는 그대로 드러내는 방식으로 실패를 다루는 법이 달라졌다. ADR은 그 뒷부분을 이렇게 적는다. Groq가 실패하면 그 실행은 실패하고, 최종 확인 도구가 끊긴 실행으로 남겨 다시 돌린다.

되돌린 결정 로컬 예비를 단번에 뺀 것은 아니다. 처음에는 VLM을 qwen3-vl:8b에서 4b로 낮추고, 다음에는 설정은 두고 개발 PC에서만 확인을 건너뛰었으며, 마지막에 실측 뒤 설정에서 지웠다. 마지막에 설정까지 지운 이유를 뺀 나머지는 기록에 있고, 아래 코드 순서에서 하나씩 짚는다.

Code walkthrough

흐름: 확인 절 추가 → 첫 모델을 Groq로 바꾸고 확인 위저드 추가 → 첫 실행에서 VLM 이름·문맥 길이·경로 변환 수정 → 속도 제한 대기 → 로컬 VLM 낮추기 → 개발 PC에서 로컬 확인 건너뛰기 → 로컬 예비 제거.

1. 6절을 만든다 (422814e)

티켓 26 5절에 있던 「Cerebras·Groq 실제 키로 llm·vlm이 답하는지」 항목을 새 6절로 옮기고, 티켓 22의 체크 항목에는 「티켓 26 6절로 옮김」이라고 적었다. 6절 항목은 이렇다. Cerebras 키로 llm·vlm이 답하는지, Cerebras VLM 이름 qwen3.8-27b가 실제 모델 이름인지, Cerebras 키를 비우면 Groq가, 둘 다 비우면 로컬 모델이 답하는지, 그리고 각 경우에 합성 서랍장으로 파이프라인을 돌려 형식 오류가 다음 단계로 새지 않는지를 본다.

.scratch/configurator-pipeline/issues/26-fusion-real-check.md:40-42 

### 6. 실제 키로 예비 모델 전환 확인 (티켓 22에서 옮김)

Docker 구성(`docs/docker.md`)을 띄우고 `.env`에 실제 키를 넣어 확인한다. 어느 모델이 답했는지는 LiteLLM 응답 헤더 `x-litellm-model-group`으로 본다.

2. 첫 모델을 Groq로 바꾸고 Cerebras를 뺀다 (8d3a519)

기록의 이유는 하나다. Cerebras 가입에 카드 등록이 필요해 뺐다. 설정은 Cerebras 1순위, llm-groq·vlm-groq 2순위, 로컬 3순위의 세 칸이 이어진 순서였는데, 앞 두 칸이 하나로 합쳐져 llm·vlm이 곧바로 Groq가 되었다. 넘어갈 순서를 적는 fallbacks는 llm: [llm-local]처럼 한 칸으로 줄었다.

이 시점의 diff는 Cerebras 블록을 지우고 Groq 블록의 이름을 올린다.

docker/litellm/config.yaml, 8d3a519의 변경

  - model_name: llm
    litellm_params:
      model: cerebras/gpt-oss-120b
      api_key: os.environ/CEREBRAS_API_KEY
  - model_name: llm-groq
    litellm_params:
      model: groq/openai/gpt-oss-120b
      api_key: os.environ/GROQ_API_KEY
# elided: vlm 쪽의 같은 변경과 embedding 설정
    - llm: [llm-groq, llm-local]
    - vlm: [vlm-groq, vlm-local]
    - llm: [llm-local]
    - vlm: [vlm-local]

같은 커밋이 .env.example, 구성 파일, 용어집, 설명 문서를 맞추고, ADR-0015 본문의 외부 API 이름을 고친 뒤 「바뀐 것」 절을 새로 달아 바꾼 이유를 날짜와 함께 적는다. 설정 시험도 따라 바뀐다: 시험은 llm·vlm이 groq/로 시작하고 예비가 로컬 모델 하나인지 본다.

이 커밋은 확인 절차를 안내하는 위저드(scripts/fallback-check-wizard.sh)도 처음 만든다. 사람이 해야 하는 일은 키를 만들어 붙여 넣는 것뿐이고, 나머지는 스크립트가 한다. 최종 모습에서 핵심 두 단계가 있다. 하나는 Groq가 내놓는 모델 목록을 받아 설정의 모델 이름이 거기 있는지 보는 단계이고(scripts/fallback-check-wizard.sh:297-324), 하나는 키를 넣은 채 LiteLLM만 다시 띄우고 파이프라인을 돌리는 단계다.

scripts/fallback-check-wizard.sh:209-212 

litellm_with_key() {
  GROQ_API_KEY="$1" docker compose up -d --force-recreate --no-deps litellm
  until curl -sf "$LITELLM/health/liveliness" >/dev/null; do sleep 2; done
}

셸 환경 변수는 .env보다 앞서므로, 이 함수가 키를 바꿔 끼워 LiteLLM을 다시 만든다. 처음에는 같은 함수에 빈 키를 넘겨 「Groq 키를 비우면 로컬 모델이 답하는가」를 보는 2회차도 있었는데, 뒤에서 나오듯 지금은 Groq 회차만 남았다.

위저드를 처음 돌린 기록이 티켓 26에 남았다(26-fusion-real-check.md:55-62). 나온 문제는 넷이고 고친 곳은 서로 다르다.

경로 변환 수정은 바로 위 두 줄 주석에 범위를 남긴다. 아래는 마지막 커밋에서 --no-deps가 붙은 최종 모습의 실행 줄이다.

scripts/fallback-check-wizard.sh:244-245 

  # --no-deps: 없으면 compose가 litellm_with_key로 띄운 litellm을 .env 설정으로 다시 만들어, 재시작 중에 연결이 거부된다.
  MSYS_NO_PATHCONV=1 docker compose run --rm -T --no-deps -e CASES_DIR="/app/$out/cases" pipeline scripts/run-pipeline.ts \

MSYS_NO_PATHCONV=1은 이 명령 앞에만 붙는다. 컨테이너 안 경로 /app/…를 Git Bash가 Windows 경로로 바꾸지 못하게 막되, 위저드의 다른 명령(curl이 읽는 /tmp/… 임시 파일)은 변환을 받게 한다. --no-deps는 마지막 커밋에서 붙었다: docker compose run이 의존 서비스 litellm을 .env 설정으로 다시 만들어 버리기 때문이다. 별도 커밋인 4c96ebe는 위저드가 요약 파일에 돌린 커밋(git log -1)을 남기게 하는 한 줄 수정이다.

그림 3장 제한은 기록으로 확인되는 결과이고, 해결은 이 문서의 범위 밖이다. 0040614는 티켓 27(VLM에 보내는 그림을 모음 그림으로 묶기)을 새로 만들고, 티켓 23의 「그림 수 제한에 걸리면 나눠 묻는다」 항목에 「티켓 26 6절에서 걸렸다. 미룸(티켓 27)」을 덧붙인다. 최종 상태의 파이프라인 코드에서 maxImages 기본값 3이 이 제한을 따른다(configurator/pipeline/litellm-ai.ts:26-27).

4. 속도 제한은 기다려 다시 묻는다 (1d47b40)

티켓 27로 그림이 모음 그림이 된 뒤의 두 번째 실행에서, 부품 탐색은 형식 오류로 두 번 다시 물었고 세 번째 물음에서 Groq 무료 등급 VLM의 분당 입력 토큰 제한 7,000에 걸렸다. 요청 하나가 약 2,750토큰이니 한 분에 세 번이면 8,250이다(계산은 이 문서 쓴 사람의 것). 그때 설정은 num_retries: 0이어서 바로 로컬 VLM으로 넘어갔고, 8b 모델은 CPU에서 9분 40초 뒤 그림을 읽다 죽었다.

고친 방향은 「속도 제한만 기다린다」다. 현재 설정은 이렇다.

docker/litellm/config.yaml:24-33 

  # Groq가 이 시간(초) 안에 답하지 않으면 실패로 돌려준다
  timeout: 120
  # 속도 제한(429)만 Groq가 알려 준 대기 시간(60초 이하)을 기다려 다시 묻는다. 무료 등급 VLM은 분당 입력 7천 토큰이라
  # 모음 그림 요청(약 2,750토큰)을 1분에 세 번 물으면 걸린다(티켓 26 6절). 다른 오류는 다시 묻지 않고 실패로 돌려준다.
  # 다시 물으면 응답하지 않는 Groq를 제한 시간만큼 한 번 더 기다린다. 최종 확인 도구는 실패를 끊긴 실행으로 남겨 다시 돌리게 한다.
  # num_retries가 0이면 LiteLLM이 retry_policy를 보지 않아, 0이 아닌 값으로 두고 횟수는 retry_policy로 정한다.
  num_retries: 3
  retry_policy:
    DefaultRetries: 0
    RateLimitErrorRetries: 3

읽는 법: 일반 오류의 재시도는 0번(DefaultRetries), 속도 제한 오류의 재시도는 3번(RateLimitErrorRetries)이다. 그런데 num_retries가 0이면 LiteLLM이 retry_policy를 아예 보지 않는다고 설정 주석은 말한다. 그래서 num_retries는 0이 아닌 3으로 두고, 실제 횟수는 정책이 정하게 했다. 티켓 26 6절 두 번째 실행 기록에 따르면 컨테이너 안 Router에 같은 설정과 가짜 응답을 넣어 보니, 속도 제한은 앞 모델을 4번 부른 뒤 예비로 넘어가고 서버 오류는 1번 부르고 넘어갔다. 시험은 이 약속을 지킨다.

def test_속도_제한만_기다려_다시_묻고_다른_오류는_바로_실패로_돌려준다() -> None:
    router = config["router_settings"]
    # num_retries가 0이면 LiteLLM이 retry_policy를 보지 않는다
    assert router["num_retries"] > 0
    assert router["retry_policy"]["DefaultRetries"] == 0
    assert router["retry_policy"]["RateLimitErrorRetries"] > 0

이 커밋은 로컬 VLM을 qwen3-vl:8b에서 4b로 낮추는 일도 한다(운영자 결정). 위저드 안내, docs/docker.md, docs/plan.md가 함께 바뀐다.

Quiz

LiteLLM 설정이 num_retries: 0이 아니라 num_retries: 3과 DefaultRetries: 0의 조합인 까닭은?

설정 주석이 이유를 적는다. num_retries가 0이면 정책 자체를 보지 않으므로, 0이 아닌 값으로 문을 열어 두고 실제 횟수는 정책이 정한다. 일반 오류 0번, 속도 제한 3번이라는 구분은 정책에서 나온다.

최종 상태에서 Groq가 VLM 요청에 HTTP 500 서버 오류를 낸다. 무슨 일이 생기는가?

fallbacks가 설정에서 사라졌으므로 넘어갈 곳이 없다. 재시도 3번은 속도 제한(429)에만 적용되고 일반 오류는 0번이다. 실패한 실행은 최종 확인 도구가 끊긴 실행으로 남겨 다시 돌린다.

86236f4가 개발 PC에서 로컬 확인을 미루며 적은, 로컬 예비를 볼 기계의 조건은?

문제는 로컬 모델이 개발 PC의 메모리와 CPU로 감당되지 않는 것이었다. 그래서 큰 메모리나 GPU가 있는 기계에서 보자고 적었다(이 문장은 다음 커밋에서 문서에서 사라진다). 최종 ADR은 「사양이 되는 기계에서는 되살리면 된다」로만 말한다. Groq 쪽 조건은 로컬 모델의 속도와 관계가 없다.

위저드의 파이프라인 실행 줄에서 --no-deps를 빼면 어떤 문제가 생기는가?

docker compose run은 의존 서비스를 .env 설정으로 다시 만든다. 위저드가 Groq 키를 바꿔 끼워 띄운 litellm이 재시작되므로, 그 사이에 파이프라인의 요청이 거부된다. 경로 문제는 MSYS_NO_PATHCONV가 맡는 별개의 일이다.

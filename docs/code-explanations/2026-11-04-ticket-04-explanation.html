티켓 04: 수치 검증과 검증 피드백 루프

조립한 구성기가 Fusion의 실제 형상과 합격선 안에서 맞는지 검증점마다 재고, 어긋나면 고칠 명세 위치를 담은 검증 피드백으로 명세 작성에 돌려보내는 변경이다.

jun-1993-p/threejs-configurator-ai 티켓 04 (93f0683) at 93f0683, explained 2026-11-04. References link to this commit.

배경

이 영역이 처음이면 펼쳐서 읽는 깊은 배경

이 프로젝트는 Fusion CAD 모델을 쇼핑몰 페이지의 three.js 구성기로 바꾼다. 고객은 슬라이더를 움직여 상품의 치수를 바꾼다. 브라우저에서 CAD를 다시 계산할 수는 없으므로, 업로드할 때 CAD 애드인이 Fusion에서 파라미터 값을 바꿔 가며 형상을 미리 뽑아 둔다. 이 묶음이 스윕이다. 파라미터 하나만 움직이고 나머지는 기본값으로 둔 것이 단독 스윕이다.

구성기의 변형 엔진은 스윕 샘플끼리 꼭짓점 위치를 섞어 중간 값의 형상을 만든다(ADR-0002). 샘플 사이의 값은 선형 보간으로 채운다. 그래서 샘플 사이 값에서 보간이 Fusion과 얼마나 다른지를 잰다.

상품 하나를 만드는 파이프라인은 실행기가 순서를 정하고(ADR-0014), AI는 후보를 제시하고 명세(JSON)를 쓰는 단계에서만 일한다. 실행기는 Fusion 연결, AI 모델, 저장소 세 포트(바깥 시스템과 닿는 인터페이스)로만 바깥에 접근한다.

이 변경 앞의 실행기는 후보 제시, 후보 선택, 스타일 선택, 명세 작성, 조립을 차례로 돌린 뒤 검증 단계를 빈 피드백으로 통과시켰다. 소스에는 "수치 검증(티켓 04), 축 반응 검증(티켓 06), AI 판정(티켓 19)이 여기에 들어온다"는 주석만 있었다. 이 변경이 그 자리를 채운다.

다음 이름이 이 문서에 계속 나온다. 각각 한 줄로 정의한다.

  • 검증점: 단독 스윕에서 이웃한 두 샘플 사이의 가운데 파라미터 값. 여기서 Fusion을 한 번 더 재계산해 둔 형상이다. 업로드 묶음에서는 이 목록을 checks 필드로 담는다.
  • 치수 오차: 검증점에서 잰 부품별 W·D·H와 판재 두께의 Fusion 값과 변형 결과 차이 중 최댓값. 합격선은 0.2 mm.
  • 형상 오차: 같은 꼭짓점끼리 잰 거리의 최댓값. 합격선은 1 mm와 바운딩 박스 대각선의 0.1% 중 큰 값.
  • 검증 피드백: 실패한 항목마다 고칠 명세 위치(path), 슬라이더, 부품, 실패 종류(kind), 잰 값과 기대값, 규칙으로 만든 hint를 담은 기록.
  • 후보 제시: 명세를 쓰기 전에 AI가 슬라이더 구성 후보를 사람에게 보여 주는 단계.
  • 코드 이름: createMorph는 변형 엔진을 만드는 함수, faceKey는 샘플 사이에서 면을 짝짓는 (바디, 면 이름) 키, writeSpec은 AI가 명세를 쓰는 포트 호출, SPEC_RETRIES는 같은 후보로 명세를 다시 쓰는 상한 횟수(3)이다.
핵심 개념: 두 가지 합격선 ADR-0012는 정확도 기준을 하나가 아니라 둘로 나눈다. 고객이 숫자로 보는 치수는 0.2 mm로 엄격하게 잰다. 곡면 꼭짓점까지 0.2 mm를 요구하면 샘플과 격자 보강이 크게 늘어 상품이 막히므로, 꼭짓점 단위는 1 mm와 대각선의 0.1% 중 큰 값으로 느슨하게 둔다.

핵심 아이디어

이 문서의 해석으로는, 샘플 값에서 엔진이 기록한 꼭짓점을 그대로 쓰므로 어긋남은 샘플 사이에서만 생길 수 있다. 그래서 샘플 사이 한가운데에서 Fusion을 한 번 더 재 두고, 엔진이 같은 값에서 내놓는 형상과 겹쳐 본다. 어긋남이 합격선 안이면 통과, 밖이면 "이 슬라이더의 이쪽 끝을 이 값보다 안쪽으로 좁히세요"라는 피드백이 된다. 피드백은 AI에게 돌아가 명세를 고치게 한다.

작은 예시: 파라미터 하나의 단독 스윕과 검증점

구분값 (기본값의 배율)역할
샘플0.5, 0.75, 1.0, 1.25, 1.5엔진이 섞는 재료
검증점0.625, 0.875, 1.125, 1.375이웃 샘플의 가운데. 엔진에 넣지 않고 비교에만 쓴다

샘플 배율은 addin/ConfiguratorUploader/uploader/core.py:98의 SWEEP_FACTORS이고, 샘플 다섯 개 사이에 검증점이 네 개 생긴다.

위 숫자는 docs/spec-schema.md의 예시 피드백에서 가져왔다. 기본값보다 큰 검증점(825)에서 실패했으므로 path는 sliders[0].max가 되고, 힌트는 max를 825보다 작게 좁히라고 한다. 기본값보다 작은 검증점이면 min을 좁히라고 한다.

경계 사례: 부품과 무관한 실패 검증점에서 Fusion이 재계산에 실패했거나 면 구성이 기본 형상과 다르면 부품을 가릴 수 없다. 이때는 recompute_failed 또는 topology_change로 내고 part를 빈 문자열로 둔다. 위상 묶음이 들어오면 이 비교를 묶음별 면 구성으로 바꿔야 한다고 코드에 메모가 있다.

실패가 반복되면 후보 제시부터 다시 시작하는 바깥 반복문이 돈다. 같은 후보로 명세를 처음 한 번, 피드백을 붙여 다시 쓰기를 세 번까지 시도한다. 그래도 통과하지 못하면 마지막 피드백을 실패 이유로 붙여 후보 제시로 돌아간다.

코드 따라가기

흐름: 애드인이 검증점을 담음 → 업로드 묶음 스키마와 서버가 검증점을 받음 → 검증기가 엔진과 Fusion 형상을 비교 → 실행기가 피드백으로 명세를 다시 쓰고 3번 넘게 실패하면 후보 제시로 돌아감.

1. 애드인: 검증점을 단독 스윕마다 함께 뽑는다

_sample이 값 하나를 Fusion에서 재계산해 형상을 뽑는 일을 맡고, 이전에는 _sweep 안에 있던 반복문이 이 함수로 빠졌다. 검증점은 샘플 값의 이웃 쌍 평균으로 같은 함수를 부른다.

addin/ConfiguratorUploader/uploader/core.py:130-148

def _sample(model: FusionModel, parameter: ParameterInfo, value: float) -> dict[str, Any]:
    recomputed = model.set_parameter(parameter.name, value)
    shape = _shape_json(model) if recomputed else {"faces": [], "edges": []}
    return {"value": value, "status": "ok" if recomputed else "recompute_failed", **shape}

def _sweep(model: FusionModel, parameter: ParameterInfo) -> dict[str, Any]:
    values = [parameter.value * factor for factor in SWEEP_FACTORS]
    samples = [_sample(model, parameter, value) for value in values]
    # 검증점: 이웃 샘플 사이 가운데 값. ...
    checks = [_sample(model, parameter, (a + b) / 2) for a, b in zip(values, values[1:])]
    # elided: 수식을 되돌리는 restore_parameter 호출
    return {
        "parameter": parameter.name,
        "range": {"min": values[0], "max": values[-1]},
        "samples": samples,
        "checks": checks,
    }

2. 스키마와 서버: 검증점이 필수이고, 평면·원기둥 면은 표면 정의가 필수다

업로드 묶음 스키마에 checks가 필수로 들어가고, 샘플과 검증점이 같은 $defs/sample 형식을 쓰도록 정의가 밖으로 빠졌다. 또 평면과 원기둥 면은 geometry가 있어야 한다. 판재 두께를 재려면 평면의 법선이 필요한데, 이것이 비어 있어도 조용히 지나가면 두께 검사가 빠지기 때문이다. 이 이유는 티켓 파일의 리뷰 반영 항목에 적혀 있다. 해당 정의는 schema/upload-bundle.schema.json:71과 schema/upload-bundle.schema.json:110에 있다.

서버는 샘플과 같은 기준으로 검증점의 점 수도 기본 형상과 맞는지 본다. _samples_and_checks가 두 목록을 이어 붙이고(server/bundle.py:55), bundle_errors가 이를 순회한다(server/bundle.py:86).

4. 검증기: 엔진과 Fusion 형상을 겹쳐 본다

진입점은 verifyNumeric(configurator/pipeline/verify-numeric.ts:42)이다. 검증기는 구성기와 같은 createMorph를 불러 결과물의 sweeps.json으로 엔진을 만든다. 실제로 내보낼 결과를 재기 위해서다. 합격선은 파일 맨 위에 상수로 있다.

configurator/pipeline/verify-numeric.ts:8-14

export const DIMENSION_TOLERANCE = 0.2;

/** 형상 오차의 합격선: 1 mm와 그 검증점 Fusion 형상(상품 전체) 바운딩 박스 대각선의 0.1% 중 큰 값 */
export const shapeTolerance = (diagonal: number) => Math.max(1, diagonal * 0.001);

/** 판재 두께로 보는 맞선 두 평면의 최대 간격: 표준 두께 목록의 가장 두꺼운 값, mm */
const MAX_THICKNESS = 30;

슬라이더마다, 그 슬라이더 범위 안의 검증점만 본다. 비교할 때는 그 슬라이더만 검증점 값으로 두고 나머지는 기본값으로 둔다. 어느 쪽 범위를 좁힐지는 검증점이 기본값보다 작은가로 정한다(configurator/pipeline/verify-numeric.ts:52). 검증점은 샘플 사이 값이라 기본값과 같을 수 없으므로 둘 중 하나로 갈린다.

Fusion 형상을 엔진 쪽 꼭짓점 순서에 맞추는 일은 recordedPositions가 한다. 면을 (바디, 면 이름) 키로 짝짓는데, 이 키가 엔진 안에 있던 비공개 함수 key를 faceKey로 이름을 바꿔 내보낸 것이다(configurator/src/engine.ts:76). 면 개수나 점 수가 다르면 undefined를 돌려주고, 호출한 쪽은 topology_change로 낸다.

configurator/pipeline/verify-numeric.ts:146-156

function recordedPositions(morph: Morph, faces: SampleFace[]): Float64Array | undefined {
  if (faces.length !== morph.faces.length) return undefined;
  const byKey = new Map(faces.map((f) => [faceKey(f), f]));
  const out = new Float64Array(morph.faces.reduce((n, f) => n + f.count, 0) * 3);
  for (const face of morph.faces) {
    const recorded = byKey.get(faceKey(face));
    if (recorded?.points.length !== face.count) return undefined;
    recorded.points.forEach((p, j) => out.set(p, (face.start + j) * 3));
  }
  return out;
}

부품별로 형상 오차(shapeFailures), W·D·H(sizeFailures), 판재 두께(thicknessFailures)를 잰다. 두께는 panelPairs가 기본 형상에서 한 번 정한 면 쌍으로 잰다. 같은 바디의 평면 중 법선이 서로 반대이고 서로 등지고 있으며 기본 형상 간격이 30 mm 이하인 쌍이다(configurator/pipeline/verify-numeric.ts:200). 한 부품에 판이 여럿이면 가장 크게 어긋난 판 하나만 알린다. 티켓 파일은 홈이나 턱 양쪽 면도 판으로 잡힐 수 있다고 적고, 그런 쌍이 0.2 mm 넘게 어긋나면 형상이 실제로 틀린 것이라 거짓 실패는 아니라고 적었다.

5. 실행기: 피드백으로 다시 쓰고, 3번 넘게 실패하면 후보 제시로

명세 작성, 조립, 검증을 묶은 writeVerifiedSpec이 새로 생겼다. 시도는 attempt 0부터 SPEC_RETRIES(3)까지라서 같은 후보에 최대 네 번이다. 검증이 비어 있지 않은 피드백을 내면 그 피드백을 다음 writeSpec에 붙인다.

configurator/pipeline/runner.ts:172-190

async function writeVerifiedSpec(candidate: Candidate): Promise<...> {
  let feedback: Feedback[] = [];
  for (let attempt = 0; attempt <= SPEC_RETRIES; attempt++) {
    const spec = await askUntilValid<Spec>("spec", checkProductSpec, (schemaErrors) =>
      ai.writeSpec({ bundle, intake, candidate, feedback, schemaErrors }),
    );
    // elided: 처리 기록과 조립 호출
    feedback = verifyNumeric(spec, JSON.parse(files["sweeps.json"]), bundle as UploadBundle);
    await log("verification", { attempt, feedback });
    if (feedback.length === 0) return { spec, files };
  }
  return { feedback };
}

위 발췌의 반환 타입 줄은 줄여 적었다(원문은 명세와 결과물, 또는 피드백의 합집합 타입이다). 바깥에서는 후보 제시부터 시작하는 for (;;) 고리가 이 결과를 받는다. 피드백만 돌아오면 failures에 후보와 마지막 피드백을 쌓고 처음으로 돌아간다. 다음 proposeCandidates 호출에는 structuredClone(failures)가 들어가므로 AI는 지난 실패를 본다(configurator/pipeline/runner.ts:200).

열린 고리 후보 제시로 돌아오는 바깥 고리에는 회차 상한이 없다. 티켓 파일은 회차마다 사람이 후보를 고르므로 사람 없이 끝없이 돌지는 않고, 명세에도 상한 수치가 없다는 이유를 적었다. 코드 주석은 사람이 회차마다 후보를 고르므로 사람 없이 끝없이 돌지는 않는다고만 적는다.

6. 시험: 검증기 단독 시험과 파이프라인 전체 시험

configurator/test/verify-numeric.test.ts는 녹화된 검증점 형상을 조금 바꿔 합격선 밖을 만든다. 서랍장 합성 녹화본은 슬라이더에 거의 선형이라 그대로는 실패가 나오지 않기 때문이다(티켓 파일). configurator/test/pipeline.test.ts는 미리 짠 답만 하는 가짜 AI가 일부러 틀린 명세를 내게 해, 피드백을 붙인 재시도 후 제출되는 경우와 3번 넘게 실패해 후보 제시로 돌아가는 경우를 확인한다.

퀴즈

검증점(checks)을 스윕 샘플과 따로 담고 변형 엔진 입력에는 넣지 않는 까닭은 무엇인가?

엔진은 샘플 값에서는 Fusion과 같은 꼭짓점을 쓰므로, 비교할 수 있는 곳은 샘플이 없는 사이 값뿐이다. 그 값을 엔진 입력에 섞으면 정답이 엔진 안으로 들어가 비교의 의미가 사라진다.

기본값 750인 body_w 슬라이더(범위 400~1100)의 검증점 825에서 치수 오차가 나면 피드백의 path는 무엇인가?

825는 기본값보다 크므로 위쪽 끝인 max를 825 안쪽으로 좁히라는 피드백이 된다. 기본값보다 작은 검증점이면 min이다. default는 이 규칙이 건드리지 않는다.

한 후보의 검증이 계속 실패하면, 후보 제시로 돌아가기 전에 writeSpec이 최대 몇 번 불리는가(형식 오류 재질문은 세지 않는다)?

반복문이 attempt 0부터 SPEC_RETRIES(3)까지 돌므로 처음 한 번에 다시 쓰기 세 번을 더해 네 번이다. 문서의 "3번 넘게 실패"는 다시 쓰기 3번을 모두 쓰고도 실패한다는 뜻이다.

용어집의 면 표시 항목은 Fusion이 재계산마다 면 순서를 바꾼다고 적는다. 이름 키로 짝지어야 같은 면끼리 비교된다. 면 개수 검사는 키와 별개로 남는다.

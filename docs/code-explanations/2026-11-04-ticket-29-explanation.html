티켓 29: AI 판정은 최종 승인에 알리기만

AI 판정이 문제를 짚어도 명세를 다시 쓰지 않고, 짚은 이유와 렌더링을 최종 승인 화면에 띄워 운영자가 판단하게 바꾼다. 이미지 모델의 오판이 운영자가 정한 슬라이더 범위를 깎던 문제를 없앤다.

배경

처음 보는 사람을 위한 배경

파이프라인은 명세(JSON)를 AI가 쓰고, 코드가 조립한 뒤 여러 겹으로 검증한다. 수치 검증(치수·형상 오차), 축 반응(슬라이더가 부품을 움직이는 방향), 교차 검증(슬라이더 쌍 조합)은 코드가 재는 값이다. 마지막 AI 판정만 이미지 모델이 렌더링을 보고 뚫림, 겹침, 비례 깨짐을 판정한다. 수치로 잡을 수 없는 것만 본다(GLOSSARY.md).

이 변경 전에는 AI 판정이 문제를 짚으면 그 피드백으로 AI가 명세를 다시 썼다. 판정만 3번 실패하면(JUDGMENT_FAILURES = 3) 그제야 마지막 판정 이유를 붙여 최종 승인으로 넘겼다. 티켓 26 6절의 Groq 회차에서 VLM(qwen3.8-27b)이 멀쩡한 서랍장을 세 번 모두 오판했다(겹침, 구멍, 비례). 명세 작성이 그 피드백대로 끝값을 빼서 메모에 있던 폭 400~800이 420~760으로 줄어 제출되었다고 티켓에 적혀 있다.

용어

최종 승인은 사람이 결과물로 띄운 구성기를 직접 조작해 보고 승인하는 단계다. 슬라이더 이름과 범위는 여기서 고칠 수 있고, 반려하면 후보 선택으로 돌아가거나 거절 이유를 적어 후보 제시로 돌아간다. 처리 기록은 단계마다 남는 로그이고, 검증 단계 기록의 모양은 { attempt, feedback }이다.

운영자 결정은 "AI 판정은 명세를 바꾸지 않고, 짚은 이유와 렌더링을 최종 승인 화면에 띄워 운영자가 판단한다"이다(티켓 본문).

핵심 아이디어

핵심 아이디어는 "믿을 수 없는 판정자의 말을 고치기 입력이 아니라 참고 자료로 쓴다"이다. 이전에는 판정이 명세를 직접 움직였지만, 이제는 사람 앞에 증거(문제로 짚은 렌더링과 이유)를 놓을 뿐이다.

AI 판정은 이제 재시도에 들지 않는다. 수치 검증, 축 반응, 교차 검증에서 떨어지는 경우의 재시도(같은 후보로 다시 쓰기 3번)는 그대로다.

이어지는 영향: 최종 확인 판정

티켓 23이 만든 최종 확인 판정(judgeRun)은 사람이 범위를 고치거나 반려할 때마다 그 앞 검증의 피드백을 근거로 붙인다. 이제 운영자가 AI 판정을 보고 범위를 고치면 근거에 ai_judgment가 남고, 이 종류는 엔진 한계 목록에 없으므로 명세 문제로 센다. 리뷰 때 용어집에서 AI 판정을 명세 문제에서 뺐더니 이 코드와 어긋나서, "사람이 AI 판정을 보고 범위를 고치거나 반려한 것"을 명세 문제에 포함한다고 용어집을 고쳤다. 코드(judgeRun)는 바꾸지 않았다.

코드 따라가기

흐름: 검증 루프(writeVerifiedSpec)에서 AI 판정을 한 번만 받음 → 반환값에 judgment를 실어 최종 승인으로 → 최종 승인 화면이 "AI 판정이 짚은 곳"으로 표시 → 처리 기록에는 판정 피드백이 한 줄로 남음.

1. 실행기: 판정이 재시도에서 빠진다

이전 코드는 판정 실패 횟수 변수(judgmentFailures)를 두고, 판정이 실패하면 피드백으로 반복을 계속하다가 세 번째에 넘겼다. 첫 커밋(d1aff1a)에서 판정 분기를 이렇게 바꿨다.

const judged = feedback.length === 0;
if (judged) feedback = await judge(spec, files);
await log("verification", { attempt, feedback });
if (feedback.length === 0) return { spec, files, judgment: [] };
if (judged && ++judgmentFailures === JUDGMENT_FAILURES) return { spec, files, judgment: feedback };
if (feedback.length === 0) {
  const judgment = await judge(spec, files);
  await log("verification", { attempt, feedback: judgment });
  return { spec, files, judgment };
}
await log("verification", { attempt, feedback });

리뷰 커밋(0762d35)이 이를 처리 기록을 한 번만 쓰는 형태로 모았다. 현재 코드는 다음과 같다.

configurator/pipeline/runner.ts:595-597

      const judgment = feedback.length === 0 ? await judge(spec, files) : null;
      await log("verification", { attempt, feedback: judgment ?? feedback });
      if (judgment) return { spec, files, judgment };

검증이 통과했을 때만(feedback.length === 0) judge를 부르고, 그 결과를 처리 기록에 남긴 뒤 judgment가 있으면 바로 돌려준다. 판정이 아무것도 못 짚으면 judgment는 빈 배열 []인데, 배열은 JavaScript에서 비어 있어도 참으로 취급되므로 if (judgment)는 문제 없음에서도 통과한다. 검증이 실패했을 때는 judgment가 null이라 판정을 부르지 않고 실패 피드백이 기록되며 루프가 계속된다. 상수 JUDGMENT_FAILURES와 그 변수는 없어졌고, 기록의 모양은 그대로다.

함수 설명과 HumanPort의 judgment 설명도 새 동작에 맞게 고쳤다(configurator/pipeline/runner.ts:274).

4. 시험

3번 실패해 넘어오는 시험과 판정 실패 세기 시험(수치 검증 실패가 끼어도 판정 실패만 센다)은 없앴다. 대신 판정이 문제를 짚으면 명세를 다시 쓰지 않고 최종 승인에 붙는지 본다. 명세 작성 호출은 한 번뿐이고(ai.calls.spec.length가 1), 판정 호출도 한 번이며, 승인 화면이 받은 judgment가 기대한 피드백인지 확인한다.

function approveAndKeep() {
  const reviews: { spec: Spec; judgment: Feedback[] }[] = [];

    chooseCandidate: () => Promise.resolve({ candidate: "c1" }),
    finalApproval: (review) => {

    },

최종 승인에서 받은 검토 거리를 모아 승인하는 사람(approveAndKeep)을 새로 만들어 기존 시험 몇 개가 함께 쓴다. operator-screens.test.ts의 문구 시험도 "AI 판정이 짚은 곳"으로 바뀌었다.

5. 문서와 용어집

docs/plan.md의 흐름 그림에서 "AI 판정 → 명세 작성으로 돌아감"과 "3회 실패 (판정만)" 화살표를 빼고 "짚은 곳을 알림" 화살표 하나로 바꿨다. docs/spec-schema.md의 AI 판정 절과 재시도 절, GLOSSARY.md의 AI 판정 항목도 고쳤다. 리뷰 커밋은 원래 명세(spec.md)의 사용자 스토리 67과 재시도 문장에도 바뀐 것을 적었다.

남는 점

판정을 한 번만 받으므로 이미지 모델이 진짜 문제를 짚어도 AI가 스스로 고치지는 않는다. 운영자가 보고 범위를 좁히거나 반려해야 한다. 이는 티켓이 선택한 비용이다(오판으로 범위가 깎이는 피해를 막는 쪽을 택했다).

퀴즈

AI 판정이 짚은 곳으로 명세를 다시 쓰던 방식을 버린 직접 원인은?

티켓 26 6절 Groq 회차에서 VLM이 멀쩡한 서랍장을 세 번 오판했고, 명세 작성이 끝값을 빼서 폭 400~800이 420~760으로 줄었다. 판정을 믿을 수 없다면 판정이 명세를 직접 움직이게 하면 안 된다.

판정이 아무 문제도 못 짚었다(problems가 빈 목록). runner는 어떻게 하는가?

배열은 비어 있어도 참으로 취급되므로 if (judgment)는 통과하고 { spec, files, judgment: [] }를 돌려준다. 화면은 reasons가 비면 "AI 판정이 짚은 곳" 구획을 그리지 않는다.

같은 후보로 수치 검증이 실패하면 AI 판정은 어떻게 되는가?

feedback.length === 0일 때만 judge를 부르고, 그렇지 않으면 judgment가 null이라 실패 피드백만 기록하고 루프가 계속된다. 판정은 재시도 횟수에 들지 않는다.

운영자가 AI 판정이 짚은 곳을 보고 슬라이더 범위를 좁혀 승인했다. 최종 확인(티켓 23)은 이 상품을 어떻게 보는가?

최종 승인에서 범위를 고친 것은 개입이다. 앞 검증의 피드백이 ai_judgment인데 이 종류는 엔진 한계 목록(ENGINE_LIMIT_KINDS)에 없으므로 명세 문제가 된다. 그래서 용어집의 명세 문제를 이에 맞게 고쳤다.

이 변경을 이해했는지 가장 잘 드러내는 설계 원칙은?

수치 검증은 재면 되는 값이라 실패 때 자동으로 고친다. 이미지 모델 판정은 오판할 수 있어서 고침 대신 알림으로 바뀌었다. 사람이 최종 승인에서 판단한다.

티켓 28: 구성이 하나로 정해지면 후보 하나 허용

후보 제시가 늘 서로 다른 후보 2개 이상을 요구하던 규칙을 1개 이상으로 풀되, 두께 선택 노출을 AI가 정하는 경우는 계속 막고, 후보 하나가 검증을 통과하지 못하면 같은 후보를 되풀이하지 않고 멈추게 한다.

배경

처음 보는 사람을 위한 배경

이 프로젝트의 파이프라인은 사람이 슬라이더 구성을 고르게 하려고 AI에게 후보를 만들게 한다(후보 제시 단계). 후보 하나는 정면 방향(front), 고객이 바꿀 치수의 파라미터 목록(sliders), 두께 선택을 고객에게 보일지(showThickness)로 이루어진다. AI의 답은 JSON이고, 스키마와 다양성 검사를 통과하지 못하면 실행기가 오류 문장을 붙여 다시 묻는다.

후보 제시 단계는 이 변경 전에 후보를 2~4개로 요구했고(사용자 스토리 19), 서로 정면, 노출할 치수의 파라미터, 두께 선택 노출 중 하나 이상이 달라야 했다(candidateDiversityChecker). 그런데 세 가지가 모두 정해지는 상품이 있다.

  • 부품 탐색(VLM이 여섯 방향 그림으로 부품과 정면을 찾는 일)이 정면을 확신한다. 정면 후보가 하나다.
  • 정보 입력이 두께 선택 노출을 "보이기" 또는 "숨기기"로 정했다. "AI 판단"이 아니다.
  • 정보 입력의 메모가 노출할 치수를 하나로 정했다.

이때 서로 다른 후보는 하나뿐이다. 티켓 26 6절의 Groq 회차(data/runs/fallback-check/1-groq/log.json)에서 모델이 "두께 선택 노출이 정보 입력과 다름"과 "후보끼리 모두 같음" 사이를 오가다 멈췄다고 티켓에 적혀 있다.

용어(GLOSSARY.md)

후보 제시는 명세 작성 전에 AI가 슬라이더 구성 후보를 스윕 미리보기와 함께 사람에게 보여 주는 단계다. 부품 탐색이 정면을 확신하고 정보 입력이 두께 선택 노출과 노출할 치수를 하나로 정했으면 후보는 하나다. 후보 선택은 사람이 후보를 고르는 다음 단계다.

핵심 아이디어

핵심 아이디어는 "다양성 요구는 다양하게 만들 수 있을 때만 건다"이다. 변경은 세 부분이다.

상황후보 수 1개
정면 확신, 두께 선택 노출이 보이기 또는 숨기기, 메모가 한 구성으로 정함허용
두께 선택 노출이 "AI 판단"다시 묻는다. 두께 선택 노출로 다른 후보를 만들 수 있다
정면 후보가 여럿(정면을 확신하지 못함)기존 검사가 잡는다. 빠진 정면으로 다시 묻는다
메모가 구성을 하나로 정했는지코드가 검사하지 않는다. 지시문이 알리고, 어긋나면 운영자가 반려한다

메모는 자유 문장이라 코드로 "슬라이더를 하나로 정했는지" 확인할 수 없다. 그래서 확인 가능한 것(정면 개수, 두께 선택 노출 값)만 코드가 검사하고, 나머지는 지시문과 사람 반려에 맡긴다는 것이 티켓의 구현 기록에 적힌 설계다.

리뷰에서 나온 두 번째 문제: 끝없는 반복

후보가 하나뿐인 회차에서 그 후보가 검증을 통과하지 못하면, 파이프라인은 원래 "후보 제시로 돌아가 다른 후보를 받는" 길로 간다. 그런데 후보가 하나뿐이라 돌아가도 같은 후보를 받는다. 후보를 자동으로 고르는 실행 도구(run-pipeline.ts)에서는 끝없이 돌았다고 티켓 기록에 있다. 그래서 이 경우 후보 제시 단계에서 멈추고 정보 입력의 메모나 두께 선택 노출을 바꿔 다시 돌리라고 알린다.

후보 1개만 고름
명세 작성·검증
검증 실패
candidates.length === 1
한 가지뿐
fail: PipelineStop (후보 제시 단계
PipelineStop (후보 제시 단계)

후보가 여럿이면 기존대로 실패한 후보와 마지막 피드백을 failures에 담아 후보 제시로 돌아간다.

코드 따라가기

흐름: 후보 제시 응답 스키마 → 다양성 검사 → 지시문 → 실행기의 실패 처리 → 시험.

1. 스키마: 최소 후보 수

CANDIDATES_SCHEMA의 minItems가 2에서 1로 바뀌었다(configurator/pipeline/schemas.ts:109). 최대 4개는 그대로다.

2. 다양성 검사: 두께 선택 노출이 AI 판단이면 하나는 안 된다

후보 하나일 때 "서로 같다"는 검사는 비교 대상이 없어 저절로 통과한다. 새로 막아야 할 경우를 검사에 더했다.

configurator/pipeline/schemas.ts:349-355

    const missing = fronts.length > 1 ? fronts.filter((f) => !candidates.some((c) => c.front === f)) : [];
    if (candidates.length === 1 && thickness === "ai") {
      errors.push(`${ROOT}: 두께 선택 노출을 AI가 정하므로 후보가 하나일 수 없습니다. 두께 선택 노출이 다른 후보를 더하세요`);
    }
    if (missing.length > 0) {
      errors.push(`${ROOT}: 정면을 확신하지 못해(정면 후보 ${fronts.join("·")}) 후보끼리 정면이 달라야 합니다. 빠진 정면: ${missing.join("·")}`);
    }

오류 문장은 ROOT 경로((최상위))에 붙고 AI에게 다시 물을 때 전달된다. 정면 후보가 여럿인데 하나만 낸 경우는 같은 범위의 missing 검사(configurator/pipeline/schemas.ts:349)가 이미 막고 있다.

3. 지시문

후보 제시 지시문(CANDIDATES_PROMPT)이 언제 후보 하나를 내는지 알리고, 리뷰 뒤에는 첫 줄도 "1~4개, 보통 2~4개"로 고쳐 두 줄이 부딪치지 않게 했다.

configurator/pipeline/litellm-ai.ts:98-99

- 답은 후보 객체 1~4개를 담은 JSON 배열 하나([ … ])다. 보통 2~4개이고, 후보끼리 정면(front)·노출할 치수의 파라미터(sliders의 parameter)·두께 선택 노출(showThickness) 중 하나 이상이 다르다.
- parts.fronts가 하나이고 intake.thickness가 "ai"가 아니며 intake.memo가 노출할 치수를 하나의 구성으로 정했으면, 서로 다른 후보를 만들 수 없으니 후보 하나만 낸다. 그 후보의 diff는 "다른 구성 없음"이다.

같은 리뷰 커밋은 거절 이유를 따른 구성이 반려된 후보와 같아질 수밖에 없으면, 같은 구성을 다시 내고 summary에 거절 이유를 어떻게 반영했는지 적으라는 줄도 지시문(litellm-ai.ts:105)에 더했다. 후보가 하나뿐일 때 거절 이유를 따르면 같은 구성이 될 수밖에 없는 경우를 위한 줄이다. 사람이 회차마다 고르므로 끝없이 돌지는 않는다.

4. 실행기: 하나뿐이면 멈춘다

멈춤은 PipelineStop("candidates", …)이고 이유 문장에 실패 피드백 종류가 들어간다. 후보가 여럿이면 기존 길(failures.push)로 간다.

퀴즈

후보가 하나인데 정보 입력의 두께 선택 노출이 "AI 판단"이면 다시 묻는 까닭은?

서로 다른 구성이 하나뿐인 조건은 정면, 두께 선택 노출, 노출할 치수가 모두 정해진 경우다. "AI 판단"이면 두께 선택 노출이 아직 정해지지 않았으므로 그것으로 다른 후보를 만들 수 있다. 오류 문장도 "두께 선택 노출이 다른 후보를 더하세요"다.

정면 후보가 -Y와 +X 둘인데 모델이 정면 -Y인 후보 하나만 냈다. 어떻게 되는가?

정면을 확신하지 못했으면(정면 후보 여럿) 후보끼리 그 정면을 모두 나눠 써야 한다. 이 규칙은 이 티켓 전부터 있던 missing 검사로 바뀌지 않았고, 후보 하나를 허용하는 것은 스키마의 최소 개수일 뿐이다.

후보 하나만 고른 회차에서 명세가 검증을 통과하지 못한다. 후보가 둘이었다면 하지 않았을 일은?

후보가 여럿일 때는 다른 후보나 새 구성을 받으러 돌아가지만, 하나뿐인 회차에서는 돌아가도 같은 후보를 받는다. 자동으로 고르는 도구에서는 이것이 끝없이 도는 반복이 되므로 멈춘다. 검증 기록은 어느 쪽이든 남는다.

메모가 슬라이더를 하나로 정했는지 코드가 검사하지 않는 까닭으로 가장 알맞은 것은?

정면 후보 개수와 두께 선택 노출은 정해진 값이라 코드가 검사하지만, 메모는 자유 문장이다. 그래서 지시문이 언제 하나를 내는지 알리고, 모델이 그렇지 않은데도 하나만 내면 운영자가 후보 선택이나 반려로 바로잡는다.

이 티켓의 "하나뿐이면 멈춘다"와 같은 원칙을 쓴 것은?

후보가 하나뿐인 회차에서 후보 제시로 돌아가도 입력이 같으므로 같은 후보가 나온다. 결과를 바꿀 수 있는 것은 정보 입력의 메모나 두께 선택 노출뿐이라, 그것을 바꾸라고 알리고 멈춘다.

티켓 23: 최종 확인 실행 도구

개발이 끝난 뒤 처음 보는 상품을 실제 파이프라인으로 하나씩 돌려, 사람 개입이 후보 선택과 최종 승인뿐이었는지 처리 기록으로 판정하고 실패를 명세 문제와 엔진 한계로 나눠 남기는 명령줄 도구를 추가한다.

jun-1993-p/threejs-configurator-ai 티켓 23, 기준 커밋 e1d5be1 (포함한 커밋: e3fb863, 48f4822, e1d5be1), 2026-11-04 작성. 48f4822는 처리 기록 계약 시험(configurator/test/pipeline.test.ts)과 티켓 파일 두 줄만 이 문서에 넣었고, 같은 커밋의 티켓 점검 스크립트 변경은 다루지 않는다. References link to this commit.

배경

처음 보는 사람을 위한 배경

이 프로젝트는 Fusion 모델을 쇼핑몰용 3D 구성기로 바꾸는 파이프라인을 만든다. 파이프라인은 정해진 순서로 단계를 지나간다(ADR-0014: 순서는 코드가 정하고 AI는 단계 안에서만 일한다). 업로드, 후보 제시, 후보 선택, 명세 작성, 검증, 최종 승인 순이고, 사람은 후보를 고르고 마지막에 승인하는 두 곳에서만 일하는 것이 목표다. 단계마다 무슨 일이 있었는지는 처리 기록(로그)에 남는다.

이 프로젝트는 "고정 코어"(configurator/src의 변형 엔진 등)를 상품마다 고치지 않고 어떤 가구든 다룬다는 범용성을 약속한다. 개발 중에 쓴 모델에만 맞춘 것이 아닌지 확인하려면, 개발이 끝난 뒤 처음 보는 상품으로 시험해 봐야 한다.

기획 문서(.scratch/configurator-pipeline/spec.md)의 사용자 스토리 83~85가 이 도구가 하는 일이다. 개발이 끝난 뒤 새 상품 약 10개를 등록하고, 고정 코어와 변형 엔진을 고치지 않은 채 10개 중 8개 이상이 후보 선택과 최종 승인만으로 끝나면 통과다. 슬라이더 이름 고치기는 허용한다. 실패한 상품은 "명세 문제"와 "엔진 한계"로 나눠 기록하고, 엔진 한계는 범용화 단계의 근거로 넘긴다.

용어(GLOSSARY.md)

명세 문제는 명세의 선언이나 범위를 고치면 되는 실패다. 엔진 한계는 명세를 고쳐도 없어지지 않는 실패로, 형상 오차·치수 오차, 섞을 수 없는 위상 변화, 상한을 넘은 위상 묶음·격자 보강 쌍이다. 모델 지문은 업로드 묶음의 파라미터 이름(개수형 여부 포함)과 부품 이름이다. 값과 수식은 넣지 않는다.

실제 파이프라인을 돌리려면 두 가지 연결이 더 필요했다. 하나는 서버를 거쳐 Fusion 애드인에게 추가 샘플을 요청하는 포트, 다른 하나는 사람이 후보를 고르고 승인하는 운영자 화면을 띄우는 포트다. 티켓 08, 16, 22가 "실행기를 띄울 때 붙이기"로 미뤄 둔 일이었고, 이 티켓이 받았다.

주의

이 도구는 Fusion과 실물 상품이 있어야 진짜 최종 확인을 할 수 있다. 티켓의 "남은 일(사람)"에 따르면 실제 판정은 티켓 26의 Fusion 실물 확인 뒤에 docs/final-check.md대로 돌린다. 이 변경은 도구와 그 시험까지다.

핵심 아이디어

핵심 아이디어는 "사람의 손이 닿은 곳은 이미 처리 기록에 남아 있다"는 점이다. 실행기는 사람 결정을 받을 때마다 처리 기록에 적으므로, 판정은 사람 결정 포트를 감싸지 않고 기록만 읽으면 된다. 두 번째 아이디어는 "처음 보는 상품"과 "고정 코어"를 도구가 스스로 증명하게 하는 것이다. 사람이 약속하는 대신, 시작 때 코어 트리 해시를 기록하고 상품마다 그 해시와 모델 지문을 견준다.

코드 따라가기

흐름: 명령줄 start → run(코어 해시 대조, 업로드 묶음 받기, 모델 지문 대조) → 운영자 화면과 Fusion 연결 포트를 붙여 파이프라인 실행 → 처리 기록 판정 → report로 전체 판정. 끝으로 회고 반영 커밋 두 개가 도구를 임시 저장소와 가짜 서버로 시험하고, 실행기의 처리 기록 모양을 판정이 제대로 읽는지 시험한다.

1. 시작: 코어를 고정한다

start는 상품 목록의 정보 입력을 검사하고, 개발이 끝난 커밋과 configurator/src의 git 트리 해시를 check.json에 적는다. 커밋하지 않은 변경이 있으면 시작하지 않는다.

configurator/scripts/final-check.ts:78-82

/** 고정 코어·변형 엔진(configurator/src)의 커밋된 트리. 커밋하지 않은 변경이 있으면 멈춘다. */
function coreTree(root: string): string {
  if (git(root, "status", "--porcelain", "--", "configurator/src") !== "") fail("configurator/src에 커밋하지 않은 변경이 있습니다. 고정 코어·변형 엔진을 고치지 않고 돌려야 합니다");
  return git(root, "rev-parse", "HEAD:configurator/src");
}

Git이 필요하므로 Docker 밖에서 돌려야 한다는 안내가 docs/final-check.md에 있다.

3. 실제 연결 두 개

httpFusion은 서버의 추가 샘플 요청 API에 요청을 걸고 애드인이 답할 때까지 요청 상태를 본다. 애드인 소식이 끊기면 disconnected를 돌려주고, 이후 같은 요청을 다시 걸지 않고 기다린다. 요청을 JSON 문자열 키로 외워 두기 때문이다.

후보 제시가 두 번째 이후에 나타났는데 앞선 최종 승인 반려가 거절 이유로 후보를 다시 받으라고 한 것이 아니면, 검증을 통과하지 못해 돌아온 것으로 보고 개입으로 센다(configurator/pipeline/final-check.ts:50). 업로드나 검증 단계에서 멈췄고 이유가 AI 형식 실패로 시작하지 않으면 엔진 한계다(configurator/pipeline/final-check.ts:68). AI 응답 형식은 명세를 쓰는 쪽의 문제라는 판단이 주석에 있다.

상품 목록 전체의 판정은 finalVerdict가 낸다.

configurator/pipeline/final-check.ts:129-139

export function finalVerdict({ products, core, records }: { products: string[]; core: string; records: ProductRecord[] }): FinalVerdict {
  const problems = records.flatMap((r) => [
    ...(r.core === core ? [] : [`${r.id}: 고정 코어·변형 엔진이 최종 확인을 시작할 때와 다르다(${r.core}, 시작 ${core})`]),
    ...(r.unseen.matches.length === 0 ? [] : [`${r.id}: 개발 중 녹화본과 같은 모델이다(${r.unseen.matches.join(", ")})`]),
  ]);
  const missing = products.filter((id) => !records.some((r) => r.id === id));
  const passed = records.filter((r) => r.outcome.passed).length;
  const total = products.length;
  const status = problems.length > 0 ? "invalid" : missing.length > 0 ? "running" : passed >= PASS_RATIO * total ? "passed" : "failed";
  return { status, passed, total, missing, problems };
}

5. 끊긴 실행은 판정에 넣지 않는다

LiteLLM이나 서버 오류처럼 파이프라인 밖에서 끊긴 실행은 판정에 넣지 않고 interrupted.json에 남긴다(final-check.ts:148). 원인을 고쳐 다시 돌릴 수 있어야 하고, 보고서에는 끊긴 실행이 보여 어느 상품을 다시 돌렸는지 운영자가 알 수 있다.

6. 회고 반영 커밋 e1d5be1: 명령줄을 시험할 수 있게

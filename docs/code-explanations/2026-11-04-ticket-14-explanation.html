티켓 14: 범위 교집합

슬라이더 범위를 치수 규칙, 정보 입력 메모의 범위, 스윕 범위의 교집합 안에서만 정하게 한 변경이다. 명세의 source가 가리키는 치수 규칙이 실재하고 슬라이더와 같은 축인지 검사하며, 교집합이 비면 범위를 지어내지 않고 운영자에게 알린다.

jun-1993-p/threejs-configurator-ai 티켓 14 (커밋 079504d), 2026-11-04에 설명함. References link to this commit.

배경

이 프로젝트가 처음이라면: 깊은 배경을 펼치세요.

프로젝트는 Fusion CAD 모델을 쇼핑몰 페이지의 div 안에서 도는 three.js 구성기로 바꾼다. CAD 애드인이 업로드 때 파라미터 값을 바꿔 가며 형상을 미리 뽑아 두는데, 이 스윕이 덮는 값의 구간이 스윕 범위다(기본값의 ±50%에서 재계산 실패와 위상 한계만큼 줄어든다). 구성기의 슬라이더 범위는 이 구간 안에 있어야 한다. 그 밖에는 변형 엔진이 섞을 데이터가 없다.

운영자는 상품을 올릴 때 정보 입력(상품명, 상품 종류, 자유 문장 메모)을 준다. 파이프라인은 정해진 순서로 단계를 진행하고, 명세(슬라이더를 어떤 범위로 노출할지 적은 JSON)는 AI가 쓴다. AI의 답은 먼저 형식과 규칙을 검사하는 명세 검사를 거치고, 틀리면 이유를 붙여 다시 묻는다. 그 뒤 조립과 검증을 거친다. 검증이 틀린 곳을 알리는 것이 검증 피드백이다.

ADR-0009의 결정은 이렇다. 슬라이더 범위는 치수 규칙(가구 부위별 인체공학적 범위), 정보 입력의 범위 메모, 스윕 범위의 교집합 안에서 AI가 고른다. 어느 치수 규칙에 근거했는지 명세에 남긴다. 기본값은 업로드한 Fusion 모델의 현재 값이다. ADR는 이유를 두 가지 든다. AI가 상품 감각만으로 범위를 정하면 근거를 확인할 수 없고, 스윕 범위를 넘으면 변형 엔진이 섞을 데이터가 없다. 교집합이 비면 범위를 정하지 않고 검증 피드백으로 사람에게 알린다.

명세에는 이미 source(범위의 근거가 된 치수 규칙 이름)를 적는 칸이 있었다. 이 티켓은 치수 규칙의 모양과 저장소 포트의 읽기 메서드, 그리고 source와 범위를 검사하는 코드를 더한다.

용어

치수 규칙은 상품 종류, 부위, 축(W·D·H), 범위, 출처로 이루어진 자료 한 건이다. 명세의 source가 그 id를 가리킨다. 범위 교집합은 치수 규칙 ∩ 메모의 그 부위 범위 ∩ 스윕 범위다. 비었거나 업로드한 모델의 값을 담지 않으면 범위를 정하지 않는다.

핵심 아이디어

세 범위는 출처가 서로 다르다. 치수 규칙은 부위별 인체공학적 범위(저장소의 자료), 메모는 운영자가 적은 범위(예: "폭 1000~1200"), 스윕 범위는 업로드 때 Fusion이 실제로 계산해 본 구간이다. 교집합이 비어도, 업로드한 모델의 값을 담지 않아도 범위를 정하지 않는다. 슬라이더 범위는 셋이 모두 허락하는 구간이어야 하고, 업로드한 모델의 기본값이 그 안에 있어야 한다. 구성기를 처음 열면 원본 상품의 모습이 보여야 하기 때문이다(코드 주석의 까닭이다).

서랍장 body_w(기본 600)의 세 범위

문서가 든 예다. 이 경우 AI는 범위를 지어내지 않고 no_range_intersection 피드백을 받으며, 힌트는 이 슬라이더를 빼고 운영자가 메모와 모델을 확인하라고 한다.

min·max가 교집합 안인지 볼 때 명세 검사는 애드인이 줄인 쪽의 스윕 범위를 무제한으로 친다. 그쪽은 범위 검증(verifyRange, 티켓 11에서 다룬 줄어든 범위를 알리는 검증)이 까닭과 함께 알린다. 다만 교집합이 비었는지는 실제 값으로 세므로, 줄어든 쪽 때문에 비면 교집합 없음 피드백이 먼저 나간다.

코드 따라가기

흐름: 저장소 포트의 치수 규칙 → 메모에서 부위별 범위 읽기 → 슬라이더마다 세 범위 모으기 → 명세 검사 → 교집합 없음 피드백 → 실행기의 분기와 처리 기록.

1. 치수 규칙과 저장소 포트

새 파일 configurator/pipeline/range-intersection.ts:8이 규칙의 모양을 정한다. 저장소 포트 StorePort에는 상품 종류로 규칙을 거르는 dimensionRules(kind)가 추가됐고, 시험용 메모리 저장소는 넣은 규칙을 종류로 걸러 돌려준다. 실제 규칙 내용은 준비 단계에서 따로 만든다고 티켓 기록에 적혀 있다.

configurator/pipeline/range-intersection.ts:8-21

export interface DimensionRule {
  /** 명세의 source가 가리키는 이름(치수규칙/서랍장/폭) */
  id: string;
  /** 상품 종류. 정보 입력의 상품 종류와 같은 말이다. */
  kind: string;
  /** 부위. 정보 입력 메모의 범위는 이 이름으로 찾는다. */
  part: string;
  /** 부위가 놓인 축. source로 고른 규칙은 슬라이더와 같은 축이어야 한다. */
  axis: Axis;
  min: number;
  max: number;
  /** 범위의 출처(문헌·표준) */
  origin: string;
}

2. 메모에서 부위별 범위 읽기

메모는 자유 문장이다. memoRanges(configurator/pipeline/range-intersection.ts:44)는 규칙의 부위 이름 바로 뒤에 오는 "값~값"만 범위로 읽는다. 조사(은·는·이·가)와 쌍점, 쉼표 천 단위, mm·cm를 받아들이고, 단위가 없으면 mm다. 부위 이름은 치수 규칙에서 가져오되 긴 이름부터 찾는다. 읽은 부분은 공백으로 덮으므로 한 범위가 두 부위에 붙지 않는다.

configurator/pipeline/range-intersection.ts:47-56

  for (const part of [...new Set(parts)].sort((a, b) => b.length - a.length)) {
    const name = part.split(/\s+/).map(escapeRegExp).join("\\s*");
    const pattern = new RegExp(String.raw`(?<![\p{L}\p{N}_])${name}${JOINER}${RANGE}`, "gu");
    rest = rest.replace(pattern, (match, a: string, unitA: string | undefined, b: string, unitB: string | undefined) => {
      const [from, to] = [toMm(a, unitA ?? unitB), toMm(b, unitB ?? unitA)];
      if (!ranges.has(part)) ranges.set(part, { min: Math.min(from, to), max: Math.max(from, to) });
      return " ".repeat(match.length);
    });
  }
  const unread = [...rest.matchAll(new RegExp(RANGE, "gu"))].map((m) => m[0].trim());

어느 부위에도 붙지 않은 "값~값"은 unread로 돌려주고, 실행기가 정보 입력 처리 기록에 { "memoUnread": [...] }로 남겨 운영자가 의도를 확인하게 한다.

3. 슬라이더마다 세 범위 모으기

sliderBounds(configurator/pipeline/range-intersection.ts:108)가 슬라이더의 source로 규칙을 찾고, 같은 이름의 스윕과 업로드한 모델 값을 붙인다. 스윕 범위에서 애드인이 줄인 쪽은 reduced로 표시한다. 규칙이나 스윕이 없으면 undefined인데, 그 경우는 다른 검사가 이미 알린다.

configurator/pipeline/range-intersection.ts:110-117

    const rule = rules.find((r) => r.id === slider.source);
    const sweep = bundle.sweeps.find((s) => s.parameter === slider.id);
    const model = modelValue(bundle, slider.id);
    if (!rule || !sweep || model === undefined) return undefined;
    const reduced = { min: false, max: false };
    for (const r of sweep.reductions ?? []) reduced[r.side] = true;
    return { rule, memo: memo.get(rule.part), sweep: { ...sweep.range, reduced }, model };

교집합은 각 범위의 하한 중 가장 큰 값부터 상한 중 가장 작은 값까지다(메모에 그 부위 범위가 없으면 둘만 쓴다). 아래 intersection은 이 구간 안에 업로드한 모델의 값이 드는지로 쓸 수 있는지(usable)를 판정한다.

configurator/pipeline/range-intersection.ts:92-95

function intersection(bounds: Bounds): { range: Range; usable: boolean } {
  const range = intersectBounds(bounds);
  return { range, usable: range.min <= bounds.model && bounds.model <= range.max };
}

4. 명세 검사

rangeErrors(configurator/pipeline/range-intersection.ts:132)가 세 가지를 본다. source가 규칙에 없는지, 규칙의 축이 슬라이더 축과 같은지, min·max가 교집합 안인지. 기본값은 defaultErrors(configurator/pipeline/range-intersection.ts:161)가 따로 본다(모델 값과 같고 범위 안인가). 교집합이 비어 있으면 AI가 min·max를 고쳐도 소용없으므로 명세 검사는 넘기고 5번 단계가 알린다.

configurator/pipeline/range-intersection.ts:136-143

    if (rule.axis !== slider.axis) return [`/sliders/${i}/source: ${rule.id}의 축(${rule.axis})이 슬라이더 축(${slider.axis})과 다릅니다`];
    const bounds = boundsOf(slider);
    if (!bounds || !intersection(bounds).usable) return [];
    // 줄어든 쪽 스윕 범위는 범위 검증이 그 까닭과 함께 알린다
    const allowed = intersectBounds(bounds, true);
    const outside = [...(slider.min < allowed.min ? (["min"] as const) : []), ...(slider.max > allowed.max ? (["max"] as const) : [])];
    return outside.map((side) => `/sliders/${i}/${side}: 범위 교집합 ${span(allowed)} 밖의 값(${slider[side]})입니다(${boundsText(bounds)})`);
  }

축 검사의 주석은 이유를 적었다. 다른 축 부위의 규칙을 붙이면 메모의 범위를 비켜 갈 수 있다. 메모 범위는 규칙의 부위 이름으로 찾기 때문이다.

6. 실행기: 규칙을 읽어 AI에게 주고, 조립 전에 막는다

실행기는 상품 하나를 처리하는 동안 한 번만 규칙을 읽고 rangeIntersection(configurator/pipeline/range-intersection.ts:127)으로 검사 객체를 만든다. 이 객체의 check(명세 검사)가 checkProductSpec에 붙는다. AI에게는 정보 입력의 상품 종류로 거른 규칙이 입력으로 가며, source도 그 안에 있어야 한다.

configurator/pipeline/runner.ts:243-244

  const rules = await store.dimensionRules(intake.kind);
  const ranges = rangeIntersection({ rules, intake, bundle: uploaded });

명세 검사를 통과한 명세에 교집합 없음이 있으면 조립하지 않고 다음 시도로 돌아간다. 피드백은 처리 기록의 검증 항목으로 남아 운영자에게도 보인다.

configurator/pipeline/runner.ts:333-339

      // 범위 교집합이 없으면 범위를 지어내지 않도록 조립하지 않고 돌려준다. 처리 기록으로 운영자에게도 보인다.

      if (noIntersection.length > 0) {
        feedback = noIntersection;
        await log("verification", { attempt, feedback });

티켓 기록은 교집합 없음도 같은 후보 재시도 3번을 쓴다고 적었다. AI가 고칠 수 있는 길(그 슬라이더 빼기)이 있고, 후보 제시로 돌아가면 이유가 실려 다른 부모 파라미터를 고를 수 있기 때문이다.

퀴즈

상품 종류의 치수 규칙에 부위 "폭"과 "서랍 폭"이 있고, 메모는 "서랍 폭 300~500"이다. 부위 "폭"의 규칙은 메모에서 어떤 범위를 받는가?

긴 이름부터 찾으므로 "서랍 폭"이 먼저 그 문장을 가져가고 읽은 부분은 공백으로 덮인다. 남은 메모에는 "폭"에 붙는 "값~값"이 없다. 메모에 그 부위의 범위가 없으면 그 범위는 교집합에서 빠지고, 읽지 못한 범위도 없으니 처리 기록에도 남지 않는다.

치수 규칙은 300~1200, 메모는 700~1000, 스윕 범위는 300~900이고 업로드한 모델의 값은 600이다. 이 슬라이더는 어떻게 되는가?

교집합은 700~900으로 비어 있지 않지만 기본값(업로드한 모델의 값) 600이 그 밖이다. 이 경우 쓸 수 있는 범위가 없으므로 usable이 거짓이고 no_range_intersection이 나온다. 기본값을 모델 값이 아닌 값으로 고치는 길은 없다. 애드인에 재업로드를 요청하는 길은 이 티켓이 더한 코드에 없다.

교집합이 비어 있을 때 명세 검사가 범위 오류로 되묻지 않고 조립 전의 별도 피드백으로 알리는 이유는?

코드 주석이 이유를 적었다. 교집합이 비면 범위를 고칠 수 없으므로 명세 검사는 넘기고 교집합 없음 판정이 알린다. 알림은 슬라이더를 빼라는 힌트를 담는다. 명세 검사는 값의 범위도 본다. 예를 들어 min·max가 교집합 밖이면 실패한다.

명세 검사에서 "규칙의 축이 슬라이더 축과 같은가" 검사를 빼면 어떤 문제가 생기는가?

메모의 범위는 규칙의 부위 이름으로 찾으므로, 폭 슬라이더가 깊이 규칙을 source로 가리키면 메모의 폭 범위는 적용되지 않는다. 축 검사가 그 우회를 막는다. 기본값 검사와 줄어든 스윕 범위 처리는 다른 코드가 맡는다.

메모에서 범위를 AI에게 해석시키지 않고 부위 이름 뒤의 "값~값" 규칙으로 읽는 가장 직접적인 이유는?

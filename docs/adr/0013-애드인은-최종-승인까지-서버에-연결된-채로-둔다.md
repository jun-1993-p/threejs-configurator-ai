# 애드인은 최종 승인까지 서버에 연결된 채로 둔다

업로드 뒤에도 교차 검증 샘플, 격자 보강, 두께 선택 후보 형상은 Fusion이 새로 계산해야 한다. 어떤 슬라이더 쌍이 필요한지는 후보 선택 뒤에야 정해진다. 그래서 업로드부터 최종 승인까지 CAD 애드인을 서버에 연결해 두고, 검증 중에 서버가 추가 샘플을 요청한다. 업로드 때 모든 파라미터 쌍(n(n−1)/2)과 두께 후보를 미리 뽑는 방법은 업로드를 크게 늦춘다. 1인 운영·LAN 로컬 서버이므로 Fusion을 켜 두는 부담은 작다. 연결이 끊기면 검증을 멈추고 "Fusion 연결 필요"를 표시한다.

Fusion을 껐다 켜도 이어지게, 애드인은 업로드 ID를 업로드한 디자인 문서의 속성에 적어 둔다(면 표시와 같은 곳이라 문서를 저장하면 따라온다). 다시 켠 뒤 그 문서가 열려 있고 서버가 그 업로드를 알면 애드인이 알아서 이어 답한다. 업로드 뒤 문서를 저장하지 않고 끄면 ID가 사라져 이어지지 않는다. 처음 확인한 결과(티켓 26 3절)는 ID를 메모리에만 두었을 때 다시 켠 뒤 이어지지 않았다.

업로드 완료는 메시지 창 대신 Fusion의 텍스트 명령 창에 알린다(티켓 33). Fusion API는 주 스레드에서만 부를 수 있어 일꾼 스레드는 주 스레드에 일을 넘길 뿐인데, 메시지 창은 닫을 때까지 주 스레드를 막는다. 티켓 26 선반 실물 확인에서 완료 창이 열린 동안 업로드 직후의 추가 샘플 요청이 "Fusion 연결 필요"로 끝났다. 업로드 ID와 점검 결과는 점검 파일(`data/addin-checks/<업로드 ID>.json`)에도 남아 위저드가 읽으므로, 사람이 창을 보고 옮겨 적을 일이 없다. 창을 띄운 채 답하게 하는 길(일꾼 스레드에서 Fusion API 부르기)은 API가 허용하지 않는다. 업로드 전 확인 창과 실패 창은 그대로 둔다. 그동안은 업로드 명령이 도는 중이라 원래 답하지 않는다.

끊김의 까닭을 가리려고 애드인의 일꾼 스레드가 몇 초마다 `data/addin-checks/serving.json`에 답하는 업로드, 열린 문서의 업로드, 주 스레드가 마지막으로 일한 시각, 마지막으로 서버를 찾은 시각, 마지막 오류를 쓴다. 파일이 오래되면 Fusion이 꺼졌거나 애드인이 멈춘 것이고, 파일은 새로운데 주 스레드가 일한 시각만 멈추면 주 스레드가 막힌 것이다. 까닭은 `scripts/serving_status.py`가 고른다.

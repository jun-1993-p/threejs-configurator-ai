# 명세(JSON) 스키마

상품 하나의 명세 구조. AI가 쓰는 유일한 산출물이다(ADR-0001). 용어는 `GLOSSARY.md`를 따른다.

## 예시

```json
{
  "product": "3단 서랍장",
  "front": "-Y",
  "axes": { "W": "X", "D": "Y", "H": "Z" },
  "sliders": [
    {
      "id": "W_total",
      "name": "전체 폭",
      "axis": "W",
      "min": 600, "max": 1200, "default": 800, "step": 10, "unit": "mm",
      "source": "치수규칙/서랍장/폭",
      "children": ["drawer_w", "divider_x"],
      "affects": { "shape": ["상판", "하판", "서랍_1"], "move": ["측판_우"] }
    }
  ],
  "thickness": [
    { "ids": ["t_body"], "name": "몸통 두께", "default": 18, "options": [15, 18, 24] }
  ],
  "fixed": ["t_back", "t_drawer_bottom"]
}
```

## 필드

| 필드 | 뜻 | 누가 정하나 / 검증 |
| --- | --- | --- |
| `product` | 상품명 | 정보 입력에서 가져온다 |
| `front` | 정면 방향(Fusion 좌표 기준) | 부품 탐색(VLM)이 정면 후보를 내고, 운영자가 고른 후보 카드의 정면이어야 한다(명세 검사). 부품 탐색이 확신하지 못하면 후보끼리 정면 후보를 나눠 갖는다 |
| `axes` | W 폭·D 깊이·H 높이와 Fusion 축의 대응 | `front`와 부품 탐색의 위쪽에서 정해진다. D는 `front` 방향의 축, H는 위쪽의 축, W는 남은 축이고, 고른 후보 카드에 보인 대응과 같아야 한다(명세 검사) |
| `sliders[].id` | 부모 파라미터의 Fusion 이름 | Fusion 사용자 파라미터에 있어야 하고, 업로드 묶음에 그 스윕이 있어야 한다. 운영자가 고른 후보의 부모여야 한다(자식 치수면 운영자가 고른 부모) |
| `sliders[].name` | 슬라이더 이름(한국어) | 후보 제시에서 AI가 고객이 보는 치수의 뜻으로 짓고, 명세는 고른 후보 카드의 이름 그대로다. Fusion 파라미터 이름이 낱말로 들어 있으면(대소문자 무시, "d12 폭"도) 실패한다. 최종 승인에서 고칠 수 있다 |
| `sliders[].axis` | 슬라이더가 움직이는 축 | 축 반응으로 검증한다 |
| `sliders[].min/max` | 범위 | 치수 규칙 ∩ 정보 입력 메모 ∩ 스윕 범위 안에서 AI가 고른다(ADR-0009) |
| `sliders[].source` | 범위의 근거가 된 치수 규칙 | 정보 입력의 상품 종류의 치수 규칙에 있는 항목이어야 한다 |
| `sliders[].default` | 기본값 | 업로드한 모델의 현재 값이고, `min`~`max` 안이다 |
| `sliders[].step`, `unit` | 슬라이더 단위 | AI |
| `sliders[].children` | 이 부모를 따르는 자식 파라미터 | 기록과 검증용. 업로드 묶음의 수식(`expression`)이 이 부모를 직접 또는 간접으로 따르는 파라미터만 적고, 자식 치수를 바꾸려고 고른 부모면 그 자식을 꼭 적는다. 변형 엔진은 읽지 않는다(ADR-0003) |
| `sliders[].affects.shape` | 형태 변경 부품 | 업로드 묶음의 부품 이름이어야 한다(Fusion 업로드는 `컴포넌트 경로#순번`, 순번은 위치 순서). 단독 스윕의 축 반응과 비교한다 |
| `sliders[].affects.move` | 위치 이동 부품 | 위와 같고, `shape`와 겹칠 수 없다 |
| `thickness[].ids` | 하나의 두께 선택으로 묶인 두께 파라미터 | 같은 기본 두께여야 한다 |
| `thickness[].name` | 두께 선택의 이름 | AI |
| `thickness[].options` | 두께 후보 | 표준 두께 목록에서 기본 두께의 앞뒤 한 칸이어야 한다(ADR-0010) |
| `fixed` | 고정 두께 파라미터 | 어떤 슬라이더의 `children`에도, 두께 선택에도 들어갈 수 없다 |

## 후보와 자식 치수의 부모 (ADR-0003)

후보 제시 응답(`configurator/pipeline/schemas.ts`의 `CANDIDATES_SCHEMA`)의 `sliders`는 고객이 바꿀 치수마다 `{ "parameter": "d5", "name": "서랍 폭" }`이다.

- 후보는 1~4개다. 보통 2~4개이고 서로 정면·부모 파라미터·두께 선택 노출 중 하나 이상이 다르다. 부품 탐색이 정면을 확신하고 정보 입력이 두께 선택 노출을 정하면(메모가 슬라이더를 하나로 정할 때) 서로 다른 구성이 하나뿐이라 후보 하나도 받는다. 두께 선택 노출이 "AI 판단"이면 후보 하나는 다시 묻는다. 후보 하나뿐인 회차에서 그 후보가 검증을 통과하지 못하면 후보 제시로 돌아가도 같은 후보뿐이라 후보 제시 단계에서 멈춘다(티켓 28).

- `parameter`는 스윕한 부모 파라미터이거나, 고객이 원하는 치수가 수식으로 부모를 따르는 자식 파라미터다. 개수형은 쓸 수 없고, 한 후보에서 같은 파라미터를 두 번 쓰지 않는다.
- 자식이면 부모 후보는 업로드 묶음의 수식을 거슬러 닿는 스윕한(개수형이 아닌) 파라미터이고, 가까운 것부터 늘어선다. 수식은 읽기만 하고 풀지 않는다. 부모 후보가 없거나, 모두 그 후보의 다른 슬라이더면 후보를 다시 묻는다.
- `name`에 Fusion 파라미터 이름이 낱말로 들어 있으면(대소문자 무시) 다시 묻는다. 이름이 뜻을 말하지 않는 파라미터(`d12`)는 AI에게 보내는 업로드 묶음 요약의 `sweeps[].response`(단독 스윕에서 상품 전체 `overall`과 부품 `parts`의 Fusion 축별 치수 `size`·위치 `move`가 기본 형상에서 가장 크게 바뀐 양, 0.2 mm 이하는 0)를 보고 짓는다.
- 후보 카드의 `choices`는 슬라이더마다 부모 후보(부모 파라미터면 자기 하나)와, 그 부모를 움직이면 같이 변하는 다른 치수(`alsoChanges`)다. 같이 변하는 치수는 단독 스윕에서 바뀌는 "전체 폭"과 "몸통 폭"처럼 부품 탐색의 역할 이름을 붙인 W·D·H 치수에서 슬라이더 자신의 이름을 뺀 것이다. 미리보기는 부모 후보마다 그린다.
- 운영자는 부모 후보가 여럿인 자식 치수마다 부모를 고른다(`HumanPort.chooseCandidate`의 `parents`: 자식 → 부모). 부모 후보가 하나면 고르지 않아도 그 부모다. 고르지 않았거나 부모 후보 밖이거나 두 슬라이더가 같은 부모를 움직이게 되면(명세의 슬라이더 id가 겹친다) 후보 선택 단계에서 멈춘다.
- 스타일 고르기와 명세 작성 입력의 `candidate`는 카드의 `axes`가 붙고 `sliders`가 `{ parameter, name, parent }`인 고른 후보다. 명세 검사는 슬라이더 `id`가 어느 `parent`이고 `name`이 그 `name`이며, `parent`가 `parameter`와 다르면 `children`에 `parameter`가 있는지 본다. 범위 교집합이 없으면 슬라이더를 빼라고 하므로 고른 슬라이더가 모두 있어야 하지는 않다.

## 스타일 선택 (ADR-0001)

스타일 선택은 명세에 적지 않고 결과물의 `style.json`으로 따로 나온다. 쇼핑몰 div는 `data-style="style.json"`으로 불러온다.

- UI 스타일 목록(`configurator/pipeline/ui-styles.ts`, 저장소 포트의 `styles()`)의 스타일 하나는 `{ id, summary, colors: { background, text, accent, parts }, font, slider }`다. 색은 `"#rrggbb"`, `parts`는 부품마다 돌려 쓰는 색, `font`는 CSS `font-family`, `slider`는 슬라이더 모양 `thin`·`bold`·`square`(`src/style.ts`의 `SLIDER_SHAPES`) 중 하나다.
- 목록이 이 형식(`schemas.ts`의 `checkStyles`)에 맞지 않으면 고르기 전에 스타일 단계에서 멈춘다. 고정 코어가 값을 그대로 CSS와 재질 색에 넣기 때문이다.
- 스타일 고르기 입력은 `intake`, `candidate`, `styles`(목록 그대로)이고, 응답은 `{ "style": "<목록의 id>" }`다. 목록 밖의 id는 고를 수 있는 id를 붙여 다시 묻고, 3번 다시 물어도 맞지 않으면 명세 작성으로 가지 않고 멈춘다.
- 고정 코어는 고른 스타일의 바탕·글자 색과 글꼴을 구성기 div에, 강조 색을 슬라이더와 두께 선택 슬롯에, 부품 색을 부품 메쉬에 입힌다. 슬라이더 모양마다의 CSS는 고정 코어에 있다.

## 명세에 적지 않는 것

- 개수형 파라미터와 위상 묶음: 애드인이 찾아 스윕 결과에 담는다(ADR-0005).
- 스윕 샘플 위치: 애드인이 업로드 때 적응형으로 정한다(ADR-0007).
- 격자 보강 쌍: 애드인 결과에 담는다(ADR-0008).

## 검증 피드백

실패 하나당 항목 하나.

```json
{
  "path": "sliders[2].affects.shape",
  "slider": "drawer_w",
  "part": "칸막이_좌",
  "kind": "unexpected_shape_change",
  "measured": { "value": 950, "axis": "W", "size_delta_mm": 14.2, "move_mm": 7.1 },
  "expected": "위치 이동만",
  "hint": "칸막이_좌를 위치 이동 부품으로 옮기거나, 자식 수식 확인"
}
```

- `path`: 고칠 명세 위치.
- `kind`: 정해진 목록(`configurator/pipeline/feedback.ts`의 `FEEDBACK_KINDS`).

  | `kind` | 뜻 |
  | --- | --- |
  | `dimension_error` | 치수 오차 초과 |
  | `shape_error` | 형상 오차 초과 |
  | `unexpected_shape_change` | 예상하지 못한 형태 변경 |
  | `off_axis_change` | 다른 축 변화 |
  | `missing_axis_change` | 선언한 축 반응 없음(형태 변경 부품의 치수, 위치 이동 부품의 자리가 그대로) |
  | `unexpected_move` | 예상하지 못한 위치 이동 |
  | `thickness_change` | 두께 변화(두께 고정 위반) |
  | `topology_change` | 위상 변화 |
  | `recompute_failed` | 재계산 실패 |
  | `range_shrunk` | 범위 축소 |
  | `modeling_error_suspected` | 모델링 오류 의심 |
  | `volume_jump` | 부피 튐(경고) |
  | `no_range_intersection` | 범위 교집합 없음 |
  | `ai_judgment` | AI 판정(이미지 경로와 이유 한 줄 포함) |
  | `grid_limit` | 격자 보강이 필요한 쌍이 상품당 2쌍을 넘음 |
  | `topology_group_limit` | 파라미터 하나의 위상 묶음이 4개를 넘어 범위가 줄어듦 |

- `part`: 부품과 무관한 실패(검증점 재계산 실패, 스윕 범위의 재계산 실패 축소, 검증점의 `topology_change`)는 빈 문자열이다. 범위 축소(`range_shrunk`·`modeling_error_suspected`·`topology_group_limit`)는 바뀐 면이 속한 부품이고, 기준 형상에 없는 바디(새로 생긴 칸막이 등)면 그 바디 이름이다.
- `range_shrunk`·`modeling_error_suspected`·`topology_group_limit`·`recompute_failed`: 애드인이 위상 변화(면 또는 모서리 구성)나 재계산 실패로 스윕 범위를 줄인 기록(업로드 묶음 `sweeps[].reductions`, `reason`이 이 `kind`와 같다)에서 나온다(ADR-0005, 0007). 쪽마다 가장 안쪽 까닭 하나만 남는다.
  - 재계산 실패: 기본값에서 그쪽으로 가며 처음 실패한 샘플이나 검증점(`at`)부터 바깥을 버리고, 그 안쪽의 가장 먼 점(검증점이면 샘플로 삼는다)이 범위 끝이 된다. 힌트는 "`at`에서 Fusion이 재계산하지 못했습니다"다.
  - 범위 안에서 개수형 파라미터 값과 함께 면 구성이 바뀌면 범위를 줄이지 않고 위상 묶음으로 나눈다(`sweeps[].groups`). 묶음이 파라미터당 4개(기본 묶음 포함)를 넘으면 기본값에서 먼 묶음부터 빼고 `topology_group_limit`으로 줄인다.
  - 개수형 값은 그대로인데 면 구성이 바뀌면 `modeling_error_suspected`로 줄인다.
  - 위상 묶음 안의 단독 스윕(`groups[].sweeps`)은 다시 묶음으로 나누지 않는다. 면 구성이 바뀌면 개수형 값이 바뀌었으면 `range_shrunk`, 그대로면 `modeling_error_suspected`로 줄인다. 힌트 앞에 그 묶음(`shelf_w=1200.04 위상 묶음에서`)이 붙고 `measured.values`에 묶음 기준 값이 들어간다.
  - 업로드 단계: 처리 기록으로 운영자에게 알린다. 명세가 없으므로 `path`는 빈 문자열이고, `slider`에는 그 파라미터 이름(슬라이더가 된다면 그 id)이 들어간다.
  - 검증 단계: 명세 범위가 줄어든 쪽을 넘으면 수치 검증 전에 `sliders[i].min`/`max`에 다시 낸다. `expected`는 줄어든 범위 끝(`{ "min": 337.5 }`)이다. 위상 묶음 안의 단독 스윕은 묶음의 파라미터가 슬라이더이고 그 슬라이더 범위가 묶음에 닿을 때만 본다.
- 보간 실패(업로드 묶음 `sweeps[].interpolation_failure`, ADR-0007): 업로드 단계 처리 기록에 `kind`가 `shape_error`·`dimension_error`인 피드백으로 남는다. `path`는 빈 문자열, `measured`는 `{ at, error }`, `expected`는 `{ max_error_mm }`이고, 힌트는 그 파라미터를 슬라이더 후보에서 뺀다고 알린다. 후보 검사와 명세 검사는 그 파라미터를 슬라이더로 쓰면 거절한다. 위상 묶음 안의 단독 스윕에서 실패해도 같다. 재계산 실패로 범위가 줄어 재계산에 성공한 샘플이 2개보다 적은 단독 스윕의 파라미터도 같은 검사에서 거절한다(보간할 수 없다).
- `volume_jump`(경고): 업로드 단계 처리 기록에만 남고 실패로 치지 않는다. `path`는 빈 문자열, `part`는 그 바디가 속한 부품, `measured`는 `{ value, body, volume }`, `expected`는 `{ volume }`(이웃 두 샘플의 선형 보간)이다. 같은 위상 묶음의 이웃 샘플끼리만 견주고, 바디 측정값이 없는 녹화본에서는 나오지 않는다.
- `slider`: 한 슬라이더의 실패가 아니면(`grid_limit`) 빈 문자열이고, 이때 `path`는 `sliders`다.
- `hint`: 규칙으로 만든다(AI가 쓰지 않음).

### 범위 교집합 (ADR-0009)

슬라이더마다 세 범위의 교집합을 본다(`configurator/pipeline/range-intersection.ts`).

- 치수 규칙: `source`가 가리키는 규칙의 범위. 규칙은 상품 종류·부위·축(W·D·H)·범위·출처로 이루어진다. 정보 입력의 상품 종류로 거른 것만 명세 작성에 주고, `source`도 그 안에 있고 슬라이더와 같은 축이어야 한다.
- 정보 입력 메모: 메모에서 그 규칙의 부위 이름 바로 뒤에 오는 "값~값"(`폭 600~1200`, `폭은 60~120cm`, `폭: 600mm ~ 1,200mm`). 조사(은·는·이·가)와 쌍점, 쉼표 천 단위, mm·cm 단위(한쪽에만 붙어도 양쪽에 씀), `~`·`-`·`～`를 읽는다. 단위가 없으면 mm다. 부위 이름은 그 상품 종류의 치수 규칙에서 가져오고 긴 이름부터 읽는다("서랍 깊이 300~500"은 "깊이"의 범위가 아니다). 메모에 그 부위의 범위가 없으면 이 범위는 빠진다. 어느 부위에도 붙지 않은 "값~값"은 정보 입력 처리 기록에 `{ "memoUnread": ["100~200"] }`으로 남겨 운영자가 의도를 확인하게 한다.
- 스윕 범위: 업로드 묶음의 그 파라미터 스윕 범위.

명세 검사(형식이 틀린 응답과 같이 다시 묻는다):

- `source`가 치수 규칙에 없거나 그 규칙의 축이 슬라이더 축과 다르면 실패한다(다른 축 부위의 규칙으로 메모 범위를 비켜 가지 못하게).
- `default`가 업로드한 모델의 값과 다르거나 `min`~`max` 밖이면 실패한다.
- `min`·`max`가 교집합 밖이면 실패한다. 다만 애드인이 줄인 쪽 스윕 범위(`reductions`)는 범위 검증이 줄어든 까닭과 함께 검증 피드백으로 알리므로 여기서는 보지 않는다(오류 문구의 교집합도 그쪽을 뺀 것이다).

교집합(줄어든 쪽 스윕 범위 포함)이 비었거나 업로드한 모델의 값을 담지 않으면 범위를 지어내지 않도록 조립하지 않고 `no_range_intersection`을 낸다. 처리 기록의 검증 항목으로 운영자에게 보이고, 명세 작성으로도 돌아간다(같은 후보로 3번 넘게 실패하면 후보 제시로).

```json
{
  "path": "sliders[0].source",
  "slider": "body_w",
  "part": "",
  "kind": "no_range_intersection",
  "measured": { "rule": { "id": "치수규칙/서랍장/폭", "min": 300, "max": 1200 }, "memo": { "min": 1000, "max": 1200 }, "sweep": { "min": 300, "max": 900 }, "default": 600 },
  "expected": "세 범위가 겹치고 기본값을 담는 구간",
  "hint": "body_w의 세 범위(치수 규칙 치수규칙/서랍장/폭 300~1200, 정보 입력 메모 폭 1000~1200, 스윕 범위 300~900)가 겹치지 않습니다. 범위를 지어내거나 다른 부위의 치수 규칙으로 바꾸지 말고 이 슬라이더를 빼세요. 운영자는 정보 입력 메모와 모델을 확인해야 합니다"
}
```

메모에 그 부위 범위가 없으면 `measured.memo`가 없다. 스윕 범위가 애드인이 줄인 것이면 힌트의 스윕 범위 뒤에 `(min 쪽은 애드인이 줄임)`이 붙는다.

### 수치 검증 (ADR-0012)

업로드 묶음의 단독 스윕마다 `checks`(이웃 샘플 사이 가운데 값의 Fusion 형상, 검증점)가 있다. 슬라이더 범위 안의 검증점마다 그 슬라이더만 검증점 값으로 두고(나머지는 `default`) 변형 결과를 잰다.

위상 묶음이 있는 슬라이더는 검증점이 든 묶음의 면 구성으로 잰다. 슬라이더 범위가 닿는 묶음마다 묶음 안 단독 스윕의 검증점도 잰다. 이때 묶음의 슬라이더는 기준 값(`anchor`)에 두고, `measured`는 `{ values }`, 힌트의 자리는 `shelf_d=337.5·shelf_w=1200.04` 꼴이다. 검증점 형상이 그 묶음의 기준 형상과 면 구성이 다르면 `topology_change`다.

- 치수 오차: 부품별 W·D·H(`axes`에 따른 바운딩 박스 길이)와 판재 두께가 0.2 mm를 넘으면 `dimension_error`. 판재 두께는 같은 바디에서 서로 등진 두 평면 중 기준 형상(기본 형상, 위상 묶음이면 그 묶음의 기준 형상) 간격이 30 mm(표준 두께 목록의 최댓값) 이하인 쌍의 간격이며, 부품마다 가장 크게 어긋난 판 하나를 알린다.
- 형상 오차: 부품별로 같은 꼭짓점끼리 잰 거리의 최댓값이 max(1 mm, 그 검증점 Fusion 형상 바운딩 박스 대각선의 0.1%)를 넘으면 `shape_error`.
- `path`는 검증점이 기본값보다 작으면 `sliders[i].min`, 크면 `sliders[i].max`이고, 힌트는 그쪽 범위를 검증점 값 안쪽으로 좁히라고 한다.

```json
{
  "path": "sliders[0].max",
  "slider": "body_w",
  "part": "DrawerBox",
  "kind": "dimension_error",
  "measured": { "value": 825, "dimension": "W", "engine_mm": 785, "fusion_mm": 785.3, "error_mm": 0.3 },
  "expected": { "max_error_mm": 0.2 },
  "hint": "DrawerBox의 W가 825에서 Fusion과 0.3 mm 다릅니다. body_w의 max를 825보다 작게 좁히세요"
}
```

두께는 `measured.dimension`이 `thickness`이고 `faces`에 판의 두 면 이름이 붙는다. 형상 오차의 `measured`는 `{ value, error_mm }`, `expected`는 `{ max_error_mm }`이다.

### 두께 고정 실측 (ADR-0010)

범위 검증을 통과한 명세에서 수치 검증보다 먼저 본다. 슬라이더마다 단독 스윕 전체(슬라이더 범위 밖 포함)의 샘플과 검증점(재계산 성공, 면 구성이 기준 형상과 같은 것)에서 판재 두께를 Fusion 형상으로 잰다. 슬라이더 범위가 닿는 위상 묶음이 있으면 묶음 안 단독 스윕도 잰다(`measured`는 `{ values }`). 판은 수치 검증의 판재 두께와 같은 면 쌍이고, 그 위상 묶음 기준 형상의 간격에서 0.2 mm를 넘게 바뀌면 `thickness_change`다. 슬라이더·부품마다 가장 크게 바뀐 곳 하나를 알린다.

두께가 슬라이더의 비율 수식(`body_w * 0.03`)이면 변형 엔진의 보간이 Fusion과 맞아 수치 검증은 통과하고, 명세 검사(고정 두께가 슬라이더 자식에 없음)로는 Fusion 수식을 볼 수 없어서 따로 잰다. 수치 검증보다 먼저 보는 것은, 비선형 두께 수식에서도 판 두께 치수 오차 대신 원인(슬라이더 X가 부품 Y의 두께를 바꿈)을 알리기 위해서다.

```json
{
  "path": "sliders[0]",
  "slider": "body_w",
  "part": "Carcass",
  "kind": "thickness_change",
  "measured": { "value": 300, "faces": ["F2:side:l4", "F3:inner:F2:side:l4"], "baseline_mm": 18, "fusion_mm": 9, "change_mm": 9 },
  "expected": { "max_change_mm": 0.2 },
  "hint": "슬라이더 body_w가 부품 Carcass의 두께를 바꿉니다: 판 두께(F2:side:l4·F3:inner:F2:side:l4)가 300에서 18 mm → 9 mm. 모델에서 두께 수식에 이 슬라이더(또는 그 자식)가 섞여 있는지 확인하거나, 이 슬라이더를 빼세요"
}
```

### 축 반응

수치 검증과 두께 고정 실측을 통과한 명세만 본다. 업로드 묶음의 단독 스윕에서 슬라이더 범위 안의 샘플과 검증점(재계산 성공, 기본값 제외)마다, 부품의 W·D·H별 치수(바운딩 박스 길이)와 가운데 위치가 기본 형상에서 얼마나 바뀌었는지 Fusion 형상으로 잰다. 부품은 그 바디의 모든 면으로 재므로 면 구성이 바뀐 샘플도 잴 수 있다. 0.2 mm(치수 오차 합격선과 같은 값)를 넘으면 바뀐 것으로 본다. "바뀌지 않는다"는 범위 안에서 가장 크게 바뀐 샘플도 0.2 mm 이하라는 뜻이다. 한 축에 슬라이더가 여러 개여도(전체 폭·서랍 폭) 슬라이더마다 따로 본다.

| 부품 | 슬라이더 축에서 기대 | 어기면 `kind` | `path` |
| --- | --- | --- | --- |
| `affects.shape` | 치수가 바뀐다 | `missing_axis_change` | `sliders[i].affects.shape` |
| `affects.move` | 치수는 그대로, 자리가 옮겨진다 | 치수가 바뀌면 `unexpected_shape_change`, 자리가 그대로면 `missing_axis_change` | `sliders[i].affects.move` |
| 선언하지 않은 부품 | 그대로 | 치수가 바뀌면 `unexpected_shape_change`(`affects.shape`), 자리가 옮겨지면 `unexpected_move`(`affects.move`) | 괄호 안 |
| 모든 부품 | 다른 축의 치수와 위치가 그대로 | `off_axis_change` | `sliders[i].axis` |

- 표는 위에서부터 보고, 부품마다 처음 걸린 행 하나(와 다른 축 변화)만 알린다. 알리는 샘플은 그 양이 가장 크게 바뀐 샘플이다. `measured`는 `{ value, axis, size_delta_mm, move_mm }`(그 샘플 값, 잰 축, 치수 변화, 가운데 위치 변화)이다.
- 힌트는 부품을 어느 목록에 넣거나 빼라고 하고, 자식 수식도 확인하라고 한다.

### 교차 검증 (ADR-0004, ADR-0013)

두께 고정 실측·수치 검증·축 반응을 통과한 명세만 본다. 슬라이더가 둘 이상이거나 두께 선택이 있으면 서버가 애드인에 교차 검증 샘플을 요청한다. 슬라이더 쌍마다 두 범위의 모서리 조합 4곳(`min`·`max` × `min`·`max`, 나머지 슬라이더는 `default`), 그다음 두께 선택마다 기본 두께가 아닌 두께 후보마다 각 슬라이더의 범위 끝 2곳(나머지 슬라이더는 `default`, `{ "shelf_w": 500, "shelf_d": 300, "t": 24 }`)을 한 요청으로 보낸다. 이 값 묶음으로 변형 결과(단독 스윕 이동량과 두께 후보 이동량의 덧셈)와 받은 Fusion 형상을 비교한다.

- 재는 방법과 합격선은 수치 검증과 같다(형상 오차, 부품별 W·D·H와 판 두께의 치수 오차, 재계산 실패, 위상 변화).
- `path`는 쌍의 앞 슬라이더 `sliders[i]`, `slider`는 그 슬라이더다. `measured.values`에 쌍의 두 슬라이더 값이 있어 어느 쌍인지 알 수 있다.
- 힌트는 한쪽을 다른 쪽의 자식으로 두거나 두 범위를 좁히라고 한다(ADR-0008).
- 두께 쌍(`[두께 선택의 첫 파라미터, 슬라이더]`)은 `path`가 `thickness[i].options`, `slider`가 함께 움직인 슬라이더다. `measured.values`에 두께 후보와 슬라이더 값이 있고, 힌트는 "두께 t와 body_w를 함께 움직이면 덧셈이 맞지 않습니다"에 이어 슬라이더 수식(자식 수식 포함)에 두께가 섞여 있는지 확인하거나 그 슬라이더 범위를 좁히라고 한다.
- 두께 쌍에서 판 두께 치수 오차가 나면 `kind`는 `thickness_change`다(`measured`는 치수 오차와 같은 꼴). 엔진은 고른 두께를 그대로 두므로, 그 두께 후보에서 슬라이더가 판 두께를 바꾼다는 뜻이다. 힌트는 "슬라이더 body_w가 두께 t=24에서 부품 Carcass의 두께를 바꿉니다"로 시작한다.

```json
{
  "path": "sliders[0]",
  "slider": "body_d",
  "part": "DrawerBox",
  "kind": "dimension_error",
  "measured": { "values": { "body_d": 600, "drawer_d": 600 }, "dimension": "D", "engine_mm": 750, "fusion_mm": 600, "error_mm": 150 },
  "expected": { "max_error_mm": 0.2 },
  "hint": "DrawerBox의 D가 body_d=600·drawer_d=600에서 Fusion과 150 mm 다릅니다. body_d와 drawer_d를 함께 움직이면 덧셈이 맞지 않습니다. 한쪽을 다른 쪽의 자식으로 두거나 두 범위를 좁히세요"
}
```

### 격자 보강 (ADR-0008)

교차 검증에 실패한 쌍은 먼저 위 피드백으로 명세를 다시 쓰게 한다. 다시 쓴 명세(같은 후보)에서도 같은 쌍이 실패하면, 그 쌍을 격자로 보강하고 같은 명세를 다시 검증한다.

- 요청: `kind` `grid`로 두 슬라이더의 `min`·`default`·`max`를 엇건 9곳(앞 슬라이더가 바깥 고리) 다음에 검증점 8곳(격자 칸 가운데 4곳, 그다음 기본값 줄 위의 마디 사이 가운데 4곳)을 이어 보낸다. 나머지 슬라이더는 `default`다. `default`가 범위 끝이면 그 축은 값 2개라 격자가 2×3(검증점도 그만큼 적음)이 된다.
- 격자 보강은 명세에 적지 않는다. 결과물의 `sweeps.json`에 `grids: [{ parameters: [앞, 뒤], samples }]`(격자 마디, 교차 검증 샘플 형식)로 담기고, 변형 엔진은 덧셈 결과에 격자 마디의 나머지(격자 샘플 - 두 단독 스윕 이동량)를 쌍선형으로 섞어 더한다.
- 격자 보강 쌍의 슬라이더는 수치 검증에서 단독 스윕 검증점을 재지 않는다. 짝 슬라이더가 Fusion 수식으로 따라가는 단독 스윕(전체 깊이·서랍 깊이)은 짝 값을 고정한 구성기 상태가 아니기 때문이다. 대신 교차 검증에서 격자 검증점을 같은 측정과 합격선으로 재고, 넘으면 교차 검증과 같은 형식의 피드백(힌트에 "격자 보간으로도 맞지 않습니다")이 나온다.
- 재계산 실패·위상 변화로 실패한 쌍은 격자로 섞을 수 없어 보강하지 않는다. 격자 샘플에 재계산 실패·위상 변화가 있으면 그 피드백을 낸다.
- 두께 쌍도 같은 규칙으로 보강한다. 요청은 기본 두께가 아닌 두께 후보마다 슬라이더의 `min`·`default`·`max`(후보가 바깥 고리) 다음에 후보마다 슬라이더 마디 사이 가운데(검증점)다. `grids`에는 `parameters: [두께 선택의 첫 파라미터, 슬라이더]`로 담기고, 변형 엔진은 고른 두께 후보의 나머지(격자 샘플 - 슬라이더 이동량 - 두께 후보 이동량)를 슬라이더 값으로 선형 보간해 더한다. 기본 두께에서는 더하지 않으므로, 이 슬라이더의 단독 스윕 검증점은 수치 검증에서 그대로 잰다. 2쌍 상한에 함께 센다. 슬라이더 쌍의 격자와 같이 기본 묶음에서만 쓴다. 슬라이더 범위가 다른 위상 묶음에 닿으면 범위 끝 격자 샘플의 면 구성이 기본 형상과 달라 보강하지 않으므로(`topology_change`), 보강한 슬라이더가 고른 두께에서 위상 묶음으로 넘어가 보정이 사라지는 일은 없다.
- 받은 격자는 같은 후보의 다음 명세에서도 쓰되, 요청한 값 묶음(범위·기본값·두께 후보)이 같을 때만 쓴다. 같은 요청은 다시 보내지 않는다.
- 보강이 필요한 쌍(이미 보강한 쌍 포함)이 2쌍을 넘으면 격자를 요청하지 않고, 교차 검증 피드백에 `grid_limit` 항목 하나를 더한다.

```json
{
  "path": "sliders",
  "slider": "",
  "part": "",
  "kind": "grid_limit",
  "measured": { "pairs": [["body_w", "body_h"], ["body_w", "body_d"], ["body_h", "body_d"]] },
  "expected": { "max_pairs": 2 },
  "hint": "덧셈이 맞지 않아 격자 보강이 필요한 슬라이더 쌍이 3쌍으로, 상품당 2쌍을 넘습니다. 한쪽을 다른 쪽의 자식으로 두거나 슬라이더를 줄이세요"
}
```

### AI 판정

두께 고정 실측·수치 검증·축 반응·교차 검증(격자 보강 포함)을 모두 통과한 명세만 본다. 비싼 VLM 호출을 수치로 잡을 수 있는 실패에 쓰지 않기 위해서다(`configurator/pipeline/verify-judgment.ts`).

- 렌더링: 결과물의 `sweeps.json`으로 변형 엔진이 만든 형상을 그린다. 슬라이더마다 `min`·`max`, 그다음 슬라이더 쌍마다 모서리 조합 4곳(앞 슬라이더가 바깥 고리)이고 나머지 슬라이더는 `default`다. 두께 선택은 바꾸지 않는다. 모두 같은 축척이고, 정면에서 오른쪽 위로 비켜 본 직교 투영이며 부품마다 색이 다르다. 렌더링 이름은 기본값에서 옮긴 슬라이더의 자리 표기(`body_w=800`, `body_w=400·body_h=1000`)다.
- 형식 오류로 다시 묻는 기록과 끝내 형식이 맞지 않아 멈추는 단계는 검증(`verification`)이다. AI 판정은 검증 단계 안의 일이다(ADR-0014).
- 판정 입력은 `intake`, `spec`, `renders`(`{ name, values, image }`, `values`는 모든 슬라이더 값, `image`는 PNG base64), `colors`(부품 이름과 그림 속 색)다. LiteLLM 구현은 렌더링을 모음 그림(320×240 칸을 한 장에 3×3칸까지 크기를 바꾸지 않고 이어 붙인 PNG)으로 붙이고, 문장에는 칸마다 `name`·`values`와 칸 위치 `sheet`(요청에 붙인 모음 그림 순서)·`row`·`column`(모두 1부터)만 남긴다. 부품 탐색의 여섯 방향 그림도 같은 방식으로 모음 그림 한 장(`views`는 `{ from, sheet, row, column }`)으로 간다.
- 요청 하나에 붙이는 모음 그림은 VLM 그림 수 제한(`liteLlmAi`의 `maxImages`, 실행 도구는 `LITELLM_VLM_MAX_IMAGES`, 기본 3)까지다. 넘으면 렌더링을 차례로 나눠 묻고(요청마다 출력 형식의 그림 이름은 그 요청의 렌더링만) `problems`를 합친다. 나눈 답 하나라도 형식이 틀리면 그 답을 돌려줘 형식 오류로 다시 묻고, 그때는 나눈 요청을 모두 다시 묻는다.
- 응답은 `{ "problems": [{ "image": "<렌더링 이름>", "reason": "<한 줄>" }] }`이다. 문제가 없으면 빈 목록이고 통과다. 보내지 않은 렌더링 이름이나 줄바꿈이 든 이유는 형식 오류로 다시 묻는다.
- 같은 렌더링을 여러 번 짚으면 이유를 `; `로 이어 붙여 하나로 둔다. 문제가 있는 렌더링마다 그 그림을 저장소 포트의 `saveRender`로 저장하고(메모리 저장소는 `renders/<상품명>/<렌더링 이름>.png`) 피드백 하나를 낸다. `path`는 그 렌더링에서 옮긴 첫 슬라이더 `sliders[i]`(쌍이면 앞 슬라이더), `slider`는 그 id, `part`는 빈 문자열이다. `measured`는 `{ image, values, reason }`(저장한 경로, 슬라이더 값, 판정 이유), `expected`는 `"뚫림·겹침·비례 깨짐 없음"`이고, 힌트는 운영자에게 렌더링을 보고 문제가 맞으면 그 끝값을 범위에서 빼거나 반려하라고 한다.
- AI 판정은 한 번만 받고 명세를 다시 쓰게 하지 않는다. 짚은 곳이 있든 없든 최종 승인으로 가고, 사람 결정 `finalApproval`의 `judgment`에 판정 피드백이 담겨 최종 승인 화면에 "AI 판정이 짚은 곳"으로 이유와 렌더링이 보인다. 짚은 곳이 없으면 `judgment`는 빈 목록이다. 이미지 모델이 멀쩡한 형상을 오판하면 끝값을 빼느라 운영자가 정한 범위가 줄었기 때문이다(티켓 26 6절 Groq 회차, 티켓 29). 처리 기록의 검증 단계에는 `{ attempt, feedback }`로 판정 피드백이 남는다.

```json
{
  "path": "sliders[0]",
  "slider": "body_w",
  "part": "",
  "kind": "ai_judgment",
  "measured": { "image": "renders/1단 서랍장/body_w=800.png", "values": { "body_w": 800 }, "reason": "폭 끝값에서 서랍과 몸통 옆판 사이가 벌어져 뚫려 보임" },
  "expected": "뚫림·겹침·비례 깨짐 없음",
  "hint": "body_w=800에서 AI 판정이 짚음: 렌더링을 보고 문제가 맞으면 그 끝값을 범위에서 빼거나 반려"
}
```

### 두께 선택 (ADR-0010)

- 명세 검사(형식 검사와 함께 `schemaErrors`로 다시 묻는다): `options`는 표준 두께 목록(3·6·9·12·15·18·24·30 mm, 고정 코어의 `STANDARD_THICKNESSES`)에서 `default`의 앞뒤 한 칸과 `default`다(목록 끝은 2개). `ids`는 업로드 묶음의 파라미터이고 기본 두께가 모두 같으며, 그 값이 `default`다. `fixed`와 `thickness[].ids`의 파라미터는 어떤 슬라이더의 `children`에도 없고(두께 고정), 한 파라미터는 고정 두께와 두께 선택 하나 중 한 곳에만 있다.
- 두께 후보 형상: 조립 전에 서버가 애드인에 `kind` `thickness`로 요청한다. 두께 선택마다, 기본 두께가 아닌 후보마다, 기본 형상과 슬라이더 범위가 닿는 위상 묶음의 기준 값(`anchor`)마다 값 묶음 하나다(`{ "t": 24 }`, `{ "t": 24, "shelf_w": 675 }`). 나머지 파라미터는 업로드한 모델의 값이다.
- 받은 형상은 결과물의 `sweeps.json`에 `thickness`(교차 검증 샘플 형식 목록)로 담긴다. 변형 엔진은 고른 후보의 이동량(그 묶음 기준 형상에서)을 사이 값 없이 바꿔 끼워 슬라이더 이동량에 더한다. 구성기와 엔진에는 두께 선택 값을 묶인 파라미터 중 아무 이름으로 준다.
- 두께 후보 형상이 재계산에 실패하거나 기준 형상과 면 구성이 다르면 `recompute_failed`·`topology_change` 피드백이 나온다. `path`는 `thickness[i].options`, `slider`·`part`는 빈 문자열, `measured`는 `{ values }`이고, 힌트는 그 두께 선택을 빼고 고정 두께로 두거나 두께 수식을 확인하라고 한다.
- 두께 고정 실측과 두께 후보 × 슬라이더 교차 검증·격자 보강은 위 각 절에 있다. 두 두께 선택을 함께 바꾼 조합은 아직 보지 않는다.

### 애드인 연결

애드인 연결이 끊겨 있으면 실패로 세지 않는다. 처리 기록에 `{ "fusion": "Fusion 연결 필요" }`를 남기고 기다렸다가, 다시 연결되면 `{ "fusion": "다시 연결됨" }`을 남기고 같은 요청을 다시 보낸다. 애드인이 샘플을 뽑지 못했다고 알리거나(모델에 없는 파라미터, Fusion API 오류) 응답이 형식(업로드 묶음 스키마의 `sampleResponse`)에 맞지 않으면 검증 단계에서 멈춘다.

### 재시도

- 같은 후보로 피드백과 재시도를 3번 넘게 거쳐도(처음 명세 + 다시 쓰기 3번) 통과하지 못하면, 마지막 피드백을 실패 이유로 붙여(`failures`) 후보 제시로 돌아간다.
- 후보 선택은 5회차(`runner.ts`의 `CANDIDATE_ROUNDS`)까지 돈다. 회차는 고른 후보로 명세를 써 보는 횟수로, 검증 실패, 최종 승인 반려, 다른 후보로 다시 고르기를 함께 센다. 5회차까지 제출하지 못하면 후보 제시 단계에서 멈춘다. 사람이 고르지 않는 실행 도구에서도 끝나게 하기 위해서다(티켓 31).
- AI 판정은 재시도에 들지 않는다. 수치 검증·축 반응·교차 검증을 통과하면 판정 결과와 함께 최종 승인으로 간다(티켓 29).

## 최종 승인 (사용자 스토리 68~72)

사람 결정 `HumanPort.finalApproval({ spec, files, judgment, errors, edits })`의 답은 셋 중 하나다. `errors`는 앞서 낸 답이 막힌 까닭, `edits`는 그 답이 고친 내용(화면이 칸에 다시 채운다)이고, 처음 물을 때는 둘 다 비어 있다. `spec`은 늘 승인 전 명세다. 막힌 답은 처리 기록 `approval` 단계에 `{ "errors": [...] }`로 남기고 다시 묻는다.

- `{ "decision": "approve", "edits": { "<슬라이더 id>": { "name"?, "min"?, "max"? } } }`: 고친 이름과 범위를 명세에 넣어 제출하고 사례로 기록한다. 결과물에서는 `spec.json`과, 그 명세로 다시 거른 `sweeps.json`(좁힌 범위가 닿지 않는 위상 묶음이 빠진다)이 바뀐다. 좁힌 범위는 검증한 범위 안이라 다시 검증하지 않는다.
  - 범위는 좁히기만 한다. `min`은 승인 전 `min` 이상, `max`는 승인 전 `max` 이하이고, 기본값(업로드한 모델의 값)이 범위 안에 남는다. 고친 끝은 기본값에서 `step`의 배수만큼 떨어져야 하고(고정 코어의 슬라이더가 `min`에서 `step`씩 움직이므로 기본값을 고를 수 있게), 범위가 한 값뿐이면 안 된다. 오류 경로는 `/<슬라이더 id>/min`처럼 고친 내용을 가리킨다(`approvalEditChecker`).
  - 고친 이름은 비우거나 두 줄로 쓸 수 없고, 명세 검사처럼 Fusion 파라미터 이름이 낱말로 들어 있으면 막힌다(오류 경로는 명세의 `/sliders/i/name`).
- `{ "decision": "reject", "back": "choice" }`: 후보 제시를 다시 하지 않고 이미 받은 후보 카드로 후보 선택에 돌아간다.
- `{ "decision": "reject", "back": "candidates", "reason": "<한 줄>" }`: 거절 이유를 후보 제시 입력 `rejections`(`{ candidate, reason }` 목록, 이 상품에서 쌓인 것 모두)에 붙여 새 후보를 받는다. 비었거나 줄바꿈이 든 이유는 막힌다.
- 처리 기록 `approval` 단계의 `detail`은 받아들인 답 그대로다(고친 내용과 거절 이유가 남는다).
- 최종 승인 화면(`finalApprovalHtml`)은 결과물의 고정 코어로 구성기를 띄우고, 고치는 칸의 값이 바뀌면 그 이름·범위로 다시 띄운다. 범위 칸의 `min`·`max` 속성은 위 좁히기 규칙과 같다. 양식은 `readFinalApproval`이 위 답으로 읽는다.

## 사례 저장소 (ADR-0011, 사용자 스토리 75~77)

- **사례 기록**: 최종 승인해 제출하면 `cases.jsonl`에 한 줄로 남는다(`CaseRecord`에 `id`가 붙는다). 담는 것은 `kind`(상품 종류), `intake`(정보 입력), `candidates`(후보 제시 회차마다 제시된 후보 목록), `chosen`(최종 승인된 명세의 고른 후보: 축 대응과 슬라이더마다 움직일 부모가 붙는다), `spec`(최종 승인 때 고친 내용을 넣은 명세), `edits`(최종 승인 때 고친 내용, 없으면 `{}`), `rejections`(이 상품에서 반려하며 적은 `{ candidate, reason }`), `backToChoice`(거절 이유 없이 "다른 후보"로 반려한 고른 후보)다. `rejections`와 `backToChoice`의 후보는 고른 후보(축 대응과 부모가 붙은 것)다. 실행기는 저장소 포트의 `cases`(`CaseStore`)로 기록하고 꺼낸다.
- **예시 주입**: 정보 입력을 검사한 뒤 상품마다 한 번, 같은 상품 종류의 사례 중 정보 입력(상품 종류·상품명·메모를 이은 문장, `caseQuery`)의 임베딩 유사도(코사인)가 높은 3개를 꺼내 후보 제시·명세 작성·AI 판정 입력의 `examples`(`CaseRecord` 목록, `id` 없음)로 넣는다. 사례가 없으면 빈 목록이다.
- **색인**: 임베딩 색인은 LanceDB(`cases.lance`)이고 사례 기록이 원본이다. 검색할 때마다 색인을 기록에 맞춰, 기록에서 빠진 사례와 운영자가 정보 입력을 고친 사례는 지우고 색인에 없는 사례만 임베딩한다. 임베딩 모델을 바꿔 벡터 길이가 달라지면 색인을 기록 전체로 다시 만든다. 임베딩은 LiteLLM 임베딩 API(`liteLlmEmbed`)로 부른다. 기록에 JSON으로 읽을 수 없는 줄이 있으면 그 줄 번호를 알리며 실패한다.
- **사례 빼기**: `node scripts/cases.ts remove <id>`(목록은 `list`)나 `cases.jsonl`에서 그 줄을 지우면 다음 상품부터 예시에 나오지 않는다.
- 기본 폴더는 저장소 루트의 `data/cases/`이고(`CASES_DIR`로 바꾼다), `.gitignore`의 `data/`라 공개 저장소에 올라가지 않는다.

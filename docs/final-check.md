# 최종 확인 실행

개발이 끝난 뒤 처음 보는 상품 약 10개를 실제 파이프라인으로 돌려 범용성을 판정한다(`GLOSSARY.md`의 최종 확인, 사용자 스토리 83~85). 도구는 `configurator/scripts/final-check.ts`다.

## 준비

1. Docker 구성(`docs/docker.md`)을 띄운다. 도구는 업로드 서버(`SERVER_URL`, 기본 `http://localhost:8000`)와 LiteLLM(`LITELLM_URL`, 기본 `http://localhost:4000`)을 쓴다.
2. 도구는 git으로 고정 코어·변형 엔진을 확인하므로 Docker 밖, 저장소의 `configurator` 폴더에서 돌린다.
3. 상품마다 Fusion에서 애드인으로 업로드하고, 최종 승인까지 Fusion과 애드인을 켜 둔다(ADR-0013). 업로드 id는 애드인이 보여 준다.
4. 확인 폴더(예: `data/final-check/`, 저장소에 올라가지 않음)에 상품 목록 `products.json`과 치수 규칙 파일을 둔다.

```json
{
  "rules": "rules.json",
  "products": [
    { "id": "p1", "upload": "<업로드 id>", "intake": { "name": "3단 책장", "kind": "책장", "memo": "폭 600~1200", "thickness": "ai" } }
  ]
}
```

## 실행

```
node scripts/final-check.ts start <확인 폴더>
node scripts/final-check.ts run <확인 폴더> <상품 id>
node scripts/final-check.ts report <확인 폴더>
```

- `start`: 개발이 끝난 커밋과 고정 코어·변형 엔진(`configurator/src`)의 git 트리를 `check.json`에 남긴다. `configurator/src`에 커밋하지 않은 변경이 있으면 시작하지 않는다.
- `run`: 상품 하나를 돌린다. 운영자는 찍힌 주소(`HUMAN_PORT`, 기본 8100)를 브라우저로 열어 후보 선택과 최종 승인을 한다. 결정할 일이 없는 동안은 진행 중 화면이 몇 초마다 다시 읽힌다. 처리 기록·렌더링·결과물은 `<확인 폴더>/<상품 id>/`에, 판정은 `results.json`에 쌓인다.
  - 돌리기 전에 멈추는 경우: 고정 코어·변형 엔진이 시작 때와 다르다. 이미 돌린 상품이다. 업로드 묶음이 개발 중 녹화본(`fixtures/` 아래 합성·실물 녹화본)과 모델 지문이 같다.
  - 모델 지문은 파라미터 이름(개수형 여부 포함)과 부품 이름이다. 값과 수식은 넣지 않아, 개발 중 모델의 기본값만 바꿔 다시 올린 상품도 겹침으로 잡는다.
  - LiteLLM·서버 오류처럼 파이프라인 밖에서 끊기면 판정에 넣지 않고 `interrupted.json`에 남긴다. 원인을 고치고 다시 돌릴 수 있다. 끊긴 실행은 `report.md`에 보이므로, 다시 돌린 상품을 운영자가 알아볼 수 있다.
- `report`: 상품마다 결과·사람 개입·실패의 까닭·처음 보는 상품 근거를 `report.md`로 쓰고 판정을 찍는다.

## 판정

- 상품 통과: 제출까지 갔고, 사람이 후보 선택과 최종 승인만 했다. 최종 승인에서 슬라이더 이름 고치기는 허용한다.
- 사람 개입으로 세는 것: 최종 승인에서 범위 고치기, 반려(다른 후보 고르기, 거절 이유로 후보 다시 받기), 같은 후보로 검증을 통과하지 못해 후보를 다시 고르기. 같은 후보 안에서 검증 피드백으로 명세를 고친 것은 자동 진행이라 세지 않는다.
- 최종 확인 통과: 상품 목록 전부를 돌렸고, 80% 이상(10개 중 8개)이 통과했다. 고정 코어·변형 엔진이 시작 때와 다른 기록이나 개발 중 녹화본과 겹치는 기록이 있으면 무효다.

## 실패의 까닭

통과하지 못한 상품은 사람 개입 바로 앞 검증의 피드백으로 나눈다.

- 엔진 한계: 명세를 고쳐도 없어지지 않는 피드백(`shape_error`, `dimension_error`, `topology_change`, `topology_group_limit`, `grid_limit`)이 있었다. 업로드 묶음을 읽지 못했거나 애드인이 추가 샘플을 주지 못해 멈춘 것도 여기다. 범용화 단계의 근거로 넘긴다.
- 명세 문제: 그 밖의 것이다. 축 반응·범위·두께 선택·AI 판정 피드백, 사람이 범위를 고치거나 반려한 것, AI 응답이 끝내 형식 검사를 통과하지 못한 것.

`report.md`의 까닭 칸에 근거(개입과 피드백 종류·슬라이더·부품)가 함께 있으니, 나눈 결과가 맞는지 운영자가 읽어 본다.

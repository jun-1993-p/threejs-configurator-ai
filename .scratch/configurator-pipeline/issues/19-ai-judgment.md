# 19: AI 판정

**What to build:** 수치 검증과 축 반응을 통과한 구성기를, 슬라이더 끝값과 쌍별 모서리 조합에서 렌더링해 VLM이 뚫림·겹침·비례 깨짐을 판정한다. 실패는 `ai_judgment` 피드백으로 명세 작성에 돌아가고, 판정만 3번 실패하면 이유를 붙여 최종 승인으로 넘어간다.

**Blocked by:** 06 (축 반응 검증), 15 (LiteLLM 포트와 실제 명세 작성)

**Status:** ready-for-agent

- [x] 검증기가 슬라이더 끝값과 쌍별 모서리 조합의 렌더링 이미지를 만든다
- [x] AI 판정이 수치 검증·축 반응을 통과한 뒤에만 돈다
- [x] 판정 결과가 JSON Schema 형식이고, 실패는 이미지 경로와 이유 한 줄을 담은 `ai_judgment` 피드백이 된다
- [x] 수치·축 반응은 통과했는데 판정만 3번 실패하면, 판정 이유를 붙인 채 최종 승인으로 넘어간다
- [x] 최종 승인 화면에 넘어온 판정 이유가 표시된다

## Comments

### 2026-11-02 구현

- **렌더링**: `pipeline/verify-judgment.ts`의 `judgmentShots`가 결과물의 `sweeps.json`으로 변형 엔진 형상을 그린다. 슬라이더마다 `min`·`max`, 그다음 쌍마다 모서리 조합 4곳이고 나머지는 기본값이다. 모두 같은 축척이고, 후보 카드 미리보기와 같은 비켜 본 시점(`obliqueView`)이며 부품마다 색이 다르다. 렌더링 이름은 옮긴 슬라이더의 자리 표기(`body_w=800`, `body_w=400·body_h=1000`)다.
- **순서**: `writeVerifiedSpec`에서 두께 고정 실측·수치 검증·축 반응·교차 검증(격자 보강 포함)이 모두 피드백 없이 끝난 시도만 판정한다.
- **AI 모델 포트**: `judge({ intake, spec, renders, colors, rejected, schemaErrors })`, 응답은 `{ problems: [{ image, reason }] }`이다(`judgmentSchema`). 보내지 않은 렌더링 이름이나 두 줄짜리 이유는 형식 오류로 다시 묻는다. LiteLLM 구현은 VLM 모델(`judgment`)에 그림을 조각으로 붙인다. `run-pipeline.ts`는 `LITELLM_VLM_MODEL`을 부품 탐색과 같이 쓴다.
- **피드백**: 문제가 있는 렌더링을 저장소 포트의 새 `saveRender`로 저장하고(메모리 저장소 `renders/<상품명>/<이름>.png`), `measured: { image, values, reason }`인 `ai_judgment` 피드백을 낸다. `path`는 끝값의 슬라이더나 쌍의 앞 슬라이더다.
- **3번 실패**: 같은 후보 안에서 판정까지 가서 실패한 시도를 세고, 3번째에 그 명세·결과물과 마지막 판정 피드백을 `finalApproval`의 `judgment`로 넘긴다. 최종 승인 화면(`finalApprovalHtml`)에 이유와 렌더링이 보인다. `run-pipeline.ts`가 `approval.html`과 렌더링 PNG를 출력 폴더에 쓴다.
- 시험: `pipeline.test.ts` 7개(렌더링 목록과 같은 축척, 수치 검증 통과 뒤에만 판정, 판정 실패 피드백과 저장, 형식 재질문, 3번 실패 시 최종 승인, 판정 실패만 세기, 같은 렌더링 합치기), `operator-screens.test.ts` 2개, `litellm-ai.test.ts` 1개.

### 리뷰 뒤 반영과 남긴 것

- 반영:
  - 비켜 본 시점과 부품 색 목록을 `candidate-cards.ts`의 `obliqueView`·`partColorsOf`로 모아 후보 카드와 같이 쓴다.
  - `measured` 모양을 `JudgmentMeasured`로 내보내 피드백을 만드는 쪽과 화면이 같이 쓴다.
  - 렌더링마다 가리킬 슬라이더를 `slider` 필드로 둔다(객체 키 순서에 기대지 않음).
  - 화면 문구와 주석의 "3번"을 `JUDGMENT_FAILURES`로 바꿨다.
  - 같은 렌더링을 여러 번 짚으면 이유를 `; `로 이어 피드백 하나, 저장 한 번으로 둔다.
  - 용어집의 AI 판정 정의에 교차 검증을 넣었다. `operator-screens.ts` import 순서를 맞췄다.
- 남긴 것:
  - **`spec.front as Front` 형 변환**: 고정 코어의 `Spec.front`가 `string`이라서다. 정면 목록을 `src/`로 옮기는 일은 이 티켓 범위를 넘는다. 명세 검사를 통과한 값이라 주석만 달았다.
  - **최종 승인 화면에 마지막 판정 이유만 보인다**: 넘어간 명세가 마지막 명세라, 앞선 두 판정은 다른 명세에 대한 것이다. 앞선 이유는 처리 기록의 검증 항목에 남는다.
  - **판정 실패를 연속이 아니라 누적으로 센다**: 사이에 수치 검증 실패가 끼면 "수치는 통과"가 아닌 시도가 끼었을 뿐, 판정 실패가 3번 쌓였다는 사실은 그대로라 VLM 오판으로 막히지 않게 하려는 스토리 67의 뜻에 맞다. `docs/spec-schema.md` 재시도 절에 적었다.
  - **형식 재질문 기록과 멈춤 단계가 `verification`이다**: 단계 순서는 ADR-0014의 10단계이고 AI 판정은 검증 안의 일이다. `judgment`는 AI 모델 포트의 메서드(와 LiteLLM 모델) 이름일 뿐이다. 문서에 적었다.
  - **렌더링 수가 2n + 4·C(n,2)장이다**: 티켓이 요구한 조합 그대로다. 슬라이더 4개면 32장이라 VLM의 그림 수 제한에 걸릴 수 있다. 실제 모델로 돌려 보는 최종 확인에서 걸리면 나눠 묻는다. 미룸(티켓 23).
  - **최종 승인 화면의 슬라이더 목록과 승인 단추**: 판정 이유를 보일 화면이 필요해 최소한만 만들었다. 이름 고치기·범위 좁히기·반려는 티켓 20이다.
  - **`saveRender` 추가**: 피드백에 이미지 경로를 담으려면 그림을 둘 곳이 필요하다.

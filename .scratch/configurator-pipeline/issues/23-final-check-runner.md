## Comments

### 2026-11-03 구현

- 판정(`configurator/pipeline/final-check.ts`):
  - `judgeRun(처리 기록, 실행 결과)`는 처리 기록의 사람 결정만 읽어 사람 개입을 찾는다. 사람 결정 포트를 감쌀 필요가 없다.
  - 사람 개입으로 세는 것: 최종 승인에서 범위 고치기, 반려 두 경로, 같은 후보로 검증을 통과하지 못해 후보 제시로 돌아가 다시 고르기. 이름만 고친 승인과 같은 후보 안의 명세 재작성은 세지 않는다.
  - 실패 분류: 개입 바로 앞 검증의 피드백에 `ENGINE_LIMIT_KINDS`(형상·치수 오차, 위상 변화, 위상 묶음·격자 보강 상한)가 있으면 엔진 한계다. 업로드나 검증 단계에서 멈췄고 AI 형식 실패(`AI_FORMAT_FAILURE`, AI 판정은 검증 단계 안에서 묻는다)가 아니면 엔진 한계다. 나머지는 명세 문제다. 근거 문장(개입, 피드백 종류·슬라이더·부품, 멈춘 까닭)을 함께 남긴다.
  - `finalVerdict`: 상품 목록 전부를 돌렸고 80% 이상이 통과하면 통과다. 고정 코어·변형 엔진 트리가 시작 때와 다르거나 개발 중 녹화본과 겹치는 기록이 있으면 무효다. 값 목록 `FAILURE_CLASSES`·`VERDICT_STATUSES`는 `schemas.ts`에 있다.
  - 처음 보는 상품: `unseenEvidence`가 모델 지문(파라미터 이름·개수형 여부, 부품 이름)을 `fixtures/` 아래의 업로드 묶음과 견준다. 값·수식을 빼서 기본값만 바꿔 다시 올린 개발 모델도 잡는다.
- 실제 파이프라인에 필요한 포트 두 개: 티켓 08·16·22가 "실행기를 띄울 때" 붙이기로 미뤘다가 남아 있던 것이다.
  - `pipeline/http-fusion.ts`: 서버의 추가 샘플 요청 API에 요청을 걸고 상태를 본다. 끊기면 `disconnected`를 돌려준다. 다시 연결되면 같은 요청을 기다리고 새로 걸지 않는다.
  - `pipeline/browser-human.ts`: 기존 운영자 화면(후보 카드, 최종 승인)을 작은 HTTP 서버로 띄우고 보낸 양식을 읽는다. 막힌 양식은 까닭을 화면에 보이고 다시 기다린다. 결정이 없는 동안은 진행 중 화면(`progressHtml`)이 3초마다 다시 읽힌다. 후보 카드 화면에 오류 목록 인자를 더했다.
- 도구(`configurator/scripts/final-check.ts`, 안내 `docs/final-check.md`): `start`(개발이 끝난 커밋과 `configurator/src` 트리를 기록, 커밋하지 않은 변경이 있으면 거부), `run`(상품 하나), `report`(`report.md`). 이미 돌린 상품, 바뀐 고정 코어·변형 엔진, 개발 중 녹화본과 겹치는 상품은 돌리지 않는다. 파이프라인 밖 오류로 끊긴 실행은 판정에 넣지 않고 `interrupted.json`에 남겨 보고서에 보인다. git이 필요해 Docker 밖에서 돈다.
- `scripts/run-pipeline.ts`의 `runWithLiteLlm`이 사람 결정·Fusion 연결·저장소를 바꿔 끼우게 했고 처리 기록을 돌려준다. 저장소 만들기는 `liteLlmStore`로 나눴다.
- 시험: `final-check.test.ts` 12개, `http-fusion.test.ts` 4개, `browser-human.test.ts` 4개.
- 회고 뒤 더한 시험: `final-check-cli.test.ts` 4개. 임시 git 저장소, 가짜 업로드 서버·LiteLLM, 양식을 보내는 손으로 도구를 돌린다. 통과 기록과 다시 돌리기 거부, 개발 중 녹화본 거부, 바뀐 고정 코어·커밋하지 않은 변경 거부, 끊긴 실행 기록을 본다. 이를 위해 도구의 거부는 `CheckRefused` 예외로 던지고(명령줄에서는 찍고 1로 끝냄), 저장소 루트·서버 주소·운영자 화면 주소를 `CheckEnv`로 받는다. `run-pipeline.ts`는 LiteLLM 환경 변수를 부를 때 읽는다.
- 수동 확인: 임시 데이터 폴더로 띄운 업로드 서버, 가짜 LiteLLM, 양식을 보내는 스크립트로 합성 서랍장(슬라이더로 쓰지 않는 파라미터 하나를 더해 지문을 바꿈)을 돌렸다. `start → run`이 통과로 기록됐고, 다시 `run`은 거부됐고, `report`가 표를 썼다. 지문을 바꾸지 않은 합성 서랍장은 `fixtures/synthetic/drawer.json`·`drawer-shell-point.json`과 겹쳐 거부됐다.

### 리뷰 뒤 반영과 남긴 것

- 반영:
  - 검증 단계의 AI 형식 실패 시험을 더했다. 앞 시험은 spec 단계에서 멈춰 예외 규칙을 지나지 않았다.
  - 판정 상태를 `schemas.ts` 값 목록으로 옮겼다.
  - 이름을 바꿨다(`lastFeedback`, `engineLimit`).
  - `Recording` 타입을 더했고, 시험이 `RequestStatus`를 가져다 쓰게 했다.
  - 분류 이름은 한 곳에서 꺼내 쓴다.
  - 확인 폴더 파일 경로를 한곳에 모았다.
  - 렌더링을 바깥 변수로 넘기던 콜백을 없앴다. 저장소를 먼저 만들어 넘긴다.
  - 모델 지문에서 값·수식을 뺐다.
  - 끊긴 실행을 기록한다.
  - 후보를 다시 고른 것을 개입으로 세는 결정을 GLOSSARY에 적었다.
- 남긴 것:
  - 멈춘 까닭을 문장 앞부분(`AI_FORMAT_FAILURE`)으로 가린다. 문장은 실행기의 상수 하나에서 나오고 판정이 같은 상수를 쓰므로 어긋나지 않는다. `PipelineResult`에 종류 필드를 더하는 것은 계약 변경이라 이 판정 하나를 위해 하지 않는다.
  - 업로드 묶음·애드인 응답 형식 오류를 엔진 한계로 센다. 애드인도 상품마다 고치지 않는 고정된 코드라 범용화 근거에 들어간다(GLOSSARY에 적음). 보고서의 근거 문장으로 구분된다.
  - 최종 승인 반려는 앞 검증이 통과였으므로 대개 명세 문제로 떨어진다. 의도한 동작이다.

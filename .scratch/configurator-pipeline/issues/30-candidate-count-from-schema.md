# 30: 후보 제시 지시문의 후보 수를 스키마에서 가져오기

**What to build:** 후보 제시 지시문(`configurator/pipeline/litellm-ai.ts`의 `CANDIDATES_PROMPT`)은 후보 수를 "1~4개"로 직접 적는다. 같은 수가 `CANDIDATES_SCHEMA`의 `minItems`·`maxItems`에도 있어, 티켓 28에서 스키마만 고치고 지시문의 "2~4개"가 남아 바로 다음 줄과 부딪쳤다(티켓 28 리뷰, 티켓 28·29 회고 3번). 지시문이 스키마 값을 가져다 쓰면 둘은 어긋날 수 없다.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] 후보 제시 지시문의 후보 수(최소·최대)는 `CANDIDATES_SCHEMA`의 `minItems`·`maxItems`에서 만든다
- [x] 후보 제시 요청의 지시문이 스키마의 후보 수를 알리는지 시험한다

## Comments

### 2026-11-04 구현

- `CANDIDATES_PROMPT`의 후보 수 두 곳("답은 후보 객체 N~M개", "보통 2~M개")을 `CANDIDATES_SCHEMA.minItems`·`maxItems`에서 만든다. "보통 2"는 서로 다른 후보를 낼 수 있을 때의 하한이라 스키마 값이 아니다.
- 시험: `litellm-ai.test.ts`에 1개. 지시문에 적힌 개수 범위가 스키마 범위와 `2~최대`뿐인지 본다. 스키마의 `maxItems`를 잠시 3으로 바꾸면 옛 지시문에서는 실패하고, 고친 지시문에서는 통과하는 것을 확인했다.

### 리뷰 뒤 반영

- 부품 탐색 지시문의 "확신하지 못하면 2~4개"도 `PARTS_SCHEMA`의 fronts `maxItems`와 따로 적혀 있어 같은 식으로 어긋날 수 있었다. 스키마 값을 쓰게 하고 시험에 넣었다.
- 시험에 따로 적힌 하한 "2"를 없앴다. 이제 시험은 두 지시문에 적힌 "N~M개"가 모두 스키마의 최대값에서 끝나고 최소값보다 작지 않은지 본다. 후보 제시는 첫 범위가 스키마 범위 그대로인지도 본다. 부품 탐색 fronts의 `maxItems`를 잠시 3으로 바꾸면 옛 지시문에서는 실패하고, 고친 지시문에서는 통과하는 것을 확인했다.
- `schemas.ts`의 후보 제시 응답 주석에서 "2~4개"를 빼고, 개수 범위는 `minItems`·`maxItems`가 정한다고 적었다.
- 남긴 것: 시험은 "N~M개" 꼴만 본다. "최대 4개"처럼 다른 꼴로 숫자를 적으면 놓친다. 이번에 어긋났던 꼴을 막는 것이 목적이고, 지시문을 고치는 사람이 같은 꼴로 쓰면 시험이 잡는다.
- 남긴 것: "후보 하나만 낸다"는 `minItems`가 1이라는 데 기댄다. 최소값을 바꾸면 후보 하나 허용(티켓 28) 자체가 바뀌는 일이라, 그때 이 문장도 같이 고친다.

# 12: 두께 선택

**What to build:** 명세에 두께 선택을 쓸 수 있고, 고객은 구성기의 두께 슬롯에서 표준 두께 목록의 앞뒤 한 칸 중 하나를 고른다(ADR-0010). 두께 후보 형상은 추가 샘플 요청으로 받고, 변형 엔진은 후보를 사이 값 없이 바꿔 끼운 뒤 다른 슬라이더와 덧셈으로 섞는다.

**Blocked by:** 08 (추가 샘플 요청과 교차 검증)

**Status:** ready-for-agent

- [x] 고정 코어에 표준 두께 목록(3·6·9·12·15·18·24·30 mm)이 있다
- [x] 명세의 `thickness[].options`가 기본 두께의 앞뒤 한 칸이 아니면 명세 검사가 실패한다(목록 끝은 후보 2개)
- [x] `thickness[].ids`로 묶인 파라미터의 기본 두께가 다르면 실패한다
- [x] `fixed`의 파라미터가 어떤 슬라이더의 `children`에 있으면 실패한다
- [x] 서버가 두께 후보 형상을 애드인에 요청해 받는다
- [x] 고정 코어가 명세의 두께 선택마다 슬롯을 만들고, 고르면 형상이 그 두께로 바뀐다

## Comments

### 2026-10-29 구현

- 고정 코어(`src/engine.ts`): `STANDARD_THICKNESSES`와 `thicknessOptions(기본 두께)`(앞뒤 한 칸과 기본 두께, 목록 끝은 2개, 목록 밖이면 빈 목록). 구성기와 검증기가 같이 쓰는 파일이라 명세 검사도 이 목록을 쓴다.
- 명세 검사(`pipeline/schemas.ts`, 형식 검사와 함께 `schemaErrors`로 다시 묻는다):
  - `thicknessChoiceChecker`: `options`가 앞뒤 한 칸이 아님, `default`가 목록 밖, `ids`가 업로드 묶음에 없음, 묶인 파라미터의 기본 두께가 다름, `default`가 업로드한 모델 값과 다름.
  - `fixedThicknessChecker`: `fixed`나 `thickness[].ids`의 파라미터가 슬라이더 `children`에 있음, 한 파라미터가 고정 두께와 두께 선택(또는 두 두께 선택)에 함께 있음.
  - 모델 값은 Fusion이 cm에서 바꾼 부동소수라 1e-6 mm 안이면 같다고 본다. 업로드 묶음 타입에 `parameters[].value`를 더했다(스키마에는 이미 있었다).
- 두께 후보 형상 요청: `thicknessSamplePlan(spec, data)`가 기본 형상과 슬라이더 범위가 닿는 위상 묶음의 기준 값(`anchor`)마다, 두께 선택마다, 기본 두께가 아닌 후보마다 값 묶음 하나를 정한다(`{t: 24}`, `{t: 24, shelf_w: 675}`). 실행기는 조립 전에 `kind` `thickness`로 요청하고(같은 요청은 다시 보내지 않는다), 받은 형상을 `sweeps.json`의 `thickness`에 담는다. 서버·애드인은 티켓 08에서 이미 `thickness` 종류를 받으므로 코드 변경 없이 시험만 더했다.
- 받은 형상이 재계산 실패이거나 그 묶음 기준 형상과 면 구성이 다르면 `recompute_failed`·`topology_change` 피드백(`path` `thickness[i].options`)으로 돌려준다. 격자 보강과 같은 판정(`unusableSample`)을 쓴다.
- 변형 엔진: 위상 묶음마다 두께 후보 이동량(그 묶음 기준 형상에서)을 두고, 고른 후보를 사이 값 없이 더한다. 후보가 아닌 값은 오류다. 두께 선택 값은 묶인 파라미터 중 아무 이름으로 준다.
- 구성기(`src/core.ts`): 두께 선택마다 `<select>` 슬롯(`판재 두께`, `15 mm`…). `set(id, mm)`은 묶인 파라미터 중 아무 이름이면 두께 선택으로 처리하고 묶인 파라미터를 모두 바꾼다.
- 합성 녹화본: `shelf.thickness.json`(t=15·24 × 기본·2칸·4칸 묶음 기준 값), `shelf.thickness-checks.json`(t와 전체 폭·깊이를 함께 바꾼 4곳, 덧셈을 재는 정답). `python -m synthetic.make_cross_checks solidcraft-test/shelf.sc --recording fixtures/synthetic/shelf.json --sample t=15 ...`로 만들었다.
- 시험: 엔진 `test/engine-thickness.test.ts`(후보 목록, 후보 형상 일치, 위상 묶음 안 일치, 덧셈이 Fusion과 형상 오차 합격선 안, 보간하지 않음, 형상이 없으면 오류, 아무 이름으로 줌), 경계 1 `pipeline.test.ts`(명세 검사 7개, 요청과 결과물, 재계산 실패·위상 변화 피드백), 서버·애드인 Python 시험 각 1개.
- Chrome에서 결과물을 열어 슬롯에 15·18·24 mm가 뜨고, 24t와 15t에서 판이 두꺼워지고 얇아지며, 24t를 고른 채 전체 폭을 600(2칸 묶음)으로 옮겨도 두께가 유지되고 콘솔 오류가 없음을 확인했다.

### 설계 판단

- 두께 후보 형상을 위상 묶음마다 받는다: 기본 묶음에서만 받으면 고객이 두께를 고른 뒤 폭을 위상 경계 너머로 옮기는 순간 두께가 기본으로 돌아간다(격자 보강은 기본 묶음에서만 쓰는 것과 다르다).
- 요청 값 묶음과 엔진이 찾는 값 묶음을 `thicknessSamplePlan` 하나로 정해 어긋나지 않게 했다. 그래서 파이프라인이 쓰는 이 함수가 엔진 파일에 있다.
- 두께와 슬라이더를 함께 바꾼 교차 검증, 두께 고정 실측, 두 두께 선택을 함께 바꾼 조합은 티켓 13의 몫이다(코드와 `spec-schema.md`에 적었다).

### 리뷰 반영

- 격자 보강과 두께 후보 형상의 "넣을 수 없는 샘플" 판정이 겹치던 것을 `unusableSample` 하나로 모았다. 격자 위상 변화 힌트는 "기본 형상" 대신 "기준 형상"이 된다.
- 값 묶음 표기를 `placeOf`로 모았다.
- 두께 검사가 받은 값 묶음에서 위상 묶음을 거꾸로 찾던 것(`!` 사슬, 두께 아닌 값이 하나라는 가정)을 없애고, 계획(`ThicknessSample`: 두께 선택 번호·후보·`GroupAnchor`·기준 형상·값 묶음)을 그대로 받는다.
- 두께 선택 검사와 두께 고정 검사를 `thicknessChoiceChecker`·`fixedThicknessChecker`로 나눴다. 이름을 `dotted`·`uploadedIds`·`modelValue`·`board`로 바꿨다.
- 두께 선택의 파라미터가 슬라이더 자식이거나 고정 두께·다른 두께 선택에도 있는 명세를 거른다(시험 추가).
- 엔진이 `ids[0]`만 읽던 것을 묶인 파라미터 중 아무 이름이나 읽게 했다(시험 추가).
- 용어집에 기본 두께·두께 후보·두께 후보 형상을 더했다. `STANDARD_THICKNESSES` 주석에 명세 검사가 쓴다고 적었다.

### 리뷰에서 반영하지 않은 것

- 엔진도 두께 후보 형상의 누락·재계산 실패·면 구성을 다시 보고 예외를 던지는 것: 격자 보강과 같은 방식이다. 실행기는 피드백으로 먼저 거르고, 엔진의 예외는 실행기를 거치지 않고 엔진을 부르는 쪽을 위한 불변식 검사다.
- "슬라이더 범위가 닿는 위상 묶음" 거르기가 `thicknessSamplePlan`과 `assemble.ts`의 `engineSweeps` 두 곳에 있는 것: 둘 다 같은 판정 `reaches`를 부른다(티켓 11에서 모은 것). 하나는 요청할 것을, 하나는 결과물에 담을 것을 고른다.
- 명세를 다시 쓸 때마다 두께 후보 형상을 다시 요청한다는 지적: `requestSamples`가 같은 요청을 캐시하므로 다시 보내지 않는다. 코드에 메모를 남겼다.
- 구성기 슬롯의 자동 시험: 저장소에 DOM·WebGL 시험 환경이 없고 기존 `mount`도 시험하지 않는다. Chrome에서 직접 확인했다(위).

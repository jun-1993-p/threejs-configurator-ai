# 14: 범위 교집합

**What to build:** 슬라이더 범위가 치수 규칙 ∩ 정보 입력의 범위 메모 ∩ 스윕 범위 안에서 정해지고, 근거가 된 치수 규칙이 명세의 `source`에 남는다(ADR-0009). 교집합이 비면 범위를 지어내지 않고 운영자에게 알린다.

**Blocked by:** 04 (수치 검증과 검증 피드백 루프)

**Status:** ready-for-agent

- [x] 치수 규칙 저장소가 있고, 부위별 범위와 출처를 담는다
- [x] 명세의 범위가 세 범위의 교집합을 벗어나면 명세 검사가 실패한다
- [x] `source`가 치수 규칙에 없는 항목이면 실패한다
- [x] 교집합이 비면 `no_range_intersection` 피드백이 나오고 운영자에게 표시된다
- [x] 슬라이더 기본값이 업로드한 Fusion 모델의 현재 값인지 검사한다

## Comments

### 2026-10-29 구현

- 치수 규칙 저장소: 저장소 포트에 `dimensionRules(kind)`를 더했다. 규칙 하나는 `id`(명세 `source`가 가리키는 이름)·`kind`(상품 종류)·`part`(부위)·`axis`(W·D·H)·`min`·`max`·`origin`(출처)이다(`pipeline/range-intersection.ts`의 `DimensionRule`). 메모리 저장소는 넣은 규칙을 상품 종류로 걸러 준다. 실제 규칙 내용은 명세대로 준비 단계에서 따로 만든다.
- 명세 작성 AI 입력에 정보 입력의 상품 종류로 거른 규칙(`rules`)을 넣었고, `source`도 그 안에 있어야 한다.
- 정보 입력 메모는 자유 문장이라, 규칙의 부위 이름 바로 뒤의 "값~값"만 범위로 읽는다(긴 부위 이름부터; 조사·쌍점·쉼표 천 단위·mm/cm·전각 물결 허용). AI가 메모를 해석하게 하면 검사가 결정적이지 않아 규칙으로 읽는다. 메모에 그 부위 범위가 없으면 치수 규칙 ∩ 스윕 범위만 본다. 어느 부위에도 붙지 않은 "값~값"은 정보 입력 처리 기록(`memoUnread`)에 남긴다.
- 명세 검사(`rangeIntersection(...).check`, `checkProductSpec`에 붙음): `source`가 규칙에 없거나 규칙 축이 슬라이더 축과 다름, `default`가 업로드한 모델 값과 다르거나 범위 밖, `min`/`max`가 교집합 밖이면 실패. 애드인이 줄인 쪽 스윕 범위는 범위 검증(`verifyRange`)이 줄어든 까닭과 함께 알리므로 명세 검사에서는 보지 않는다.
- 교집합이 비었거나 업로드한 모델 값을 담지 않으면 명세 검사는 넘기고, 실행기가 조립 전에 `no_range_intersection`(path `sliders[i].source`)을 낸다. 처리 기록의 검증 항목에 남아 운영자에게 보이고, 명세 작성으로 돌아간다.
- 시험: `configurator/test/pipeline.test.ts`(경계 1) 9개. 기존 시험의 정보 입력 메모는 "틀린 명세"(폭 900까지)가 수치 검증까지 가도록 폭 400~900으로 바꿨다.
- 리뷰 뒤 반영: 메모 읽기를 넓히고(위), 읽지 못한 범위를 처리 기록에 남긴다. 치수 규칙에 축을 더해 다른 축 부위 규칙으로 메모 범위를 비켜 가지 못하게 했다. 교집합 없음 힌트는 "다른 치수 규칙이 맞는지 보세요" 대신 다른 부위 규칙으로 바꾸지 말고 슬라이더를 빼라고 한다. 범위 밖 오류 문구의 교집합은 실제로 검사한 것(줄어든 쪽 제외)을 보이고, 힌트의 스윕 범위에 애드인이 줄인 쪽을 적는다. 메모는 한 번만 읽고, 모델 값 찾기와 교집합 계산을 한 함수로 모았다. `escape` 이름이 전역을 가려 `escapeRegExp`로, 쓰는 곳 없는 `memoRanges` export를 뺐다.
- 리뷰에서 반영하지 않은 것:
  - 교집합 없음을 HumanPort로 따로 묻지 않고 처리 기록과 검증 피드백으로 알린다. ADR-0009가 "검증 피드백으로 사람에게 알린다"이고, 업로드 단계 범위 축소도 같은 방식(처리 기록)이다. 처리 기록을 보여 주는 화면은 이 티켓 범위 밖이다.
  - 교집합 없음도 같은 후보 재시도 3번을 쓴다. AI가 고칠 수 있는 길(그 슬라이더 빼기)이 있고, 후보 제시로 돌아가면 `failures`에 이유가 실려 다른 부모 파라미터를 고를 수 있다. 메모·모델을 고치는 일은 사람 몫이라 반려 경로(티켓 20)에서 다시 본다.
  - 교집합에 업로드한 모델 값이 없는 경우도 `no_range_intersection`으로 내고, 기본값이 범위 밖인지도 본다. 사용자 스토리 36(기본값은 모델의 현재 값)과 함께 지키면 그 교집합으로는 쓸 수 있는 범위가 없기 때문이다.
  - 줄어든 쪽 스윕 범위 때문에 교집합이 비면 범위 검증(`range_shrunk` 등)보다 `no_range_intersection`이 먼저 나간다. 이때도 범위를 정할 수 없는 것이 맞고, 힌트의 스윕 범위에 줄어든 쪽을 적어 까닭을 잃지 않게 했다.
  - 시험 `setup`의 세 번째 위치 인자(치수 규칙)는 기존 두 번째 위치 인자(Fusion 연결)와 같은 방식이다. 선택 인자 객체로 바꾸면 기존 호출 수십 곳이 바뀌어 이 티켓 범위를 넘는다.
  - `DimensionRule`의 `min`·`max`를 `Range`로 묶지 않았다. 저장소에 놓일 규칙 자료의 평평한 모양을 그대로 쓰고, `Range` 자리에 그대로 넘길 수 있다.
  - `checkProductSpec`의 검사기 나열은 기존 방식대로 하나를 더했다.
  - 공용 시험 정보 입력 메모를 폭 400~900으로 바꿨다. 범위를 900까지 넓힌 "틀린 명세" 시험들이 원래대로 수치 검증까지 가게 하려는 것이다.

# 33: 애드인이 추가 샘플에 답하는 상태를 파일로 남기기

**What to build:** 서버가 애드인을 "Fusion 연결 필요"로 볼 때 에이전트가 그 까닭을 가릴 수 없다. 티켓 26 선반 실물 확인에서 추가 샘플 요청이 끊김으로 끝났는데, 원인(업로드 완료 메시지 창이 Fusion 주 스레드를 막아 애드인이 서버를 찾지 못함)을 추측해 사람에게 물어야 했다. 애드인이 지금 답하는 상태를 파일로 남겨, 끊김이 Fusion이 꺼진 것인지, 주 스레드가 막힌 것인지, 애드인이 답할 업로드를 모르는 것인지를 파일로 가린다.

업로드 완료를 모달 창으로 알리는 동안에는 애드인이 답하지 못한다. 창을 띄우지 않고 알리는 방법(점검 파일과 짧은 알림)도 함께 정한다.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] 애드인의 일꾼 스레드가 `data/addin-checks/serving.json`에 답하는 업로드 ID(없으면 null), 마지막으로 주 스레드가 일한 시각, 마지막으로 서버를 찾은 시각, 마지막 오류를 몇 초마다 쓴다. 주 스레드가 일한 시각이 멈춰 있으면 주 스레드가 막힌 것이다
- [x] 연결 확인 위저드(`scripts/fusion-connection-wizard.sh`)가 끊김을 알릴 때 이 파일로 까닭을 함께 찍는다. 파일을 읽어 까닭을 고르는 일은 시험 있는 Python 도구(`scripts/`)가 하고 위저드는 그 출력을 보인다. 티켓 32의 도구는 이 파일을 직접 읽는다(32에 그 항목이 있다)
- [x] 업로드 완료를 모달 창 없이 알릴 수 있는지 정하고, 그 결정과 까닭을 ADR-0013에 적는다. 바꾸면 업로드 직후 추가 샘플 요청에 바로 답하는지 위저드로 확인한다 (아래 2026-11-05 결과. 업로드와 위저드 사이가 29분이라 "직후"는 재지 못했지만, 알림이 메시지 창 없이 텍스트 명령 창에만 찍혀 주 스레드를 막을 창이 없다)
- [x] 상태를 쓰는 판단(무엇을 언제 쓰는지)은 Fusion 없이 시험할 수 있는 모듈에 두고 시험한다

## Comments

- 2026-11-05: 티켓 26 선반 회고 4번에서 만들었다.
- 2026-11-05: 구현. 상태를 모으고 쓰는 판단은 `uploader/serving_status.py`(`ServingStatus`, 서버 호출마다 찾은 시각·오류를 남기는 `ObservedServer`, 임시 파일로 바꿔 넣는 `write_record`), 까닭을 고르는 도구는 `scripts/serving_status.py`. 기록에는 열린 문서의 업로드 ID, 주 스레드가 추가 샘플 일을 하는 중(`busy`, 샘플 뽑기·이어받기는 막힌 것이 아니다), 업로드 명령이 도는 중(`paused`)도 넣었다. 업로드 완료는 메시지 창 대신 텍스트 명령 창에 알린다(ADR-0013). 건식 업로드 완료 창과 확인·실패 창은 그대로 둔다(그동안은 원래 답하지 않는다). 녹화 위저드의 업로드 단계 문구도 바꿨다.
  - 리뷰 반영: 연결 확인 위저드가 상태 파일을 마지막 업로드로 고르던 결함(같은 폴더라 늘 가장 새 파일이다)을 고쳤다. 마지막 업로드 고르기는 `scripts/addin_checks.py latest`로 모으고, 녹화 위저드도 서버가 다른 폴더에 저장할 때 사람에게 ID를 묻지 않고 그것으로 찾는다. 까닭이 틀리던 경우(디자인이 아닌 문서가 열림, 실행·업로드 직후의 빈 시각, 이어받기 재시도 대기, 업로드 없이 서버가 꺼짐, 끝나지 않는 바쁜 표시)를 기록의 `started_at`·`resume_retry_at`과 읽는 순서로 고쳤다. 업로드 명령 중에는 문서 속성을 읽지 않는다.
  - 리뷰에서 남긴 지적 둘:
    - `ConfiguratorUploader.py`의 부르는 순서(주 스레드가 일한 시각 → 바쁨·업로드 명령 확인 → 문서 확인)는 시험하지 않는다. Fusion 객체(활성 디자인, 문서 속성)와 맞물려 있고 그 파일은 시험·mypy 밖이다. 부르는 쪽은 메서드 한 번씩이라 얇고, 그 결과로 나오는 기록마다의 까닭은 `scripts/tests/test_serving_reason.py`가 덮는다. 실물 확인에서 까닭이 틀리면 그때 순서를 모듈로 옮긴다.
    - `ObservedServer`는 메서드마다 감싸기만 한다(Middle Man). 서버 호출을 지켜보는 것이 목적이라 그대로 둔다.
- 2026-11-05: 연결 확인 위저드 결과(커밋 13dd937). 연결된 채로 5초 뒤 답함, Fusion을 끈 뒤 Fusion 연결 필요와 까닭 "46초째 상태를 쓰지 않는다: Fusion이 꺼졌거나 애드인이 멈췄다", 다시 켠 뒤 6초 뒤 답함. 상태 파일은 3초마다 새로 쓰이고 까닭 도구는 답하는 중을 낸다. 알림 실패 기록 없음. 업로드(13:00)와 위저드(13:29) 사이가 길어 업로드 직후 바로 답하는지는 이 결과로 보지 못했다. 사람 확인: 업로드 때 메시지 창 없이 텍스트 명령 창에만 "업로드했습니다"가 찍혔다.

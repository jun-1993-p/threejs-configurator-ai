# 08: 추가 샘플 요청과 교차 검증

**What to build:** 검증 중에 서버가 애드인에 교차 검증 샘플(슬라이더 쌍의 모서리 조합)을 요청하고, 애드인은 업로드부터 최종 승인까지 연결된 채로 응답한다(ADR-0013). 덧셈이 합격선을 넘는 쌍은 검증 피드백으로 돌아간다. 연결이 끊기면 실패로 기록하지 않고 "Fusion 연결 필요" 상태로 기다린다.

**Blocked by:** 04 (수치 검증과 검증 피드백 루프), 07 (여러 슬라이더 덧셈)

**Status:** ready-for-agent

- [x] 서버가 파라미터 값 묶음으로 추가 샘플을 요청하고, 애드인이 업로드 묶음의 샘플과 같은 형식으로 답한다
- [x] 슬라이더 쌍마다 모서리 조합 교차 검증 샘플을 받아 덧셈 결과와 비교한다
- [x] 덧셈 오차가 합격선을 넘으면 해당 쌍을 가리키는 검증 피드백이 나온다
- [x] 애드인 연결이 끊기면 검증이 멈추고 "Fusion 연결 필요"가 표시되며, 다시 연결되면 이어서 진행한다
- [x] Fusion 연결 포트를 녹화 응답으로 바꿔 끼운 경계 1 테스트가 있다

## Comments

### 2026-10-29 구현

- 요청과 응답: 요청은 `{ kind, values }`(`values`는 파라미터 이름과 값을 짝지은 값 묶음 목록)이고, 응답은 `{ samples }`로 값 묶음마다 교차 검증 샘플 하나씩 같은 순서다. 응답 형식은 업로드 묶음 스키마의 `$defs/sampleResponse`·`$defs/crossSample`(단독 스윕 샘플과 같고 `value` 대신 `values`)이며, 서버와 파이프라인이 같이 검사한다.
- 애드인(`uploader/core.py`): `serve_sample_request(model, server, upload_id)`가 기다리는 요청 하나를 가져가 `cross_check_sample`로 답한다. 샘플을 뽑지 못하면(모델에 없는 파라미터, Fusion API 오류) 실패 이유를 알린다. `cross_check_sample`은 예외가 나도 바꾼 파라미터의 수식을 되돌린다(`try/finally`). Fusion 진입점은 업로드 뒤 일꾼 스레드가 3초마다 사용자 이벤트를 쏘고 주 스레드가 요청에 답하며, 샘플을 뽑는 동안에는 연결 신호를 보낸다.
- 서버(`server/app.py`): 업로드마다 요청 목록을 메모리에 둔다. 파이프라인 쪽 `POST /uploads/{id}/sample-requests`, `GET .../{요청}`(`status` pending·answered·failed, `fusion` connected·disconnected). 애드인 쪽 `GET .../next`(답하지 않은 가장 오래된 요청, 없으면 204), `POST .../{요청}/response`, `POST .../{요청}/failure`, `POST /uploads/{id}/fusion`(연결 신호). 애드인 소식이 15초 넘게 없으면 끊긴 것으로 본다. 가져가고 답하지 못한 요청은 다시 붙으면 또 내준다.
- 교차 검증기(`pipeline/verify-cross.ts`): 슬라이더 쌍마다 범위 모서리 4곳(나머지 슬라이더는 `default`)을 요청하고, 수치 검증과 같은 측정(형상 오차, W·D·H·판 두께 치수 오차, 재계산 실패, 위상 변화)으로 비교한다. 측정은 `verify-numeric.ts`의 `shapeComparer`로 나눠 함께 쓴다. 피드백은 `path` `sliders[i]`(쌍의 앞 슬라이더), `measured.values`에 쌍의 두 값, 힌트는 자식으로 두거나 범위를 좁히라고 한다(`docs/spec-schema.md`).
- 실행기: 수치 검증 → 축 반응 → 교차 검증 순서다. Fusion 연결 포트가 `disconnected`를 주면 처리 기록에 `{ fusion: "Fusion 연결 필요" }`를 남기고 `reconnected()`를 기다린 뒤 `{ fusion: "다시 연결됨" }`을 남기고 다시 요청한다. 재시도 횟수에 세지 않는다. `failed`나 형식 오류는 검증 단계에서 멈춘다.
- 합성 녹화본: `drawer.cross-corners.json`(전체 폭 400·800 × 전체 높이 500·1000, 덧셈이 맞는 쌍), `drawer.cross-depth.json`(전체 깊이 300·600 × 서랍 깊이 300·600). 서랍 깊이가 `body_d - 20 mm` 수식이라 덧셈이 서랍 깊이를 두 번 더하며, 경계 1 시험이 이 실제 형상으로 교차 검증 피드백을 확인한다. 만든 명령은 `python -m synthetic.make_cross_checks solidcraft-test/drawer.sc --sample ...`.
- 시험: 경계 1(`test/pipeline.test.ts`)에 녹화 응답 포트로 덧셈 통과, 몸통을 3 mm 올린 모서리로 쌍 피드백, 전체 깊이·서랍 깊이의 실제 실패, 연결 끊김 대기와 재개, 애드인 실패와 형식 오류에서 멈춤. 축 반응 시험 두 개는 깊이 쌍 명세가 이제 교차 검증에 걸리므로 각본에 세 번째 명세(전체 폭 하나)를 더했다. 애드인 핵심과 서버 중계는 Python 시험.
- 리뷰에서 반영하지 않은 것:
  - 파이프라인 쪽 HTTP Fusion 연결 포트(서버의 `GET .../{요청}`을 `SampleAnswer`로 바꾸는 어댑터)는 두지 않았다. 실행기가 아직 운영 호스트 없이 시험에서만 돌고 AI·저장소·사람 포트도 가짜다. 실행기를 서버에서 띄우는 티켓 22에서 함께 붙인다. 그동안 "Fusion 연결 필요" 표시는 처리 기록이다(사람 화면은 티켓 18~20).
  - 서버 요청의 `kind`에 `grid`·`thickness`를 미리 둔다. 명세 계약의 요청 종류(교차 검증·격자 보강·두께 후보)이고, 티켓 09·12가 쓴다.
  - 응답의 값 묶음이 요청과 같은지 서버와 실행기가 둘 다 본다. 포트 구현이 서버를 거치지 않을 수 있어서다(코드에 메모).
  - 응답 도중에 끊긴 경우는 서버 시험(가져가고 답하지 못한 요청을 다시 내준다)으로만 본다. 실행기 쪽은 어댑터가 생길 때 시험한다.
  - Fusion 안에서의 연결 동작(사용자 이벤트·일꾼 스레드)은 자동 시험이 없고 사람 확인 전이다. Fusion 업로드 자체가 티켓 26(옛 티켓 25) 사람 확인을 기다린다.

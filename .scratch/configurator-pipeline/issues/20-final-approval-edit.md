# 20: 최종 승인 편집과 반려

**What to build:** 운영자가 최종 승인에서 구성기를 직접 조작해 보며 슬라이더 이름을 고치고 범위를 좁힐 수 있다. 반려하면 다른 후보를 고르러 후보 선택으로 돌아가거나, 거절 이유를 한 줄 적어 후보 제시를 다시 할 수 있다.

**Blocked by:** 16 (정보 입력, 후보 제시·선택)

**Status:** ready-for-agent

- [x] 최종 승인 화면에서 슬라이더 이름을 고치면 명세에 반영된다
- [x] 범위는 좁히기만 할 수 있고, 넓히려 하면 막힌다
- [x] 반려 후 "다른 후보"를 고르면 이미 받은 후보로 후보 선택에 돌아간다
- [x] 반려 후 거절 이유를 적으면 그 문장이 후보 제시 입력에 들어가 새 후보 2~4개가 만들어진다
- [x] 고친 내용과 거절 이유가 처리 기록에 남는다

## Comments

### 2026-11-02 구현

- **사람 결정**: `HumanPort.finalApproval`의 답이 `ApprovalDecision`이 됐다. 승인(`edits`: 슬라이더 id → 새 이름·좁힌 범위), 반려하고 다른 후보(`back: "choice"`), 반려하고 거절 이유로 후보 다시 받기(`back: "candidates"`, `reason`). 입력에는 앞 답이 막힌 까닭 `errors`와 그 답이 고친 내용 `edits`가 붙는다.
- **고친 내용 검사**: `schemas.ts`의 `approvalEditChecker`. 범위는 좁히기만 하고(승인 전 `min` 이상·`max` 이하), 기본값(업로드한 모델의 값)이 범위 안에 남고, 고친 끝은 기본값에서 `step`의 배수만큼 떨어지며, 한 값뿐인 범위는 안 된다. 실행기는 고친 명세에 형식 검사와 Fusion 파라미터 이름 검사(`specReferenceChecker`)도 돌린다. 막히면 처리 기록에 `{ errors }`를 남기고 같은 명세로 다시 묻는다(후보 선택의 잘못된 답처럼 멈추지 않는 것은, 운영자가 칸 하나만 고치면 되는 일이라서다).
- **반영**: 승인하면 고친 명세로 `spec.json`을, 그 명세로 다시 거른 `sweeps.json`을 만들어 제출하고(`assemble.ts`의 `withApprovedSpec`) 사례로 기록한다. 좁힌 범위는 검증한 범위 안이라 다시 검증하지 않는다.
- **반려 두 경로**: 실행기의 후보 제시 고리 안에 후보 선택 고리를 두었다. "다른 후보"는 같은 카드로 후보 선택에 돌아가고, 거절 이유는 후보 제시 입력 `rejections`(`{ candidate, reason }`, 이 상품에서 쌓인 것 모두)에 붙는다. LiteLLM 후보 제시 지시문에 `rejections`를 적었다.
- **처리 기록**: `approval` 단계의 `detail`이 받아들인 답 그대로라 고친 내용과 거절 이유가 남는다.
- **최종 승인 화면**: `finalApprovalHtml`이 결과물의 고정 코어 번들과 명세·스윕 데이터·스타일 선택을 화면에 싣고 구성기를 띄운다(`</script`는 끊고, JSON의 `<`는 이스케이프). 슬라이더마다 이름·최소·최대 칸(범위 칸의 `min`·`max` 속성은 좁히기 한계), 승인 단추, 반려 단추 둘과 거절 이유 칸이 있고, 칸 값이 바뀌면 그 이름·범위로 구성기를 다시 띄운다. 양식은 `readFinalApproval`이 읽는다. 서랍장 결과물로 만든 화면을 브라우저에서 열어 구성기가 뜨고, 최대를 700으로 바꾸면 슬라이더 범위가 400~700으로 다시 뜨는 것을 봤다(처음엔 미리보기 상자 높이를 고정해 캔버스가 양식을 덮어서, 고정 코어가 폭의 4:3으로 그리는 데 맞춰 폭만 정했다).
- 시험: `pipeline.test.ts` 8개(이름 고치기 반영과 기록, 넓히기 막힘과 좁히기 반영, 다른 후보, 거절 이유로 새 후보, 빈·두 줄 거절 이유, 고친 이름의 Fusion 파라미터 이름, step 맞춤과 한 값 범위, 좁힌 범위의 위상 묶음 빠짐), `operator-screens.test.ts` 5개.

### 리뷰 뒤 반영과 남긴 것

- 반영:
  - 좁힌 끝의 `step` 맞춤과 한 값뿐인 범위를 막는다.
  - 제출할 때 `sweeps.json`도 고친 명세로 다시 거른다.
  - 다시 물을 때 막힌 답이 고친 내용(`edits`)을 넘겨 화면이 칸을 다시 채운다.
  - 숫자가 아닌 칸 오류가 같은 슬라이더의 이름 오류를 가리지 않게 했고, 두 줄 이름을 막는다.
  - 오류 문장을 JSON 경로로 시작하게 하고(`/decision: …`), 한 값 범위 오류에 고칠 값을 적었다.
  - `SliderEdits`를 `schemas.ts` 한 곳에 두고 실행기가 다시 내보낸다. 거절 이유 검사는 `rejectionReasonErrors` 하나를 실행기와 화면이 같이 쓴다. 양식 칸 이름 구분자를 상수로 두고 화면 스크립트에 넣는다.
  - 승인 뒤 제출·사례 기록을 실행기의 `submit`으로 뺐다.
- 남긴 것:
  - **결정 값(`approve`·`choice`·`candidates`)을 값 목록으로 모으지 않았다**: 판별 태그와 양식 단추 값이고, 코딩 표준의 "도메인 값 목록"(정면·상품 종류처럼 고를 거리인 도메인 값)에 해당하지 않는다.
  - **화면 스크립트의 범위 판정이 검사기와 겹친다**: 브라우저에서 미리보기를 다시 띄울지 정하는 데만 쓰고, 받아들일지는 서버가 `approvalEditChecker`로 정한다. 브라우저 코드에 서버 모듈을 실을 수 없다.
  - **실행기가 `edits`의 런타임 형태를 따로 검사하지 않는다**: 사람 포트는 타입으로 묶여 있고(후보 선택의 `parents`도 같다), 운영 화면은 `readFinalApproval`이 문자열·숫자로 읽어 넘긴다.
  - **사례 기록에 고친 내용·거절 이유·버려진 후보를 따로 담지 않았다**: 사례 저장소는 티켓 21이다. 지금은 고친 명세가 사례의 `spec`에 들어간다.

# 16: 정보 입력, 후보 제시·선택

**What to build:** 운영자가 정보 입력(상품명, 상품 종류, 원하는 슬라이더와 범위 메모, 두께 선택 노출 여부)을 적으면, AI가 명세 작성 전에 슬라이더 구성 후보 2~4개를 업로드한 스윕으로 만든 미리보기와 함께 보여주고, 운영자가 하나를 고른다.

**Blocked by:** 15 (LiteLLM 포트와 실제 명세 작성)

**Status:** ready-for-agent

- [x] 정보 입력 화면에 상품명, 상품 종류(목록), 범위 메모(자유 문장), 두께 선택 노출 여부(기본 "AI 판단")가 있고 직업 항목은 없다
- [x] 후보 제시가 JSON Schema 형식의 후보 2~4개를 내고, 부품 탐색은 VLM이 맡는다
- [x] 후보끼리 정면·노출할 부모 파라미터·두께 선택 노출 여부 중 하나 이상이 다르지 않으면 다시 만든다
- [x] 후보 카드마다 업로드 스윕으로 만든 실제 변형 미리보기와, 다른 후보와의 차이 한 줄, 정면에 따른 W·D·H 축 대응이 표시된다
- [x] AI가 정면을 확신하지 못하면 후보끼리 정면이 다르다
- [x] 운영자가 고른 후보가 명세 작성의 입력이 된다

## Comments

### 2026-11-02 구현

- **정보 입력 화면**: `configurator/pipeline/operator-screens.ts`의 `intakeFormHtml()`(상품명, 상품 종류 목록, 범위 메모, 두께 선택 노출 여부 기본 "AI 판단")과 `readIntakeForm(form)`. 직업 항목은 없다. 상품 종류 목록은 `schemas.ts`의 `PRODUCT_KINDS`(서랍장·책장·선반·수납장·테이블·의자)이고, 실행기가 정보 입력 단계에서 `checkIntake`로 검사해 형식이 틀리면 후보 제시 전에 멈춘다.
- **부품 탐색(VLM)**: AI 모델 포트에 `findParts`(단계 `parts`)를 더했다. 서버가 기본 형상을 여섯 방향(±X·±Y·±Z)에서 직교 투영해 부품마다 색을 칠한 PNG(`pipeline/render.ts`, WebGL 없는 소프트웨어 래스터라이저)와 부품 색 목록을 보낸다. 답은 JSON Schema(`PARTS_SCHEMA`)로 부품 역할·정면 후보(`fronts`, 확신 순서)·위쪽(`up`)이다. 상품마다 한 번 묻고, 결과는 후보 제시 입력(`parts`)에 들어간다. LiteLLM 구현은 그림을 OpenAI 호환 `image_url` 조각(data URI)으로 싣고, 모델 이름은 `models.parts`(실행 도구는 `LITELLM_VLM_MODEL`)다.
- **후보 검사**: `candidateDiversityChecker`. 두 후보의 정면·부모 파라미터(순서 무관)·두께 선택 노출이 모두 같으면, 그리고 부품 탐색의 정면 후보가 여럿인데 후보에 빠진 정면이 있으면 형식 오류로 다시 묻는다. 위쪽과 같은 축은 정면이 될 수 없다. 부품 탐색 답도 업로드 묶음의 부품 이름과 위쪽 축을 검사한다(`partsReferenceChecker`).
- **후보 카드**: `pipeline/candidate-cards.ts`의 `candidateCards`. 사람 포트 `chooseCandidate`가 후보 대신 카드(`CandidateCard` = 후보 + `axes` + `previews`)를 받는다. 축 대응은 정면과 부품 탐색의 위쪽으로 정한다(D = 정면 축, H = 위쪽 축, W = 남은 축). 미리보기는 부모 파라미터마다 스윕 범위 끝·기본값의 형상을 변형 엔진으로 만들어(스윕 범위 전체를 슬라이더로 둔 임시 명세, 위상 묶음도 그대로 탄다) 정면 오른쪽 위에서 같은 축척으로 그린다. 카드 화면은 `candidateCardsHtml`, 고른 값은 `readCandidateChoice`.
- **고른 후보가 명세 작성의 입력**: 명세 작성 입력의 `candidate`는 카드에서 그림을 뺀 후보다. 명세 검사에 `chosenCandidateChecker`를 더해 명세의 정면이 고른 후보의 정면이고 축 대응이 카드에 보인 것과 같아야 한다(카드가 보여 준 축과 다른 명세가 제출되지 않게).
- 처리 기록의 단계 순서는 그대로다. 부품 탐색의 형식 오류는 `candidates` 단계로 남는다.
- 시험: `pipeline.test.ts`에 10개(정보 입력 검사, 부품 탐색 입력, 여섯 개 넘는 부품 색, 부품 탐색 다시 묻기, 같은 후보 다시 만들기, 정면 미확신, 정면 확신, 두께 선택 숨기기, 카드 축·미리보기, 고른 후보와 명세 정면). 미리보기는 PNG를 풀어 폭 300·600·900 그림의 그려진 너비가 커지는지 본다. `litellm-ai.test.ts`에 그림 싣기 1개, `operator-screens.test.ts` 5개.
- 운영자 화면을 띄우는 호스트는 아직 없다(티켓 22). 화면 함수는 HTML 문장을 만들고 양식 값을 읽기까지다. 수동 실행 도구(`scripts/run-pipeline.ts`)는 후보 카드 화면을 출력 폴더에 `candidates-N.html`로 남긴다.
- 렌더링은 한 실행에 0.3초 안팎 든다(여섯 방향 320×240, 미리보기 200×150).

### 리뷰 뒤 반영과 남긴 것

- 반영:
  - 정보 입력의 두께 선택 노출 여부가 "보이기"·"숨기기"면 모든 후보의 `showThickness`가 따른다. 칸막이 선반 두께 시험의 정보 입력은 후보끼리 두께 노출이 달라 "AI 판단"으로 바꿨다.
  - 부품 탐색이 정면을 확신하면(정면 후보 하나) 모든 후보가 그 정면이어야 한다. 서랍장 시험의 기본 부품 탐색 답은 정면 후보 -Y·+Y로 바꿔, 기존 후보 c1(-Y)·c2(+Y)가 그대로 맞게 했다.
  - 부품 색은 정해 둔 6색 뒤로 색상환을 황금각씩 돌려 만들어, 부품이 많아도 겹치지 않는다.
  - 정면이 위쪽과 같은 축인지 보는 검사를 `frontOnUpAxis` 하나로 합쳤다.
  - `Front`·`ProductKind`·`ThicknessExposure`(`THICKNESS_CHOICES`)를 `schemas.ts`에 한 번만 두고, `Intake.kind`를 상품 종류 유니온으로 좁혔다.
  - `render.ts`의 `cross`를 다시 쓰고, `sweepSpec` 두 번 부르던 것을 한 번으로 줄였다. `axesFor`는 같은 축이면 오류를 낸다.
  - `readIntakeForm`에서 상품 종류도 trim한다. 그 밖에 자잘한 정리(이른 반환 전 문장 만들기, 필요 없는 타입 표기).
- 남긴 것:
  - 부품 탐색의 형식 오류는 단계 `candidates`로 기록한다. GLOSSARY대로 부품 탐색은 후보 제시 첫머리에 있고, 처리 기록의 단계 순서(ADR-0014의 10단계)를 바꾸지 않으려는 것이다. 형식 재요청 횟수는 `askUntilValid` 호출마다 따로 센다.
  - 미리보기에 두께 후보를 넣지 않았다. 두께 후보(표준 두께 앞뒤 한 칸)는 명세 작성에서 정해지고, 그 형상은 추가 샘플 요청으로만 받기 때문에 후보 제시 때는 없다. 카드에는 "두께 선택 보이기/숨김"이 글로 표시된다.
  - 부품 탐색 지시문이 템플릿 문자열 안에 실제 줄바꿈을 쓰는 것은 같은 파일의 다른 지시문과 같은 방식이다.
  - 범위 밖이라는 지적(명세 정면·축 검사, 실행 도구의 카드 화면 파일, 상품 종류에 선반·의자)은 둔다. 명세 정면·축 검사는 카드에 보인 축과 다른 명세가 나오지 않게 하려는 것이고, 선반은 기존 시험의 상품 종류, 카드 화면 파일은 수동 확인용이다.

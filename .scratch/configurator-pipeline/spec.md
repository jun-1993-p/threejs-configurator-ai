# 구성기 자동 생성 파이프라인

Status: ready-for-agent

용어는 `GLOSSARY.md`, 결정은 `docs/adr/`, 명세 구조는 `docs/spec-schema.md`, 전체 흐름은 `docs/plan.md`를 따른다.

## Problem Statement

쇼핑몰 운영자(이 프로젝트의 1인 개발자)는 Fusion으로 만든 가구 모델마다, 고객이 치수를 바꿔 볼 수 있는 three.js 구성기를 손으로 따로 구현해야 한다. CAD 파라미터는 이름이 없거나(`d34`) 수식으로 얽혀 있어서, 어느 값이 어느 치수인지 매번 사람이 알아내야 한다. 기존 프로토타입(stool1)은 슬라이더 구성이 코드에 박혀 있어 상품이 바뀔 때마다 코드를 고쳐야 한다. 그래서 상품 하나를 구성기로 올리는 데 시간이 많이 들고, 결과가 CAD 형상과 정확히 맞는지 확인할 방법도 없다.

## Solution

운영자는 Fusion에서 CAD 애드인으로 모델과 스윕을 업로드하고 정보 입력을 적는다. 그 뒤에는 AI가 제시한 슬라이더 구성 후보 중 하나를 고르고, 완성된 구성기를 직접 조작해 본 뒤 최종 승인만 하면 된다. 그 사이의 일은 고정된 순서로 자동 진행된다(ADR-0014).

- 슬라이더 구성 후보 만들기
- UI 스타일 고르기
- 명세(JSON) 작성
- 고정 코어와 변형 엔진에 조립
- 검증: 수치 → 축 반응 → AI 판정

검증에 실패하면 슬라이더·부품별 원인이 검증 피드백으로 명세 작성에 돌아가 자동으로 고쳐진다. 승인된 구성기는 쇼핑몰에 넣을 div 하나짜리 JS 번들로 나온다. 결정 기록은 사례 저장소에 쌓여 다음 상품의 후보 제시, 명세 작성, AI 판정에 예시로 쓰인다. 고정 코어와 변형 엔진은 상품마다 바뀌지 않고, AI는 명세와 스타일 선택만 쓴다(ADR-0001).

## User Stories

### 업로드

1. 운영자로서, 업로드 전에 애드인이 서버 연결을 시험하기를 원한다. 긴 스윕을 돌린 뒤에야 연결 실패를 알게 되지 않기 위해서다.
2. 운영자로서, 애드인이 사용자 파라미터 전부를 기본값 ±50% 범위로 자동 스윕하기를 원한다. 어떤 파라미터가 슬라이더가 될지 미리 몰라도 되게 하기 위해서다.
3. 운영자로서, 스윕 중 Fusion 재계산이 실패하는 지점에서 애드인이 스윕 범위를 줄이기를 원한다. 만들 수 없는 형상이 범위에 남지 않기 위해서다.
4. 운영자로서, 스윕 샘플이 비선형 구간에서만 촘촘해지기를 원한다(5점에서 시작해 최대 17점, ADR-0007). 업로드 시간을 줄이면서도 경사나 원형 패턴 구간을 놓치지 않기 위해서다.
5. 운영자로서, 17점으로도 합격선을 못 맞춘 파라미터가 실패로 보고되기를 원한다. 그 파라미터를 슬라이더 후보에서 빼야 함을 알기 위해서다.
6. 운영자로서, 애드인이 꼭짓점을 메쉬 출력 대신 면마다 (u,v) 격자로 찍기를 원한다(ADR-0002). 크기가 바뀌어도 꼭짓점이 1:1로 짝지어지게 하기 위해서다.
7. 운영자로서, 범위 안에서 B-rep 면 구성이 바뀌는 지점을 애드인이 찾아 위상 묶음으로 나누기를 원한다(ADR-0005). 칸막이 수가 늘어나는 상품도 다룰 수 있게 하기 위해서다.
8. 운영자로서, 파라미터 하나당 위상 묶음이 4개를 넘으면 범위를 줄이라는 검증 피드백을 받기를 원한다. 샘플 수가 폭증하지 않게 하기 위해서다.
9. 운영자로서, 개수형 파라미터는 슬라이더 후보로 나오지 않기를 원한다. 섞을 수 없는 값이 고객에게 노출되지 않기 위해서다.
10. 운영자로서, 업로드 묶음에 부품 정보(Fusion 컴포넌트 단위, 없으면 바디 단위, ADR-0006)와 부품 이름이 담기기를 원한다. 검증 피드백이 부품 이름으로 나오게 하기 위해서다.
11. 운영자로서, 업로드 묶음에 파라미터 이름·값·수식이 담기기를 원한다. AI가 부모/자식 관계를 읽을 수 있게 하기 위해서다.
12. 운영자로서, 업로드부터 최종 승인까지 애드인이 서버에 연결된 채로 추가 샘플 요청에 답하기를 원한다(ADR-0013). 교차 검증, 격자 보강, 두께 후보 형상을 업로드 뒤에 뽑을 수 있게 하기 위해서다.
13. 운영자로서, 애드인 연결이 끊기면 검증이 멈추고 "Fusion 연결 필요"가 표시되기를 원한다. 실패가 형상 문제로 잘못 기록되지 않기 위해서다.

### 정보 입력

14. 운영자로서, 상품명을 적기를 원한다. 후보 설명과 결과물에 상품이 식별되게 하기 위해서다.
15. 운영자로서, 상품 종류를 정해진 목록(서랍장·책장·수납장·테이블 등)에서 고르기를 원한다. 사례 저장소에서 비슷한 사례가 찾아지게 하기 위해서다.
16. 운영자로서, 원하는 슬라이더와 범위를 자유 문장 메모로 적기를 원한다(예: "폭 600~1200, 높이는 고정"). AI가 내 판매 의도를 따르게 하기 위해서다.
17. 운영자로서, 두께 선택 노출 여부를 정하거나 "AI 판단"에 맡기기를 원한다. 두께 선택이 필요 없는 상품에서 슬롯을 숨기기 위해서다.
18. 운영자로서, 정보 입력에 직업 같은 쓰이지 않는 항목이 없기를 원한다. 입력 부담을 줄이기 위해서다.

### 후보 제시와 후보 선택

19. 운영자로서, 명세 작성 전에 슬라이더 구성 후보를 2~4개 받기를 원한다. 비싼 검증을 돌리기 전에 방향을 고를 수 있게 하기 위해서다.
20. 운영자로서, 후보마다 업로드한 스윕으로 만든 실제 변형 미리보기를 보기를 원한다. 슬라이더를 움직이면 무엇이 바뀌는지 눈으로 확인하기 위해서다.
21. 운영자로서, 후보끼리 정면, 노출할 부모 파라미터, 두께 선택 노출 여부 중 하나 이상이 다르기를 원한다. 사실상 같은 후보 중에서 고르는 일이 없게 하기 위해서다.
22. 운영자로서, 후보 카드마다 다른 후보와 무엇이 다른지 한 줄로 보기를 원한다. 빠르게 비교하기 위해서다.
23. 운영자로서, AI가 정면을 확신하지 못하면 후보끼리 정면을 다르게 두기를 원한다. 정면 판단을 내가 후보 선택으로 할 수 있게 하기 위해서다.
24. 운영자로서, 후보마다 정면에 따라 W 폭·D 깊이·H 높이 축 대응이 표시되기를 원한다. 슬라이더 이름이 어느 축 기준인지 알기 위해서다.
25. 운영자로서, 원하는 치수가 수식에 묶인 자식 파라미터이면 그 치수를 바꾸려고 움직일 부모를 고르기를 원한다(ADR-0003). Fusion 원본을 고치지 않고 원하는 치수를 조절하기 위해서다.
26. 운영자로서, 부모를 움직이면 같이 바뀌는 다른 치수가 후보 카드에 적히기를 원한다(예: "전체 폭도 같이 변함"). 부작용을 알고 고르기 위해서다.
27. 운영자로서, 후보 제시에서 같은 상품 종류의 비슷한 사례가 예시로 쓰이기를 원한다. 이전에 내가 고른 방식이 반영되게 하기 위해서다.
28. 운영자로서, 슬라이더 이름이 Fusion 파라미터 이름이 아니라 고객이 보는 치수의 뜻으로 지어지기를 원한다(예: `d12` → "서랍 폭"). 고객이 이해할 수 있게 하기 위해서다.

### UI 스타일

29. 운영자로서, AI가 정해진 UI 스타일 목록에서 색·글꼴·슬라이더 모양을 고르기를 원한다. 상품마다 디자인을 따로 만들지 않기 위해서다.
30. 운영자로서, 스타일 선택이 목록 밖의 값을 만들 수 없기를 원한다. 구성기 모양이 예측 가능하게 하기 위해서다.

### 명세 작성

31. 운영자로서, AI가 고른 후보를 바탕으로 `docs/spec-schema.md` 구조의 명세를 쓰기를 원한다. 조립과 검증이 하나의 형식만 읽게 하기 위해서다.
32. 운영자로서, 명세가 JSON Schema 검사를 통과하지 못하면 다음 단계로 가지 않기를 원한다. 형식 오류가 구성기를 깨뜨리지 않기 위해서다.
33. 운영자로서, 슬라이더 범위가 치수 규칙 ∩ 정보 입력 메모 ∩ 스윕 범위 안에서 정해지기를 원한다(ADR-0009). 범위가 인체공학적이면서도 실제로 만들 수 있게 하기 위해서다.
34. 운영자로서, 범위의 근거가 된 치수 규칙이 명세에 `source`로 남기를 원한다. 왜 그 범위인지 나중에 확인하기 위해서다.
35. 운영자로서, 세 범위의 교집합이 비면 범위를 지어내지 말고 그 사실을 알려 주기를 원한다. 근거 없는 범위가 나가지 않기 위해서다.
36. 운영자로서, 슬라이더 기본값이 업로드한 Fusion 모델의 현재 값이기를 원한다. 구성기를 처음 열었을 때 원본 상품 모습이 보이게 하기 위해서다.
37. 운영자로서, 슬라이더마다 형태 변경 부품과 위치 이동 부품이 선언되기를 원한다. 한 축에 슬라이더가 여러 개여도 각 반응을 검증할 수 있게 하기 위해서다.
38. 운영자로서, 자식 파라미터가 기록용으로만 명세에 남고 변형 엔진은 읽지 않기를 원한다(ADR-0003). 엔진에 수식 계산이 들어가지 않게 하기 위해서다.
39. 운영자로서, 두께 선택 후보가 표준 두께 목록(3·6·9·12·15·18·24·30 mm)에서 기본 두께의 앞뒤 한 칸이기를 원한다(ADR-0010). 주문할 수 없는 두께가 고객에게 뜨지 않기 위해서다.
40. 운영자로서, 같은 기본 두께를 쓰는 판재가 하나의 두께 선택으로 묶이고, 고객에게는 1~2개만 노출되기를 원한다. 고객이 뒤판 두께 같은 것으로 혼란스럽지 않기 위해서다.
41. 운영자로서, 고정 두께 파라미터가 어떤 슬라이더의 자식에도 들어갈 수 없기를 원한다. 슬라이더를 움직이다 두께가 바뀌지 않게 하기 위해서다.
42. 운영자로서, 명세 작성 때 같은 상품 종류의 비슷한 사례 3개가 예시로 쓰이기를 원한다(ADR-0011). 내가 이전에 고친 내용이 반영되게 하기 위해서다.

### 조립

43. 운영자로서, 고정 코어가 명세·스타일 선택·스윕 데이터만으로 구성기를 만들기를 원한다. 상품마다 코드를 고치지 않기 위해서다.
44. 운영자로서, 슬라이더 개수와 두께 선택 슬롯이 명세에서 자동으로 구성되기를 원한다. UI를 손으로 맞추지 않기 위해서다.
45. 운영자로서, 결과물이 쇼핑몰 페이지에 넣을 div 하나와 JS 번들이기를 원한다. 쇼핑몰에 바로 붙이기 위해서다.

### 변형 엔진 (고객이 쓰는 구성기)

46. 쇼핑몰 고객으로서, 슬라이더를 움직이면 상품 형태가 매끄럽게 바뀌기를 원한다. 원하는 치수를 직관적으로 찾기 위해서다.
47. 쇼핑몰 고객으로서, 여러 슬라이더를 함께 바꿔도 형태가 자연스럽기를 원한다(ADR-0004의 덧셈, ADR-0008의 격자 보간). 조합을 자유롭게 시험하기 위해서다.
48. 쇼핑몰 고객으로서, 위상 경계를 넘으면 칸막이 같은 부품이 바로 나타나거나 사라지기를 원한다. 실제 상품이 그렇게 바뀌기 때문이다.
49. 쇼핑몰 고객으로서, 두께 선택 슬롯에서 두께를 고르면 형상이 그 두께로 바뀌기를 원한다. 판재 두께 차이를 눈으로 보기 위해서다.
50. 쇼핑몰 고객으로서, 슬라이더를 움직이는 동안 판재 두께가 변하지 않기를 원한다(두께 고정). 실제 판재처럼 보이게 하기 위해서다.
51. 쇼핑몰 고객으로서, 화면의 형상이 실제 상품과 맞기를 원한다. 치수는 0.2 mm, 모양은 max(1 mm, 대각선 0.1%) 안이어야 한다(ADR-0012). 주문한 상품이 본 것과 같게 하기 위해서다.

### 검증

52. 운영자로서, 검증이 수치 → 축 반응 → AI 판정 순서로, 앞 단계를 통과해야 다음으로 가기를 원한다. 비싼 AI 판정을 수치로 잡을 수 있는 실패에 쓰지 않기 위해서다.
53. 운영자로서, 수치 검증이 스윕 샘플 사이 검증점에서 변형 엔진 결과와 Fusion 형상을 비교하기를 원한다. 샘플 위치에서만 맞는 보간을 걸러 내기 위해서다.
54. 운영자로서, 수치 검증이 부품 치수 오차(0.2 mm)와 형상 오차(max(1 mm, 대각선 0.1%))를 따로 판정하기를 원한다. 숫자로 보이는 치수와 눈으로 보는 모양에 각각 맞는 기준을 쓰기 위해서다.
55. 운영자로서, 슬라이더 쌍마다 교차 검증 샘플로 덧셈이 맞는지 확인되기를 원한다. 서로 영향을 주는 슬라이더 쌍을 찾기 위해서다.
56. 운영자로서, 덧셈이 틀린 쌍은 먼저 명세를 고쳐 다시 시도하고, 그래도 안 되면 3×3 격자로 보강하기를 원한다. 상품당 2쌍까지다(ADR-0008). 흔한 쌍 상호작용 때문에 상품이 막히지 않게 하기 위해서다.
57. 운영자로서, 두께 선택의 각 후보도 다른 슬라이더와 교차 검증되기를 원한다. 두께를 바꾼 상태에서 폭을 바꿔도 맞게 하기 위해서다.
58. 운영자로서, 축 반응 검증이 세 가지를 확인하기를 원한다. 선언한 형태 변경 부품만 그 축 치수가 바뀌는지, 위치 이동 부품은 자리만 바뀌는지, 다른 축은 그대로인지다. 한 축에 슬라이더가 여러 개일 때(전체 폭·서랍 폭) 각자 맡은 부품만 움직이게 하기 위해서다.
59. 운영자로서, 두께 고정 검증이 슬라이더를 움직이는 동안 고른 두께의 실측이 변하지 않는지 형상으로 확인하기를 원한다. 수식에 두께가 비율로 섞인 경우도 잡기 위해서다.
60. 운영자로서, 두께 선택 후보가 표준 두께 목록의 앞뒤 한 칸인지 검증되기를 원한다. AI가 목록 밖 두께를 쓰지 않게 하기 위해서다.
61. 운영자로서, AI 판정이 슬라이더 끝값과 쌍별 모서리 조합의 렌더링을 보고, 뚫림·겹침·비례 깨짐을 판정하기를 원한다. 수치로 잡을 수 없는 이상을 찾기 위해서다.
62. 운영자로서, AI 판정 때 같은 상품 종류의 비슷한 사례가 비교 예시로 쓰이기를 원한다. 판정이 내 기준에 맞춰지게 하기 위해서다.
63. 운영자로서, 모든 검증 실패가 `docs/spec-schema.md`의 검증 피드백 형식(명세 경로, 슬라이더, 부품, 실패 종류, 측정값, 기대값, 규칙으로 만든 힌트)으로 나오기를 원한다. AI가 고칠 위치를 바로 찾게 하기 위해서다.
64. 운영자로서, 검증 피드백의 힌트를 AI가 아니라 규칙이 만들기를 원한다. 힌트가 결정적이고 믿을 수 있게 하기 위해서다.
65. 운영자로서, 검증 피드백이 명세 작성으로 돌아가 자동으로 재시도되기를 원한다. 내가 개입하지 않고 고쳐지게 하기 위해서다.
66. 운영자로서, 같은 후보로 3번 넘게 재시도해도 통과하지 못하면 실패 이유를 붙여 후보 제시로 돌아가기를 원한다. 끝없는 루프를 막기 위해서다.
67. 운영자로서, 수치와 축 반응은 통과했는데 AI 판정만 3번 실패하면, 판정 이유를 붙여 최종 승인으로 넘어가기를 원한다. VLM 오판 때문에 상품이 막히지 않게 하기 위해서다.

### 최종 승인

68. 운영자로서, 완성된 구성기를 직접 조작해 보고 승인하기를 원한다. 고객이 볼 화면을 내가 마지막으로 확인하기 위해서다.
69. 운영자로서, 최종 승인 화면에서 슬라이더 이름을 고치기를 원한다. 이름만 마음에 안 들 때 처음부터 다시 하지 않기 위해서다.
70. 운영자로서, 최종 승인 화면에서 슬라이더 범위를 좁히기를 원한다. 판매 범위만 조정할 때 다시 만들지 않기 위해서다.
71. 운영자로서, 반려할 때 다른 후보를 고르러 후보 선택으로 돌아갈 수 있기를 원한다. 이미 받은 후보를 다시 활용하기 위해서다.
72. 운영자로서, 반려할 때 거절 이유를 한 줄로 적어 후보 제시를 다시 할 수 있기를 원한다. 기존 후보가 모두 마음에 안 들 때 방향을 고치기 위해서다.
73. 운영자로서, AI 판정 실패로 넘어온 구성기에는 판정 이유가 표시되기를 원한다. 무엇을 눈여겨봐야 하는지 알기 위해서다.

### 제출과 기록

74. 운영자로서, 승인하면 결과물(고정 코어, 명세, 스윕 데이터)이 제출되기를 원한다. 바로 쇼핑몰에 쓰기 위해서다.
75. 운영자로서, 승인한 명세가 기록되어 사례 저장소에 쌓이기를 원한다. 함께 남는 것은 선택한 후보와 버려진 후보, 내가 고친 슬라이더 이름·범위, 거절 이유다. 다음 상품에서 AI가 내 선택을 따라오게 하기 위해서다.
76. 운영자로서, 사례가 학습에 쓸 수 있는 JSONL 형식으로 남되 지금은 예시로만 쓰이기를 원한다(ADR-0011). 나중에 학습으로 넘어갈 여지를 남기기 위해서다.
77. 운영자로서, 잘못된 사례를 빼면 바로 다음 상품부터 반영되지 않기를 원한다. 사례 품질을 쉽게 관리하기 위해서다.

### 운영

78. 운영자로서, 서버가 LAN의 로컬 Docker에서 무료·오픈소스 구성으로 돌기를 원한다. 운영 비용을 없애기 위해서다.
79. 운영자로서, LLM·VLM 호출이 LiteLLM을 거쳐 외부 API(Cerebras, 예비 Groq)와 로컬 모델 사이에서 바뀔 수 있기를 원한다(ADR-0015). 외부 API가 막혀도 계속 쓰기 위해서다.
80. 운영자로서, 모델을 바꿔도 단계별 입출력 형식이 그대로이기를 원한다. 모델 교체가 파이프라인을 깨뜨리지 않기 위해서다.
81. 운영자로서, 모든 AI 응답이 JSON Schema 검사를 거치기를 원한다. 형식이 틀린 응답이 다음 단계로 새지 않기 위해서다.
82. 운영자로서, 상품 하나의 처리 과정(단계 전이, 검증 피드백, 재시도 횟수)이 기록으로 남기를 원한다. 실패 원인을 추적하기 위해서다.

### 최종 확인

83. 운영자로서, 개발이 끝난 뒤 처음 보는 새 상품 약 10개를 등록해 최종 확인을 하기를 원한다. 실제 상품에만 맞춘 것이 아닌지 확인하기 위해서다.
84. 운영자로서, 최종 확인의 합격 기준을 다음으로 두기를 원한다. 고정 코어와 변형 엔진을 고치지 않고, 10개 중 8개 이상이 후보 선택과 최종 승인만으로 끝나야 한다(슬라이더 이름 수정은 허용). 범용성을 숫자로 판단하기 위해서다.
85. 운영자로서, 최종 확인에서 실패한 상품이 "명세 문제"와 "엔진 한계"로 나뉘어 기록되기를 원한다. 엔진 한계는 범용화 단계의 근거로 넘기기 위해서다.

## Implementation Decisions

### 모듈

- **CAD 애드인** (Fusion 안에서 동작)
  - 하는 일: 서버 연결 시험, 사용자 파라미터 적응형 스윕, 면별 (u,v) 격자 점 추출, 위상 묶음 판별, 부품(컴포넌트) 정보 추출, 업로드 묶음 전송.
  - 업로드 뒤에는 서버의 추가 샘플 요청에 답한다. 요청 종류는 교차 검증 샘플, 격자 보강, 두께 후보 형상이다.
  - 샘플 위치는 애드인이 정한다. AI는 정하지 않는다.
- **파이프라인 실행기**
  - 하는 일: 10단계 순서와 실패 경로를 코드로 고정해 진행한다(ADR-0014).
  - 바깥 의존은 세 포트로만 접근한다. **Fusion 연결**(추가 샘플 요청), **AI 모델**(LiteLLM 경계), **저장소**(사례 저장소·치수 규칙·UI 스타일·결과물)다.
  - 재시도 횟수를 센다. 같은 후보로 3번 넘게 실패하면 후보 제시로, AI 판정만 3번 실패하면 최종 승인으로 보낸다.
- **AI 단계들**: 후보 제시, UI 스타일, 명세 작성, AI 판정.
  - 각 단계는 정해진 입력을 받아 JSON Schema가 정해진 출력만 낸다.
  - 사례 저장소는 같은 상품 종류로 거른 뒤 임베딩 유사도 상위 3개를 예시로 넣는다.
  - 후보 제시와 AI 판정에서 부품 탐색과 렌더링 판정은 VLM이, 나머지는 LLM이 맡는다.
- **명세 검사기**: 명세의 JSON Schema 검사와 규칙 검사.
  - 범위가 치수 규칙 ∩ 정보 입력 메모 ∩ 스윕 범위 안인지, `source`가 치수 규칙에 있는지.
  - 두께 선택 후보가 표준 두께 목록의 앞뒤 한 칸인지, 고정 두께가 어떤 슬라이더의 자식에도 없는지, `ids`로 묶인 두께의 기본값이 같은지.
- **검증기**: 수치 검증(치수 오차, 형상 오차, 두께 고정 실측), 교차 검증, 축 반응 검증.
  - 변형 엔진을 직접 호출해 Fusion 형상과 비교한다.
  - 실패는 검증 피드백 형식으로 내고, 힌트는 규칙으로 만든다.
  - AI 판정용 렌더링(슬라이더 끝값, 쌍별 모서리 조합)도 만든다.
- **변형 엔진** (고정 라이브러리, 직접 구현)
  - 입력: 명세, 스윕 데이터, 슬라이더 값, 두께 선택 값. 출력: 꼭짓점 위치.
  - 단독 스윕 사이는 보간하고, 슬라이더끼리는 덧셈으로 섞는다. 격자 보강 쌍은 격자 보간을 쓴다.
  - 위상 묶음 경계에서는 형상을 바로 바꾼다. 두께 후보는 사이 값 없이 바꿔 끼운 뒤 덧셈으로 섞는다.
  - 구성기(브라우저)와 검증기(서버, Node)가 **같은 JS 라이브러리**를 쓴다. 그래야 검증이 실제로 내보낼 엔진을 잰다.
- **고정 코어** (구성기 본체)
  - 명세·스타일 선택·스윕 데이터를 읽어 슬라이더와 두께 선택 슬롯을 자동 구성한다. 결과는 div 하나에 들어가는 JS 번들이다.
  - 최종 승인 화면에서는 슬라이더 이름 수정과 범위 좁히기를 허용한다.
- **사례 저장소**: JSONL 기록과 임베딩 색인(LanceDB). 거르는 기준은 상품 종류다.

### 계약

- **명세(JSON)**: `docs/spec-schema.md`의 구조를 따른다.
  - 최상위: `product`, `front`, `axes`, `sliders[]`, `thickness[]`, `fixed`.
  - 슬라이더 필드: `id`, `name`, `axis`, `min`, `max`, `default`, `step`, `unit`, `source`, `children`, `affects.shape`, `affects.move`.
  - 명세에 적지 않는 것: 개수형 파라미터, 위상 묶음, 샘플 위치, 격자 보강 쌍. 이것들은 스윕 데이터와 애드인 결과에 담긴다.
- **검증 피드백**: 항목 하나당 실패 하나.
  - 필드: `path`, `slider`, `part`, `kind`, `measured`, `expected`, `hint`.
  - `kind` 목록: 치수 오차 초과, 형상 오차 초과, 예상하지 못한 형태 변경, 다른 축 변화, 두께 변화, 위상 변화, 재계산 실패, 범위 축소, 범위 교집합 없음, AI 판정(`ai_judgment`, 이미지 경로와 이유 포함).
- **업로드 묶음**: 담는 것은 다음과 같다.
  - 파라미터(이름·값·수식·사용자 파라미터 여부·개수형 여부)
  - 부품(컴포넌트 이름, 소속 면)
  - 파라미터별 스윕 범위, 샘플 값, 위상 묶음별 면 구성
  - 샘플마다 면별 (u,v) 격자 점
- **추가 샘플 요청**: 서버가 애드인에 보낸다.
  - 내용: 파라미터 값 묶음(교차 검증, 격자, 두께 후보). 응답 형식은 업로드 묶음의 샘플과 같다.
  - 연결이 끊기면 실패로 기록하지 않고 대기 상태가 된다.
- **사례 기록**: 담는 것은 다음과 같다.
  - 상품 종류, 정보 입력, 제시된 후보 전부와 선택된 후보
  - 최종 명세, 최종 승인 때 고친 내용, 거절 이유

### 수치

- 합격선: 치수 오차 0.2 mm. 형상 오차는 1 mm와 바운딩 박스 대각선 0.1% 중 큰 값.
- 스윕: 기본값 ±50%. 5점 균등에서 시작해 구간을 반으로 나누며 최대 17점까지 늘린다.
- 위상 묶음: 파라미터당 4개까지. 격자 보강: 상품당 2쌍, 3×3.
- 재시도: 같은 후보로 3번까지. 후보: 2~4개. 사례 예시: 3개.
- 표준 두께 목록: 3·6·9·12·15·18·24·30 mm.

## Testing Decisions

### 좋은 테스트의 기준

- 경계 밖에서 보이는 동작만 시험한다. 내부 함수 호출 순서나 중간 자료 구조는 시험하지 않는다.
- 입력은 실제 상품에서 녹화한 업로드 묶음과 추가 샘플 응답이다. 정답은 녹화된 Fusion 형상이다.
- AI 모델 포트는 각본대로 답하는 가짜로 바꾼다. 일부러 틀린 명세·후보·판정을 내게 해서 실패 경로를 시험한다.

### 경계 1 (주 경계): 상품 하나를 처리하는 파이프라인 실행

- 들어가는 것: 업로드 묶음, 정보 입력, 사람 결정 각본(어느 후보를 고르고, 승인할지 거절할지).
- 나오는 것: 단계 전이 기록, 검증 피드백 목록, 최종 결과물(구성기 번들, 명세, 사례 기록).
- 주입하는 포트: Fusion 연결(녹화 응답), AI 모델(각본 가짜), 저장소(메모리).
- 시험하는 것:
  - 단계 순서와 실패 경로
  - 3회 제한 두 가지
  - 범위 교집합과 `source`
  - 두께 선택 규칙
  - 축 반응 검증
  - 교차 검증과 격자 보강 전환(2쌍 상한)
  - 연결이 끊겼을 때의 대기
  - 반려 두 경로
  - 최종 승인 때 고친 내용과 거절 이유의 사례 기록
  - 사례 예시 주입(같은 상품 종류, 상위 3개)

### 경계 2: 변형 엔진

- 들어가는 것: 명세, 스윕 데이터, 슬라이더 값, 두께 선택 값. 나오는 것: 꼭짓점.
- 녹화된 Fusion 정답과 직접 비교한다.
  - 검증점에서 치수 오차와 형상 오차가 합격선 안인지
  - 덧셈과 격자 보간
  - 위상 묶음 경계에서 형상이 바로 바뀌는지
  - 두께 후보 전환과 두께 고정(슬라이더를 움직이는 동안 두께 불변)
- 브라우저와 서버가 같은 라이브러리를 쓰므로 Node에서 시험한다.

### 테스트 경계로 두지 않는 것

- CAD 애드인은 Fusion 밖에서 자동 시험하지 않는다. 실제 상품으로 수동 확인하고, 그때 나온 업로드 묶음과 샘플 응답을 녹화해 경계 1·2의 테스트 데이터로 쓴다.
- 기존 테스트 선례는 없다(새 저장소). 첫 녹화 데이터는 기존 프로토타입 stool1과 실제 상품 몇 개에서 만든다.

### 최종 확인

- 개발이 끝난 뒤 처음 보는 상품 약 10개로 실제 파이프라인을 끝까지 돌린다(평가 전용).
- 합격 기준은 사용자 스토리 84번과 같다.
- 이 상품들은 개발 중 테스트 데이터로 쓰지 않는다.

## Out of Scope

- OBJ 입력과 피규어 등 가구 밖으로의 범용화(ADR-0002)
- 개수형 파라미터를 슬라이더로 직접 노출하는 일
- 애드인이 Fusion 수식을 풀어 자식 파라미터를 독립 파라미터로 바꾸는 일
- 두께의 연속 변경. 재질별 표준 두께 목록
- 위상 경계에서의 페이드 전환
- 사례 저장소로 모델을 학습하거나 미세조정하는 일
- 정보 입력의 직업 항목
- 구성기에 치수를 숫자로 보여주는 UI(합격선은 이를 대비해 정했지만, 표시 기능 자체는 이 명세에 없음)
- 쇼핑몰 쪽 결제·주문 연동

## Further Notes

- 저장소는 Public(GitHub)이다. 실제 상품의 CAD 데이터와 녹화한 테스트 데이터는 저장소에 넣지 않거나 따로 관리해야 한다.
- 외부 API로 파라미터·명세·렌더링 이미지가 나가는 것은 의도된 결정이다(ADR-0015).
- 면별 (u,v) 격자 밀도 규칙은 애드인 구현 때 정한다(ADR-0002).
- 치수 규칙과 UI 스타일 목록의 초기 내용은 준비 단계에서 따로 만들어야 하며, 이 명세에 포함되지 않는다.
